# Reflection：Agent 怎样用反馈修订输出

假设让模型写一个函数：把 $n$ 条记录按每批最多 $c$ 条处理，需要多少批？它写出 `n // c + 1`，并解释“整数除法后加一，补上最后一批”。再问“请仔细检查”，模型继续用同一句话证明自己正确。可是一共 8 条记录、每批 4 条，明明只需要 2 批，函数却返回 3。

第二次回答增加了文字，没有增加能推翻原判断的信息。这里说的 Reflection（反思）是 Agent 应用拿到候选输出后，安排检查、反馈、修订和再次检查的过程。它处理已有结果如何改进；任务怎样拆分见 [Planning](#/lesson/planning)。关键是检查能否提供足以推翻原判断的信息，下一次尝试是否真的消除了偏差。下面用一个人为构造的 Python 样本走完整轮；本文实际运行了检查代码，没有调用模型生成或修订代码。

## 一次修订：输入、检查、反馈和再次尝试

先固定需求，避免模型为了通过测试重新解释任务：`batch_count(n, capacity)` 的两个参数均为整数；`n` 非负，`capacity` 为正；返回容纳全部记录所需的最少批数。空输入需要零批。负记录数或非正容量抛出 `ValueError`。本例不接收浮点数和字符串，因此不讨论这些输入的类型处理。

初稿如下。代码是人为构造的错误样本，用来观察反馈如何约束修订：

```python
def batch_count(n, capacity):
    if n < 0 or capacity <= 0:
        raise ValueError("invalid count or capacity")
    return n // capacity + 1
```

测试期望值从需求手工推导，并在修订前固定。五个正常用例分别覆盖空输入、未满一批、刚好一批、超过一批、刚好两批；另有两个非法输入用例。

```python
cases = [
    (0, 4, 0),
    (1, 4, 1),
    (4, 4, 1),
    (5, 4, 2),
    (8, 4, 2),
]
for n, capacity, expected in cases:
    assert batch_count(n, capacity) == expected

for args in [(-1, 4), (1, 0)]:
    try:
        batch_count(*args)
    except ValueError:
        pass
    else:
        raise AssertionError("expected ValueError")
```

上面是可直接执行的断言检查，发现第一处错误就会停止。为展示全部失败，本课实际运行时用一个汇总器逐项记录结果，初稿得到以下输出：

```text
initial: 4/7 passed
(0, 4): expected 0, got 1
(4, 4): expected 1, got 2
(8, 4): expected 2, got 3
```

这时应用把原始需求、初稿和这份反馈一起提供给修订模型，并明确“修复实现，保持需求与期望值不变”。这是外部反馈：失败输入、期望和实际值来自预先固定的检查，而非模型对自己的评价。仅提供“有三个测试失败”过于粗糙；具体记录让模型能够比较共同条件。也不必要求它公开一大段内部推理，要求可核对的错误摘要和修改即可。

一份有用的反思是：“空输入和整除时额外增加了一批；原式总是加一，应仅在有余数时向上取整。保留非法输入检查。”它指出了触发条件、错误机制与修改边界，应用才有东西可交给下一次修订。若只写“以后仔细考虑边界情况”，下一轮仍要重新猜哪一个边界。

修订代码可以写成：

```python
def batch_count(n, capacity):
    if n < 0 or capacity <= 0:
        raise ValueError("invalid count or capacity")
    return (n + capacity - 1) // capacity
```

为什么这一修改符合需求，可以用整数除法核对。设 $n=qc+r$，其中 $c$ 表示 `capacity`，$q$ 是完整批数，余数满足 $0\le r<c$。余数为零时需要 $q$ 批；余数非零时需要 $q+1$ 批。修订式实现这两种情况，并在 $n=0$ 时返回零。它适用的条件是前面已经固定的非负整数 $n$ 和正整数 $c$。

用相同的七个用例重新运行，实际输出为：

```text
revised: 7/7 passed
```

至此，这一次修订因检查通过而停止。七项检查和整数推导支持前述输入范围内的公式；它们不证明某个模型已经掌握任务，也不是生产代码安全、性能或所有输入类型的验证。初稿、反思与修订由本文构造，实际运行的是测试检查，没有调用模型生成代码。

## 自检和外部验证各提供什么

自我反思（self-reflection）通常指模型回看自己的答案或行动记录，指出可能的问题，再生成修订。最弱的形式是“再想想有没有错”：它没有给模型新的约束，只改变了生成任务。模型可能发现遗漏，也可能重复原先的错误假设，甚至把正确答案改坏。

外部反馈（external feedback）提供来自答案之外的观察，例如编译错误、单元测试失败、数据库实际返回值，或文档中与回答矛盾的条款。反馈不一定直接告诉模型怎样修；它至少让“目前哪里不符合要求”可以被检查。独立验证（independent verification）进一步要求验收依据不由当前答案随意改写。测试代码若把模型返回值直接复制成期望值，虽然运行成功，也没有验证功能。

因此，可以区分三个问题：是否发现了偏差，是否正确解释了原因，修订是否消除了偏差。测试失败能确认偏差，却不保证模型的归因正确；一段合理的反思能提出修正方向，却不保证新代码正确。需要把这些阶段连接起来，而不是让最后一句“我已确认无误”同时充当全部证据。

这也解释了研究结果为何不能一句话概括。Self-Refine 提出由同一个模型生成初稿、反馈和修订，在作者评估的任务上报告了改进。另一篇研究专门考察缺少外部反馈的内在自纠错，在其推理实验中发现模型可能无法改正，甚至退步。它们使用的任务、反馈与比较条件不同，不能据此断言所有模型永远能或永远不能自我修正。[Self-Refine 摘要](https://arxiv.org/abs/2303.17651)、[Large Language Models Cannot Self-Correct Reasoning Yet](https://arxiv.org/abs/2310.01798)

## Reflexion 是一个具体方法名

泛称 reflection 指一类回看与修订行为；2023 年论文中的 Reflexion 则有明确结构。Actor 生成行动或答案，Evaluator 对执行轨迹或结果给出评价，Self-Reflection 组件结合反馈与轨迹写出文字经验，并把它放入跨尝试保留的记忆，供下一轮 Actor 参考。[Reflexion：摘要与方法部分](https://arxiv.org/abs/2303.11366)

这些组件是职责划分，不意味着必须采购三个不同的基础模型。论文里的评价来源包括任务答案比较、预设规则、模型评价和编程任务中的测试；“得到反馈”也不等于反馈必然来自可靠的人工标准。需要逐项问清当前实验使用哪一种信号。

论文标题中的 verbal reinforcement learning 通过文字反馈改变后续输入，没有在这套流程里更新语言模型权重。这里所谓“学会避免错误”，指后续尝试能够利用保留的经验，不等于模型参数完成了训练，也不保证删掉这些上下文后仍保留改进。论文自己讨论了反馈质量与模型自评能力的限制。本课借用“生成—评价—具体反思—再尝试”的结构，不复现论文的完整实验，也不使用论文基准成绩来预测这个小函数的表现。

## 怎样避免把错误反思变成新规则

外部反馈也可能被误读。假如只看第一条失败，模型可能加上 `if n == 0: return 0`，然后认为问题已解决。空输入通过了，整除输入仍然失败。也可能把用例的期望 2 改成 3，让测试与代码“达成一致”。前者是修复不完整，后者则破坏了验收依据。

保留所有原始失败和原本通过的用例，再测一次，能够发现这两种问题。再增加独立用例还有另一层价值：不要让修订只记住 0、4、8 这几个数字。例如把容量改成 3，检查 6 条记录需要 2 批，便能区分一般规则与样本特判。独立验证的关键是不同证据来源和覆盖范围；单纯把同一份错误说明复制给另一个模型，不会自动形成独立证据。

错误还可能通过文字记忆固化。若模型把失败归因为“测试期望不可靠”，并长期保存这条结论，以后每轮都会更倾向于忽略测试。经验记录应保留可验证的触发条件和依据，例如“本任务在空输入与整除输入失败，原因是无条件加一”，并标明范围。没有证据支撑的归因只是候选解释，不能因为它被写成“经验总结”就升级成事实。

在文档问答中也是同一问题：模型说“缺少引用”不等于答案事实错误；补上一个形式正确的链接也不代表链接支持该结论。有效反馈应指出哪句话、哪段来源、二者怎样冲突。更长的答案、更高的自评分和更肯定的语气，都不能替代这些证据。

## 何时使用，以及何时停止修订

当代码有失败测试、问答有可定位的来源冲突，或工具调用有实际错误时，修订者才有可核对的偏差可处理。若只有模型反复给自己打分，同一个误解可能在每轮保留，增加尝试也会增加成本。一个有界循环应冻结任务与验收要求，生成候选并运行检查；通过则返回候选和验证范围，失败则把具体反馈交给修订，再次运行检查。代码负责次数、时间、候选版本和测试结果，模型负责解释偏差与提出修改。

例如本课可以设定最多两次修订，初稿不计入修订次数；另设总耗时预算。若同一失败在修改后原样出现，应检查归因是否错误；没有新证据时不靠重复“再检查一次”无限循环。达到预算后应保存最后候选、仍失败的输入和原因未知项，明确交付未通过结果，而不是在最后一轮强行宣布成功。已经通过既定验收后，若没有新风险或新需求，也应停止无目的的润色。

反思增加模型调用、测试执行和上下文成本。判断它是否值得使用，应在同一批任务上比较不修订与有修订的结果，并记录原本正确却被改错的数量。还要控制总计算预算，避免把更多尝试带来的收益全部归给“反思方式”。关于内在自纠错的研究也专门提醒，比较时要考虑推理成本与初始提示是否同样充分。[自纠错研究：Introduction](https://arxiv.org/abs/2310.01798)

一分钟回答：Reflection 为什么可能有效，也可能越改越错？

Reflection 让模型回看结果和反馈，提出具体修订。它有用的前提是能识别真实偏差，例如测试失败或文档证据冲突；如果只是重复自评，原来的错误假设可能继续保留。工程上要冻结验收要求，提供失败输入、期望和实际结果，修订后重跑检查，保留原本正确的用例防止退化。还要设定次数和时间预算。论文 Reflexion 是 Actor、Evaluator、文字反思与经验记忆的特定框架，通常通过上下文改进后续尝试，不等于更新模型权重。

追问一：让另一个模型做 reviewer 就算独立验证了吗？

不一定。它可能与生成模型共享同样的误解，或者被初稿带偏。要看 reviewer 是否基于固定需求、独立数据或工具结果作判断。代码任务中，规格推导的用例和实际执行结果比一个没有证据的“看起来正确”更可核对；但测试覆盖不足仍需承认。

追问二：所有测试都通过，是否应继续反思？

先看验收范围是否足够。若存在明确遗漏，就补充有理由的检查；如果既定检查已通过且没有新风险，不应为了显得认真继续改。反复改动会增加成本，也可能破坏正确结果。停止条件应由要求与证据决定，不能由模型的满意程度决定。

追问三：Reflexion 和反复提示“再想一次”有什么区别？

Reflexion 指论文定义的反馈、文字经验和跨尝试记忆过程。简单重问可能没有评价信号，也没有保存上轮教训。把一个普通修订提示命名为 Reflexion，不能说明它实现了论文方法，更不能继承论文成绩。

## 练习：一次不完整的修复

面对本课失败反馈，模型提出“空列表是特殊情况”，只增加 `if n == 0: return 0`，其他代码保持初稿。它重新运行 `(0,4)` 后宣布已修复。请说明缺少什么证据，给出至少两个仍会失败的输入，并写一条足以指导下一轮的具体反馈。最多允许一次额外修订。
