# DSec：Agent 训练为什么需要专门的执行环境

假设要训练一个会修改代码并运行测试的 Agent。模型生成一条命令只用了几秒，后面的任务却需要准备仓库、加载依赖、启动服务、等待测试，再读取结果。训练同时产生上千条这样的轨迹时，GPU 未必是唯一瓶颈：环境创建排队、镜像分发拥塞、少量长任务迟迟不结束，都可能让训练拿不到足够的有效样本。

DeepSeek Elastic Compute，简称 DSec，是论文介绍的一套沙盒执行平台。它管理环境的创建、状态、资源和回收，并与强化学习框架协同。它不定义奖励怎样变成参数更新，也不是一种新的 RL 优化算法。执行平台更快，表示训练与评估能够更有效地获得环境反馈；不能直接推成模型解题率提高。[DSec v1：摘要与第 1 节](https://arxiv.org/html/2609.22978v1)

先修 [强化学习](#/lesson/rl-foundations) 已解释轨迹和奖励，[工具失败](#/lesson/tool-reliability) 已解释超时与未知结果。本篇把注意力放在动作实际发生的地方。论文机制来自 2026-09-28 对指定 v1 原文的阅读；下面的代码任务、时间与内存算术均为教学假设，没有部署或复现 DSec。

## 一条轨迹需要的远不止一次模型调用

假设任务 R17 要修复一个 CSV 日期解析问题。初始环境包含仓库版本 C1、Python 依赖和测试入口。Agent 先读代码，修改文件，再启动测试；下一轮命令必须看见前一轮留下的修改。如果每次工具调用都得到一台干净机器，任务就无法持续；如果所有轨迹共用同一份可写目录，它们又会相互影响。

这里需要有状态沙盒（stateful sandbox）：在一条轨迹内部，文件、已启动服务与依赖变化能够跨调用保留；在独立任务之间，状态应按约定隔离。状态不仅是聊天历史。对话写着“已修改函数”，实际磁盘却回到旧版本，会使后续反馈与动作记录不一致；只保留磁盘、不保留 Agent 执行进度，也不知道哪些结果已经交给模型。

DSec 通过统一 SDK 暴露不同后端。短而无状态的调用可以用 FnCall，复用预先创建的执行环境；常规软件工程任务主要使用容器；microVM 提供更强的虚拟机边界；完整 VM 用于依赖完整操作系统或图形功能的任务。后端在启动成本、兼容性和隔离程度之间取舍，没有一个后端适合所有任务。[DSec 第 2.1—2.3 节](https://arxiv.org/html/2609.22978v1)

R17 可以选择容器，但“容器启动成功”还不是环境就绪。仓库、工具和依赖必须准备好，测试所需服务也应可访问。DSec 的用户可见生命周期包括选择后端与环境、等待准备、执行多轮交互，最后显式停止或按生存期限回收。准备失败、工具失败、任务解答失败应分别记录，否则评估会把基础设施故障混成模型能力不足。

## 为什么要把镜像拆成独立层

R17 使用的环境可以概念上分成三部分：基础操作系统与通用依赖、任务仓库、Agent 工具。下一批任务可能换了仓库，却继续使用同一套工具。如果每次工具升级都重建每个仓库的完整镜像，仓库越多，重复构建与分发就越多。

DSec 将 base image、workspace 和 toolkit 作为独立版本层组合。发布后的层只读，运行时的修改进入各沙盒自己的可写层；底层内容可以复用，任务的文件改动不会写回共享基底。容器通过 overlayfs 组合这些目录，microVM 也采用相应的只读层与可写磁盘安排。这里的共享是共享不可变内容，不能理解成让两个 Agent 共享一份会互相覆盖的工作目录。[DSec 第 5.1 节](https://arxiv.org/html/2609.22978v1)

这也改善了复查条件。若记录了基础层、仓库层与工具层版本，就能更清楚地解释“同一个任务为什么后来测试不同”。但版本固定只是复现的必要部分：随机种子、外部服务、时间、网络权限和评估器仍可能改变结果，不能因为有镜像就承诺每次执行逐字一致。

镜像很大时，另一项成本是必须等整包下载并解压后才能开始。论文采用 EROFS 只读文件系统与 3FS 分布式存储，按沙盒实际访问的内容加载数据。以容器路径为例，元数据尽量预先放到本地，文件数据按需读取，写操作留在节点本地可写层。它试图减少实际搬运的数据量，不只是把下载时间藏到另一个阶段。[DSec 第 5.3 节](https://arxiv.org/html/2609.22978v1)

按需加载也有代价：第一次访问尚未缓存的内容仍会产生 I/O。任务若最终访问几乎全部镜像，能节省的传输量就小得多；小随机读取与大顺序读取也有不同特征。因此，评价不能只看“容器变成运行状态”有多快，还要看首次工具可用时间、完整任务完成时间以及读写总量。

## 长尾等待为什么改变沙盒容量需求

Agent 执行会在模型生成与工具调用之间交替。等待模型生成时，沙盒 CPU 可能很空闲，但内存、文件状态和服务仍然占着资源。反过来，某个测试耗时很长时，这条轨迹暂时不能产生下一轮模型请求。批量训练因此面对不规则的时间分布，而不是每条样本都整齐完成相同步数。

假设四条轨迹分别需要 60、60、60、240 秒，全部在同一时刻开始。如果调度必须等四条都结束才补新任务，前三条完成后有 180 秒不能在其位置继续收集样本。持续补充已完成任务可以减少这种等待，但是否允许异步收集、怎样限制策略版本滞后，属于 RL 框架的设计，不能由沙盒平台单独决定。

资源配置同样不能只按峰值简单相加。假设 100 个沙盒各存活 180 秒，其中每个只有 30 秒在使用一个 CPU 核心，其余时间等待模型。它们的总核心工作量是 3000 核秒；若为每个沙盒独占一核，则预约容量是 18000 核秒，平均利用率为：

$$
U=\frac{100\times30}{100\times180}=\frac16\approx16.7\%
$$

$U$ 是这个理想化例子的平均 CPU 利用率，不是 DSec 实测值，也不能据此直接把机器数量缩小六倍。多个沙盒可能同时开始编译或测试，瞬间争用仍然存在；有些任务还有严格的单步延迟要求。

DSec 的高密度资源管理同时处理内存与 CPU。只读页面尽量共享，冷内存能够回收；对有延迟要求和尽力而为的任务采用不同调度，并处理同一物理核心上硬件线程之间的干扰。增加共置密度必须检查工具反馈是否因资源争用变慢，否则平台虽容纳更多沙盒，轨迹长尾却可能变得更严重。[DSec 第 4.3、5.2 节](https://arxiv.org/html/2609.22978v1)

## GPU 训练被抢占，Agent 不应该一起丢失

论文指出，GPU 训练任务会被调度器抢占。早期方案把 Agent loop 放在可被抢占的训练 pod 中，训练进程退出时，Agent 控制进度丢失，但远端沙盒可能还保留文件与执行结果。恢复需要对齐两种状态，并避免重新执行已完成、可能带副作用的命令。

DSec 报告的新设计将 rollout 执行移到训练 GPU 池之外，拆成两部分：agent sandbox 承载实际工具与执行框架，worker container 管理沙盒并维护 rollout 控制层。两者一起保留轨迹执行状态，训练任务恢复后重新连接，而不是从一串命令记录重新猜测执行到了哪里。这是生命周期解耦：一条轨迹能活多久，不再完全取决于当前 GPU 训练进程能活多久。[DSec 第 6.2 节](https://arxiv.org/html/2609.22978v1)

把它放回 R17：Agent 已修改文件，测试结果已经返回 worker，但 GPU 任务此时被抢占。恢复时需要继续这条轨迹，把正确的观察提供给后续生成，而不是重新修改一次文件或启动第二份测试。若某个动作尚未确认完成，仍须按其实际状态处理；“环境还在”不代表所有动作结果都已清楚。

训练暂停期间，如果数千个环境一直驻留，内存成本又会积累。DSec 因此让 RL 框架通知相关沙盒暂停：容器冻结进程并回收可回收内存；microVM 保存执行快照，再释放运行进程所占资源。后续请求会先恢复环境，再继续执行。暂停保留任务状态，与任务结束后的销毁是两个不同动作；这里的抢占恢复也不能推出任意宿主机故障都能无损恢复。[DSec 第 6.3 节](https://arxiv.org/html/2609.22978v1)

恢复也不应被理解为万能撤销。外部服务已经发生的行为，不会因为恢复沙盒快照自动回退。论文描述的是平台与训练协作维护执行状态的机制，不是任意工具跨所有系统都“恰好执行一次”的证明。训练框架还应关联轨迹、策略版本、环境版本与奖励版本，才能判断恢复后的样本如何使用；这是从一致性要求推导出的训练记录需求，不是本文验证过的 DSec 全部日志字段。

## 有效轨迹的吞吐比创建数量更重要

沙盒复用必须区分三种情况：无状态调用复用预热执行资源，独立任务复用只读环境层，同一轨迹恢复自己的可写状态。把前一任务未清理的文件直接交给下一任务，并不能算安全的复用。若残留内容影响测试或给出了答案线索，收集得再快也可能是错误的训练信号。

DSec 论文提供 pack_diff，把交互构建的环境保存成可复用的增量磁盘快照。作者同时说明构建者与运行 Agent 使用不同账号，并在发布环境前清理构建残留，以减少参考答案进入运行任务的风险。运行侧还使用文件、通信与网络范围控制保护任务完整性。这些措施是部分防线，论文没有承诺通用、绝对的隔离保证。[DSec 第 6.1、6.4—6.5 节](https://arxiv.org/html/2609.22978v1)

对 R17，训练系统真正需要的是“Agent 在规定环境和权限下完成修改，评估器给出可核实结果”的轨迹。镜像加载失败不应自动变成模型不会修代码；评估器读到上一任务残留的成功文件，也不能当作本任务成功。环境故障、结果未知、隔离异常与正常任务失败都应保留可区分的状态，怎样纳入奖励由明确的训练规则决定。

因此，可以分别监测创建成功率、就绪时间、工具 p95/p99 延迟、暂停恢复正确性，以及单位时间内完成且通过完整性检查的轨迹数。最后一个指标比“创建了多少沙盒”更接近有效采样能力，但它仍不同于模型能力评估：创建更多环境不等于每条轨迹更优秀，也不证明训练后模型更强。

## 怎样阅读论文里的性能数字

论文第 8 节使用独立于生产部署的 10 节点 CPU 测试集群。在第 8.2 节的 8192 容器突发实验中，作者报告按需加载约 35 分钟完成全部任务，冷启动全量拉取需要超过 60 分钟；比较对象还有已缓存镜像的本地基线。这组数字说明该工作负载下镜像分发会影响端到端完成时间，不能转述为任意 Agent 都快约两倍。[DSec 第 8.1—8.2 节](https://arxiv.org/html/2609.22978v1)

另一项层格式实验用预先录制的确定性工具调用替换模型生成，以隔离环境准备方式的影响。这样的控制有助于分析基础设施，但也正说明它没有测量“模型因为 DSec 而更会解决问题”。本篇未复现这些实验，也没有用生产沙盒数量反推模型成功率。

如果要判断某套 Agent 训练是否需要类似平台，应先量出时间花在哪里：环境准备、模型生成、工具执行、评估还是恢复。只有当执行环境的生命周期、规模与状态管理成为明显约束，DSec 的这些机制才提供对应的设计思路；RL 目标、奖励质量和模型更新仍需另外解决。

**一分钟回答：** DSec 是为大规模 Agent rollout 和评估提供环境的执行基础设施。Agent 需要跨轮保留文件与服务状态，又要隔离不同任务，环境创建、镜像读取和长尾工具等待都会影响采样。DSec 组合多种沙盒后端，独立版本化基础层、工作区与工具层，按需加载并管理高密度资源。它把 worker 和 agent sandbox 放在可抢占 GPU 训练之外，暂停时保留执行状态并回收资源，恢复后继续轨迹。有效轨迹吞吐需要同时保证任务完整性；平台速度不是 RL 算法，也不能直接当成模型成功率。

**追问一：为什么不能把所有东西放进训练 pod？** 长轨迹与 GPU 训练进程生命周期不同。pod 被抢占时，控制进度可能丢失，沙盒动作却已发生，需要复杂对齐。把执行状态移到独立生命周期中，可以减少这种耦合，但仍要维护动作结果与训练版本的一致性。

**追问二：预热复用和状态隔离是否矛盾？** 不必然。可以复用只读层或无状态执行资源，同时给不同轨迹独立可写状态。错误在于把前一任务残留当作下一任务的干净起点。恢复同一轨迹与重置后服务新任务必须有不同契约。

**追问三：吞吐提升为什么不等于模型更强？** 吞吐衡量系统处理样本的速度；模型能力还取决于任务分布、奖励、有效样本比例与参数更新。若环境污染或评估器错误，更高吞吐只会更快地产生有问题的信号。需要独立做能力评估。

<summary>练习参考思路</summary>

干净沙盒没有 R17 的文件修改、服务状态和后续执行位置，只有成功文字无法继续原轨迹，也无法核对结果对应哪份代码。应保留并恢复关联的 worker 与沙盒状态，确认工具结果属于这次任务与环境版本，再继续收集或完成轨迹。

需要区分“暂停但可恢复”“任务已终止”“已保存可复用环境”与“清理完成可服务新任务”。暂停可以释放部分运行资源，但不能把尚需恢复的状态当作垃圾删除；用于新任务的可写空间必须按隔离契约重置。恢复是否正确，应检查实际文件与工具结果，而不是只检查能否重新打开会话。

</details>
