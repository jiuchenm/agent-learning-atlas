# DSec 论文解读：Agent 训练环境怎样供给轨迹

DeepSeek Elastic Compute（DSec）是为大规模 Agent 训练和评估提供执行环境的沙箱平台。模型可以提出“修改文件”“运行测试”，实际执行这些动作、保存文件并返回结果，还需要一套环境。DSec 管理许多环境的创建、资源、状态和回收，让训练系统能持续取得交互数据。论文讨论的是这套基础设施怎样运行。[DSec v1：摘要与第 1 节](https://arxiv.org/html/2609.22978v1)

先分清三个概念。**轨迹（rollout）**是 Agent 对一个任务的一次完整尝试，包含逐轮的动作与环境观察；沙箱（sandbox）是动作运行的受控环境，里面可以有仓库、进程和服务；强化学习（Reinforcement Learning，RL）算法则决定怎样利用轨迹和奖励更新模型参数。DSec 主要负责沙箱及其与训练系统的协作。环境更快地返回结果，能够改善采样效率，但不能直接证明模型更会解题。

本篇是系统案例选读，可先读[强化学习基础](#/lesson/rl-foundations)与[工具失败](#/lesson/tool-reliability)。固定来源为 2026-09-19 发布的 arXiv v1，正文机制与数字于 2026-10-01 重新核对；未部署 DSec，也未独立复现实验。下面继续用原任务 R17：修复 CSV 日期解析。任务输入、测试结果、时间和资源算术均为**教学假设**。

## 从代码修复到一条可交付的轨迹

R17 的要求是把 CSV 中按“日/月/年”记录的日期转成 ISO 日期。仓库版本固定为 C1，现有程序误用了“月/日/年”的解析格式，因此输入 `19/09/2026` 会报错。假设 Agent 需要找到解析函数、修改格式，再运行测试。修复后的预期输出是 `2026-09-19`；这项具体设定用于讲清状态变化，不是论文的测评题。

一次尝试按下面的顺序推进：

1. 训练系统为 R17 选择环境，给出仓库、依赖、资源上限和网络规则，等待沙箱就绪。
2. 模型请求读文件；执行端运行命令，把解析代码作为观察返回模型。
3. 模型请求修改格式；沙箱写入文件，后续命令看到这次改动。
4. 模型请求运行测试；假设测试通过，执行端返回退出状态与测试输出。
5. 轨迹收集端保存动作、观察与最终产物，评估器按任务规则给出反馈；任务结束后停止沙箱。

这条轨迹的交付物包含代码改动和对应的测试记录。模型说“已修复”，并不能替代实际磁盘上的修改；测试输出也必须对应这次运行的代码。训练中的失败尝试同样可以有学习价值，但应分清：日期格式仍然错误是任务失败，依赖没有准备好则是环境失败。两者怎样计入奖励，应由明确的训练规则决定。

R17 需要**有状态沙箱（stateful sandbox）**：同一条轨迹内，文件修改、安装的依赖和启动的服务能跨调用保留。如果每次工具调用都换成干净机器，第 4 步就会测试旧代码。如果两条独立轨迹共用一个可写目录，第二个 Agent 又可能读到第一个的修复。所需的契约是“轨迹内部持续、独立任务之间隔离”。聊天记录只能描述动作，无法代替执行状态。[DSec 第 2.3 节](https://arxiv.org/html/2609.22978v1)

## 环境怎样准备：后端、版本层与按需读取

DSec 通过 Python 客户端 `libdsec` 提供统一入口，但调用者仍需选择后端。R17 是常规 Linux 仓库任务，可以考虑容器；其他任务的隔离和系统功能要求可能不同。论文的四类后端各有代价，统一 SDK 不会消除这些差异。[DSec 第 2.1—2.2 节](https://arxiv.org/html/2609.22978v1)

| 后端 | 典型任务 | 主要取舍 |
| --- | --- | --- |
| FnCall | 短、无状态的代码或函数执行 | 复用预先创建的执行环境，减少单次创建成本；不适合依赖连续状态的 R17 |
| 容器 | 软件工程与一般工具任务 | 启动快、密度高，但共享宿主内核 |
| microVM | 需要更强隔离的 Linux 任务 | 提供虚拟机边界，启动和内存成本高于容器 |
| 完整 VM | 依赖完整操作系统、GUI 或图形的任务 | 系统功能更完整，资源开销也更高 |

选好容器后，还要让仓库、依赖和测试入口可用。“容器已经运行”和“R17 可以开始”是两个状态。若把所有内容打成一个大镜像，更新 Agent 工具时，所有仓库镜像都可能要跟着重建。DSec 将基础环境（base image）、任务工作区（workspace）与工具包（toolkit）作为独立版本层组合；工具包更新后可以与原有仓库层重新组合。[DSec 第 5.1 节](https://arxiv.org/html/2609.22978v1)

容器用 overlayfs 将多个只读层呈现为一棵目录树，运行时写入进入每个沙箱自己的可写层。于是两个 R17 尝试可以共享 C1 和工具包的不可变内容，同时各自保存修改。microVM 也组合独立版本的只读层与可写磁盘，但具体存储路径与容器不同。**共享内容不等于共享可写状态。**固定这些层的版本有利于复查结果；外部服务、随机性、时间和评估规则仍可能影响执行，镜像本身不保证逐字复现。

环境准备还有传输成本。R17 或许只读解析模块、Python 和少量依赖，却需要一个包含许多工具的大镜像。DSec 使用 EROFS 只读文件系统，从 Fire-Flyer File System（3FS）分布式存储按访问需要读取镜像内容。容器路径尽量把元数据预取到本地，文件数据按需读，运行写入留在节点本地。这样既减少重复解包，也可能减少实际传输量。[DSec 第 5.3 节](https://arxiv.org/html/2609.22978v1)

成本仍会出现：R17 第一次访问未缓存的文件时要等 I/O；若最终读取几乎整个镜像，节省的数据量就有限。3FS 擅长较大的顺序 I/O，小随机读取需要相应处理。因此不能只比较启动按钮多快返回，还要量从请求到第一次工具可用、直到整个任务完成的时间。

## 并发轨迹怎样占用资源

扩大训练规模后，可以同时运行 R17 的多次尝试。它们会交替等待模型、修改文件、运行测试。等待生成时，沙箱 CPU 可能空闲，文件、内存和服务却仍需保留；测试繁忙时，又可能暂时没有下一轮模型请求。沙箱的存活时长因此不同于 CPU 的工作时长。

假设四条尝试分别用时 60、60、60、240 秒，且同时开始。若调度要等整批结束才补任务，前三个位置各有 `240−60=180` 秒不能继续采样。在完成的位置补新任务可以减少等待，但异步收集是否允许、样本能落后当前策略多少版本，属于 RL 框架的约束，沙箱平台不能单独决定。

再作一个容量手算：假设 100 个沙箱都存活 180 秒，每个只使用一个 CPU 核心工作 30 秒，其余时间等待模型。如果每个沙箱始终独占一核，总工作量是 3000 核秒，预约容量是 18000 核秒，平均 CPU 利用率为：

$$
U=\frac{100\times30}{100\times180}=\frac16\approx16.7\%
$$

这里 $U$ 表示这组假设任务的平均利用率；100 是沙箱数，30 和 180 分别是每个沙箱的 CPU 工作秒数与存活秒数，分子、分母的单位都是核秒。它不是 DSec 实测值，也不能据此把机器数直接缩小六倍：100 个沙箱可能同时开始测试，产生瞬时争用。

DSec 的高密度管理会共享可共享的只读内存页面、回收冷内存，并区分延迟敏感与尽力而为的工作。后者可以利用空闲 CPU，但还需控制同一物理核心上硬件线程之间的干扰。增加共置密度时应检查工具延迟；如果 R17 的测试因争用变慢，容纳更多沙箱也可能拉长轨迹尾部。[DSec 第 4.3、5.2 节](https://arxiv.org/html/2609.22978v1)

## 训练暂停时，哪些状态要留下

现在假设 R17 已修改文件，测试成功结果也已回到轨迹收集端，GPU 训练任务却被调度器抢占。若 Agent 循环与训练进程一起退出，可能出现一边控制进度丢失、一边远端沙箱仍保留改动的情况。恢复时既要知道磁盘上是什么，也要知道哪些观察已经交给模型，才能决定下一步。

论文报告的新设计把 rollout 执行移到可抢占 GPU 池之外：agent sandbox 保存执行框架与工具，worker container 管理沙箱并维护轨迹控制层。两者联合保留轨迹状态，训练恢复后重新连接，降低对命令日志重放的依赖。这让轨迹生命周期与训练进程生命周期解耦。[DSec 第 6.2 节](https://arxiv.org/html/2609.22978v1)

对 R17，恢复目标是取回这份已修改的文件和对应结果，再继续或结束轨迹。只新建一个干净沙箱、复制一句“测试成功”，无法解释成功属于哪份代码。若动作尚未确认完成，还需检查实际状态，避免重复执行；沙箱快照也不会撤销已发生的外部操作。关联轨迹、策略、环境和奖励版本是从一致性要求推导出的记录建议，本篇没有验证 DSec 的全部日志字段。

长时间暂停又会占资源。DSec 接收 RL 框架的暂停请求：容器冻结进程后回收内存；microVM 保存内存与执行快照，再释放运行进程，后续请求先恢复再执行。**暂停保留继续原轨迹的条件；终止与清理则结束这份执行状态。**这项抢占恢复机制不等于任意宿主故障都能无损恢复。[DSec 第 6.3 节](https://arxiv.org/html/2609.22978v1)

R17 正常结束后可以显式停止，闲置或被遗弃的环境也可按生存期限回收。用于下一条任务时，应重置独立可写状态。论文的 `pack_diff` 还能把交互构建的环境保存成可复用增量磁盘快照；它用于环境构建时，必须清理构建残留，避免把参考答案带入运行任务。作者采用构建者与运行 Agent 分账号，以及文件、通信和网络访问控制来保护任务完整性，同时说明这些措施只覆盖部分风险。[DSec 第 2.3、6.1、6.4—6.5 节](https://arxiv.org/html/2609.22978v1)

## 怎样判断吞吐取舍是否值得

对训练有用的是按规定环境产生、反馈可核实的轨迹。模型没修好日期可以是有效的失败样本；读到前一任务遗留的答案、环境准备失败或结果无法归属，则需要另行标记。只数“启动了多少沙箱”，无法说明提供了多少可信的交互数据。监测应覆盖就绪时间、工具 p95/p99 延迟、暂停恢复正确性，以及单位时间内完成且通过完整性检查的轨迹数；这些是本篇的工程检查建议。

论文性能数字也要按这个口径阅读。第 8 节使用独立于生产部署的十节点 CPU 测试集群；第 8.2 节在真实 RL 评估工作负载下，突发创建 8192 个容器，任务需要多样的、数 GB 的镜像。作者比较按需 EROFS、冷启动全量拉取与镜像已缓存的本地基线，报告按需方案约 35 分钟完成全部任务，接近本地基线，冷全量拉取超过 60 分钟。这反映该负载的环境准备与端到端完成时间，不能推广为所有 Agent 的固定加速比。[DSec 第 8.1—8.2 节](https://arxiv.org/html/2609.22978v1)

第 8.3 节比较工作区与工具层格式时，还用预录的确定性工具调用替换 LLM 生成，让对照主要变化来自环境供给方式。这有助于研究基础设施，却没有测量模型训练后的解题能力。论文的实验和生产规模均是作者报告，本篇未独立复现。

选择类似平台前，可以先给 R17 做一份时间账：环境准备、模型生成、工具执行、评估和恢复各占多少。当任务很少、环境稳定时，普通容器配合明确的生命周期管理也可能足够；大规模突发创建、长期保留状态与稀疏资源利用成为约束时，DSec 的设计才提供对应的思路。更高吞吐扩大了采样能力，模型质量仍需用固定任务分布、可靠奖励和独立能力评估检验。

<summary>面试怎么回答</summary>

**约一分钟回答：**DSec 是为大规模 Agent 训练和评估提供沙箱的执行平台。模型提出动作，沙箱实际改文件、跑测试并返回观察，一次完整尝试构成轨迹。平台要在轨迹内保留状态、在独立任务间隔离状态，还要处理镜像准备、长尾等待和闲置资源。DSec 提供多后端，组合独立版本的环境层，按需加载，并把轨迹执行与可抢占的 GPU 训练解耦。暂停时保留 worker 与沙箱状态，结束后回收。它改善轨迹供给；RL 算法怎样更新参数和模型是否变强仍需分别验证。

**追问一：为什么不能只保留聊天记录？** 聊天描述“改了文件”，却不能恢复实际文件与进程；只保留文件又不知道哪些工具结果已被模型消费。续跑需要控制进度和沙箱执行状态对齐。外部副作用还需单独核对。

**追问二：环境复用怎样避免污染？** 无状态调用可复用预热执行资源；独立轨迹可以复用只读层，但要有各自的可写空间；恢复同一轨迹则保留它自己的状态。把上一任务残留交给下一任务，会改变初始条件，甚至泄漏答案。

**追问三：平均 CPU 利用率低，为什么还要限制密度？** 平均值掩盖同时测试的峰值，也不包含长期占用的内存。过多共置会增加单步延迟和长尾，应同时检查资源峰值与延迟要求。

**追问四：35 分钟对超过 60 分钟，能说明什么？** 能说明论文十节点、8192 容器及指定负载下，按需供给比冷全量拉取更早完成任务。不能据此证明模型成功率提高，也不能推成任意负载都有同样收益。

练习：R17 的测试成功结果已被 worker 保存，随后 GPU 训练被抢占，沙箱暂停。有人建议释放所有状态，只保留“测试成功”，恢复时创建干净环境。请说明这会丢失什么，并分别为“继续 R17”和“把资源交给新任务”写出所需条件。你会检查哪个结果，确认恢复确实正确？

<summary>练习参考思路</summary>

只保留文字会丢失代码改动、服务或进程状态，以及控制层的执行位置和结果归属。继续 R17 要恢复关联的 worker 与沙箱状态，核对测试记录属于这次代码与环境；动作结果未知时先查状态。可以读取修复文件，并核对输入 `19/09/2026` 的输出和对应测试记录，不能只确认会话能打开。

交给新任务时则应结束旧任务，并按隔离契约清理或重置可写状态。暂停但可恢复、任务终止、打包的可复用环境与清理完成是不同状态：尚需续跑的状态不能当作垃圾删除，含答案的结果也不能当成新任务的起点。
