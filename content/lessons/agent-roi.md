# Agent ROI：省下时间以后，收益在哪里

假设一个团队每月处理 10000 个内部请求，演示中的 Agent 能在几十秒内写好答案，于是有人把每单人工处理时间全部算成收益。上线后却发现，员工只在部分任务中使用它，生成内容仍要核对，失败请求还需要人工重新处理。模型费用很低，月度收益却没有按演示推算出现。

投入产出回报率（Return on Investment，ROI）要比较同一范围、同一周期内的增量收益和完整成本。关键不是把一个除法算对，而是解释收益如何发生、哪些任务真正受益，以及没有 Agent 时本来会怎样。本课承接 [Agent PRD](#/lesson/agent-prd) 和 [Agent 评估](#/lesson/agent-metrics)，使用用户源文第 25 节的数字建立一份假设测算，不代表用户或任何团队的实际业绩。

Azure Well-Architected 的成本优化原则要求成本模型服务于业务目标，并把基础设施、实施、人员和运维纳入考虑；成本优化也不等于一味采用最便宜的技术。[Azure：Cost Optimization design principles](https://learn.microsoft.com/en-us/azure/well-architected/cost-optimization/principles)

## 从任务量走到真正节省的时间

先固定口径：一个月有 10000 个同类范围内的有效任务，其中 4000 个实际使用 Agent，3000 个经核验成功，且每个成功任务平均减少人工主动处理时间 2 分钟。这里的 2 分钟已经扣除该成功任务中的正常阅读、核对和修改时间；另外 1000 个失败尝试没有记入收益，它们额外造成的恢复工作放在成本中。

由此，采用率为 $4000/10000=40\%$，采用后的成功率为 $3000/4000=75\%$，最终产生已核验节时的任务覆盖率为 $3000/10000=30\%$。三个比例回答不同问题。工具能成功调用，不等于员工实际采用；员工采用，也不等于任务正确完成并减少了工作。

若直接拿“10000 单都省 2 分钟”计算，会把收益放大到 20000 分钟。本例真正计入的是：

$$
T_{save}=3000\times2=6000\text{ 分钟}=100\text{ 小时}
$$

$T_{save}$ 是本月成功任务合计减少的人工主动处理时长。人工综合成本假设为每分钟 1 元，包含本次测算选定的人力成本范围，则这些时间对应的容量价值为 6000 元。这个单价是假设，不是对任何岗位薪酬的估计。

也可以写成预测式 $B=V\times a\times s\times t\times w$：$V$ 为任务量，$a$ 为采用率，$s$ 为采用后的有效成功比例，$t$ 为每个成功任务的净节时，$w$ 为每分钟估值。代入本例，就是 $10000\times0.4\times0.75\times2\times1=6000$ 元。这里已通过 $a$ 与 $s$ 得到 3000 个有效任务，不能再把结果乘一次 30%，否则重复扣减。

## 把每月 4000 元成本拆开

假设本例按月计入的增量成本如下。原有人工作业中没有发生变化的部分，在前后比较中抵消；新增成本包括成功和失败尝试，不能只统计最后成功那一次模型调用。

| 成本项 | 假设月金额 | 计入内容 |
| --- | ---: | --- |
| 模型、检索与工具服务 | 1000 元 | 输入输出、重试、精排、所有子 Agent 调用 |
| 平台与运行支持 | 500 元 | 存储、日志、监控及相关基础设施 |
| 持续维护与评估 | 700 元 | 数据更新、标注、回归、安全检查与问题处理 |
| 失败后的额外人工纠错 | 800 元 | 失败尝试相对原流程新增的恢复工作 |
| 初始实施投入的月度分摊 | 1000 元 | 假设 12000 元初始投入按 12 个月分配 |
| 合计 | 4000 元 | 本月完整测算成本 |

正常成功任务的核对时间已经扣在净节时里，因此表中不能再把同一段时间列为成本。失败任务原本就需要的人工处理时间，与原流程相比没有节省；表中只加上 Agent 导致的额外检查、清理和重做，避免把原本要做的工作也重复扣一次。

初始实施可能包含开发、数据接入、集成测试、培训和流程调整。本例用 12000 除以 12 得到每月 1000 元，是管理测算中的分摊假设，不是会计资本化或折旧政策结论。若预计只能使用六个月，同样投入每月应分摊 2000 元，月成本就变成 5000 元，其他条件不变时 ROI 会下降。

Azure 的成本模型指南同样要求估计初始成本、运行成本与持续成本，并把监控、测试、人员、维护和支持纳入模型，再关联到每笔业务或每个用户等单位指标。[Azure：Architecture strategies for creating a cost model](https://learn.microsoft.com/en-us/azure/well-architected/cost-optimization/cost-model)

按容量价值口径，本例计算为：

$$
\mathrm{ROI}=\frac{B-C}{C}=\frac{6000-4000}{4000}=50\%
$$

$B$ 是本月认可的收益估值，$C$ 是同月完整成本。净收益估值为 2000 元，收益成本比为 $6000/4000=1.5$。50% 的意思是每计入 1 元成本，对应 0.5 元净收益估值；它不是“节约了公司总成本的 50%”，也没有说明初始投入在什么时候收到现金回报。

## 一百小时为什么不自动变成六千元现金

节约时间至少可能走向三种不同结果。第一，工作更轻松或等待更少，但预算和产出都没有变化；第二，释放的容量被用于处理积压、改善服务或承接新增任务；第三，确实减少了加班、外包、采购或其他实际支出。三者都有可能有价值，但证据和货币口径不同。

因此本例可以报告“核验减少 100 小时人工工作，按既定单价折算容量价值 6000 元”，不能直接写“现金节省 6000 元”。若这 100 小时零散分布在许多人每天的几分钟里，且无法重新安排任务，即使计时真实，兑现程度也可能有限。需要查看吞吐量、积压、服务质量或实际支出怎样变化。

做情景分析时，可以引入容量兑现系数 $u$：只认可已节约时间中能够转化为目标产出的比例。若假设 $u=50\%$，认可收益为 $6000\times0.5=3000$ 元，成本仍为 4000 元，则这一口径下 ROI 为 $-25\%$。这不是随意打折，而是提醒测算者为“时间如何被利用”提供证据；没有证据时应列出情景，不把系数写成实测事实。

同一份报告最好把工时、容量价值、增量产出和现金影响分开呈现。如果新增产出带来收入，也不能把收入全部当成净收益，要考虑为该产出额外付出的成本。还要避免双重计入：同一小时若已经按人工价值折算，就不能又把用这小时完成任务的全部收入作为另一笔独立收益。

月度分摊也不能取代现金流记录。初始投入可能集中在开始时发生，而月报把它分配到 12 个月；判断资金支出应看实际支付时间，评价长期方案则要看完整周期。已经花掉的历史投入应保留在项目全生命周期回顾中；决定是否继续运行时，还要另看未来可避免的成本和收益，不能把这两个问题混用一个数字回答。

## 没有 Agent 时，本来会怎样

反事实基线（counterfactual baseline）指在可比较条件下，没有采用这项方案时预计会发生的结果。若过去处理一单平均 5 分钟，现在降到 3 分钟，不能立刻把两分钟差额都归给 Agent：本月任务可能更简单，表单可能同时被优化，熟练员工比例也可能上升。

可行的比较是把相近难度、相同类型和时间窗口的任务分组，在一致质量要求下比较。A/B 测试需要设计合理分配，避免只让熟练用户或简单任务进入 Agent 组；无法随机分组时，可以用前后对照并说明任务构成、季节性和其他流程变化的限制。不要把员工点击“使用”当成成功，也不要只计生成等待时间而漏掉后续复核。

本例的 3000 单应来自这些检查：任务确实使用了 Agent，结果满足原有质量门槛，人工主动处理时长下降，并且没有在几天后的退回或复核中把节省抵消。对失败、误拒绝和异常任务要记录额外纠错时间，才能解释成本表的 800 元从哪里来。

基线也应包括已有的简单方案。如果一个固定表单校验就能减少同样的重复工作，比较对象不应只有“完全人工”和“复杂 Agent”。应把普通脚本、流程整理、检索改进等可行方案放入同一任务与质量范围，比较长期维护和运行成本。这样才能判断收益来自 Agent 的能力，还是来自原本就可以进行的流程改进。

## 哪个变量最可能改变结论

保持每单净节时 2 分钟、每分钟 1 元、月成本暂时固定 4000 元，只改变有效节时任务数，可以得到：

| 有效节时任务 | 时间价值 | 净价值 | ROI |
| ---: | ---: | ---: | ---: |
| 2000 单 | 4000 元 | 0 元 | 0% |
| 3000 单 | 6000 元 | 2000 元 | 50% |
| 4000 单 | 8000 元 | 4000 元 | 100% |

这是一张控制其他条件不变的敏感性表，真实任务量增长可能带来更多推理和人工成本，不能把固定成本假设无限外推。在当前简化条件下，盈亏平衡需要 $4000/(2\times1)=2000$ 个有效任务。按 40% 采用率、4000 个采用任务计算，至少需要其中 50% 获得已核验的节时收益。

如果要求只有部分时间能够兑现，则需要 $u\ge4000/6000\approx66.7\%$ 才能覆盖本例成本。若模型账单降了 200 元，却让失败纠错增加 500 元，总成本实际增加 300 元；单看 token 单价会得出相反结论。质量、采用与维护这些变量，往往比一项模型费用更能改变项目结果。

最终交付可以是一份很短的业务测算：“月范围 10000 单；采用 4000 单；有效节时 3000 单，净省 6000 分钟；容量价值 6000 元，月成本 4000 元，容量口径 ROI 50%；现金影响尚未确认。下一阶段验证采用持续性、退回率、容量利用及成本分摊。”它比一个脱离前提的百分比更便于审查和复算。

<summary>面试怎么回答</summary>

**一分钟回答：怎样计算 Agent ROI？**

先明确业务范围、周期和反事实基线，再从总任务量经过采用率、有效成功比例得到真正节时的任务。每单节时要扣除正常复核，失败纠错也要计入。成本包含模型、检索、平台、维护、评估和初始实施分摊。按同一口径计算收益减成本再除成本，同时区分工时、容量价值和实际现金。本例 3000 单各省 2 分钟，每分钟 1 元，价值 6000 元；成本 4000 元，容量口径 ROI 50%，但现金收益还需要证据。

**追问一：自动化率 80%，为什么仍可能没有回报？**

自动化可能只表示工具运行，未反映采用、正确完成和复核负担。失败恢复、少量高成本异常、低任务量下的固定投入，都可能抵消收益。应追踪每个阶段的分母与人工工作变化，不能由自动化率直接推出 ROI。

**追问二：员工没有减少，节省时间还算收益吗？**

可以作为容量或体验改善，但不能自动记作现金节省。要看是否消化积压、增加有效产出、降低加班或外包，以及这些变化是否由方案带来。没有兑现证据时，报告已核验工时和不同兑现情景更准确。

**追问三：为什么初始开发成本不能忽略？**

它是取得能力的投入，长期比较时应纳入完整周期，月度展示可按说明的使用期限分摊。但这与实际付款时间不同；决定继续运行还应单独看未来增量成本，不能为了好看的月 ROI 把历史投入从项目回顾中删掉。

## 练习：净节时被高估了

复核发现，本例 3000 个成功任务每单只净省 1.5 分钟；失败恢复又比预计多花 600 元。其他数据不变，且成本表原有的 800 元纠错仍需保留。请计算新收益、完整成本和 ROI，并判断能否通过删除失败任务让测算重新为正。

<details>
<summary>参考思路</summary>

新收益为 $3000\times1.5\times1=4500$ 元；成本为 $4000+600=4600$ 元，其中已经包含原有 800 元纠错，不应再次加入。净价值为负 100 元，ROI 为 $-100/4600\approx-2.17\%$。在成本不变的简化条件下，每个成功任务至少净省 $4600/3000\approx1.533$ 分钟才覆盖成本。

不能删除失败任务。它们真实消耗了服务与恢复资源，必须留在完整范围内。后续可以减少失败、降低维护成本或改善有效采用，但需要重新验证，不能只改报表口径。即使容量 ROI 改善，现金影响仍需另行确认。

</details>
