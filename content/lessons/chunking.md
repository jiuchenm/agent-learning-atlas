# Chunking：一份文档该切多大

用户问“相机能否再借 7 天？已经有人预约还可以吗？”助手找到了“可以续借一次，最长 7 天”，便回答可以。可同一份政策还有一句：“已有后续预约的设备不得续借。”如果这句没有进入模型上下文，助手即使准确引用了前一句，结论仍可能错。**分块边界切断了规则与例外**，问题在生成答案前就已埋下。

分块（chunking）是 [RAG](#/lesson/rag-basics) 的资料准备步骤：把解析后的文档拆成可单独检索的片段，每段称为一个 chunk。应用检索到片段后，再决定把哪些原文放入模型输入。块决定了搜索能选择的单位，也影响一次命中携带多少上下文。小块可能只带来一般规则，大块可能挤掉其他必要证据；“切多大”实际是在问**什么内容必须一起进入回答**。

前一篇 [文档解析](#/lesson/document-parsing) 已说明如何取得正文、标题、段落和来源位置。分块应利用这些结构信息。下面始终使用同一份相机政策，走完错误切法、几种修正办法和检验过程。政策内容、token 长度、预算和检索顺序都是教学假设；没有运行 tokenizer、检索模型或生成模型。

## 同一份政策，先看一次错误切法

假设政策 P7 第 3 版的标题是“相机借用规则”，正文只有四条。S1 至 S4 是本例的原文位置标记，供后面检查引用。

> **P7 第 3 版：相机借用规则**
>
> S1　相机标准借用期为 7 天，应在到期前归还。  
> S2　借用人可以申请续借一次，续借期限最长为 7 天。  
> S3　已有后续预约的设备不得续借，仍须按原到期日归还。  
> S4　归还时应一并交回电池、充电器和存储卡。

Token 是模型计量输入文本的单位。为了便于手算，假定 S1 至 S4 各占 40 token，正文共 160 token；附在一个块前的标题与来源标签合计占 10 token。真实中文的字符数与 token 数不是一一对应，实际工程必须用所选模型对应的 tokenizer 测量，不能从这几句文字反推这里的示意计数。

第一版切分器以正文 80 token 为上限，没有重叠。它按位置切出以下两块；表中的“包含”指原文，不是模型自动补全的内容。

| 错误切法 | 包含的条款 | 进入模型后能说明什么 |
| --- | --- | --- |
| C1：标题 + S1、S2 | 标准借用 7 天；可申请续借一次、最长 7 天 | 只有一般规则，缺少预约例外 |
| C2：标题 + S3、S4 | 有后续预约不得续借；归还配件 | 有例外，却缺少续借次数和期限 |

两块各占 90 token。用户问：“相机能续借多久？已经有人预约还可以吗？”假设检索把 C1 排第一，而应用留给政策证据的预算只有 100 token，便只放入 C1。模型看到了“最长 7 天”，看不到“不得续借”。**检索命中相关主题，不等于取得回答所需的完整证据。**

此时要求模型“认真阅读”无济于事：S3 根本没送进去。若它回答“可以续借 7 天”，就是把一般规则错误地用于已有预约的情形。即使 C2 也被检索到，当前 100 token 预算仍装不下两个各 90 token 的块；检索排序和上下文组装都要纳入检查。

Azure 的 RAG 分块指南明确指出，块过小会缺少回答所需上下文，跨块的相关信息可能无法同时捕获；块过大则增加输入与处理负担。文档结构、查询类型和处理成本都影响切法，不能单靠一个长度参数确定答案。[Azure Architecture Center：Chunking phase，2026-09-28 查阅](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/rag/rag-chunking-phase)

## 固定长度、结构和语义分别在做什么

固定 token 分块（fixed-size chunking）按长度推进，可以实现稳定的大小上限，适合作为简单基线。长度上限与模型输入限制直接相关，但 token 边界并不知道哪句话是例外，也不知道“仍须”指向哪条主规则。一些实现会尽量在句末截断，因此配置的上限不一定等于每块的实际长度。字符切分则计量不同，不能把字符上限直接当成 token 上限。

结构分块（structure-based chunking）利用标题、段落、列表项和表格边界。对于这份政策，可以按规则关系重组候选块：

| 结构块 | 应保留在一起的原文 | 原因 |
| --- | --- | --- |
| B1：借用期限 | S1 | 交代标准期限 |
| B2：续借规则 | **S2 一般规则 + S3 预约例外** | S3 限定 S2 的适用条件，单独给出任一条都不足以回答有预约的续借问题 |
| B3：归还物品 | S4 | 交代归还时的配件 |

B2 的正文 80 token，加标题与来源后占 90 token，能够放进同一个 100 token 证据预算。若检索选中 B2，模型就会同时看到续借次数、期限和预约例外。这里的 B1、B2、B3 是为本例设计的结构块，并不是原政策已经提供了这三个小标题。

这里并不是见到每个段落就切一次。S2 和 S3 恰好位于相邻段落，却共同构成完整规则。结构提供候选边界，业务含义决定哪些边界不能直接切开。若例外位于远处附件，就应保留明确的关联，让检索到主条款后可以补取相关例外；只复制相邻一小段文字未必够用。

语义分块（semantic chunking）根据主题与内容关系确定边界，常见做法会比较相邻句段的语义相似程度，将紧密相关的部分组合起来。这里可以先把向量理解为帮助比较文本含义的数值表示，计算细节留到 [Embedding](#/lesson/embeddings)。Azure 的指南描述了使用 embeddings 聚合同主题内容的方式，也指出这种方案会增加逻辑与处理成本。[Azure：Semantic chunking](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/rag/rag-chunking-phase#semantic-chunking)

语义接近不等于法律或业务上的完整。S2 在谈续借天数，S3 在谈预约限制，算法可能将它们归为同一主题，也可能因为措辞变化而拆开。没有哪个相似度阈值天然知道“不得续借”必须跟随一般续借条款。对于规则文档，可以在语义边界之外加入完整条款、例外与交叉引用的检查，并抽样读回原文。

这三种方法可以组合：先按标题和条款组织内容，再对过长部分按句段切分，并用 token 上限限制大小。整张大表装不进一个块时，也应让分出的行带上列名、单位和适用范围。分块可以复制原有标题帮助理解；像 B2 这样的新增组织标签，则要与原文标题区分。若另外生成摘要，应标明它是摘要并保留原文引用，不能让它冒充原始条款。

## 重叠保留连续性，也会占用预算

重叠（overlap）是在相邻块中重复一段原文，目的是让边界附近的内容有机会一起被检索。它适合缓解连续叙述被切开的情况，但重叠长度与真正需要的上下文长度不一定一致。

继续用 160 token 的示意正文。如果块长 80、重叠 20，步长就是 60 token。三个块分别覆盖第 1—80、61—140、121—160 个 token，正文长度为 80、80、40，总共存入 200 token，比原文多 40 token，即多 25%。若每块再附 10 token 标签，索引文本合计 230 token；之前两个不重叠块连同标签为 180 token。这只是本例的算术，没有计入向量和索引结构的存储。

它是否修好了 S2 与 S3 的关系？不一定。S2 占第 41—80 个 token，S3 占第 81—120 个 token。第一个块没有 S3，第二个块只有 S2 的后半段。重叠虽然把例外带进第二块，却没有保证完整续借规则也在其中。如果边界正好切掉“只能一次”这样的限定，问题仍然存在。

检索后还会遇到另一种浪费：两个相邻块同时命中，模型上下文里就出现重复段落。它们消耗两次预算，却未必提供两份独立证据。去重应参考文档 ID、版本、原文区间和父块关系。来自同一版本的相邻重叠区间可以合并，保留不重复的原文；来自不同版本的相似句子可能是规则变化，不能仅按文本相似就删除其中一份。

Azure AI Search 文档把重叠作为保留连续性的办法，也说明合适参数依赖内容与使用场景。文档中的起始参数是试验起点，不是所有语言、政策与模型的通用答案。[Azure AI Search：Content overlap considerations](https://learn.microsoft.com/en-us/azure/search/vector-search-how-to-chunk-documents#content-overlap-considerations)

## 用小块检索，用父块补足上下文

如果文档较长，完整章节适合阅读，却未必适合直接作为每次搜索的单位。父子分块（parent-child chunking）把这两个角色分开：子块（child chunk）较细，用来定位相关内容；父块（parent chunk）保存更完整的原文范围，用于命中后的上下文补充。父块可以是一组条款或一个小节，不必总是整份文档。

在本例中，可以把 S2 与 S3 分别作为子块，但让它们共同指向父块 B2“续借规则”。检索命中 S2 后，应用依据父块 ID 取回 B2，于是带回完整的 S2 和 S3。如果两个子块都命中，只需放入同一个 B2 一次。这个过程改变了检索后的组装方式，不是要求模型凭记忆补出例外。

父子关系需要明确存储，例如文档 P7、第 3 版、子块 ID、父块 ID、原文位置与权限范围。Azure AI Search 的 index projections 文档展示了子块如何关联父文档，以及父级字段怎样随子块保存；检索后是否扩展为某个完整父块，是应用需要实现的行为，不是保存一个父 ID 就自动完成的。[Azure AI Search：Index projections](https://learn.microsoft.com/en-us/azure/search/search-how-to-define-index-projections)

父块也受预算与权限限制。若本例取回整份 P7，正文 160 token 加标签为 170，仍然装不进 100 token 预算。选择 B2 时是 90，才满足当前预算。若一个父块混合不同可见范围，也不能因为其中某个子块可读，就把父块全文交给用户；分块关系不能扩大访问权限。

修订后的假设检索结果是 B2 排第一，占用 90 token，剩下 10 token 不足以放入另一块，也无需硬塞。回答应为：“一般可申请续借一次，最长 7 天；已有后续预约时不得续借，应按原到期日归还。”引用定位到 P7 第 3 版的 S2、S3。这里能够回答的是政策规则，若用户问某台设备现在是否有预约，还需要查询当前预约状态，政策分块本身无法提供实时事实。

## 用问题与证据评估粒度

比较切法时，固定“返回两个块”不公平：两块小段和两块完整章节可能消耗完全不同的输入预算。更有意义的做法是固定可用证据 token，再观察回答所需的原文是否完整进入上下文，同时记录多带了多少无关或重复内容、检索与组装耗时、索引大小和更新成本。

对这份政策，至少准备不同类型的问题：标准借用几天，能续借几次，已有预约还能否续借，归还需要哪些配件。还可以加入跨条款问题：“已经借了 7 天且后续有预约，能否再延长？”每题先标注必须出现的证据，再看每种切法在同一预算下是否覆盖。只测试“续借多久”这一个简单问题，很可能看不出例外被切掉。

人工检查还要问：块离开原文后是否知道主题，“本条”“上述设备”等指代是否完整，否定词和数值单位有没有被截掉，引用能否定位到正确版本。如果证据完整但模型答错，应继续检查生成环节；如果证据根本没入选，则再区分切块缺失和检索排序问题。分块不是所有错误的共同原因。

变更策略会改变块 ID、边界和检索结果，可能需要重建相关索引并重新生成文本表示。保存解析结果、切分配置和版本，可以在同一份输入上比较方案，避免同时修改解析、分块和检索后却无法解释收益。最后选择哪种粒度，应由实际问题和预算下的证据完整性决定，而不是因为某个数字在示例中很常见。

<summary>面试怎么回答</summary>

**一分钟回答：** Chunking 把文档变成可检索与传递的证据单位。固定 token 切分易控制长度，结构切分利用标题与条款，语义切分根据内容关系组织句段，几种方式可以组合。小块可能缺上下文，大块可能带入噪声；主条款和例外尤其要一起保留。Overlap 能减少边界损失，但增加重复与成本，检索后需要按来源区间去重。父子方案用小块定位，再取回适当父块补上下文。评估时固定证据预算，检查必要条款是否完整、引用是否正确，并同时看耗时和索引成本。

**追问一：为什么不直接增大块？** 增大会保留更多内容，也会占用更多预算，甚至让一个块都放不下。本例整份政策为 170 token，而证据预算只有 100；包含续借和例外的父块只需 90。目标是带回当前问题的完整证据，不是尽量多带文字。

**追问二：增加 overlap 能保证不丢上下文吗？** 不能。需要的上下文可能比重叠区更长，或者例外在远处附件。本例 20 token 重叠只保留了续借条款后半段。应检查真实边界与引用关系，必要时合并条款或通过父块补取，而不是只增加百分比。

**追问三：语义分块是否一定最好？** 不一定。它有额外处理与维护成本，相似度也不直接表达规则依赖。标题清晰、条款稳定的文档可能用结构规则更容易核验。应在相同数据与预算下比较，而不是根据方法名称判断质量。
