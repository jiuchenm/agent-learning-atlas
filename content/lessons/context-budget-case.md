# 面试案例：召回 20 段，窗口只能放 5 段

“检索已经找到了 20 段，模型窗口放不下，取前 5 段可以吗？”这个问题缺少两个信息：每段多长，以及回答究竟需要哪些证据。五段重复的额度说明，可能不如三段同时包含额度、例外和适用日期的材料。窗口限制的是 token 总量，答案质量依赖的是证据是否足以支持结论。

这是 [RAG](#/lesson/rag-basics) 里的“组装上下文”问题：检索输出 20 段候选，应用要选出少量原文放进模型请求，再由模型回答。上下文窗口是模型一次请求可处理的内容容量，token 是该容量的计数单位，具体计数依模型而异；[上下文窗口](#/lesson/context-window) 讲这个预算从哪里来。这里要做的不是给模型换一个更聪明的排序口令，而是在送入模型之前决定哪些证据值得占空间。

本篇把问题收窄为一次上下文组装。假设用户问：“我下周去海城出差，酒店每晚 760 元，住 3 晚。当前每天最多能报多少？会议指定酒店有例外吗？如果想用例外，需要提前找谁确认，批准后要交什么材料？”城市、政策、金额、日期、检索排名、长度与评估数值全部是教学假设，没有调用真实业务系统或模型；金额仅用于说明检索与计算，不是实际报销建议。

先修 [Reranking](#/lesson/reranking) 和 [Agent 评估](#/lesson/agent-metrics) 已解释排序与指标。这里不再重讲检索全流程，只处理一件事：在候选已经出现以后，怎样让有限预算留下完整、合法且互补的证据。

用本篇的问题走一遍：输入是用户同时问额度、例外、批准人和材料；检索输出 20 段。应用先排除无权限或过期段落，再从剩余内容选能分别证明这些条件的片段，合起来不得超过可用 token；模型最后才根据选入的证据计算与作答。输出应能分别指出“标准额度来自哪段、例外条件来自哪段”，不能只给一个数。这一轮选择若漏掉批准条件，模型没有机会靠文字技巧补回来。

## 先定义答案需要什么，再计算空间

对于这道题，人工标注的必要证据可以分成五个单元。第一，政策是否适用于本次城市、员工类别和出差日期；第二，住宿标准额度及计价单位；第三，会议指定酒店是否存在例外，以及例外的条件；第四，例外由谁在何时批准；第五，入住后提交哪些材料。最后一项回应材料要求，也避免把“获得批准”误解为无需凭证即可报销。

这些单元需要在测试集准备时依据权威原文标注，而不是让模型为了填满五格编出五种规定。不同问题需要的单元数可以不同。这里假设已核实：这 20 段中确实包含全部五项，瓶颈在于排序和组装，而非源材料不存在。

再算预算。假设本次选择的模型与 API 按输入加最大输出共享 8000 token 计算，系统指令、历史消息、当前问题和工具定义已占 3600，预留 1000 给回答，另留 400 处理封装与计数偏差。可用于证据的空间为：

$$
B=8000-3600-1000-400=3000
$$

$B$ 是证据预算。这里的 1000 是输出上限预留，不代表模型一定生成这么多。真实 API 还可能有不同的输出、推理或工具计数规则，应按实际契约与 tokenizer 计数。本例所有片段成本都已包含片段标题、版本、来源标签和分隔符，不能在装好 3000 token 后再额外添加一大段引用说明。

Azure 的 RAG 设计指南把检索结果的选择与包装明确放在应用编排层，并要求分别评估步骤与最终结果。也就是说，预算组装是应用要设计和验证的行为，不能把截断后的输入交给模型，再期望模型自行修复丢失内容。[Azure Architecture Center：RAG design and evaluation](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/rag/rag-solution-design-and-evaluation-guide)

## 给 20 段建立一份可核对的台账

下面的 ID 同时表示这次初检中的名次。分组只为便于阅读，每个 ID 都有长度；总数正好 20 段，总成本 12000 token。

| 初检 ID | 内容与来源状态 | 每段成本 | 本次处理 |
| --- | --- | --- | --- |
| D1、D2、D3、D4 | 当前政策 P9 v3 的同一住宿额度条款及重叠窗口 | 600、600、600、600 | 相同证据，保留最完整一段 D1 |
| D5 | 当前政策 P9 v3 的酒店设施说明 | 600 | 与额度及批准问题无关 |
| D6 | 去年 P9 v2 的旧额度 | 600 | 当前题不适用，剔除 |
| D7、D8 | 无权访问的另一业务单位申请记录 | 600、600 | 拒绝返回正文，模型不得读取 |
| D9 | 权威人事范围记录：员工类别、海城、P9 v3 生效日期 | 700 | 证据 E1 |
| D10 | P9 v3 额度表：海城住宿上限 600 元/晚 | 400 | 证据 E2，替代较长 D1 |
| D11 | P9 v3 例外条款及引用条件 | 500 | 证据 E3 |
| D12 | P9 v3 例外审批步骤：入住前由指定财务审批角色确认 | 650 | 证据 E4 |
| D13 | P9 v3 凭证要求、已批准例外的适用说明 | 750 | 证据 E5 |
| D14、D15 | D11、D12 的重叠摘录 | 500、650 | 合并重复来源，不能算额外证据 |
| D16 | 另一城市的住宿额度 | 650 | 城市不符，剔除 |
| D17、D18 | 当前政策里的差旅背景与餐饮说明 | 700、700 | 本题不需要 |
| D19 | 当前题已经在 D9 覆盖的员工类别解释 | 450 | 可复用但无新增覆盖 |
| D20 | 常见问答，转述 D10 的额度 | 550 | 低于权威原条款优先级 |

D7、D8 出现在台账，只表示搜索基础设施或离线审计发现了这两个候选标识，不表示应用已经把越权正文取回。生产检索应尽量在源端按权限约束；若检索层返回候选 ID，也必须在正文出库前完成授权检查。不能先把 20 段全部送给模型，再提示它不要引用其中两段。

D6 是旧版本，不能只因包含用户问题里的词就留下。本例明确问当前标准，所以使用当前生效版本；如果用户问去年出差怎么处理，版本规则可能相反。日期、员工类别和城市是适用性条件，不能一律当作可有可无的元数据。Azure 检索指南讨论了按字段过滤和问题拆解；具体哪些字段构成业务边界，需要应用结合资料契约定义。[Azure：Information retrieval phase](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/rag/rag-information-retrieval)

## 排得靠前不等于值得一起选入

先去除无权、旧版与城市不符的候选，再根据原文位置识别重复。D1 至 D4 不能贡献四次额度证据；D14、D15 也不能因为表述略有差别就被当成独立规则。去重需要保留出处、版本和原文区间，避免把“相似但有差异的旧规则”拼成一份不存在的新规则。

随后对合法候选重排，判断它们能否回答本题。排序结果仍只是单段价值的信号。假设 D1 在单段相关性上高于 D12，但已选了 D10 以后，再加 D1 只重复额度，加 D12 才能补上“提前找谁确认”。因此，组装时要看一段相对于已选集合新增了什么证据，而不是只问它单独排第几。

本例最终明确选择 D9、D10、D11、D12、D13，分别对应 E1 至 E5，成本合计：

$$
700+400+500+650+750=3000
$$

五段恰好用满当前预算，这是例子安排出的结果，不是“模型最佳输入总是五段”。如果某一段同时完整覆盖两个单元，可能只需要四段；若其中一项必须跨两个条款才能成立，也可能需要更多段。需要固定的是完整证据与 token 约束，不是段数。

作为对照，在执行硬过滤后，如果仍按原始排名直接取前五个候选，会选 D1、D2、D3、D4、D5，总成本同样是 3000。其中只有 E2 被覆盖，另外四个必要单元都缺失；本题的有效证据覆盖为五分之一。若应用先简单去重再取前几段，结果可能改善，但仍需检查剩下的段是否覆盖审批、例外和适用性，不能把“做过重排”当成完成证明。

Azure 的检索指南区分了广泛召回和更精确的重排，并提醒重排会增加处理时间。这里在重排之后再做互补选择，是本例的应用设计，不是声称某个排序服务会自动保证五个证据单元全部覆盖。[Azure：Use reranking](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/rag/rag-information-retrieval#use-reranking)

## 保留例外与引用，才能做正确计算

假设 D9 确认用户属于政策适用类别，本次日期在 v3 生效后；D11 规定会议指定酒店可以申请例外，但必须满足会议证明与提前批准条件；D12 明确应在入住前由指定财务审批角色确认；D13 列出酒店发票、会议材料及批准记录。输出就可以将标准额度与有条件例外分开。

基于假设标准，760 元每晚的实际住宿费为 2280 元，标准额度对应 600 乘以 3，共 1800 元，两者相差 480 元。答案可以说：“本次适用 P9 v3，标准是每晚 600 元，3 晚标准额度为 1800 元，依据 D9、D10。会议指定酒店存在有条件例外，需要在入住前由指定财务审批角色确认，依据 D11、D12。批准后提交酒店发票、会议材料和批准记录，依据 D13。未确认例外已获批准，不能直接认定 2280 元全部符合报销条件。”产品中的 D9 等标识应呈现为可打开的来源引用；计算则标明由这些假设输入得出。

压缩时最容易出错的是 D11。把它总结成“会议酒店可以例外”，删掉“提前批准”和材料条件，会让例外变成默认资格。如果预算还不够，可以截取有完整含义的原文区间，移除导航和重复标题，或者使用经过核对的摘要；否定词、日期、金额单位与条件不能为了省 token 被剪掉。摘要本身也需要生成与验证成本，不能假定它免费且无损。

如果五个单元都重要、压缩后仍放不下，应调整回答范围、分阶段回答或进行针对性补充检索。需要查到的证据如果根本不在这 20 段里，选择算法没有材料可以补。必须回到检索或资料层核实，而不是用“常见政策一般如此”填补缺口。

## 怎样证明方案更好

这里定义预算内证据召回率（Evidence Recall@budget）为：在固定证据预算内，最终上下文完整覆盖的必要证据单元数，除以人工标注的必要单元总数。本例 E1 至 E5 等权，分母为 5。直接取前五段覆盖 E2，为五分之一；最终选择五个互补段覆盖全部，为五分之五。重复四次 E2 仍只算一项，半句缺少例外条件也不算完整覆盖。

这个定义是本篇采用的评估口径，不同团队需要明确自己的单元与标注规则。它也不同于“命中了多少相关文档”。如果一项证据存在于候选池，却未进入最终上下文，是组装损失；如果候选池就没有它，是上游召回缺口。线上没有标准答案时，不能临时把模型自己的猜测当成满分分母。

证据覆盖满分仍不保证回答正确。模型可能算错 600 乘以 3，也可能把例外写成已批准，所以还要检查答案正确性、条件完整性和有据性，并确认引用确实支持对应句子。Azure 的端到端评估指南将 groundedness、completeness 和 correctness 等作为不同维度，不能只用一个指标代替全部质量判断。[Azure：LLM evaluation phase](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/rag/rag-llm-evaluation-phase)

实验可以在同一测试集比较直接截断、去重加重排、按证据互补组装等方案，固定模型、输出预算和权限范围。记录预算内召回率、答案正确率、例外遗漏率、单任务输入输出量和端到端 p95 延迟，并把额度单问、例外题与跨版本题分开统计。没有实际测量时，只能说本例的算术覆盖改善，不能宣称准确率提高或延迟下降。

换更大窗口是可比较的选项，但会增加处理内容与可能的成本，也不会自动清除旧政策、越权材料和重复证据。它解决容量，不直接解决证据选择。只有在过滤、完整性与组装已经正确，而有效证据确实太多时，扩容的收益才值得与分阶段回答等方案一起验证。

**一分钟回答：** 先算实际可用 token，扣掉系统消息、历史、工具和输出预留，再确认正确答案所需证据是否已经在 20 段里。随后按权限、版本、日期和适用范围过滤，去除同一条款的重复片段，再用重排与互补选择覆盖额度、例外、审批等必要单元。完整保留限定条件和来源，不机械截成前五段。用 Evidence Recall@budget 检查组装是否漏证据，同时看答案正确性、条件遗漏、成本和 p95 延迟。窗口扩容只是候选方案，候选里没有的事实不能靠扩容创造。

**追问一：为什么重排后直接 top-5 还可能不够？** 单段都相关，不代表集合覆盖完整。五段可能都谈额度，例外与审批却没有入选。需要比较新增覆盖和成本，按已经选入的证据调整后续选择。

**追问二：既然能压缩，为什么不把 20 段全部总结一下？** 越权材料不能先送去总结，旧版本也不能混合。摘要可能丢条件，且新增模型调用、延迟和核验成本。可以压缩合法且必要的内容，但要保留支持结论所需的完整条款与来源。

**追问三：Recall@budget 达到满分就能上线吗？** 不能。它只检查必要证据是否进入上下文，不检查模型计算和表达是否正确，也不反映延迟及权限错误。仍要做答案和端到端评估，并明确满分来自怎样的测试分布。
