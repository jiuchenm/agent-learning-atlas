# RAG 案例：20 段证据只能选 5 段时怎样取舍

这是一道 **RAG 的上下文组装综合案例**：检索已经找到 20 段候选材料，模型请求只能容纳其中少数几段。该取哪五段？只取检索排名最靠前的五段，看似合理，却可能全是同一条住宿额度的重复说明，漏掉例外、批准人与凭证要求。读者先知道 [RAG 怎样找到候选](#/lesson/rag-basics)，再了解 [上下文窗口](#/lesson/context-window) 是模型一次请求可处理的容量，就能跟着本例做选择；[Reranking](#/lesson/reranking) 和 [Agent 评估](#/lesson/agent-metrics) 可作为后续延伸。

假设用户问：“我下周去海城出差，酒店每晚 760 元，住 3 晚。当前每天最多能报多少？会议指定酒店有例外吗？如果想用例外，需要提前找谁确认，批准后要交什么材料？”检索系统返回 20 段候选。应用必须在把材料送给模型**之前**决定哪些原文能进入请求；如果选入的段落没有提前批准条件，模型无法从缺席的证据中可靠地补出条件。这里的城市、政策、金额、日期、排名、长度与评估数值全是教学假设，没有调用真实业务系统或模型；金额只用于演示计算，不是实际报销建议。

“只能选五段”是这次预算恰好容纳五段互补证据的结果，并非 RAG 的固定规则。真正的限制是 **token 总量**：token 是模型计量输入和输出容量的单位，具体计数依模型而异。一次完整处理要依次回答四个问题：

1. **哪些候选能用？** 先检查权限、版本、日期和适用范围。
2. **还能放多少？** 从本次请求容量中扣掉已有消息、回答预留与封装空间。
3. **这些段落合起来能证明什么？** 去重后选能补齐不同问题的证据，而非机械截取前五名。
4. **答案有据吗？** 模型按选入证据计算与作答，再核对每个条件和引用。

本文只处理“候选出现后怎样组装上下文”这一段流程。检索能否找到材料和模型能否正确表达，仍是相邻但不同的故障位置。

## 这道题的完整答案需要哪五项证据

用户一口气问了额度、例外、批准和材料，回答“每天 600 元”只覆盖其中一角。为便于核对，本例把完整答案所需的证据人工标成五个单元：

| 单元 | 要证实什么 | 若漏掉，答案会缺什么 |
| --- | --- | --- |
| E1 | 政策适用于本次城市、员工类别和出差日期 | 无法确认引用的政策适用于提问者 |
| E2 | 住宿标准额度及计价单位 | 无法计算三晚标准额度 |
| E3 | 会议指定酒店是否有例外，以及例外条件 | 容易把例外写成无条件资格 |
| E4 | 例外由谁、在何时批准 | 无法回答“提前找谁确认” |
| E5 | 入住后提交哪些材料 | 容易把已批准误解为无需凭证 |

这些单元需要在测试集准备时依据权威原文标注，不能让模型为了填满五格编出五种规定。不同问题需要的单元数可以不同。**本例假设 20 段候选里确实有全部五项**，因此瓶颈是选择与组装；若材料原本不存在，就要回到检索或资料层。

## 这次请求还剩多少 token 空间

假设本次选择的模型与 API 按输入加最大输出共享 8000 token 计算，系统指令、历史消息、当前问题和工具定义已占 3600，预留 1000 给回答，另留 400 处理封装与计数偏差。可用于证据的空间为：

$$
B=8000-3600-1000-400=3000
$$

$B$ 是证据预算，单位为 token。式中的 8000 是本例假设的总容量，3600 是已占输入，1000 是输出上限预留，400 是封装与计数偏差余量；预留 1000 不表示模型一定会生成这么多。真实 API 可能有不同的输出、推理或工具计数规则，应按实际契约和 tokenizer 核算。本例表中每段的成本已经包含标题、版本、来源标签和分隔符，不能用满 3000 后再额外塞入引用说明。

Azure 的 RAG 设计指南把检索结果的选择与包装明确放在应用编排层，并要求分别评估步骤与最终结果。也就是说，预算组装是应用要设计和验证的行为，不能把截断后的输入交给模型，再期望模型自行修复丢失内容。[Azure Architecture Center：RAG design and evaluation](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/rag/rag-solution-design-and-evaluation-guide)

## 20 段候选里，哪些先被排除

下面的 ID 同时表示这次初检中的名次。表格把同类候选合并显示，**每个 ID 仍各代表一段和一笔 token 成本**；总数正好 20 段，总成本 12000 token。

| 初检 ID | 内容与来源状态 | 每段成本 | 本次处理 |
| --- | --- | --- | --- |
| D1、D2、D3、D4 | 当前政策 P9 v3 的同一住宿额度条款及重叠窗口 | 600、600、600、600 | 去重时可留 D1；最终以更短的 D10 覆盖同项证据 |
| D5 | 当前政策 P9 v3 的酒店设施说明 | 600 | 与额度及批准问题无关 |
| D6 | 去年 P9 v2 的旧额度 | 600 | 当前题不适用，剔除 |
| D7、D8 | 无权访问的另一业务单位申请记录 | 600、600 | 拒绝返回正文，模型不得读取 |
| D9 | 权威人事范围记录：员工类别、海城、P9 v3 生效日期 | 700 | 证据 E1 |
| D10 | P9 v3 额度表：海城住宿上限 600 元/晚 | 400 | 证据 E2，替代较长 D1 |
| D11 | P9 v3 例外条款及适用条件 | 500 | 证据 E3 |
| D12 | P9 v3 例外审批步骤：入住前由指定财务审批角色确认 | 650 | 证据 E4 |
| D13 | P9 v3 凭证要求、已批准例外的适用说明 | 750 | 证据 E5 |
| D14、D15 | D11、D12 的重叠摘录 | 500、650 | 合并重复来源，不能算额外证据 |
| D16 | 另一城市的住宿额度 | 650 | 城市不符，剔除 |
| D17、D18 | 当前政策里的差旅背景与餐饮说明 | 700、700 | 本题不需要 |
| D19 | 当前题已经在 D9 覆盖的员工类别解释 | 450 | 可复用但无新增覆盖 |
| D20 | 常见问答，转述 D10 的额度 | 550 | 低于权威原条款优先级 |

**先做硬过滤。** D7、D8 出现在台账，只表示搜索基础设施或离线审计发现了候选标识；表中两段各 600 token 的长度也是教学设定，不表示应用已经把越权正文取回。生产检索应尽量在源端按权限约束；若检索层返回候选 ID，也必须在正文出库前完成授权检查。不能先把 20 段全部送给模型，再提示它不要引用其中两段。

D6 是旧版本，D16 属于另一城市；两段都含“住宿额度”之类的相似词，却不适用于当前问题。本例明确问当前标准，所以使用当前生效版本；若用户问去年出差怎么处理，版本规则可能相反。日期、员工类别和城市是适用性条件，不能一律当作可有可无的元数据。Azure 检索指南讨论了按字段过滤和问题拆解；具体哪些字段构成业务边界，需要应用结合资料契约定义。[Azure：Information retrieval phase](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/rag/rag-information-retrieval)

## 排得靠前的五段，为何只答对一部分

硬过滤之后，还要按出处、版本和原文区间识别重复。D1 至 D4 不能贡献四次额度证据；D14、D15 也不能因为表述略有差别就被当成独立规则。保留原文区间可防止把“相似但有差异的旧规则”拼成一份不存在的新规则。

随后对合法候选重排，判断它们能否回答本题。**重排（reranking）**是对已召回候选重新估计与问题的相关程度；它给出的仍主要是单段信号。假设 D1 在单段相关性上高于 D12，但已选了 D10 以后，再加 D1 只重复额度，加 D12 才能补上“提前找谁确认”。组装时要看一段相对于已选集合新增了什么证据，而不只看它单独排第几。

因此，本例最终选择 D9、D10、D11、D12、D13，分别对应 E1 至 E5，成本合计：

$$
700+400+500+650+750=3000
$$

五段恰好用满当前预算，这是例子安排出的结果，不是“模型最佳输入总是五段”。如果某一段同时完整覆盖两个单元，可能只需要四段；若其中一项必须跨两个条款才能成立，也可能需要更多段。需要固定的是完整证据与 token 约束，不是段数。

作为对照，**即使执行了硬过滤**，若仍按原始排名直接取前五段，仍会选 D1、D2、D3、D4、D5，总成本也是 3000。它们只覆盖 E2；适用性、例外、审批和凭证四项仍缺，本题的有效证据覆盖为五分之一。若先去重再取前几段，结果可能改善，但仍需检查剩下的内容是否覆盖其余问题，不能把“做过重排”当成完成证明。

Azure 的检索指南区分了广泛召回和更精确的重排，并提醒重排会增加处理时间。这里在重排之后再做互补选择，是本例的应用设计，不是声称某个排序服务会自动保证五个证据单元全部覆盖。[Azure：Use reranking](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/rag/rag-information-retrieval#use-reranking)

## 五段证据怎样变成一份有条件的回答

假设 D9 确认用户属于政策适用类别，本次日期在 v3 生效后；D10 给出每晚 600 元的标准；D11 规定会议指定酒店可以申请例外，但必须满足会议证明与提前批准条件；D12 明确应在入住前由指定财务审批角色确认；D13 列出酒店发票、会议材料及批准记录。五段分别承担不同证明责任，输出才能将**标准额度**与**有条件例外**分开。

基于假设标准，760 元每晚的实际住宿费为 `760 × 3 = 2280` 元，标准额度为 `600 × 3 = 1800` 元，相差 `480` 元。答案可以说：“本次适用 P9 v3，标准是每晚 600 元，3 晚标准额度为 1800 元，依据 D9、D10。会议指定酒店存在有条件例外，需要在入住前由指定财务审批角色确认，依据 D11、D12。批准后提交酒店发票、会议材料和批准记录，依据 D13。未确认例外已获批准，不能直接认定 2280 元全部符合报销条件。”产品中的 D9 等标识应呈现为可打开的来源引用；计算则标明由这些假设输入得出。

压缩时最容易出错的是 D11。把它总结成“会议酒店可以例外”，删掉“提前批准”和材料条件，会让例外变成默认资格。如果预算还不够，可以截取有完整含义的原文区间，移除导航和重复标题，或者使用经过核对的摘要；否定词、日期、金额单位与条件不能为了省 token 被剪掉。摘要本身也需要生成与验证成本，不能假定它免费且无损。

如果五个单元都重要、压缩后仍放不下，应调整回答范围或分阶段回答。如果需要的证据根本不在这 20 段里，则应针对性补充检索或回到资料层核实；选择算法没有材料可以补，不能用“常见政策一般如此”填缺口。

## 漏证是在哪里发生的，怎样核对

这里定义**预算内证据召回率（Evidence Recall@budget）**为：在固定证据预算内，最终上下文完整覆盖的必要证据单元数，除以人工标注的必要单元总数。本例 E1 至 E5 等权，分母为 5。直接取前五段只覆盖 E2，为 `1/5`；选入五段互补材料则覆盖全部，为 `5/5`。重复四次 E2 仍只算一项，半句缺少例外条件也不算完整覆盖。

这个定义是本篇采用的评估口径，并非跨产品统一指标。不同团队需要明确自己的单元与标注规则。它也不同于“命中了多少相关文档”：**候选池有、最终上下文没有**，是组装损失；**候选池本来没有**，是上游召回缺口。线上没有标准答案时，不能临时把模型自己的猜测当成满分分母。

证据覆盖满分仍不保证回答正确。模型可能算错 600 乘以 3，也可能把例外写成已批准，所以还要检查答案正确性、条件完整性和有据性，并确认引用确实支持对应句子。Azure 的端到端评估指南将 groundedness、completeness 和 correctness 等作为不同维度，不能只用一个指标代替全部质量判断。[Azure：LLM evaluation phase](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/rag/rag-llm-evaluation-phase)

实验可以在同一测试集比较直接截断、去重加重排、按证据互补组装等方案，固定模型、输出预算和权限范围。记录预算内召回率、答案正确率、例外遗漏率、单任务输入输出量和端到端 p95 延迟，并把额度单问、例外题与跨版本题分开统计。没有实际测量时，只能说本例的算术覆盖改善，不能宣称准确率提高或延迟下降。

换更大窗口是可比较的选项，但会增加处理内容与可能的成本，也不会自动清除旧政策、越权材料和重复证据。它解决容量，不直接解决证据选择。只有在过滤、完整性与组装已经正确，而有效证据确实太多时，扩容的收益才值得与分阶段回答等方案一起验证。

<details>
<summary>面试怎么回答</summary>

**一分钟回答：** 先算实际可用 token，扣掉系统消息、历史、工具和输出预留，再确认正确答案所需证据是否已经在 20 段里。随后按权限、版本、日期和适用范围过滤，去除同一条款的重复片段，再用重排与互补选择覆盖额度、例外、审批等必要单元。完整保留限定条件和来源，不机械截成前五段。用 Evidence Recall@budget 检查组装是否漏证据，同时看答案正确性、条件遗漏、成本和 p95 延迟。窗口扩容只是候选方案，候选里没有的事实不能靠扩容创造。

**追问一：为什么重排后直接 top-5 还可能不够？** 单段都相关，不代表集合覆盖完整。五段可能都谈额度，例外与审批却没有入选。需要比较新增覆盖和成本，按已经选入的证据调整后续选择。

**追问二：既然能压缩，为什么不把 20 段全部总结一下？** 越权材料不能先送去总结，旧版本也不能混合。摘要可能丢条件，且新增模型调用、延迟和核验成本。可以压缩合法且必要的内容，但要保留支持结论所需的完整条款与来源。

**追问三：Recall@budget 达到满分就能上线吗？** 不能。它只检查必要证据是否进入上下文，不检查模型计算和表达是否正确，也不反映延迟及权限错误。仍要做答案和端到端评估，并明确满分来自怎样的测试分布。

## 练习：空间又少了 300 token

系统指令与历史消息从 3600 增至 3900 token，其他预留不变。D13 经人工核对，可删除 150 token 的无关说明；D9 也能删除 150 token 的重复背景。请计算新的证据预算，说明能否仍保留 E1 至 E5。若不允许删除这些内容，是否应该直接丢掉例外审批段 D12？

<details>
<summary>练习参考思路</summary>

新的证据预算是 8000 减 3900、1000 和 400，得到 2700 token。D13 从 750 变为 600，D9 从 700 变为 550，其他三段仍为 400、500、650，总计 2700。只要删除确实不影响适用性、条件与来源，就能保留五项证据。

如果不能安全删减，直接丢 D12 会让用户失去“谁在何时批准”的关键答案。应重新组装、缩减任务范围或分阶段处理，并明确尚缺的依据；不能交付看似完整但默认例外已经成立的回答。

</details>
