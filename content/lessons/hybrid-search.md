# 混合检索：关键词与向量怎样一起找证据

假设用户问：“CAM-18 连不上会议电脑，画面一直不出来，怎么排查？”资料库里有设备型号、故障代码，也有把同一现象写成“视频采集无信号”的说明。只搜 CAM-18，可能排在前面的是设备规格；只按整句语义搜索，又可能先找到另一型号相机的黑屏指南。前者抓住了准确标识，后者抓住了症状，但各自都可能少看一部分条件。

混合检索（hybrid search）让两种检索各自召回候选，再合成一个排序。关键词检索保留词项匹配的优势，稠密向量检索（dense retrieval）利用文本表示寻找含义相近的内容。它们是否互补，取决于文档、查询和配置；“同时运行两路”并不自动等于答案更可靠。

先修 [向量索引](#/lesson/vector-index) 已解释如何找到相近向量。本篇将它当作一条可用的检索路线，集中讨论两路结果怎样融合。设备、文档、排名和原始分数全部是假设，没有运行真实索引。RRF 部分按照给定排名手算，能够复核；假设排名本身不是性能实验。

## 两条路线看到的问题不同

关键词路线通常先用语言分析器处理查询与文档，再在倒排索引中查找词项。BM25 是常见的相关性排序方法，会考虑查询词在文档中出现的情况，以及该词在整个资料集合中的常见程度。某个词在当前文档较常见、在其他文档较少见，通常更有区分力。它还通过参数控制词频影响与长度归一化，避免仅因文档很长、重复次数很多就获得不成比例的优势。[Azure：BM25 参数](https://learn.microsoft.com/en-us/azure/search/index-ranking-similarity)

因此，型号、代码、专有名称等明确词项往往很有价值，但 BM25 不是原始字符串逐字相等的检查。分析器如何处理连字符、数字、中文词语与同义词，会改变参与匹配的词项。若型号必须精确匹配，应给它设计合适的字段或过滤条件，不能只相信搜索框中的字符串还保持原样。[Azure AI Search：BM25 relevance scoring](https://learn.microsoft.com/en-us/azure/search/index-similarity-and-scoring)

向量路线则把查询编码到与文档一致的表示空间，再按相似性返回候选。它有机会把“画面不出来”和“无视频信号”联系起来，即使文档没有完整复用用户措辞。代价是语义相近不保证设备、版本和适用条件相同。“另一型号也黑屏”的文档，可能比本型号的一段简短技术说明更接近查询的表达。

Azure 的混合检索说明将产品代码、专业术语、日期与人名列为关键词匹配能够发挥作用的场景，同时指出向量检索可以找到没有关键词重合的概念相关内容。在其实现中，全文与向量查询并行运行，然后通过排名融合返回一份结果。[Azure AI Search：Hybrid search overview，2026-09-28 查阅](https://learn.microsoft.com/en-us/azure/search/hybrid-search-overview)

这里的并行是两路分别检索同一份已允许访问的资料范围，不是先用关键词筛掉大部分文档，再只对剩下文档做向量检索。后者也可以设计，但候选范围已经被第一步限制，不能再指望第二路找回第一步排除的材料。混合召回的意义在于让两路分别提供候选，之后再处理它们的交集与差异。

## 用四份文档做一次融合

假设资料库有四份文档，用户仍在排查 CAM-18 无画面问题：

| 文档 | 内容摘要 | 与当前问题的关系 |
| --- | --- | --- |
| A | CAM-18 无视频输入排查：确认采集模式与连接状态 | 型号与症状都匹配 |
| B | CAM-18 产品规格：分辨率、接口与供电参数 | 型号匹配，排查信息较少 |
| C | 会议电脑视频采集无信号指南，涵盖多款相机 | 症状匹配，需要核实具体适用项 |
| D | CAM-21 黑屏处理说明 | 症状相近，型号不同 |

每路先取前三个候选。假设 BM25 的顺序为 B、A、C，向量路线为 C、A、D。两路都找到了 A，却都没有把它放在第一。融合希望利用这种共同支持，同时保留只被一路发现的文档供后续判断。

最直接的想法是把原始分数相加，但两种分数通常不在同一尺度。比如 B 的 BM25 为 12、A 为 10，而 C 的向量相似度为 0.88、A 为 0.82。这里的 12 与 0.88 不代表可相加的同一种“相关性单位”。即使各自更大的分数表示更靠前，范围、分布和查询间的变化仍可能不同。Azure 文档也明确说明 BM25、向量检索与融合的分值具有各自的范围。[Azure：Scores in hybrid search results](https://learn.microsoft.com/en-us/azure/search/hybrid-search-ranking#scores-in-hybrid-search-results)

经过校准后对分数加权是一条可研究的方案，但要验证尺度与权重。倒数排名融合（Reciprocal Rank Fusion，RRF）采用更简单的办法：不用原始分数的大小，只使用文档在各列表中的名次。名次从 1 开始。本文将融合常数写作 $c$，公式为：

$$
\operatorname{RRF}(d)=\sum_{i:d\in L_i}\frac{1}{c+r_i(d)}
$$

其中，$d$ 是某份候选文档，$L_i$ 是第 $i$ 路结果列表，$r_i(d)$ 是文档在该列表里的名次。求和只包括实际返回了这份文档的路线；如果某路没有返回它，这一路贡献为 0。$c$ 是平滑排名差距的常数，本例取 $c=60$。Azure 文档把这个常数写成 $k$，并特别说明它与向量检索返回多少近邻的参数不同。[Azure：How RRF ranking works](https://learn.microsoft.com/en-us/azure/search/hybrid-search-ranking#how-rrf-ranking-works)

为避免混淆，本文将每路候选数量记为 $N$：刚才是 $N=3$，融合常数是 $c=60$，它们控制不同事情。$N$ 决定哪些候选有资格参与融合，$c$ 决定名次转换成贡献时的差距。某个具体服务是否开放这个常数可配置，需要查服务契约，不能因为公式里有它就推断 API 一定有对应开关。

按两组排名，结果如下，保留六位小数：

| 文档 | BM25 名次 | 向量名次 | RRF 计算 | 分数 |
| --- | --- | --- | --- | --- |
| A | 2 | 2 | $1/62+1/62$ | 0.032258 |
| B | 1 | 未返回 | $1/61$ | 0.016393 |
| C | 3 | 1 | $1/63+1/61$ | 0.032266 |
| D | 未返回 | 3 | $1/63$ | 0.015873 |

融合顺序是 C、A、B、D。C 比 A 高得很少，约为 0.000008；不能把这个小差值理解成 C 更可信多少，更不能说分数 0.032266 就是回答正确的概率。如果应用只保留前两名，将交付 C 与 A，之后还要阅读它们是否真正支持本型号的处理步骤。

RRF 确实让两路共同命中的候选排到了前面，但它没有保证 A 这个型号与症状都匹配的文档成为第一。它也没有看懂文档中的适用范围，只是在合并已有排序。后续若需要更细致地比较查询与正文，可以交给 [Reranking](#/lesson/reranking)；不能把这种语义判断归功于 RRF 的公式。

## 平滑、重复与截断会怎样改变结果

$c$ 越大，第一名与第二名的单路贡献越接近；这会减弱相邻名次的差距。以本例为例，第一名贡献为 $1/61$，第二名为 $1/62$，都约为 0.016。若采用较小的常数，列表前部的名次差异会更明显。选择常数或路线权重应依靠代表性查询评估，不存在一种设置能保证每类问题都占优。

融合还需要确定文档身份。A 同时出现在两路时，应该得到两项排名贡献，最终输出一条 A；这就是交集带来的信号。如果把它直接去掉一个来源再计算，会丢失另一条路线的支持。若同一路意外返回重复的 A，则应先按候选身份处理重复，不把传输或索引重复当成额外投票。

不同块可能属于同一文档，也可能包含重叠文本。应先明确融合单位究竟是文档还是 chunk，并使用稳定标识关联。两个独立的相关段落可以都参与检索；但最终组装上下文时，要避免反复塞入相同内容。不同版本则需要保留版本差异，不能因为标题相同就合成一份从未存在的政策或手册。

截断位置也影响融合。如果每路只取一个候选，BM25 只给 B，向量只给 C，A 就完全没有进入集合。无论改变 $c$，还是把 RRF 算得更精确，都无法让 A 出现。把每路候选数与最终展示数分开，才能给融合保留足够选择：召回可以多取一些，最终再按预算选少量，但更大的候选集合也意味着更多计算和后续处理。

## 过滤是范围约束，不能交给排名碰运气

假设这四份文档属于不同租户，或某些已过期。权限和有效版本应由应用与搜索服务明确限制，两路必须遵守同一业务范围。不能只过滤关键词一路，而让向量一路把不可见文档重新加回结果。RRF 分数再高，也不能代替资源授权。

型号过滤需要根据任务判断。把范围硬限制为 CAM-18，能够排除 D，但如果 C 是适用于多个型号的通用指南，也可能被误删。一种数据建模办法是区分“专用型号”和“通用适用范围”，再让业务条件表达真正允许的集合，而不是简单地把所有不含 CAM-18 的文档当成无关。相关性问题可以交给排序，明确的权限条件不能如此处理。

过滤发生在何处，会影响候选是否充足。概念上，若先从整个集合取前三名，再删除不符合条件的两份，可能只剩一份；允许集合中其他有用文档原本排在第四名，便没有机会补进来。Azure 的向量过滤文档区分前置与后置过滤，指出后置过滤在条件严格、候选数较小时可能漏掉本可返回的文档；其具体执行还涉及分片与图遍历。[Azure AI Search：Vector query filters](https://learn.microsoft.com/en-us/azure/search/vector-search-filters)

这不意味着可以为了提高召回率放松权限。应在授权范围内调整过滤模式、候选数与索引配置，并确保任何受限正文都不会进入下游模型或用户响应。若条件过严源于错误的元数据，需要修复数据或规则，而不是让模型猜哪些限制可以忽略。

## 判断融合是否真的带来收益

融合后的候选只来自输入列表的并集。某条必要证据如果没有被解析、没有入索引、切块时丢了例外，或者两路都没召回，RRF 无法创造它。回到本例，A 不在任一路时，最终可能只剩 C 的通用说明；助手应保留适用性不确定，不能因为混合检索已经运行就声称找到了 CAM-18 的专用步骤。

评估时，用同一批问题分别跑关键词、向量和混合路线，固定权限范围及最终上下文预算。既要看必要证据有没有进候选，也要看它是否在最终选入的内容中，还要记录延迟和处理成本。型号查询、口语描述、同义词改写、版本差异等问题应分别观察；总体平均值可能掩盖某一路对精确代码的退步。

并行执行可以缩短等待两路结果的串行时间，但不会消除两路工作量，还增加融合与去重开销。如果其中一路失败，应明确结果来自降级后的单路，不再把它解释成两路共同支持。混合检索的价值是让不同检索方式提供互补候选，是否得到完整证据仍需沿输入、召回、融合和最终回答逐步核实。

**一分钟回答：** 混合检索通常并行执行 BM25 全文检索和 dense 向量检索，再融合结果。关键词适合型号、代码等明确词项，向量能补充不同措辞的语义相关内容。原始分数尺度不同，不能未经校准直接相加；RRF 用每路名次的倒数贡献求和，避开直接比较分值。要区分融合常数与每路候选数，按稳定 ID 合并重复候选，两路使用一致的权限和范围限制。融合只能重排召回并集，两路都漏掉的证据无法恢复，最终还需核对文档支持性。

**追问一：RRF 分数高说明答案更可信吗？** 它说明候选在给定列表中得到了较多或较靠前的排名贡献，不是事实正确率。本例通用指南 C 仍略高于专用指南 A。真实性、版本和适用范围都要另行检查。

**追问二：既然 A 很重要，调大 RRF 的 k 能找回它吗？** 先确认说的是哪个参数。本文用 c 表示融合常数，它只改变已有候选的排名贡献；增加每路召回数量 N 才可能让原来被截断的 A 进入集合，但也不保证能找到。两路没有 A 时，调融合常数无效。

**追问三：把两路前十名直接拼起来行不行？** 能形成候选并集，但会重复文档，而且先拼哪一路就可能偏向哪一路。RRF 给出一种利用双方名次的统一排序。是否值得用它，要与简单合并或经过校准的分数融合做任务级比较。

练习：沿用四份文档，BM25 只返回 B、A，向量只返回 C、A，常数仍为 60，最终需要两份文档。计算 A、B、C 的 RRF 分数；如果 B 与 C 同分，该如何处理？若把每路候选数再缩到 1，会发生什么？

<details>
<summary>练习参考思路</summary>

A 在两路都是第二，分数为 $2/62\approx0.032258$；B 与 C 各占一路第一，均为 $1/61\approx0.016393$。A 排第一，第二个位置在 B、C 之间同分。应用应采用明确且可复现的同分规则，或用另一个经过验证的相关性判断，不能把随机排在前面解释成更可信。

若每路只取一份，则只剩 B 与 C，A 消失，两者仍然同分。改变融合常数无法恢复 A。这个例子把召回不足与融合排序分开：先让需要的证据进入候选，之后才谈怎样排序。

</details>
