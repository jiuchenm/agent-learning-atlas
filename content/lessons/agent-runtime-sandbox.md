# Agent Runtime 与沙箱：让 Agent 运行代码时，谁来守住边界

假设用户给一个数据分析 Agent 上传了 `sales.csv`，请它写段 Python，算出每月销售额并画图。这里的 Agent 是接收任务、让模型提出代码、再由程序调用执行工具的应用。模型生成代码，工具也准备执行了。若平台直接在运行 Agent 服务的机器上调用 Python，代码就可能读到服务进程的环境变量、扫描同机其他任务的文件，或者向外部地址发请求。即使这段代码看上去只是 `pandas.read_csv()`，它导入的包、安装脚本和运行中生成的命令也可能做额外的事。这里的危险不是“模型一定恶意”，而是平台把来源不可信的代码交给了有权限的计算机。

Agent Runtime 是承担任务执行的程序和基础设施：它保存当前任务与工具调用的对应关系，准备运行环境，把允许的输入送进去，取回结果，处理超时、恢复与回收。沙箱（sandbox）则是这条链中执行不可信代码的受限环境。两者不是同义词。Runtime 可以调度多个沙箱；沙箱自己也不知道用户到底批准了什么业务动作。下文的 `sales.csv`、任务编号 A17、运行时间和输出均为教学假设，没有运行真实服务。[E2B 对代码执行沙箱用途的说明](https://e2b.dev/llms.txt)

## 从一次请求看见整条链

用户上传文件后，应用先登记任务 A17 和文件引用，而不是把宿主机上任意路径告诉模型。模型提出“运行这段 Python”的工具调用，Runtime 验证这是当前任务允许的工具，给这次执行分配操作编号 X4，并选择一个干净的环境模板。模板预装 Python 和允许使用的库；A17 只得到自己的工作目录。Runtime 把 `sales.csv` 的受控副本送入该目录，再执行代码。标准输出、错误输出、退出码和生成的图表由工具返回，Runtime 检查文件大小、类型和结果状态后再交给模型解释。

这一步的权限分配应按任务需要来定。分析上传表格时，只给沙箱读这份表格和写临时输出的能力；不需要把整份用户网盘、服务账号令牌或宿主机的 SSH 密钥挂进去。模型说“我需要读取 `/secrets` 才能完成统计”并不能扩大授权。若它要调用正式数据库、发送邮件或提交工单，那是 Runtime 在沙箱外另行验证的工具动作，不能靠沙箱里一条 shell 命令绕过审批。前一篇 [Agent 安全](#/lesson/agent-security) 讲的是指令与授权边界；这里进一步讨论代码执行时的计算边界。

举个可以手算的输入输出。假设文件只有三行数据：一月两笔销售额 40 和 60，二月一笔 30。代码在沙箱里读取这三行，按月份求和，输出 `Jan=100, Feb=30`，生成一张图片。Runtime 返回“进程退出码 0、两行统计、图片文件引用”；模型据此答复用户。一旦沙箱在中途超时，Runtime 应返回“执行未完成”或可核实的进度，不能因为模型预测结果大概是 100 和 30，就假装代码成功运行。若导出图片失败，也要区分“计算正确但制图失败”和“整个任务没有结果”。

Runtime 通常要为这次运行设资源预算：CPU、内存、磁盘空间、进程数量、执行时长，以及可发起多少并发任务。否则一段无限循环、不断创建子进程的脚本，即使碰不到秘密，也可能占满共享机器。预算触发后终止进程，并将原因反馈给上层；“代码执行失败”仍太粗，至少要让使用者分清语法错误、依赖缺失、超时、资源限制和环境准备失败。这是产品应该设计的状态分类，不是某家平台统一采用的字段。

## 沙箱究竟隔离了什么

“放进容器”常常是第一反应。容器的文件系统、进程和网络命名空间可以分开，部署也方便；但普通容器仍与宿主共享 Linux 内核。gVisor 的官方说明明确说，单靠容器并不等于适合执行不可信代码的沙箱。gVisor 提供用户态的 application kernel，让应用的许多 Linux 系统调用先经过这层实现，再访问宿主内核；它的 `runsc` 可接入现有容器工具。它也明确说明自己既不是普通 syscall 过滤器，也不是传统虚拟机。[gVisor 官方 README](https://github.com/google/gvisor/blob/master/README.md)

另一种路径是 microVM，即按任务启动的轻量虚拟机。Firecracker 用 KVM 创建轻量虚拟机，客户代码在 guest（虚拟机内部）运行。Firecracker 的设计文档把 guest 线程视为潜在恶意代码，并在 VM 边界之外再使用 seccomp、namespace、cgroup 和 `jailer` 约束 Firecracker 进程。这些名称在此都属于宿主侧的进一步隔离措施；理解本例先抓住“代码在虚拟机内，但管理虚拟机的进程仍在宿主上”。Firecracker 要求生产部署经 `jailer` 启动；选了 microVM 仍要管理宿主进程、镜像和资源。[Firecracker Design：Host Integration、Threat Containment 与 Sandboxing](https://github.com/firecracker-microvm/firecracker/blob/main/docs/design.md)

两者不是“安全”和“不安全”的简单排名。要看代码对系统调用与内核功能的兼容要求、启动和运行成本、要隔离的租户是谁、故障后如何追踪，以及团队是否有能力维护宿主。gVisor 可能遇到某些 Linux 行为的兼容问题；microVM 需要准备 guest 内核、磁盘和网络。E2B 是更高一层的托管沙箱产品，文档展示了创建、连接、暂停、恢复、销毁等接口；产品 API 与底层隔离机制也不能混成一个概念。[E2B Sandbox lifecycle](https://docs.e2b.dev/sandbox.md)

文件边界容易在“方便调试”时被打穿。假设开发者把整个项目目录挂给 A17，目录里恰好有另一个用户的上传文件和 `.env`。沙箱里的进程即使不能逃出 guest，也已经能读到这两个文件。隔离技术无法替平台决定哪些文件本来就不该送进去。更稳妥的做法是给每个任务单独工作区，只复制任务所需输入，把输出复制回受控存储，并对副本和临时数据设保留期限。恢复用的快照也含数据，不能当成无害缓存。

网络也是独立的一道门。Firecracker 提供 guest 网卡及宿主 TAP 设备，却明确**不负责过滤** guest 的网络流量；要限制网络出口，宿主侧必须另行做控制。[Firecracker Design：Threat Containment](https://github.com/firecracker-microvm/firecracker/blob/main/docs/design.md) 如果本例只分析本地 CSV，可以默认拒绝外连。若确实要安装包或访问指定数据源，再经过受控代理放行目标、方法和时段，并记录执行所用版本。只写一句“沙箱不能访问互联网”不足以证明任何真实部署已做到这一点；应检查实际网络路径和 DNS、代理配置。

## 暂停、快照和恢复是三种不同的需求

用户关掉网页，不代表分析进程应立刻消失。Runtime 可以继续任务，也可以暂停环境，等待用户回来。但暂停与销毁不能混淆。以 E2B 文档当前描述为例，运行中的沙箱可暂停并保留文件和内存，连接时恢复；`kill` 是终态，释放资源且不能恢复。文档也说暂停的沙箱不会自动删除，因此平台若采用类似能力，还得自己规定保留期限与清理责任。[E2B Sandbox persistence](https://docs.e2b.dev/sandbox/persistence.md)

快照（snapshot）是某一时刻环境的副本，适合从同一准备状态创建多个沙箱。E2B 把“暂停后恢复原沙箱”与“从快照生成新沙箱”分开，后者可以一对多；它还提醒创建快照会短暂停止环境，活动连接可能断开。[E2B Sandbox snapshots](https://docs.e2b.dev/sandbox/snapshots.md) 对 A17 来说，若每次任务都要安装相同依赖，可以先做可复用的干净模板；若执行到一半要从某个状态继续，才考虑暂停或运行时快照。把每次临时分析都做成永久快照，存储和清理成本会不断增加。

恢复并非“时间倒流”。Firecracker 的快照文档说明，快照保存 guest 内存、模拟硬件状态，磁盘文件由使用者管理；跨进程恢复时网络连接未必保留，快照文件也需要自行保护。[Firecracker Snapshotting：Overview 与 Snapshot files management](https://github.com/firecracker-microvm/firecracker/blob/main/docs/snapshotting/snapshot-support.md) 假如 A17 的代码在快照前已向外部服务写入一条记录，恢复旧环境不会自动删除那条记录。Runtime 必须把外部动作编号和结果放在沙箱外的任务状态里，恢复后先核实，再决定要不要重试；这个故障边界与 [任务状态](#/lesson/agent-state) 和 [工具失败](#/lesson/tool-reliability) 相连。

快照还可能复制本应唯一的东西。Firecracker 文档提示，从同一快照恢复多个 VM，用户态缓存的标识或令牌可能被重复使用。操作时要避免把长期密钥烘焙进镜像或快照；恢复后也要按业务要求刷新临时凭据和唯一标识。这里没有用快照模拟真实攻击，只说明副本机制自然带来的风险。[Firecracker Snapshotting：Snapshot security and uniqueness](https://github.com/firecracker-microvm/firecracker/blob/main/docs/snapshotting/snapshot-support.md)

最后是回收。A17 已把统计和图表交付用户，Runtime 应结束进程，取出需要保存的结果，销毁临时环境，并清理文件副本和短期凭据。若创建环境成功、但调用方在拿到沙箱 ID 之前崩溃，平台还要能按任务标识或租户列出“无人认领”的环境并清理。超时终止、主动销毁、暂停待续的环境要能区分，否则账单和数据保留都难以解释。E2B 文档提供手动 `kill` 和运行超时控制；上述孤儿环境清理是从一般运行时管理需求推导的设计要求，不是 E2B 文档承诺替每个应用完成的流程。[E2B Sandbox lifecycle](https://docs.e2b.dev/sandbox.md)

## 与 DSec 的位置关系

读过 [DSec](#/lesson/dsec) 容易发现它也讲沙箱、状态和恢复。区别在任务：本篇的 A17 是面向用户的应用请求，核心是租户隔离、授权、结果交付和资源回收；DSec 论文讨论大规模 Agent 训练与评估中的 rollout 执行，关心多条轨迹的环境复用、吞吐、抢占和样本完整性。底层技术可以相似，但“训练平台有 stateful sandbox”不能直接推成线上应用已有用户授权、网络出口控制或数据保留策略。后者仍需应用自己设计。[DSec v1 原文](https://arxiv.org/html/2609.22978v1)

<details>
<summary>面试怎么回答</summary>

**一分钟回答：** Agent Runtime 接住模型提出的代码执行请求，核对任务权限，分配独立环境，把必要文件送进去，限制 CPU、内存、时长、磁盘和网络，再收集输出与错误，最后暂停或回收。沙箱负责降低代码触及宿主和其他任务的风险；它不能替代 Runtime 对业务工具、上传文件和外部写入的授权。底层可选 gVisor 一类用户态系统调用隔离，或 Firecracker 一类 microVM，还要处理各自兼容性和运维成本。暂停与快照能继续工作，但不能撤销已经发生的外部动作；网络出口和快照数据也要单独治理。

**追问一：用了 Firecracker，网络是不是天然安全？** 不是。Firecracker 官方文档明确说它不做网络流量过滤，guest 出口必须由宿主侧控制。microVM 还要按任务限制文件、凭据和可访问的服务；隔离边界不决定业务授权。

**追问二：普通 Docker 容器够不够？** 要看威胁模型。容器适合打包和隔开许多资源，但共享宿主内核。运行用户或模型产生的不可信代码时，需要评估额外隔离层、权限和网络策略。gVisor 与 microVM 是不同选择，不能只按名字判断安全；要实测目标程序兼容性、性能和运维路径。

**追问三：为什么有 checkpoint 还可能重复调用外部 API？** 沙箱快照保存本地环境，外部 API 的结果在另一个系统。若写入已生效、Runtime 却在记录结果前崩溃，恢复快照看见的仍可能是“结果未知”。应该用操作标识查询或依据远端幂等契约处理，不能直接重放。

<details>
<summary>练习参考思路</summary>

给 A17 独立目录，只复制 CSV 和执行所需代码；不要挂整份用户网盘或宿主密钥。优先用已固定依赖的模板。如果确需安装，经过受控包源或代理，并限制出口、记录包版本和安装结果。超时后保留任务号、工具调用号、环境 ID、状态、原因和必要的输出引用，标明计算是否完成；不要让模型猜结果。若要续接同一个尚未完成的进程，暂停后恢复原环境更合适；若想让多个新任务从相同准备状态开始，用干净模板或经过审查的快照。无论哪种方式，恢复前都要核实沙箱外动作的结果，并决定旧环境何时销毁。
