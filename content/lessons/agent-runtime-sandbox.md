# Agent Runtime 与沙箱：运行代码时谁守住边界

**Agent Runtime（Agent 运行时）**是组织任务执行的程序和基础设施：它接住模型提出的工具调用，核对权限，准备环境，跟踪执行状态，收集结果，并处理恢复与回收。**沙箱（sandbox）**是其中运行不可信代码的受限环境。一个 Runtime 可以管理多个沙箱；沙箱限制代码能接触哪些计算资源，用户批准了哪些业务动作仍由应用判断。本篇关注代码执行这条链，名称中有 Runtime 的框架或产品，职责范围还需看各自文档。

假设用户上传 `sales.csv`，让数据分析 Agent 用 Python 计算每月销售额并画图。模型生成了代码，应用接下来要在哪里运行它？若直接在 Agent 服务所在机器启动 Python，代码可能读取服务的环境变量、其他任务的文件，或向外部地址发送数据。导入的包和安装脚本也可能执行额外操作。代码来自模型或用户，并不因此获得服务账号的权限。我们沿任务 A17 看环境怎样创建、怎样限制、交付什么，以及中断后如何收尾。任务、数据和结果均为教学假设，没有运行真实服务。

## 先给 A17 一个能执行代码的环境

Python 程序运行后成为**进程（process）**，有自己的内存和运行状态。读文件、创建子进程、发网络请求，通常需要通过系统调用向**操作系统内核（kernel）**请求服务；内核管理进程、内存、设备等资源。因此，隔离代码既要考虑给进程什么文件和身份，也要考虑它能通过内核触及哪里。Agent Runtime 管理的是任务执行，Python 自身的语言运行时则负责执行 Python 程序，二者层级不同。

A17 的假设输入如下，金额单位在本例中固定且相同：

```csv
month,amount
Jan,60
Jan,40
Feb,30
```

应用先登记 A17 与文件引用。模型提出代码执行工具调用后，Runtime 验证该工具和文件属于当前授权，再给本次执行分配编号 X4，选择预装 Python 与允许依赖的干净模板，创建独立环境。模板是准备好的起点；它不应含别的任务数据。A17 只得到自己的工作目录和这份 CSV 的受控副本，分析结果写到临时输出目录。Runtime 在沙箱外保存 A17、X4 与环境 ID 的对应关系，进程停止后仍能查到这次执行。[E2B 官方生命周期文档](https://docs.e2b.dev/sandbox.md)提供创建、连接、超时与销毁接口；上述编号与任务记录是本例设计，不能视作所有产品的统一实现。

这一步决定了代码能拿到什么。读取 CSV 不需要整份用户网盘、宿主 SSH 密钥或服务账号令牌。模型后来要求“读取 `/secrets` 才能完成统计”，不能改变已授予的权限。若任务还要发送邮件或上传企业报表库，应由 Runtime 对相应业务工具另行核验授权；沙箱里的 shell 命令不应成为绕过批准的路径。[Agent 安全](#/lesson/agent-security)讨论指令和权限，这里把同一边界落实到运行环境。

## 让代码碰不到哪些东西

隔离先从一条具体问题开始：A17 的 Python 进程尝试读取邻居任务的文件，系统在哪一层挡住它？普通容器可以隔开文件系统、进程和网络的视图，方便部署；但通常仍共享宿主 Linux 内核。面对不可信代码，单靠“已经放进容器”不能证明攻击面足够小，还要看权限、挂载、内核与额外隔离措施。[gVisor 官方 README](https://github.com/google/gvisor/blob/master/README.md)明确讨论了共享内核带来的风险。

gVisor 提供运行在用户态的 **application kernel（应用内核）**，实现 Linux 类接口。应用的系统调用由这层实现处理，减少直接暴露给应用的宿主内核接口；gVisor 自身仍要使用宿主能力。它的 `runsc` 可以接入 Docker、Kubernetes 等容器工具。它既不是简单的系统调用过滤器，也不是带完整 guest 操作系统的传统虚拟机。选择它时，还要核验目标程序所需接口是否兼容、具体负载的开销以及部署条件，不能由产品名称推断效果。[gVisor 官方定义与边界](https://github.com/google/gvisor/blob/master/README.md)

Firecracker 采用另一条路径：用 Linux 的 KVM 虚拟化能力运行 **microVM（轻量虚拟机）**，代码在 guest（虚拟机内部）通过 guest 内核运行；管理 VM 的 Firecracker 进程则在 host（宿主机）上。其设计文档把 guest 代码视为潜在恶意输入，同时要求宿主上的 Firecracker 进程继续受约束：seccomp 限制可用系统调用，namespace 隔开资源视图，cgroup 控制资源，`jailer` 准备受限环境并降低权限。生产部署文档要求经 `jailer` 启动。VM 边界、宿主进程加固与实际配置共同构成防护，还要承担镜像、启动、兼容性和运维成本。[Firecracker Design](https://github.com/firecracker-microvm/firecracker/blob/main/docs/design.md)

这些技术都不能替用户判断某次访问是否获准。若平台主动把服务令牌交给 A17，代码可能用合法 API 越权，而不必突破内核隔离。网络也需要独立控制：**Firecracker 本身不做网络流量过滤**，文档要求在宿主侧过滤 guest 出口。A17 只分析本地 CSV 时，可以设计为默认拒绝外连；确需安装包时，再经受控包源或代理放行并记录依赖版本。平台是否真的实施了这些策略，需要配置和测试证据。[Firecracker 网络边界](https://github.com/firecracker-microvm/firecracker/blob/main/docs/design.md)这些更细的技术选择与身份、网络设计，安排在[五篇系列大纲](#/lesson/runtime-sandbox-series)的第二、三篇；目前是规划，尚未写成五篇完整课程。

## 限制预算，再确认交付结果

即使 A17 无法读取秘密，一段无限循环或不断创建子进程的代码也可能占满机器。Runtime 因此需要限制 CPU、内存、磁盘、进程数量、执行时长和并发任务数。资源额度限制一次执行，队列和并发预算限制共享平台同时接纳多少工作。触发限制后要终止相应执行并记录原因；具体额度取决于负载，本例没有测量数据，也不设厂商通用数值。

成功路径中，Python 读取三行数据，按月份求和，得到手算结果 `Jan=100, Feb=30`，合计 130，并生成图表。执行工具把标准输出、错误输出、退出码与产物引用交给 Runtime。Runtime 检查产物的类型、大小、归属及结果状态，再把可交付内容传给模型解释。本例理想返回可表示为：

```text
任务 A17 / 执行 X4：完成
进程退出码：0
统计：Jan=100，Feb=30
产物：已核验的图表文件引用
```

这份输出是教学示意。退出码 0 说明进程报告成功，业务结果仍需校验；例如脚本选错列也可能正常退出。若分组已算完而制图失败，应保留可核实统计并说明缺少图表。若中途超时，Runtime 返回执行未完成或明确的部分结果，模型不能凭预测补成“已运行成功”。语法错误、依赖缺失、环境准备失败、超时和资源超限应有可区分的原因。这些是应用的状态设计要求，具体字段由产品定义。[工具可靠性](#/lesson/tool-reliability)继续解释怎样把失败反馈给任务控制逻辑。

## 用户回来时，恢复的究竟是什么

用户关闭网页时，Runtime 可以继续执行、暂停待续，或保存已完成产物后销毁环境，取舍在于之后是否还需要原进程。暂停保留环境以便继续；销毁释放环境，不能当作暂停。以核验于 **2026-10-01** 的 E2B 文档为例，暂停默认保留文件和内存，恢复时可以续接原状态；选择 `keepMemory: false` 只保留文件系统，恢复会冷启动。当前文档说暂停环境没有自动删除期限，只有明确 `kill` 才删除，所以应用仍需规定保留与清理责任。此处描述文档契约，未验证具体账号、区域或 SDK 行为；“暂停”也不意味着所有存储和管理成本消失。[E2B Persistence](https://docs.e2b.dev/sandbox/persistence.md)

**快照（snapshot）**是环境某一时刻状态的副本。E2B 区分暂停后恢复原沙箱与从快照创建多个新沙箱；其文档要求快照模板的 envd 版本至少为 `v0.5.0`，创建快照时短暂暂停并恢复，活动连接会断开。A17 每次都需要相同依赖时，可以优先使用不含任务数据的干净模板；要保存已执行到一半的环境，才考虑暂停或运行态快照。二者的保留内容、连接影响和生命周期不能凭名称互相推定。[E2B Snapshots](https://docs.e2b.dev/sandbox/snapshots.md)

Firecracker 的快照包含 guest 内存和 VM 状态，磁盘文件由使用者管理；跨进程恢复时网络连接不保证保留，快照文件也需由使用者保护。复制同一快照还会复制用户态缓存的标识、随机数或令牌，因此不要把长期密钥烘焙进模板，恢复后的临时凭据和唯一状态需要按用途刷新或去重。[Firecracker Snapshotting](https://github.com/firecracker-microvm/firecracker/blob/main/docs/snapshotting/snapshot-support.md)

更关键的是，**环境恢复不会撤销外部业务副作用**。假设 A17 后来取得了上传企业报表库的批准，上传已经生效，却在 Runtime 记录成功前断开连接。恢复上传前的 VM 快照，远端报表仍然存在，本地看到的可能还是“上传结果未知”。任务状态 checkpoint（执行检查点）保存任务走到哪一步；沙箱快照保存本地环境；远端系统保存已经发生的业务动作。Runtime 必须在沙箱外记录操作标识，恢复后先查询远端结果，或按远端幂等契约重试。幂等意味着重复同一操作不会额外产生一次业务效果；没有对应契约时，不能盲目重放。这里的恢复流程是应用设计推导，详见[任务状态](#/lesson/agent-state)和[系列第四篇的恢复大纲](#/lesson/runtime-sandbox-series)。

## 交付之后，环境怎样结束

A17 的统计和图表确认交付后，Runtime 应结束进程，保存需要留存的产物与任务记录，销毁临时环境，并清理文件副本和短期凭据。销毁环境与保留最终报告是两个动作；报告的访问权限和保存期限仍须明确。如果创建成功后调用方崩溃，未能记下环境 ID，还需要依据任务标识等信息核对无人认领的环境。超时终止、主动销毁和暂停待续应能区分，才能解释资源占用与数据保留。E2B 提供超时和 `kill` 等接口，孤儿环境核对则是应用需要设计的管理流程。[E2B Lifecycle](https://docs.e2b.dev/sandbox.md)

至此，A17 从受控输入到经过校验的结果，再到可解释的暂停或销毁，才算走完一次代码执行。本篇建立这条入口主线；公平调度、预热与成本比较放在[系列第五篇大纲](#/lesson/runtime-sandbox-series)。若已读 [DSec](#/lesson/dsec)，要保留任务差别：固定的 [DSec v1](https://arxiv.org/html/2609.22978v1)讨论 Agent 训练、评估中的 rollout 执行基础设施，相关沙箱技术不能直接证明线上应用已经具备用户授权、出口策略或数据保留规则。本轮沿用原课对 v1 的定位，没有重新核验其实验结果。

本文官方项目链接指向可变分支，在线产品文档也会更新，关键片段核验日为 2026-10-01；未锁定 Firecracker、gVisor 发布版本或 E2B SDK 版本，未部署产品、运行安全测试或性能基准。隔离能力来自相应官方资料，A17 的授权、状态和回收规则是教学设计。

<summary>面试怎么回答</summary>

**约一分钟回答：** Agent Runtime 管理任务执行，沙箱是其中运行不可信代码的受限环境。以分析上传 CSV 为例，Runtime 核对权限，分配环境，只送入必要文件，限制资源和网络，收集退出码与产物，校验后交付，再暂停或回收。进程通常通过内核请求文件、网络等能力，容器、gVisor、microVM 对这条路径设置不同隔离边界，选择时要考虑威胁模型、兼容性和运维成本。计算隔离不能决定业务授权；暂停与快照能保存本地环境，也不能撤销已发生的上传等外部动作，恢复前仍要核对操作结果。

**追问一：用了 Firecracker，网络是不是天然安全？** Firecracker 不过滤 guest 网络流量，出口过滤需要宿主侧实施。A17 是否可以访问报表库、拿到什么令牌，还由任务授权和应用策略决定。VM 隔离不能替代这些控制。

**追问二：普通 Docker 容器够不够？** 先看运行什么代码、攻击者能控制什么以及要保护什么。普通容器共享宿主内核，运行不可信代码时应评估额外隔离、权限与网络策略。gVisor 和 microVM 的机制不同，要用目标程序验证兼容性、性能和恢复路径，不能只按名字判断安全。

**追问三：为什么已有 checkpoint 和 VM snapshot，上传仍可能重复？** 远端已接受上传与本地记录成功之间可能崩溃。恢复本地状态不会删除远端记录。保留操作标识，查询远端结果或使用其幂等契约才能处理；缺少契约时应保留结果未知并核对。

<details>
<summary>练习参考思路</summary>

只送入 CSV 和必要代码，不挂用户网盘或宿主密钥。优先使用固定依赖模板；确需安装时，按获准策略走受控包源或代理，记录版本和安装结果。超时保留任务号、执行号、环境 ID、终止原因、可核实进度与产物引用，区分统计完成和制图完成。两小时后是否能续接原进程取决于保留内容：保存内存的暂停可以续状态，只存文件则要冷启动并从检查点重算，销毁后只能新建环境。恢复也需核对当前权限与临时凭据。上传结果未知时先按操作标识核查远端，或遵守远端幂等契约；不能用恢复旧快照代替这一步。最后规定旧环境何时清理。

</details>
