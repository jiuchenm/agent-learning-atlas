# Function Calling：模型如何请求调用函数

假设你在开发一个订单助手。用户问：“我的订单到哪了？”模型能理解这句话，却看不到订单数据库。如果它直接回答“正在派送”，说得再自然也没有查询依据。把所有订单塞进提示词同样不合适：数据会变化，而且当前用户只能查看自己的订单。应用需要把一个范围明确的查询能力交给模型，再把查到的事实带回对话。

函数调用（Function Calling）解决的就是这个接口问题：模型根据对话提出“使用哪个函数、传入什么参数”的结构化请求，应用接收请求，决定是否执行，并返回结果。它在网络上先是一条模型响应，不是模型进程直接跳进你的代码。这里讨论应用自己实现的函数工具。模型生成调用请求、应用执行函数、后端判断访问权限，是三个需要分别实现的环节。OpenAI 官方文档也把工具调用描述为多步交互，应用执行代码之后，还要把工具输出交还模型。[官方流程说明](https://developers.openai.com/api/docs/guides/function-calling#the-tool-calling-flow)

读过 [Agent 与 Workflow](#/lesson/agent-basics) 后，可以把这里放回观察与行动的循环：工具定义告诉模型有哪些行动可选，调用请求表达它选择了什么，工具结果带回新的观察。本篇只跟踪一次订单查询，所有订单、账号和结果均为教学假设，没有连接真实服务。API 字段按 2026-09-28 查阅的 OpenAI Responses API 文档编写。

## 先把函数定义清楚

程序员平常调用函数，已经知道函数名和参数。模型面对的却是自然语言：“到哪了”可能要求物流信息，“买了什么”可能要求订单摘要。应用需要提供工具定义（tool definition），让模型知道每个函数解决什么问题、什么时候可以使用，以及如何组织参数。下面是本例随模型请求发送的工具定义：


```json
{
  "type": "function",
  "name": "query_order",
  "description": "查询当前登录用户的一笔订单。物流进度使用 tracking，商品与金额摘要使用 summary。必须取得用户明确提供的订单号；缺少订单号时先询问。",
  "parameters": {
    "type": "object",
    "properties": {
      "order_id": {
        "type": "string",
        "description": "订单号，例如 O-1042；不得猜测。"
      },
      "view": {
        "type": "string",
        "enum": [
          "summary",
          "tracking"
        ],
        "description": "返回订单摘要或物流进度。"
      }
    },
    "required": [
      "order_id",
      "view"
    ],
    "additionalProperties": false
  },
  "strict": true
}
```

`name` 是应用分派请求时使用的标识。`description` 给模型提供语义：两个函数都叫“查询”，模型也需要知道它们各自查询什么。描述写清楚能减少歧义，但“不得猜测”只是行为指令，不能替代后面的程序检查。`parameters` 使用 JSON Schema，即描述 JSON 数据应有结构的一套规则；它描述的是函数输入，不是数据库，也没有实现查询。

在这份 Schema 里，`properties` 声明允许出现的字段以及字段类型；`required` 要求两个字段都存在；`enum` 把视图限定为两个值；`additionalProperties: false` 拒绝未声明字段。单独写 `properties` 并不意味着字段必填。JSON Schema 默认允许省略属性，也默认允许额外属性，所以这些约束需要明确表达。[JSON Schema 对象规则](https://json-schema.org/understanding-json-schema/reference/object)

要区分“字段存在”和“字段有业务意义”。`order_id` 是空字符串时，它仍属于字符串；即使形状正确，也无法定位订单。若允许空值，还要区分省略字段与显式传入 `null`。在这里两个参数都有实际用途，所以不接受空值。

`strict: true` 是本例所用 API 的严格模式配置，用来约束生成的调用参数符合受支持的 Schema。按本次查阅的文档，每层对象都要设 `additionalProperties: false`，`properties` 中的字段都必须列入 `required`；需要表达可选值时，可以把 `null` 加入允许的类型。它支持 JSON Schema 的一个子集，迁移 API 时应重新核对支持范围。[严格模式要求](https://developers.openai.com/api/docs/guides/function-calling#strict-mode)

严格模式能限制参数的形状，却无法从“字符串”这个类型判断订单号是否来自用户，也不能证明订单确实存在。把错误的 `O-9999` 填进去，仍可能满足这份 Schema。结构约束减少了一类故障，业务事实仍要向应用和数据源核实。

## 缺少参数时，先补齐信息

回到“我的订单到哪了”。当前对话没有订单号，本例也没有提供“列出我的订单”的工具。合理的下一步是普通文字澄清：“请提供订单号，例如 O-1042。”此时没有发生订单查询。`required` 的作用是定义合法输入，不会自动替用户补出事实；如果应用强迫模型每轮都必须调用查询工具，反而会制造填入无依据参数的压力。

假设用户随后回答：“O-1042，查看物流。”模型已经取得订单号，并能将“物流”映射到 `tracking`，于是返回下面这个调用条目。它是模型输出中的一种结构化条目，页面不应该把它当成已经查询成功的回答：

```json
{
  "type": "function_call",
  "call_id": "call_order_01",
  "name": "query_order",
  "arguments": "{\"order_id\":\"O-1042\",\"view\":\"tracking\"}"
}
```

注意 `arguments` 在这份 API 消息里是一个经过 JSON 编码的字符串。双引号前的反斜杠是外层 JSON 表示字符串时的转义：应用先解析外层响应，再解析 `arguments`，才能得到包含两个字段的对象。这一步就是序列化与反序列化边界；解析成功才谈得上按字段分派执行。`call_id` 标识这一次调用，后续结果通过它与请求对应；它既不是订单号，也不是查询权限凭证。一次模型响应可以没有调用，也可以有一个或多个调用，应用不能把“输出数组的第一项”固定当成函数请求。[调用条目与结果格式](https://developers.openai.com/api/docs/guides/function-calling#handling-function-calls)

信息来源同样需要设计。若用户已经在订单页面选中了某笔订单，应用知道准确订单号，可以在服务器端绑定它，向模型暴露不带 `order_id` 的工具。本例是在开放对话中查询，所以保留该参数。让模型重复生成应用已经可靠掌握的标识，会多增加一个出错位置。

## 应用怎样接住调用

收到合法 JSON 后立即执行，是最容易漏掉检查的地方。应用至少要回答几个不同的问题：这个工具名是否在允许列表里？参数是否符合 Schema？订单号格式是否符合业务约定？当前登录用户是否可以访问目标订单？这些问题不能相互替代。

下面是说明责任位置的 Python 伪代码，辅助函数由应用实现，并非可直接运行的 SDK 示例。它只处理前面已经完整收到的一个调用；真实响应仍要逐个识别调用条目。示例假定订单号规则为“O- 加四位数字”，并由订单服务执行账号范围过滤。

```python
def handle_call(call, session):
    if call.name != "query_order":
        return {"ok": False, "code": "UNKNOWN_TOOL"}

    args = parse_json_or_error(call.arguments)
    validate_schema_or_error(args, QUERY_ORDER_SCHEMA)
    validate_order_id_or_error(args["order_id"])

    # 用户身份来自已验证的登录会话，不从模型参数读取。
    result = order_service.query_visible_order(
        actor=session.user_id,
        order_id=args["order_id"],
        view=args["view"]
    )
    return result
```

解析或校验失败时，外层处理器应把已知错误转换成明确的失败结果，查询函数不继续执行。例如收到 `view: "timeline"`，不能任意猜成 `tracking`；缺少订单号时，也不能从历史里挑一个看起来像的编号。严格模式适配正确时应减少这类结构错误，但应用仍要处理手工测试、接口迁移或其他入口传入的不合法数据。

权限判断发生在持有真实身份和业务规则的应用或后端。假设 `O-1042` 属于当前用户，服务才返回对应物流；假设它属于另一个账号，格式再正确也不能返回内容。工具定义里因此没有 `user_id` 或 `is_admin` 参数。即使未来加了某种账号选择能力，也必须由后端验证当前身份是否有权代表目标账号。OWASP 要求每次请求都检查权限，并区分身份认证与授权；把入口换成模型调用，不会取消这些要求。[授权检查原则](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html#validate-the-permissions-on-every-request)

还要分清“用户想做什么”和“用户有权做什么”。一句“帮我查订单”表达了任务意图，但系统仍需确认访问范围。若未来新增修改收货地址的工具，还要根据产品规则判断是否需要用户确认具体变更。模型选中了某个工具，不代表后端已经授予操作权限；工具出现在列表中，也不等于其中所有资源都可以访问。

## 把查到的事实送回模型

假设服务查询成功，返回订单处于运输中，最近事件是“到达分拨中心”，预计送达日期暂时未知。应用把这些结果序列化，使用原来的 `call_id` 构造工具结果（tool result）：

```json
{
  "type": "function_call_output",
  "call_id": "call_order_01",
  "output": "{\"ok\":true,\"order_id\":\"O-1042\",\"status\":\"in_transit\",\"latest_event\":\"到达分拨中心\",\"estimated_delivery\":null}"
}
```

应用随后发起下一次模型请求，保留此前对话与模型输出，并附上这份结果及需要继续使用的工具定义。不能只发送一句“到达分拨中心”，把对应的调用关系丢掉。使用 Responses API 手动管理上下文时，还需按 API 要求保留模型返回的其他必要输出条目，例如推理模型返回的 reasoning items；不应自行拼出或猜测这些条目的内容。[完整示例与上下文要求](https://developers.openai.com/api/docs/guides/function-calling)

模型现在可以回答：“订单 O-1042 正在运输中，最近的物流记录是到达分拨中心，暂时没有预计送达日期。”这就走完输入、选择函数、程序执行、结果回传和自然语言回答。回答中的事实来自假设工具结果。`estimated_delivery: null` 没有支持“今天会送到”，模型不应为了让回答完整而补出日期。工具失败也要回传有区别的状态，例如无权访问、参数无效或服务暂不可用；把失败包装成空订单，会让模型把“没查成”解释成“没有订单”。对外错误信息是否合并，则由应用的隐私与产品规则决定。

这次往返的代价也很具体：模型需要读工具描述，应用需要维护参数与返回值契约，查询完成后通常还要增加一次模型请求。函数过多、描述重叠、返回结果冗长，都会增加选择与读取负担。最初只提供与当前任务有关的少量能力，更容易观察模型到底选错了工具、填错了参数，还是正确查询后误读了结果。若页面只需固定展示物流字段，应用也可以直接渲染经过检查的工具数据；是否再调用模型组织语言，是产品选择。

查询之外还涉及怎样保存任务进度，可继续读 [任务状态](#/lesson/agent-state)。超时与重复执行则放在 [工具失败](#/lesson/tool-reliability) 中讨论。

<details>
<summary>面试怎么回答</summary>

**一分钟回答：** Function Calling 让模型把使用外部能力的意图输出成函数名和参数。应用先提供工具描述与 JSON Schema，模型根据对话选择工具；缺少必要信息时先澄清。收到调用后，应用解析参数，检查结构、业务条件和访问权限，再由真正的函数执行查询或动作。结果通过调用 ID 回传，模型据此继续回答。严格模式约束参数结构，但订单号是否真实、用户是否有权限、后端是否执行成功，都需要应用确认。

**追问一：有了 JSON Schema，为什么还需要校验？** Schema 只能验证已经写进契约的条件。一个订单号可能类型正确、格式正确，却指向其他账号的订单。严格模式也没有证明参数来自用户。应用要保留执行前检查，后端要验证真实身份与资源权限。

**追问二：Function Calling 与让模型输出 JSON 有什么区别？** JSON 是数据格式，单独输出它不会产生调用。Function Calling 还约定了可用工具、调用条目、参数与结果的对应关系，以及应用的执行入口。应用当然可以自行设计 JSON 协议，但这些分派、校验与回传责任仍要实现。

**追问三：缺少订单号时，把它设为 required 就够了吗？** 不够。它只表示合法调用必须携带字段，不会生成可靠的订单号。还需要澄清策略和允许模型先回答问题的流程；若应用已绑定订单，则可以从模型参数中移除该字段。

</details>

<details>
<summary>练习参考思路</summary>

第一次含有 Schema 未声明的 `user_id`，应在参数校验处拒绝，不能把它当作查询身份。第二次参数可以通过结构与格式检查，但后端必须根据已验证会话实施资源授权，不返回别人的订单。内部记录应区分参数非法与访问被拒绝；对外是否统一为“无法查询此订单”取决于信息披露规则。直接断言“没有订单”会丢失失败原因，也可能误导用户。两次都不能靠模型改写一句话代替应用检查。
