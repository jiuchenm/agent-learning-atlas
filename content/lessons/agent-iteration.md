# 团队迭代：新模型上线前要比较什么

假设一个订单助手换用新模型后，答案更简洁，测试耗时和费用都下降了。演示里看起来进步明显，但查看完整执行轨迹——用户输入、模型提出的动作、工具实际返回和最终回答——却发现另一件事：它开始直接根据聊天历史回答实时订单状态，跳过本来必须执行的查询。速度提升的一部分，来自少做了必要工作。

团队迭代要回答的是“这个完整版本能否更好地完成业务”，而不是“新模型看起来是否更聪明”。因此要把漏调工具这个问题转成可分派、可测量的改进动作。本课沿一次假设升级说明怎样分工、比较、发布和回退；成功口径承接 [Agent 评估](#/lesson/agent-metrics)，验收约定承接 [Agent PRD](#/lesson/agent-prd)。所有任务数、模型代号、结果和预算都是教学设定，没有执行真实部署。

## 谁负责把“不够好”变成可验证的修改

产品与业务负责人定义任务边界：实时订单状态必须查询，资料不足时如何回答，哪些动作必须由人确认。模型与提示负责人分析意图、工具选择和生成错误。后端负责人实现工具契约、状态保存、幂等（重复请求不会创建第二个相同业务结果）、日志与发布开关。数据负责人维护资料版本、权限和评估样本，评估与运营人员复核坏例、观察用户返工。这些是职责，不要求每家公司设置同样的团队名称。

一个问题常常跨越这些边界。模型漏调工具时，产品要确认这是不是必要步骤，后端要证明调用确实没有发生，模型负责人再检查提示与工具描述。不能只把“准确率低”交给一个人换模型，也不能让业务人员直接在表格中把失败样本删掉。

Anthropic 的评估指南区分任务、尝试、执行轨迹和环境终态，强调评估的是模型与运行框架共同组成的系统。声称“订单已取消”的文字和后端真的存在取消结果，是不同证据。[Anthropic：Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

## 固定版本组合，才能知道谁导致变化

每次可比较的运行都应记录一个完整版本组合。除了模型，还包括 Prompt、工具 Schema（调用工具时允许的参数结构）、资料与索引、运行代码和持久状态格式。否则“只换模型”的实验，可能同时读到了刚更新的政策或不同权限的数据。

假设旧版本 A 与候选 B 的记录如下：

```json
{
  "baseline": {
    "release": "A",
    "model": "M1-fixed",
    "prompt": "P1",
    "tool_schema": "T4",
    "index_snapshot": "I9",
    "runtime": "R6",
    "state_schema": "S2"
  },
  "candidate": {
    "release": "B",
    "model": "M2-fixed",
    "prompt": "P1",
    "tool_schema": "T4",
    "index_snapshot": "I9",
    "runtime": "R6",
    "state_schema": "S2"
  }
}
```

这里只改变模型，因而可以先检查模型替换与行为变化之间的关系。真实服务若使用会漂移的模型别名，应保留提供方允许记录的具体版本信息及运行日期；无法固定的因素也要写出来。后续如果同时修改 Prompt，应该把它命名为新的候选组合，而不是覆盖 B 的旧记录。

评估集固定 20 个任务：12 个必须查询实时订单，8 个根据给定政策材料回答。每个任务有同样的起始数据、权限和验收条件。基线与候选使用重置后的独立环境，避免前一个版本的操作改变后一个版本的输入。先做一次小样本筛查，再对关键类型重复运行；一次通过不能说明随机性已经消失。

## 新模型更快，却没有达到发布条件

以下是人工构造的首轮结果。费用使用教学单位。p95 是把耗时从短到长排列后约有 95% 的任务不超过的数值；两组必须采用相同的测量起点、统计方法和负载。表格只用于展示决策方式。

| 指标 | 旧版本 A | 候选 B |
| --- | ---: | ---: |
| 实时订单任务成功 | 11/12 | 9/12 |
| 政策问答成功 | 7/8 | 8/8 |
| 总任务成功 | 18/20 | 17/20 |
| 必要查询执行覆盖 | 12/12 | 9/12 |
| p95 任务终态延迟 | 12 秒 | 9 秒 |
| 整批成本 | 100 单位 | 75 单位 |

B 的政策问答变好，延迟和费用都下降 25%，但总成功率从 90% 降到 85%，下降 5 个百分点。三个实时任务完全漏调查询，占必需查询任务的 25%。如果只查看已发生的九次正确调用，就可能报告“工具调用全对”，把被跳过的任务从分母中隐藏。

团队事前约定：本批实时任务必须执行查询，不允许根据旧聊天内容声称已确认当前状态。这项条件未通过，所以 B 不进入用户可见发布。平均文字质量或费用优势不能覆盖这类缺陷，发布结论应写“候选未达当前门槛”，而非泛称新模型整体更差。

看其中一个失败任务即可理解原因。输入为：“前面说订单 O-18 待发货，现在还能取消吗？”聊天历史中的待发货记录来自昨天，固定测试后端当前返回已发货。预期过程是先查询 O-18，再根据当前状态和取消规则回答；B 却直接回答“仍待发货，可以取消”，没有调用查询工具。

修订输入交给模型负责人时，应包含任务、旧历史时间、后端当前值、工具轨迹为空以及验收规则。把反馈压成“回答不准确”会丢掉原因。团队查到 P1 没有清楚区分历史状态与实时状态，于是在 P2 中明确要求这类问题使用当前查询结果，取不到结果则说明无法确认。后端同时检查工具结果的时间信息是否完整；不能靠补一句“务必准确”结束修复。

模型 M2 与 P2 组成候选 C，其余版本保持不变。假设重跑原集得到 19/20 成功、12/12 执行必要查询、p95 为 11 秒、成本 88 单位。它修复了已知漏调，但这只证明在已检查样本上改进。还要用未参与提示修改的保留样本测试“旧状态仍正确”“查询失败”“缺订单号”等变体，并复核剩下的失败，才能决定是否进入下一阶段。

## 影子测试、灰度和 A/B 各自回答什么

影子测试（shadow testing）复制真实请求给候选版本，但用户仍接收旧版本的结果。它适合观察生产输入分布、候选输出差异、错误和延迟。Azure Machine Learning 的官方文档将流量镜像说明为一种 shadowing：副本用于观测，不改变客户端收到的原结果。[Azure：Safe rollout for online endpoints](https://learn.microsoft.com/en-us/azure/machine-learning/how-to-safely-rollout-online-endpoints?view=azureml-api-2)

这个机制迁移到 Agent 时，必须处理工具副作用。即使候选答案不展示，候选仍可能创建申请、发送消息或修改数据库。因此影子分支的写工具应接模拟环境或受控回放，不应复制真实写入。读取敏感资料仍需要授权；影子也会增加服务成本。若使用录制工具结果，要确认候选请求与录制输入相匹配，不能给错误参数配上正确响应，制造假通过。

灰度发布（canary / progressive rollout）让一小部分真实用户使用候选，再按健康指标逐步扩大。它的主要目的在于限制故障影响并检验真实运行条件。每次扩大之前应观察足够的任务类型与时段；“半小时没人投诉”可能只是没有人用到问题功能。Azure Well-Architected 的安全部署指南要求逐步暴露、阶段健康检查，以及异常时停止推进并恢复。[Azure：Safe deployment practices](https://learn.microsoft.com/en-us/azure/well-architected/operational-excellence/safe-deployments)

A/B 测试则强调在可比较的分组中同时评估不同方案的效果，通常需要合理的随机分配、固定分析窗口和预先约定指标。它可以在灰度过程中进行，但少量流量不自动构成公平实验。如果 A 全是熟练用户、B 全是新用户，完成率差异不能直接归因于模型。多轮会话还应保持版本分配稳定；Microsoft 的 YARP 文档也提醒 A/B 路由需要考虑会话亲和设置。[Microsoft：A/B Testing and Rolling Upgrades](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/servers/yarp/ab-testing?view=aspnetcore-10.0)

对候选 C，合理的阶段结论是：保留集和重复测试通过既定条件后，先进入隔离写操作的影子验证；确认真实输入没有新的关键退化，再按授权计划开始小范围灰度。每一步都保留候选版本与证据。本文没有给出已完成的线上结果，因此不能跳到“C 已正式上线”。

## 能切回模型，不等于已经能够回滚

Agent 会留下会话、待执行工具、审批和外部业务对象。假设新运行时把状态格式从 S2 改为 S3，将 `pending_call` 改成另一组字段。若旧版本只能读 S2，出现故障后仅把模型 M2 切回 M1，旧程序仍可能无法恢复这批会话。更危险的是，它把未知状态当成没有执行过，重新提交已完成的写操作。

上线前应测试旧版本能否读取新版本产生的状态，或者准备明确的兼容适配与迁移。对正在执行的任务，可以固定到原版本完成，再把新任务切到旧版本；必须中断时，先保存已执行动作、操作标识和确认状态，避免恢复后重复写入。工具 Schema 的字段变化、索引切换和权限元数据也需要相同检查，不能只验证模型能正常输出文本。

一个可执行的回滚方案应说明：停止哪些新流量，切回哪个完整发布组合，如何处理运行中的会话，哪些外部动作需要核对，以及由谁确认恢复。外部申请已经创建，切回旧程序不会自动删除它；需要补偿动作时仍按业务授权执行。Azure 的安全部署指南明确指出，数据库、Schema 和其他有状态组件的回退可能复杂，必须事先规定数据处理方式。

因此发布门槛不仅是离线分数，还包括版本可追溯、监控能识别关键退化、旧版仍可用、状态恢复经过检查。先保留回退路径，再逐步扩大；不能在第一次灰度成功后立即移除所有旧依赖。

## 最终决策应能回到具体证据

一次迭代报告可以很短，但要区分候选与完成状态：“B 因三次必要查询遗漏被拒绝；C 修订 Prompt 后原集成功率 95%，必要查询覆盖 100%；保留集、影子和状态兼容检查仍待完成；当前生产继续使用 A。”这比“新模型效果显著提升”更方便后续接手者行动。

每次失败分桶后，还要留下可复用检查：漏查询的变体加入回归，来源过期交给数据更新，工具参数变化交给接口契约验证。产品负责人确认质量取舍，后端负责人确认部署与恢复，数据和评估负责人确认样本与证据。新模型上线只是一次带版本的变更，最终判断仍由业务目标、实际执行结果和可控的恢复路径共同决定。

**一分钟回答：团队怎样决定是否换新模型？**

先固定业务验收和完整版本组合，用同一任务集、权限与起始环境比较新旧版本。除了最终质量，还看必要工具遗漏、参数、结果利用、延迟和总成本。定位坏例后形成新的候选版本，跑回归与保留样本。再通过影子验证生产输入，小范围灰度控制影响，必要时设计公平 A/B 比较。上线前验证状态、工具 Schema 和索引兼容，并准备完整回滚方案。分数更高或更便宜，不能代替这些检查。

**追问一：影子版本不返回用户，为什么还需要隔离工具？**

它仍可能执行写入。隐藏回答只隔离了展示，没有隔离创建、发送或修改行为。应把写工具放入模拟或受控环境，并检查读取权限与额外负载，才能把影子结果作为有边界的验证。

**追问二：只改模型参数，回滚为什么仍可能失败？**

要确认实际改变的是否只有模型。Prompt、工具定义、持久状态或索引可能一起演进。旧运行时读不了新状态，或者外部动作已经发生时，切回模型不能恢复业务。需要完整版本记录和对运行中任务的处理策略。

**追问三：人工转接率上升，是不是模型退化？**

先看转接原因与任务分布。可能是新增权限控制让过去的越界操作正确转人工，也可能是漏调或误拒绝增加。需要比较转接样本的验收结果、工具轨迹与后续人工处理，不凭单个比例下结论。

## 练习：灰度前的一份不完整报告

候选 C 在原 20 题上达到 19/20，团队准备把它分给一半用户，并同时启用新工具 Schema T5。T5 把必填字段 `order_id` 改为 `order_ref`，旧会话里仍保存 T4 的待执行调用。报告只写“失败就切回 M1”。请指出缺口，并给出下一步能够审查的方案。

<details>
<summary>参考思路</summary>

当前成绩只覆盖 C 与 T4，不能证明 C 与 T5 的组合；原 20 题也参与过修改，需要保留样本和重复验证。将新组合单独标记版本，检查字段映射、旧会话恢复与错误分支，再跑相关契约与任务回归。

旧会话可以保持在兼容 T4 的运行路径，或通过已验证的显式迁移处理，不能直接交给只接受 T5 的工具。回滚应指向完整 A 组合，并说明在途任务、已执行外部动作和状态格式怎样处理。完成这些检查后，再进入隔离写操作的影子阶段和有明确停止条件的小范围灰度；一半用户不是凭原集分数自动得到的发布结论。

</details>
