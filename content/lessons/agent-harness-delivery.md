# AI Coding 的 Harness：从一句需求到可验收的代码

假设你把一张工单交给编码 Agent：“给订单查询接口加一个 `includeCancelled` 参数。”半小时后，它回复“已完成，测试通过”，还附上一段看起来合理的代码。你打开 diff，发现参数已经生效，但默认值是 `true`，旧客户端突然能查到已取消订单。测试确实跑了，只是它写的测试也把这个默认值当成正确行为。要避免这种情况，光把提示词改成“请仔细一点”帮助有限：任务本身没有讲明兼容规则，测试也没有独立的验收标准。

这篇讨论的是一个具体问题：**怎样把开发任务交给 Agent，又能知道它做了什么、哪里失败、能否安全交付？** 这里的 Agent 指能读仓库、改文件、运行命令并根据结果继续工作的程序。它背后有模型，也有围绕模型的运行框架（agent harness）：框架准备上下文和工具，执行工具调用，把结果送回下一轮，并保存任务状态。Anthropic 在评测文章中明确把模型和 harness 视为一起接受评估的系统；Claude Code 的公开介绍也把它定位为会使用代码库和 Git 工作流的编码工具。[Agent eval 的术语与边界](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)、[Claude Code 官方仓库](https://github.com/anthropics/claude-code)

腾讯这几份招聘 JD 提到的 spec-driven、context engineering、harness，以及代码生成、测试、评测和发布自动化，可以用这条交付链来理解。下面讲的是公开资料支持的**通用工程方法**，不代表腾讯内部系统就是这样实现的。JD 页面是动态加载的；本文未从页面正文核实岗位原话，仅把用户给定的技术主题作为学习范围。

## 先把需求写到可以判对错

规格（specification，简称 spec）要提前说清容易产生不同解释的地方，不一定需要十页文档。订单例子中，“加一个参数”至少缺四项：不传参数时的行为、`true` 和 `false` 的语义、非法值如何处理、哪些旧接口行为不能改变。让 Agent 自己猜，它可能选择任何一种看似合理的实现；后来再让它自己写测试，测试又可能把它的猜测固定下来。

一份足以开始工作的假设规格可以是：

```text
任务：GET /orders 增加可选查询参数 includeCancelled。
不传或传 false：只返回未取消订单，与旧版本一致。
传 true：返回未取消及已取消订单。
其他值：返回 400，错误码 INVALID_INCLUDE_CANCELLED。
约束：不修改订单写入逻辑；不在本任务中改变分页顺序。
验收：针对缺省、false、true、非法值各有独立测试；旧查询回归通过。
交付：提交代码 diff、测试命令与结果；暂不部署。
```

这里的“暂不部署”有实际作用：代码通过测试，不等于已经得到改变线上环境的授权。规格还应注明目标仓库、分支或基线提交、相关 API 文件，以及谁能决定有歧义的业务规则。若历史代码事实上把已取消订单也返回了，Agent 应把规格与现状的冲突指出来，不能悄悄改写验收条件。规格负责定义**什么叫完成**；具体怎样改代码，仍留给 Agent 和工程师判断。

## 给够上下文，但不要把整座仓库塞进窗口

编码 Agent 需要知道本仓库怎样启动、哪里放测试、有什么兼容约束、当前改动在哪个提交上。这叫上下文工程（context engineering）：每轮按任务选择进入模型输入的规则、文件、检索结果和历史状态。它不等于写一段更长的 prompt。Anthropic 的公开解释强调，上下文会随多轮工具调用增长，需要反复选择相关内容；放入更多文本也可能让重要信息更难被使用。[Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

在订单例子里，第一轮可给 `GET /orders` 的路由、查询层、现有测试、接口约定和仓库运行指令。Agent 读到分页实现以后，才需要查分页测试；若碰到错误码规范，再打开相应文件。这样留下的文件路径和版本可供下一轮复查。仓库里的 `AGENTS.md` 可以承载稳定的项目约定；Codex 官方文档说明它会沿项目目录读取这类文件，最近目录中的规则会影响该处工作。[Codex：AGENTS.md 指令发现](https://developers.openai.com/codex/guides/agents-md)

`AGENTS.md` 不是规格的替身。比如“修改 JavaScript 后运行测试”是可复用约定；“`includeCancelled` 默认 false”属于本次接口合同。当前工单中的用户要求、仓库说明、代码注释和搜索结果也不能全按同一权威程度处理。旧注释可能过时，测试可能覆盖不足，工具输出还可能含有无关指令。Agent 应能说出每个判断来自哪份材料、是否与更明确的需求冲突。

## Harness 在模型外实际做什么

可以把一次执行想成下面这段**教学伪代码**。它说明各环节的职责，不是 Codex、Claude Code 或腾讯产品的内部实现。

```text
读取任务规格、允许的工具、仓库状态
while 未达到完成条件且仍在预算内:
    选择本轮相关文件和执行结果，组成模型输入
    取得模型建议：读文件 / 编辑 / 跑命令 / 提问 / 结束
    检查操作是否在允许范围内
    执行操作，保存命令、退出码、diff 和关键输出
    如果失败，把失败反馈给模型；必要时停止并交给人
按独立验收规则检查最终代码与环境状态
生成供人审阅的变更与证据；由发布关卡决定能否上线
```

模型生成“运行测试”的建议，真正调用测试进程的是框架或其工具。模型回复“测试通过”也不是测试结果；应保存运行的命令、退出码、测试报告和对应代码版本。如果工具运行失败，harness 可以把错误返回模型让它修正；如果操作越权、预算用尽或同一错误反复出现，则应停止。一个普通 prompt 只告诉模型如何回答，不能单独提供隔离工作目录、工具权限、状态保存、独立测试和发布控制。

对长任务，状态保存尤其重要。Anthropic 的长任务实验发现，Agent 可能一次改得太多，中途耗尽上下文，下一轮不知道上一轮做了什么；也可能看见已有进展便过早宣布完成。其公开方案用初始化阶段建立环境，再让后续阶段小步修改、记录进度和 Git 历史。这是该实验的做法，不是所有系统的固定配方。[Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)

回到订单任务。第一次编辑后，Agent 只改了查询逻辑并运行单元测试。测试失败：`false` 被解析成非空字符串，在条件判断中变成真。它记录失败命令和报错，修正参数解析，再运行同一测试。随后它发现旧回归测试仍未覆盖“不传参数”的行为，于是补上独立用例。假设最后四个指定用例和旧回归都通过，diff 只涉及查询和测试文件，Agent 可以报告“达到本次验收条件，等待审阅”。这是一个**假设流程**，不表示任何真实仓库已经运行过这些测试。

## 测试通过之后，还要检查什么

测试是对确定规则最直接的检查，但“Agent 自己写的测试全绿”不足以证明需求正确。最好在任务开始时由人或独立验收方固定关键断言，例如旧请求默认结果、非法值的错误码；Agent 可以补实现测试，但不应通过修改固定断言来制造通过。对无法穷举的代码质量，再由 reviewer 看变更范围、可读性、异常处理和潜在风险。

评测（eval）把这种检查变成一组可重复运行的任务。Anthropic 区分单个任务、每次尝试（trial）、打分器（grader）、完整执行轨迹（trace）和环境最终状态（outcome）。一个编码 Agent 说“修好了”属于轨迹里的文字；真正应核实的是运行后的代码是否通过预先指定的测试，原有行为是否保留。由于模型输出可能变化，同一任务可重复尝试，统计通过率与失败类型。代码测试、静态检查、模型评审和人工评审各有用途，不能用一次主观打分代替可执行断言。[Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

这和日常 CI（持续集成）之间有联系，但两者检查的问题不同。CI 在一次提交上运行构建和测试；Agent eval 还会固定任务输入与初始环境，让不同模型、prompt 或 harness 版本分别做同一任务，再比较最终产物和执行过程。譬如设置三个订单接口任务：新增可选参数、保持分页顺序、遇到非法值返回指定错误。每个任务从同一基线开始，每次尝试在独立环境运行，避免上一次的修改污染下一次。这里的“三个任务”只是教学设计，不是一个足以代表真实生产表现的样本。

发布又是下一层。一个常见流程是：Agent 产出 diff；CI 在固定提交上跑测试、构建和检查；工程师审阅语义与风险；通过环境关卡后再部署；部署后看运行指标并保留回滚路径。GitHub Actions 官方文档把 workflow 描述为事件触发、在 runner 上执行 jobs 与 steps；GitHub Environments 支持为部署环境设置保护规则。具体是否需要人工审批、谁有权限、怎样回滚，应由项目制度决定，不能从“用了 Actions”自动推断。[GitHub Actions workflows](https://docs.github.com/en/actions/concepts/workflows-and-actions/workflows)、[GitHub Environments](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments)

把整条链连起来看，spec 给出目标和验收口径；context engineering 让模型每轮拿到相关事实；harness 控制工具、执行状态与失败反馈；测试检查这次代码；eval 检查同类任务是否稳定；发布关卡控制代码进入真实环境。每一层都可能失败，也各自留下证据。面试时若被问“怎样提升 AI Coding 的可靠性”，只答“优化 prompt”通常还没回答到交付问题。

<summary>面试怎么回答</summary>

**约一分钟回答：AI Coding 的 harness 怎样保证任务可交付？**

我先把需求写成可验证的 spec，尤其明确默认行为、边界情况、禁止改动和交付物。harness 在模型外负责准备相关代码与仓库规则、提供受控工具、记录每次编辑和测试结果，并把失败反馈给模型继续修。验收不能只听模型说“做完了”，要在固定代码版本上跑独立测试、看最终 diff 和环境状态。长期任务还要记录进度，让下一轮能接上。若要比较 Agent 版本，就用同一批任务和初始环境做重复 eval；发布则经过 CI、审阅和部署权限关卡。

**追问一：有一份很长的 spec，是否就不需要 context engineering？**

仍需要。spec 说明目标，Agent 还要知道当前仓库的实现、测试入口与最新执行结果。多轮之后输入会增长，harness 需要按当前问题选择文件和状态。给出整仓文本既可能超过窗口，也会使相关依据难找；但省略关键兼容规则同样危险。

**追问二：测试都通过了，为什么还要 eval？**

一次测试只检查这份代码在这些断言下的结果。eval 让同一类任务从固定初态反复运行，比较不同 Agent 版本的完成率、回归、耗时与失败方式。它也能发现模型经常改坏未要求的文件、只跑自己写的测试或过早宣布完成。已有测试仍是编码 eval 中很重要的 grader。

**追问三：Agent 写了测试并且全绿，可以自动发布吗？**

要看发布规则和风险。若测试由同一 Agent 根据含糊需求写成，它可能只证明自己的理解前后一致。至少要对照独立验收条件、审阅 diff，并确认 CI 运行的是准备发布的那个提交。生产部署还涉及权限、监控和回滚，不应由一次自然语言“完成”替代。

## 练习：找出缺失的交付环节

假设另一张工单写着：“让订单查询支持取消状态，尽快上线。”Agent 修改了路由，新增了两个测试，终端最后显示 `2 passed`。它的回复是“已完成，可以发布”，没有给出命令、提交版本或 diff。你会先补哪三项信息，才能判断这个结论？如果测试中将“不传参数”预期为返回所有订单，你会怎样处理？

<details>
<summary>参考思路</summary>

先补可判对错的规格，确认“不传参数”的兼容行为、非法值和分页约束；再取完整执行证据，包括实际命令、退出码、测试范围、代码基线与 diff；最后在固定提交上运行独立回归并安排审阅与发布关卡。三项的顺序并非死规定，但缺任一项都不足以从 `2 passed` 推出可上线。

若测试把默认行为设成返回所有订单，应先核对旧接口合同和业务方要求。若旧行为是只返回未取消订单，而新规格也要求保持兼容，就要修正测试与实现，重新运行，而不是把新测试通过当作改变旧合同的依据。若真实需求确实要改变默认行为，应让负责人明确这是兼容性变更，再更新规格、测试和发布计划。这里没有实际仓库和执行结果，不能预设哪一种业务选择已获批准。

</details>
