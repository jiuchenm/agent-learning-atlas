# WorkBuddy 研究工作流：角色、团队与代码编排怎样配合

WorkBuddy 是桌面 Agent 应用。做研究时，它既需要模型阅读和判断，也需要有人或程序安排任务：谁先查资料，谁等结果，谁检查结论，失败后是否继续。这种安排称为**编排（orchestration）**。假设研究一个虚构的开源笔记工具 PaperNote：“2.0 版本能否完全离线搜索？导出笔记时是否保留附件？”分别让模型以“研究员”“核查员”身份回答，只能看到角色分工；还要检查任务怎样交接，才能判断实际采用了什么编排。

WorkBuddy 安装材料里的三层编排，分别约束角色行为、成员协作和程序控制流。它们可以配合，但并非每次研究都同时用到三层：

| 层次 | 谁安排下一步 | 可检查的交接 |
| --- | --- | --- |
| 角色切换 | 当前执行者按提示词切换身份 | 角色定义、阶段产物、检查点 |
| Team 协作 | 主理人创建团队并调度成员 | 独立成员的任务、回传与中转 |
| JavaScript 工作流 | 代码按数据依赖和条件推进 | 返回值、集合、预算、分支 |

文档编排 Skill `tdoc-orchestrator` 默认要求读取角色定义、声明切换、按定义完成阶段，再回到编排角色；只有用户明确强制要求时才 spawn 子 Agent。它用 `md → html → docx` 约束阶段产物类型。这是提示词方法约定，三个角色名不证明存在三个独立上下文或 OS 进程（`tdoc-orchestrator/SKILL.md` L140–158）。[S16：角色切换](https://jiuchenm.github.io/workbuddy-study/#S16)

Team 规范进一步要求主理人执行 TeamCreate、向成员下发独立任务、接收专业产出，跨成员信息经主理人中转。无数据依赖的成员任务可以并行；后续阶段依赖前一阶段产物时，就要等待回传。主理人不能模拟成员发言来代替实际产出。不过，这份规范仍没有证明每次运行都遵守它，也没有说明成员如何映射到 OS 进程（`team-spec.md` L53–83）。[S18：Team 协作规范](https://jiuchenm.github.io/workbuddy-study/#S18)

本篇沿 PaperNote 任务分析第三层：随 Windows **5.6.2** 交付的 `deep-research.workflow.js`。它调用 `agent`、`pipeline`、`parallel` 连接研究阶段，并未在这份代码中使用 TeamCreate，也不能把文档角色切换当成它的前置步骤。原核验日期为 2026-09-28；2026-10-01 改稿重新只读核对文件哈希与相关代码。所有结论限于这份固定安装材料的静态分析；PaperNote、网页、主张和票数都是教学假设，没有运行供应商代码或外部研究。S 编号链接到[公开证据目录](https://jiuchenm.github.io/workbuddy-study/#S19)，目录提供定位信息，不是完整源码的公开地址。

## 先把研究问题变成可以分派的输入

先看 PaperNote 问题如何走到报告。下面是教学伪代码，只概括数据依赖，不能直接运行；其中函数名和箭头不代表宿主 API 的完整实现。

```text
问题 → Scope：拆成搜索角度
各角度 → Search：搜索 URL → 去重和预算过滤 → Fetch：读取并提取主张
等待整个 pipeline 返回 → 汇集、排序 → 最多取 25 条主张
每条主张 → 3 次 Verify：计有效票与反驳票 → 判断是否放行
有放行项 → Synthesis：组织发现与限制 → Markdown 报告
无候选或无放行项 → 返回对应结果，结束后续阶段
```

模型负责生成查询、阅读资料和判断主张，代码负责保存返回值并选择下一步。同样的问题可能产生不同搜索词和判断；可见代码固定的是这些结果怎样流动，以及哪些条件阻止继续。

工作流首先进入 Scope，即限定研究范围的阶段。它从 `args` 取得问题，空字符串直接返回错误；然后调用一次 `agent`，要求把问题拆成互补搜索角度。提示词倾向生成 5 个角度，但 `SCOPE_SCHEMA` 接受 3 至 6 个。因此“5 路搜索”是这份提示的目标，不是代码无条件创建的固定数量（`cli/builtin/workflows/deep-research.workflow.js` L81–92、L139–164）。[S42：Scope 与结果检查](https://jiuchenm.github.io/workbuddy-study/#S42)

对假设问题，可以产生“官方功能说明”“离线组件依赖”“2.0 导出格式”“附件丢失问题记录”“实际部署限制”五个角度。每项包含 `label` 和 `query`，之后的搜索调用就不用重新解释“研究方向是什么”。这里只是输入分解，没有任何证据表明 PaperNote 确实支持某项功能。若原问题只是“这个工具好不好”，还需要先确定使用场景；工作流入口描述要求调用前澄清含糊问题，但不能把这段要求当成程序已经实施的交互门禁。

Scope 返回值要通过 `safeParse` 才能继续；解析未通过时，工作流返回范围拆解错误并停止。这个函数先从文字或代码围栏中提取 JSON，再调用手写的 `validateJSON`。后者检查必填键、部分类型、数组长度和特定枚举，没有完整递归实现 JSON Schema。例如角度中的 `query` 被声明为字符串，数组元素检查却主要确认键存在，没有逐字段验证这个字符串类型。Schema 在这里是声明的数据形状，执行了哪些约束仍要看校验代码（同一文件 L13–73、L159–162）。[S42：解析与校验边界](https://jiuchenm.github.io/workbuddy-study/#S42)

这也解释了为什么 `safeParse` 的名称不能当成异常保证。若角度数组里有 `null`，代码对元素执行 `r in item` 时可能直接抛错；`safeParse` 自身没有包住整个校验过程。JSON 语法错误可以落到空结果，结构中的意外类型却可能走异常路径。后文对空值的处理，不能据此扩展为“所有 Agent 失败都会被吞掉”。

## 搜索、读取和 15 个名额怎样配合

Scope 之后调用 `pipeline`，把角度数组、搜索函数和后续读取函数交给流水线。一个角度的搜索完成，结果就可以先去重，再为新来源创建 Fetch 调用；不需要先收齐所有角度的搜索结果再统一开始读取。这里的无全局等待点，是这段工作流表达的调度关系；底层同时放行多少模型请求、如何限流，不能从 `parallel` 这个名称读出来（同一文件 L229–299）。[S42：Search 与 Fetch 流水线](https://jiuchenm.github.io/workbuddy-study/#S42)

假设“官方功能说明”先返回两篇文档，“附件问题记录”还在搜索，前两篇就可以进入读取。`seen` 保存已经遇到的规范化 URL；后来的相同地址会被记录为重复而不再读取。规范化去掉 `www.`、尾部斜杠和查询参数，并转小写，这能合并一部分重复链接，但也可能把依赖查询参数区分的页面合成同一个地址。这里实现的是 URL 去重，语义相同但网址不同的文章仍会留下。

Search 提示要求每个角度返回 4–6 个结果，手写 Schema 只设置最多 6 个，没有设置最少 4 个。Fetch 提示要求使用 WebFetch，从每篇提取 2–5 条**可证伪主张（falsifiable claim）**，也就是能被证据支持或推翻的具体陈述；其 Schema 只设置最多 5 条，允许空数组。本例可提取“2.0 的正文搜索索引保存在本地”，同时保存支持它的引文、来源质量与主张重要性。“产品体验很好”则缺少明确的核查条件。提示里的数量目标与实际检查条件需要分别阅读（同一文件 L93–114、L180–207）。[S42：搜索与主张提取](https://jiuchenm.github.io/workbuddy-study/#S42)

某个 Search 返回值解析未通过时，代码返回 `null`；Fetch 提示要求读取失败时返回空主张，调用的 Promise 链另有 `catch`，会把该来源记为不可靠并带空数组。这些局部分支能保留失败信息，但宿主是否让所有空结果或拒绝都安全进入汇集，本篇没有核验。因此不能据此承诺“所有 Agent 失败都能继续”（L233–239、L281–295）。[S42：读取失败处理](https://jiuchenm.github.io/workbuddy-study/#S42)

`MAX_FETCH = 15` 初始化了剩余名额 `fetchSlots`，但过滤条件是“名额已用完，并且相关性不是 high”。每个被接纳的新 URL 都会减一，所以 high 来源在名额归零后仍可加入，计数甚至可以变成负数。若已经接纳 15 个来源，下一批出现 3 个未重复的 high 和 2 个 medium，3 个 high 仍进入读取，2 个 medium 被丢弃，最终读取目标至少有 18 个。这是软预算，不能按常量名写成硬上限（L76–79、L242–256）。[S19：预算常量](https://jiuchenm.github.io/workbuddy-study/#S19)、[S42：预算实际判断](https://jiuchenm.github.io/workbuddy-study/#S42)

完成顺序也有影响。每个搜索结果内部按相关性排序，但程序没有先汇总所有角度，再选出全局最优的 15 个 URL。较早完成的角度可能先用掉 medium 的名额；后来的 high 仍可加入，后来的 medium 则可能被过滤。流水线减少阶段间等待，也让选源策略与到达顺序发生关联。这是从共享 `fetchSlots` 和逐批过滤代码得到的推论，本篇没有测量实际偏差。

整条 `pipeline` 返回后，程序才展开所有来源的主张，开始全局排序。这个等待点叫**同步屏障（barrier）**：后续步骤必须等候选池组装完，才能决定核查名额给谁。“官方说明”先读完，可以先提取主张；要把它与稍后返回的“附件问题记录”比较重要性，就必须等候选集齐。没有提取到任何主张时，代码直接返回空结果报告，后续 Verify 和 Synthesis 不启动（L301–310、L375–386）。[S42：汇集与停止分支](https://jiuchenm.github.io/workbuddy-study/#S42)、[S20：核查前的等待点](https://jiuchenm.github.io/workbuddy-study/#S20)

主张核查采用另一种边界。程序先按重要性 central、supporting、tangential 排序，同等重要性再按 primary、secondary 等来源质量排序，最后执行 `slice(0, MAX_VERIFY_CLAIMS)`，最多取 25 条。每条创建 3 次核查调用，所以这一阶段最多安排 $25 \times 3 = 75$ 次 `agent` 调用。这里的 75 仅是工作流显式安排的核查调用数，不是整次研究总调用数，也没有计入每个 Agent 内部可能发生的多轮模型与工具调用（L301–308、L387–395）。[S42：硬截取](https://jiuchenm.github.io/workbuddy-study/#S42)、[S20：三次核查](https://jiuchenm.github.io/workbuddy-study/#S20)

用一个成功路径手算：1 次 Scope、5 次 Search、18 次 Fetch、8 条候选各核查 3 次、1 次 Synthesis，共 $1+5+18+8\times3+1=49$ 次工作流层 `agent` 调用。这是假设每步都正常返回的账目，不是实测。它说明为什么不能拿“15 个来源”或“3 位核查员”直接估算整次成本。

## 三票怎样改变一条主张的去留

核查提示要求主动寻找反证：引文是否支持主张、有没有相反材料、来源是否足够、信息是否过时。每个返回值含布尔字段 `refuted`；`true` 表示反驳，`false` 表示未反驳。返回值还须通过手写检查；空结果在投票汇总中按弃权处理。三个调用都使用 `model: "lite"`，提供相同主张与来源，仅投票者编号不同，所以三票是多次判断，不等于三个独立事实来源（L209–227、L387–407）。[S42：反证提示](https://jiuchenm.github.io/workbuddy-study/#S42)、[S20：计票条件](https://jiuchenm.github.io/workbuddy-study/#S20)

实际放行条件是**有效票至少 2 张，且反驳票少于 2 张**。下面用“正文搜索索引保存在本地”这条假设主张手算；有效票包括“未反驳”和“反驳”，不包括空返回值代表的弃权。

| 三次返回 | 有效票 | 反驳票 | 能否进入合成 |
| --- | --- | --- | --- |
| 未反驳、未反驳、反驳 | 3 | 1 | 可以 |
| 未反驳、反驳、弃权 | 2 | 1 | 可以 |
| 未反驳、弃权、弃权 | 1 | 0 | 不可以，有效票不足 |
| 未反驳、反驳、反驳 | 3 | 2 | 不可以，达到反驳阈值 |

第二行说明实现没有要求“至少两票确认”；第三行避免一票未反驳、甚至全弃权时，因为反驳数为零而误放行。判断是否通过，只需按这两个条件计算，不必猜“核查员多数同意”的含义。

未通过的原因还要继续保留。代码把所有 `!survives` 主张放入 `killed`，其中既有两票反驳，也有有效票不足。后面的报告却把这一集合标作 `refuted`；全无通过项时，工作流停止合成并返回报告，摘要称所有主张被反驳。这会把“未核实”误写成“已推翻”。例如“导出保留所有附件”只有一张有效票时，正确解释应是需要补证据，不能据此断言附件会丢失；实际反证才能说明原主张为何不成立。这是静态代码推演出的分类问题，没有实测供应商运行失败（L398–423）。[S20：淘汰与反驳的语义差别](https://jiuchenm.github.io/workbuddy-study/#S20)

这些阈值降低的是某些误放行风险，并不计算事实为真的概率。三次调用可能依赖同一篇不准确的材料，也可能一起误读引文。尤其“完全离线”比“正文索引在本地”强得多：附件 OCR 也许需要联网，即便三次调用都遗漏这个条件，重复判断也不会补出缺失证据。报告仍要保留版本、功能范围和原始来源。

## 报告怎样交付，失败在哪里结束

Synthesis 是报告合成阶段：取得通过项的主张、引文、来源和核查证据，要求合并语义重复、组织发现并写出限制。代码为每条主张选择未反驳票中置信标签（`confidence`）最高的一份证据进入主要说明；其他投票理由并未完整进入这个说明块，所以少数反驳意见可能失去具体上下文。`high`、`medium`、`low` 是模型返回的标签，没有证据表明它们是经校准的真实性概率。合成提示还要求 3–5 句摘要与 2–4 个开放问题，手写校验没有完整强制这些数量。最终 `formatReport` 把结构化结果转成 Markdown（L426–486）。[S66：合成与格式化边界](https://jiuchenm.github.io/workbuddy-study/#S66)

如果合成文本正常返回，但解析不通过，代码回退到未合并的通过项，以原始引文保留结果。调用直接抛出异常则没有同样明确的本地回退分支，`safeParse` 的校验过程也可能抛错。因此阅读这条工作流，应分别识别四类停止或降级条件：空问题返回错误；Scope 解析未通过停止；无候选或无通过项返回对应报告；合成返回值解析未通过时降级交付。它们没有构成覆盖一切宿主、网络和模型异常的恢复协议。

在假设成功路径里，合适的输出可能是“正文搜索可离线，但附件处理条件尚不明确；导出能否保留全部附件仍需验证”。它应由通过项与未解决问题支持，不能把 `confirmed` 这个变量名当作已经证明全部产品承诺。程序提供排序、截取与数据交接，报告中的事实确定程度仍需要核对。

回到开头的三层：角色定义说明执行责任，Team 规范说明成员怎样协作，代码工作流说明数据与分支怎样推进。需要独立产出时可考虑 Team，需要重复执行明确的数据路径时可考虑代码；是否同时采用，取决于任务设计。深度研究工作流的 helper 如何映射到运行时对象，仍需另外检查宿主。验收 PaperNote 报告时，应检查角度是否覆盖问题、来源是否实际读到、主张为何通过、未知是否保留，以及停止原因是否正确呈现。参与者数量无法代替这些证据。一般的协作与依赖问题可回看[多 Agent](#/lesson/multi-agent)，本篇只讨论固定安装材料中的研究案例。

<details>
<summary>面试怎么回答</summary>

**一分钟回答：** WorkBuddy 安装材料中，角色切换、Team 协作和代码工作流是不同层次。角色切换默认在现有执行上下文中按角色定义做事；Team 规范要求真正创建团队并由成员回传；深度研究工作流则用代码规定 Scope、搜索读取、核查与合成。搜索和读取可以交叠，核查前要等候选池完整。预算也要看条件：15 个来源是软限制，25 条主张由 slice 硬限制，核查阶段最多安排 75 次 Agent 调用。三票只决定工作流是否放行，不保证事实独立可靠；有效票不足应保留为未核实，不能误标成已反驳。

**追问一：为什么不等所有搜索完成后再读取？** 提前读取可以减少阶段间等待，但逐批占用名额会受完成顺序影响。全局收齐再排序更方便统一选源，却增加等待。这里采用流水线，而核查排名必须依赖完整候选池，所以在核查前保留等待点。

**追问二：三票机制最容易被误解在哪里？** 它不要求两票未反驳，而是要求至少两张有效票且反驳不足两张；三次模型判断也不是三个独立来源。还要区分“被反驳”和“有效票不足”，以及模型的置信标签与经校准的概率。
