# WorkBuddy：角色切换、团队协作与代码工作流

假设要研究一个虚构的开源笔记工具 PaperNote：“2.0 版本能否完全离线搜索？导出笔记时是否保留附件？”让模型连续回答几次，并分别署名“研究员”“核查员”，还不能说明系统有真正的任务分派。需要继续追问：谁决定下一步，前一步交付什么，哪些任务可以同时开始，失败的结果会怎样进入报告？这些问题决定了编排的实际行为。

编排（orchestration）在这里指程序怎样安排多个执行者：谁先查资料，谁等结果，谁检查结论，以及失败后是否继续。WorkBuddy 安装包里可以看到三种不同安排：通过提示词切换角色、通过 Team 工具调度成员，以及 JavaScript 工作流调用多个 Agent。本篇以随 Windows 5.6.2 交付的 `deep-research.workflow.js` 为主线，从 PaperNote 的研究问题走到报告，再比较前两种安排。核验日期为 2026-09-28，材料均为只读安装文件；PaperNote、网页、结论和票数都是教学假设，没有执行供应商代码或外部研究。S 编号链接到[公开证据目录](https://jiuchenm.github.io/workbuddy-study/#S19)，目录保留定位信息，不是完整源码的公开地址。

## 先把研究问题变成可以分派的输入

代码工作流与自由对话的区别，是程序已经写下部分控制流：哪些调用先执行、返回值放进哪个集合、满足什么条件才继续。模型仍负责生成查询、阅读资料和判断主张，程序负责连接这些结果。它不是完全确定性的研究，因为同样的输入仍可能得到不同搜索词和判断；确定的是可见代码规定的数据路径。

工作流首先进入 Scope，即限定研究范围的阶段。它从 `args` 取得问题，空字符串直接返回错误；然后调用一次 `agent`，要求把问题拆成互补搜索角度。提示词倾向生成 5 个角度，但 `SCOPE_SCHEMA` 接受 3 至 6 个。因此“5 路搜索”是这份提示的目标，不是代码无条件创建的固定数量（`cli/builtin/workflows/deep-research.workflow.js` L81–92、L139–164）。[S42：Scope 与结果检查](https://jiuchenm.github.io/workbuddy-study/#S42)

对假设问题，可以产生“官方功能说明”“离线组件依赖”“2.0 导出格式”“附件丢失问题记录”“实际部署限制”五个角度。每项包含 `label` 和 `query`，之后的搜索调用就不用重新解释“研究方向是什么”。这里只是输入分解，没有任何证据表明 PaperNote 确实支持某项功能。若原问题只是“这个工具好不好”，还需要先确定使用场景；工作流入口描述要求调用前澄清含糊问题，但不能把这段要求当成程序已经实施的交互门禁。

Scope 返回值要通过 `safeParse` 才能继续。这个函数先从文字或代码围栏中提取 JSON，再调用手写的 `validateJSON`。后者检查必填键、部分类型、数组长度和特定枚举；它没有完整递归实现 JSON Schema。例如角度中的 `query` 被声明为字符串，但数组元素检查主要确认键存在，没有逐字段验证这个字符串类型。字段看起来像 Schema，不代表已经采用完整的 Schema 验证器（同一文件 L13–73）。[S42：解析与校验边界](https://jiuchenm.github.io/workbuddy-study/#S42)

这也解释了为什么 `safeParse` 的名称不能当成异常保证。若角度数组里有 `null`，代码对元素执行 `r in item` 时可能直接抛错；`safeParse` 自身没有包住整个校验过程。JSON 语法错误可以落到空结果，结构中的意外类型却可能走异常路径。后文对空值的处理，不能据此扩展为“所有 Agent 失败都会被吞掉”。

## 搜索与读取交叠，但核查要等候选集齐

Scope 之后调用 `pipeline`，把角度数组、搜索函数和后续读取函数交给流水线。一个角度的搜索完成，结果就可以先去重，再为新来源创建 Fetch 调用；不需要先收齐所有角度的搜索结果再统一开始读取。这里的无全局等待点，是这段工作流表达的调度关系；底层同时放行多少模型请求、如何限流，不能从 `parallel` 这个名称读出来（同一文件 L229–299）。[S42：Search 与 Fetch 流水线](https://jiuchenm.github.io/workbuddy-study/#S42)

假设“官方功能说明”先返回两篇文档，“附件问题记录”还在搜索，前两篇就可以进入读取。`seen` 保存已经遇到的规范化 URL；后来的相同地址会被记录为重复而不再读取。规范化去掉 `www.`、尾部斜杠和查询参数，并转小写，这能合并一部分重复链接，但也可能把依赖查询参数区分的页面合成同一个地址。这里实现的是 URL 去重，语义相同但网址不同的文章仍会留下。

读取调用要求使用 WebFetch，提取可证伪主张（falsifiable claim），即能由证据支持或推翻的具体陈述，并保存引文、来源质量与主张重要性。本例可以得到“2.0 的正文搜索索引保存在本地”，而“产品体验很好”没有足够明确的核查条件。提示要求读取失败时返回空主张；Fetch 调用的 Promise 链另有 `catch`，会把该来源记为不可靠并带空数组。无论是提示要求还是错误对象，都不能证明每次真实失败会按预想形式出现（同一文件 L192–207、L281–295）。[S42：读取与主张提取](https://jiuchenm.github.io/workbuddy-study/#S42)

整条 `pipeline` 返回后，程序才展开所有来源的主张，并开始全局排序。这是核查之前的同步屏障（barrier）：后续步骤必须等候选池组装完，才能决定有限核查名额给谁。搜索与读取可以交叠，不等于所有阶段都能无限向前推进；“核查排名靠前的主张”本身依赖候选池完整（L301–310、L384–386）。[S42：汇集与排序](https://jiuchenm.github.io/workbuddy-study/#S42)、[S20：核查前的等待点](https://jiuchenm.github.io/workbuddy-study/#S20)

## 常量写了 15，不等于最多读取 15 个来源

`MAX_FETCH = 15` 初始化了剩余名额 `fetchSlots`，但过滤条件是“名额已用完，并且相关性不是 high”。每个被接纳的新 URL 都会减一，所以 high 来源在名额归零后仍可加入，计数甚至可以变成负数。若已经接纳 15 个来源，下一批出现 3 个未重复的 high 和 2 个 medium，3 个 high 仍进入读取，2 个 medium 被丢弃，最终读取目标至少有 18 个。这是软预算，不能按常量名写成硬上限（L76–79、L242–256）。[S19：预算常量](https://jiuchenm.github.io/workbuddy-study/#S19)、[S42：预算实际判断](https://jiuchenm.github.io/workbuddy-study/#S42)

完成顺序也有影响。每个搜索结果内部按相关性排序，但程序没有先汇总所有角度，再选出全局最优的 15 个 URL。较早完成的角度可能先用掉 medium 的名额；后来的 high 仍可加入，后来的 medium 则可能被过滤。流水线减少阶段间等待，也让选源策略与到达顺序发生关联。这是从共享 `fetchSlots` 和逐批过滤代码得到的推论，本篇没有测量实际偏差。

主张核查采用另一种边界。程序先按重要性 central、supporting、tangential 排序，同等重要性再按 primary、secondary 等来源质量排序，最后执行 `slice(0, MAX_VERIFY_CLAIMS)`，最多取 25 条。每条创建 3 次核查调用，所以这一阶段最多安排 $25 \times 3 = 75$ 次 `agent` 调用。这里的 75 仅是工作流显式安排的核查调用数，不是整次研究总调用数，也没有计入每个 Agent 内部可能发生的多轮模型与工具调用（L301–308、L387–395）。[S42：硬截取](https://jiuchenm.github.io/workbuddy-study/#S42)、[S20：三次核查](https://jiuchenm.github.io/workbuddy-study/#S20)

用一个成功路径手算：1 次 Scope、5 次 Search、18 次 Fetch、8 条候选各核查 3 次、1 次 Synthesis，共 $1+5+18+8\times3+1=49$ 次工作流层 `agent` 调用。这是假设每步都正常返回的账目，不是实测。它说明为什么不能拿“15 个来源”或“3 位核查员”直接估算整次成本。

## 三票怎样改变一条主张的去留

核查提示要求主动寻找反证：引文是否支持主张、有没有相反材料、来源是否足够、信息是否过时。每个返回值含布尔字段 `refuted`；`true` 表示反驳，`false` 表示未反驳。返回值还须通过手写检查；空结果在投票汇总中按弃权处理。三个调用都使用 `model: "lite"`，提供相同主张与来源，仅投票者编号不同，所以三票是多次判断，不等于三个独立事实来源（L209–227、L387–407）。[S42：反证提示](https://jiuchenm.github.io/workbuddy-study/#S42)、[S20：计票条件](https://jiuchenm.github.io/workbuddy-study/#S20)

实际放行条件是“有效票至少 2 张，且反驳票少于 2 张”。对“正文搜索索引保存在本地”这条假设主张，若得到“未反驳、未反驳、反驳”，有效票 3、反驳票 1，可以进入合成。若是“未反驳、反驳、弃权”，有效票 2、反驳票 1，同样通过。因此不能把实现改述为“至少两票确认才通过”。一票未反驳加两票弃权则不能通过，避免所有核查都没完成时因为反驳数为零而误放行。

未通过的含义还要再分辨。代码把所有 `!survives` 主张放入 `killed`，其中既有两票反驳，也有有效票不足。后面的报告却把这一集合标作 `refuted`；全无通过项时，摘要也称所有主张被反驳。这会把“未核实”误写成“已推翻”。对读者来说，两者应导向不同结论：前者需要补证据，后者需要说明哪条证据否定了原主张（L398–423）。[S20：淘汰与反驳的语义差别](https://jiuchenm.github.io/workbuddy-study/#S20)

这些阈值降低的是某些误放行风险，并不计算事实为真的概率。三次调用可能依赖同一篇不准确的材料，也可能一起误读引文。尤其“完全离线”比“正文索引在本地”强得多：附件 OCR 也许需要联网，即便三次调用都遗漏这个条件，重复判断也不会补出缺失证据。报告仍要保留版本、功能范围和原始来源。

## 合成报告与组织团队，是两层不同的选择

Synthesis 取得通过项的主张、引文、来源和核查证据，要求合并语义重复、组织发现并写出限制。代码为每条主张选择未反驳票中置信标签最高的一份证据进入主要说明，而不是原样向合成步骤展示所有投票理由。最终 `formatReport` 把结构化结果转成 Markdown。若合成文本可返回但解析不通过，则回退到未合并主张；这不意味着 `agent` 调用直接抛出的任何异常都必然得到同样回退（L426–486）。[S66：合成与格式化边界](https://jiuchenm.github.io/workbuddy-study/#S66)

在假设成功路径里，合适的输出可能是“正文搜索可离线，但附件处理条件尚不明确；导出能否保留全部附件仍需验证”。它应由通过项与未解决问题支持，不能把 `confirmed` 这个变量名当作已经证明全部产品承诺。程序提供排序、截取与数据交接，报告中的事实确定程度仍需要核对。

现在比较另外两种组织方式。`tdoc-orchestrator/SKILL.md` L140–158 规定文档阶段默认采用角色切换：读取对应 Agent 定义，以该角色执行，再回到编排角色；只有用户明确强制要求时才 spawn 子 Agent。这是一套提示词方法约定，不能因为文档写了三个角色，就推断启动了三个独立上下文或操作系统进程。它的阶段交接另以 `md → html → docx` 的产物类型约束，角色名称只是执行责任的一部分。[S16：文档角色切换](https://jiuchenm.github.io/workbuddy-study/#S16)

`expert-manager/references/team-spec.md` L53–83 的 Team 规范则明确要求主理人执行 TeamCreate，再调度成员、接收回传，跨成员信息由主理人中转；无数据依赖可并行，有依赖则等待前阶段结果。这里要求成员实际产出，不能由主理人模拟多角色发言。但该规范本身没有证明每个成员对应一个 OS 进程，也没有证明每次运行都遵守了要求。[S18：Team 协作规范](https://jiuchenm.github.io/workbuddy-study/#S18)

深度研究工作流使用的 `agent`、`parallel`、`pipeline` 则把部分调度写进代码。它们怎样映射到运行时对象，需要另外检查宿主实现。选择哪种安排，要看是否需要独立任务、可检查的输入输出和固定分支；多几个角色名不会自动提供这些机制。沿本例验收时，应检查角度是否覆盖问题、来源有没有实际读到、每个主张为何通过、未知是否被保留，而不是只数参与了多少 Agent。

<details>
<summary>面试怎么回答</summary>

**一分钟回答：** WorkBuddy 安装材料中，角色切换、Team 协作和代码工作流是不同层次。角色切换默认在现有执行上下文中按角色定义做事；Team 规范要求真正创建团队并由成员回传；深度研究工作流则用代码规定 Scope、搜索读取、核查与合成。搜索和读取可以交叠，核查前要等候选池完整。预算也要看条件：15 个来源是软限制，25 条主张由 slice 硬限制，核查阶段最多安排 75 次 Agent 调用。三票只决定工作流是否放行，不保证事实独立可靠；有效票不足应保留为未核实，不能误标成已反驳。

**追问一：为什么不等所有搜索完成后再读取？** 提前读取可以减少阶段间等待，但逐批占用名额会受完成顺序影响。全局收齐再排序更方便统一选源，却增加等待。这里采用流水线，而核查排名必须依赖完整候选池，所以在核查前保留等待点。

**追问二：三票机制最容易被误解在哪里？** 它不要求两票未反驳，而是要求至少两张有效票且反驳不足两张；三次模型判断也不是三个独立来源。还要区分“被反驳”和“有效票不足”，以及模型的置信标签与经校准的概率。
