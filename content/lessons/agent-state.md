# 任务状态：对话之外还要保存什么

假设一个报修助手已经收到用户确认，向工单系统请求创建记录。工单系统完成了创建，但助手还没来得及保存返回的编号，运行进程就退出了。重启以后，聊天记录最后一句仍是“确认，请提交”。如果助手据此再创建一次，可能出现两张内容相同的工单；如果直接告诉用户已经完成，又拿不出能核对的编号。问题不在于模型有没有记住那句话，而在于程序没有明确区分“准备提交”“请求发出”和“结果已经确认”。

本篇讨论任务状态（task state）：一个 Agent 为了继续完成当前任务，需要明确保存的事实、进度和约束。它是应用维护的数据，例如“已获 D3 第 1 版确认，创建请求 OP17 的结果未知”；不是模型参数中的记忆，也不是聊天窗口最后一句话。例子中的用户、工具、工单与返回结果全部是假设，没有操作真实业务系统。读过 [Function Calling](#/lesson/function-calling) 后，我们已经知道模型请求调用工具，宿主程序实际执行。本篇继续追问：执行到一半时，程序究竟凭什么知道下一步该做什么？

## 对话、状态、检查点和业务记录

对话记录（conversation history）保存用户与助手说过的话，也可能包括工具请求和返回。它适合解释任务如何形成，却不天然适合作为唯一的执行凭据。用户可以先说“提交”，随后又说“等一下”；助手也可能先猜测原因，再被新证据推翻。让每次模型调用重新读整段对话，推断现在有没有许可、动作有没有完成，会把本可明确记录的事实再次交给语言理解。

任务状态则把这些信息整理为当前有效的表示。例如，目标是什么，正在处理哪份草稿，用户确认的是哪个版本，流程停在哪个阶段，是否有结果未知的工具请求，下一步还允许做什么。状态可以包含对话，也可以只保存消息引用和必要摘要。两者并不排斥，但“出现过一句话”和“当前有效状态”承担不同职责。

检查点（checkpoint）是运行到某个边界时保存的状态快照，以及恢复所需的执行位置或其他元数据。当前状态会继续变化；检查点保留的是那一刻的版本。持久化（persistence）进一步要求这些记录能够跨越需要防范的故障，例如写入磁盘或数据库后，进程退出仍可读回。只在内存里复制一个对象，也能在程序内部称为检查点，却无法抵抗进程重启。LangGraph 的官方文档区分了线程内的状态检查点与跨线程数据存储，并明确说明内存检查点会在重启时丢失。这里借用它说明机制，不依赖其具体 API。[LangGraph：Persistence，核验于 2026-09-28](https://docs.langchain.com/oss/python/langgraph/persistence)

业务数据库记录业务事实。例如，工单 8421 是否存在、是否分配负责人、目前有没有关闭，由工单系统维护。Agent 状态中的“已创建 8421”只是一次已核实结果的本地记录，并不意味着它永远知道工单的最新情况。别人随后关闭了工单，旧检查点不会自动更新；用户询问当前进展时，仍须查询业务系统。

| 信息载体 | 本例保存什么 | 不能单独证明什么 |
| --- | --- | --- |
| 对话 | 用户描述故障、确认草稿的话 | 外部创建请求是否生效 |
| 任务 state | 草稿版本、有效确认、当前阶段、待核实动作 | 业务记录此刻仍是什么状态 |
| checkpoint | 某个状态版本与恢复位置 | 所有外部系统同时回到那个时刻 |
| 业务数据库 | 正式工单、编号、当前处理进度 | Agent 已向用户正确交付结果 |

这些区别是职责上的区别，不要求使用四套独立数据库。同一个数据库可以保存对话、检查点与业务表，但应用仍须明确哪个字段由谁更新、哪个结果以哪个系统为准。把所有内容塞进一个 JSON 字段，不会自动消除这些边界。

## 把一次报修写成可恢复的状态迁移

假设用户提出：“三楼 301 会议室投影仪无法连接。帮我登记报修，先给我看内容，我确认后再创建。”任务标识为 R17。应用根据描述生成草稿 D3，第 1 版包含地点、设备和现象；没有确认的故障原因不写成事实。此时保存检查点 C1，并把阶段设为“等待确认”。进程可以退出，不需要一直占着模型等待用户回复。

用户随后确认这份草稿。程序验证这次确认对应 D3 的第 1 版，把确认记录写入状态，再保存 C2。这个关联很关键：如果用户后来把地点改为 302，原来的确认不能自然延伸到新内容。授权属于具体操作及其内容，而不是给助手一张永久有效的“可以提交”通行证。

在真正调用创建工具之前，程序为这一次预期操作分配标识 OP17，把完整请求内容和“结果待核实”一起持久保存为 C3。以下是教学用状态结构，不是框架接口，也没有包含真实个人信息：


```json
{
  "taskId": "R17",
  "stateVersion": 3,
  "phase": "create_pending",
  "goal": "创建一张已确认的报修工单并返回编号",
  "draft": {
    "id": "D3",
    "version": 1,
    "room": "301",
    "device": "projector",
    "symptom": "无法连接"
  },
  "approval": {
    "draftId": "D3",
    "draftVersion": 1,
    "receiptRef": "confirmation-R17-1"
  },
  "operation": {
    "id": "OP17",
    "kind": "create_ticket",
    "result": "unknown",
    "ticketId": null
  },
  "nextAction": "resolve_pending_creation"
}

```

这里有三类标识：R17 关联整项任务，D3 的版本说明用户确认了什么，OP17 关联这一次预期的外部创建动作。它们回答的问题不同。stateVersion 是本地状态版本，不能用它替代草稿版本；状态更新到第 3 版时，草稿仍然可以是第 1 版。把它们分开，才能识别“状态变了，但用户确认的内容没有变”的情况。

程序确认 C3 已经持久保存以后，调用创建工具，并携带 OP17。为便于讲解，本例假设工单服务支持把调用方提供的操作标识关联到工单，并提供能核实该操作结果的查询接口。这是例子的接口前提，不能推断任意工单服务都具备它。

工单服务创建了 8421，并记录它属于 OP17。随后助手进程退出，未保存创建结果。恢复时，程序先读回 C3，而不是让模型仅凭最后一条聊天推断；C3 的 operation.result 为 unknown。这个值准确表达了助手掌握的证据：操作可能尚未发出，也可能已经完成，当前记录不能区分两者。它不等于 failed，更不等于“应该重新创建”。

程序因此执行 nextAction 所规定的核实：按 OP17 查询业务服务。假设查询返回 8421，且地点、设备、现象都与已确认草稿一致，助手就把返回编号及核实依据写入状态，保存 C4，阶段变为“已创建，待返回编号”。最后对用户交付：“已创建报修工单 8421，地点为三楼 301 会议室，现象为投影仪无法连接。”这次假设执行中，应用随后确认答复已交付，保存 C5，将任务置为完成。它报告的是登记完成，没有宣称设备已修好。

| 保存边界 | 状态及已有证据 | 此后允许的下一步 |
| --- | --- | --- |
| C1 | 草稿 D3 第 1 版，尚无确认 | 等待用户确认或修改草稿 |
| C2 | 第 1 版已获有效确认 | 准备本次创建操作 |
| C3 | OP17 与请求内容已保存，结果未知 | 正常运行可发起一次；恢复时先核实结果 |
| C4 | OP17 对应工单 8421，内容已核对 | 返回编号，不再创建 |
| C5 | 本次结果已交付用户 | 结束任务 |

这个过程中的状态迁移（state transition）不仅是把 phase 换个字符串。每次迁移都要带有触发事件、成立条件和需要保存的事实。C1 到 C2 由匹配草稿版本的用户确认触发；C3 到 C4 由业务服务的可核实结果触发。模型的一句“应该成功了”不能代替第二种证据。运行时也应限制不合法的跳转，例如缺少有效确认时不能直接进入创建阶段。

## 恢复了程序，不代表撤销了外部动作

检查点解决的是“程序从哪里继续、依据什么继续”，而不是“外部动作天然只发生一次”。C3 保存和工单创建发生在两个系统中。没有额外的一致性机制时，总会存在一段间隙：外部动作已经生效，本地结果还没保存。AWS 的一手工程文章用资源创建后响应丢失的例子解释了同类问题：调用方收不到结果，无法据此判断远端有没有执行，直接重试可能产生额外资源。[AWS Builders' Library：Making retries safe with idempotent APIs](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

OP17 在本例中帮助关联和查询动作，但仅仅生成一个字符串不能保证安全重试；远端必须理解并遵守相应接口契约。如果查询也超时，状态仍然应是“结果未知，等待核实”。如果接口无法可靠区分未发生和仍在处理，就需要继续等待或交由人核查，不能用一条空结果证明可以再创建。如何设计幂等键、重试预算和退避，留到 [工具失败：超时以后能直接重试吗](#/lesson/tool-reliability)。

同样，把本地状态恢复到 C1，不会从工单系统删除已经创建的 8421。检查点并不是跨所有外部系统的撤销按钮。若业务上需要取消工单，那是一个新的业务动作，需要检查工单当前状态、取消权限以及取消结果。调试时可以从旧状态探索另一条路径，但要重新审视外部动作的执行条件，避免让历史上的“待创建”在现实中变成重复创建。

恢复还要求读到正确版本。若任务运行期间代码更新了，旧状态可能缺少新字段，或者旧 phase 名称已经不再使用。应用需要识别状态结构版本，迁移数据或明确拒绝不兼容恢复。例子里只画了一条串行任务；若多个执行者同时写同一份状态，还要防止较旧版本覆盖新结果。这些都是状态存储的契约，不能靠提示词让模型“记得小心”来替代。

保存范围也有成本。快照过密会增加写入、存储和保留数据的负担；过疏会丢掉更多可复用进度。一个可行的起点是保存用户确认、不可重做的昂贵结果，以及外部写入前后的关键事实。大附件可以保存受控引用和版本，不必在每个检查点复制全文。敏感资料仍须遵守访问和保留规则。LangGraph 文档也提醒检查点不断累积会增加存储和访问负担；具体保存频率应由任务的故障代价决定。[LangGraph：Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)

任务状态还不等于把所有字段都发给模型。程序可以保存完整的操作记录，只把当前决定需要的信息放进这一次输入：已经确认的草稿、结果未知的 OP17、允许执行的核实动作。跨任务保留偏好或长期事实属于另一个问题，见 [Memory](#/lesson/agent-memory)。先把当前任务的证据和进度保存清楚，才有资格讨论下次运行应该记住什么。

<details>
<summary>面试怎么回答</summary>

**一分钟回答：** Agent 的任务状态保存当前目标、业务对象、有效输入、授权、执行阶段和工具结果。对话是交互历史，状态是当前继续执行需要的明确表示；checkpoint 是某一时刻可恢复的状态与执行元数据，持久化后才能跨进程恢复；业务数据库则记录外部业务事实。恢复时先看有没有结果未知的动作，再决定继续哪一步。尤其要注意，远端写入可能已经成功，而本地还没保存结果，所以恢复旧 checkpoint 既不能证明动作失败，也不会撤销它，需要按业务接口核实。

**追问一：为什么不把所有聊天记录保存下来就够了？** 聊天可以是状态的一部分，但程序还需要稳定标识、版本和明确阶段。用户先确认后修改，旧确认仍在聊天里，当前许可却已经变化。若由模型每次重新猜测，很难约束非法迁移。可以从消息中提取状态，但提取结果和后续执行仍需程序校验。

**追问二：有 checkpoint 能保证工具只执行一次吗？** 不能单靠它保证。本地保存与远端写入可能分别完成，崩溃后留下未知结果。需要外部服务提供可核实的操作身份、去重等契约，或由人工处理无法判断的情况。检查点至少应保存原操作与请求内容，使恢复能核实同一次意图，而不是生成一个全新的创建请求。

<details>
<summary>参考思路</summary>

先按 OP17 核实原来针对 301 的创建结果，不能因为收到修改消息就把未知动作当成未发生。同时生成针对 302 的新草稿版本，把旧确认继续绑定在第 1 版上；它不能授权新版本。

如果 301 的工单已经存在，就向用户说明编号和当前事实，再准备更正或取消的具体动作，按权限要求取得相应确认。不要直接创建第二张工单来掩盖第一张。如果服务已可靠确认旧请求没有生效、也不会继续生效，才可结束旧操作，等待用户确认 302 的新草稿后开展新动作。查询失败或暂时查不到时，仍保留未知状态，不进入这两个已经核实的分支。

</details>
