# /compact：长对话怎样压缩后继续工作

假设 Agent 正在修复一套导出脚本。它已经读过十几个文件，试过两个方案，工具输出里有几千行日志。当前只剩一个分页测试失败，但下一次请求仍要携带大量旧探索记录。用户输入 `/compact` 后，上下文用量下降了，Agent 继续工作。究竟是模型变小了、文件被压缩了，还是它忘掉了之前的任务？

上下文压缩（context compaction）主要发生在模型外的运行框架（harness）与服务接口层：把长期积累的输入历史转换成更短的摘要或压缩条目，保留必要消息，再把新的上下文换入后续请求。命令由客户端识别并发起压缩任务；模型可能参与生成摘要，但不是看到这个词就自动改变权重。它改变的是“下一轮模型能看到什么”。模型权重不因此更新，原代码文件不会因此缩成一个摘要，已经发生的业务操作也不会被撤销。

本课先修是 [上下文窗口](#/lesson/context-window)、[Agent 状态](#/lesson/agent-state) 与 [Agent Memory](#/lesson/agent-memory)。这里只编写机制说明，**没有执行当前会话的 /compact**。官方文档核验日期为 2026-09-28；Codex 源码固定在 `1b1835f751ebdc0cfc50b3fe55d4571dbb294563`，产品特定规则不推广成所有 harness 的行为。

## 压缩的是后续输入，不是全部任务状态

长任务至少包含三类信息。第一类是模型请求中的对话、工具输出和材料摘录；第二类是工作目录里的文件；第三类是外部系统中的订单、导出任务等业务状态。compaction 主要重构第一类。它可能更新 harness 保存的会话记录与压缩元数据，但不能把另外两类状态也当成已压缩、已回滚或重新开始。

例如日志写着“导出任务 J7 已提交，仍在处理”，压缩后即使原日志不再进入模型上下文，J7 仍存在。新上下文必须保留操作标识和状态范围，才能让 Agent 查询同一任务，而不是误以为从未提交。类似地，摘要中的“测试通过”若没有对应文件版本，后续改动就可能让这个结论过期。

一种常见的文本摘要流程是：收集要压缩的历史，发出专门的压缩请求；取得摘要，选择保留项并补入必要规则；用新列表替换活动上下文，然后处理下一轮问题。摘要可以由模型生成，选择和替换由 harness 管理。“客户端管理的压缩”不意味着一定在用户本机 GPU 上推理，也不保证旧转录在所有产品中采用相同保存方式。

Codex 固定源码的一条摘要路径就是构造压缩 Prompt，生成 `summary_text`，调用 `build_compacted_history` 与 `replace_compacted_history`，然后重新计算 token 用量。它提供了具体实现证据，但同一产品还有其他压缩路径。[固定源码：压缩请求与历史替换](https://github.com/openai/codex/blob/1b1835f751ebdc0cfc50b3fe55d4571dbb294563/codex-rs/core/src/compact.rs#L268-L401)

## 一笔 token 预算怎样算

下面使用人为设定的整数，**不是实际模型窗口或 tokenizer 测量值**。假设模型窗口为 32000 tokens，下一次输出预留 4000 tokens。当前上下文由以下部分组成：

| 内容 | 假设 token 数 | 用途 |
| --- | ---: | --- |
| 规则、任务约束和必要工具定义 | 3000 | 决定允许做什么及如何调用 |
| 较早探索、旧文件摘录、重复日志 | 21000 | 包含有用信息，也有重复和失效内容 |
| 近期消息与当前失败测试详情 | 4000 | 直接影响下一步修复 |
| 当前输入合计 | 28000 | 加输出预留后恰好达到窗口 |

此时再读入 5000 tokens 的新结果，预算会变成 $28000+5000+4000=37000$，超过 32000。若将旧历史的 21000 tokens 转成 3000 tokens 的摘要，保留另外两部分，则新活动上下文为 $3000+3000+4000=10000$。加入新结果与输出预留后为 $10000+5000+4000=19000$，剩余 13000 tokens 余量。

这里节省的 18000 tokens 来自旧历史表示变短，没有让模型窗口扩容。表中 3000 tokens 的摘要预算也不是下面短示例的实际 token 数。即使输入更短，后续质量也可能下降，因为压缩选择了信息，无法保证所有细节都保留。

压缩本身还需要预算。假设专门的压缩请求需要原输入 28000、额外指令 1000、摘要输出预留 3000，已经用到 32000。如果先塞入新的 5000 再尝试压缩，可能连压缩请求都放不下。OpenAI 的独立 compact endpoint 明确要求送入的窗口仍须符合模型容量；Codex 所读摘要路径在压缩时遇到超窗，会移除最旧历史项后重试。这进一步说明应留出空间，而不是等到全部塞满才相信压缩能无损补救。[Compaction 指南](https://developers.openai.com/api/docs/guides/compaction)、[固定源码：超窗重试](https://github.com/openai/codex/blob/1b1835f751ebdc0cfc50b3fe55d4571dbb294563/codex-rs/core/src/compact.rs#L268-L401)

## 摘要需要交代什么，才能继续原任务

仍以导出脚本为例。假设用户允许修改本地脚本并运行测试，也允许发起一次测试环境导出，要求保留 CSV 字段顺序，不改生产配置。压缩前的相关历史分散在不同位置：

```text
较早任务：修复 export.py 的分页遗漏，保持现有 CSV 字段顺序。
读取材料：API 文档 v2；page_size 最大 1000，但仍需跟随 next_cursor。
方案一：只提高 page_size；已放弃，因为超过一页仍会漏数据。
当前文件：C:/demo/export/src/export.py，工作副本标记 demo-v3。
验证：demo-v3 上本地 19 个用例中 18 个通过，游标重复用例失败。
测试导出：操作标识 op-84，服务返回任务 J7，最后状态 processing。
最近要求：先修游标终止逻辑，再查询 J7；不要重复提交导出。
未知：J7 尚未返回最终文件，不能确认导出条数。
```

这些路径、版本标记和业务 ID 都是假设。压缩后的教学摘要可以组织为：

```text
目标：修复分页遗漏并核验测试导出结果。
约束：保留 CSV 字段顺序；只改本地脚本；不改生产配置；不重复提交导出。
当前依据：API 文档 v2。1000 是每页上限，必须处理 next_cursor。
当前文件：C:/demo/export/src/export.py，工作副本 demo-v3。
已做：放弃仅增大 page_size 的方案；demo-v3 的本地测试 18/19 通过。
失败：游标重复用例尚未通过；修复后需重跑相关测试。
外部状态：op-84 对应 J7；最后观察为 processing，不能视为已完成。
待办：检查重复游标终止条件；验证修改；查询 J7；核对最终条数。
未知：最终导出文件与条数未确认。操作结果以服务查询为准。
```

下一次请求由 harness 组织规则、摘要、保留的近期材料及新输入。若模型读到“继续”，它能先定位 demo-v3 的具体失败，修复后更新验证记录，并用 J7 查询状态。它不需要重演所有旧搜索，也没有理由重新提交 op-84。

这份摘要展示的是保留信息的设计要求，并非 Codex 或 Claude Code 的逐字模板。规则也不应该只靠摘要维持：harness 需要按自己的指令层级重新提供有效约束，摘要不能把工具输出中的命令提升成用户授权。对精确错误文本、代码行或政策例外，摘要最好留下稳定定位，必要时重新读取原材料。

## Codex CLI 的手动与自动压缩

Codex CLI 官方命令表把 `/compact` 描述为缩短可见对话、释放上下文空间。手动命令表示用户主动要求进行一次 compaction；自动压缩则由 harness 的预算策略触发。官方配置列有 `model_auto_compact_token_limit`，未设置时使用模型默认信息；示例数值不是所有模型统一阈值。[CLI slash commands](https://developers.openai.com/codex/cli/slash-commands)、[配置示例](https://developers.openai.com/codex/config-sample)

固定源码中，手动 compact task 先检查 TokenBudget feature 分支；否则依据 provider 的 remote compaction capability 选择 Remote V2，或在不支持时使用摘要 Prompt 路径。因此不能说“每次 CLI /compact 都生成一段公开纯文本”。手动与自动入口也不意味着一定选择不同表示；remote V2 源码同样存在自动调用入口。[固定源码：任务分派](https://github.com/openai/codex/blob/1b1835f751ebdc0cfc50b3fe55d4571dbb294563/codex-rs/core/src/tasks/compact.rs#L28-L66)、[remote 自动入口](https://github.com/openai/codex/blob/1b1835f751ebdc0cfc50b3fe55d4571dbb294563/codex-rs/core/src/compact_remote_v2.rs#L81-L115)

文本摘要分支的 `build_compacted_history_with_limit` 从较新的用户消息开始按预算选择，再附上摘要；超预算内容有文本截短与不完整标记处理。这个细节只能说明该函数在此提交下怎样保留内容，不能推广成“所有产品永远保留最近若干轮”或“每条用户规则必定无损”。版本、provider 和功能配置变化，都可能改变策略。[固定源码：保留项构造](https://github.com/openai/codex/blob/1b1835f751ebdc0cfc50b3fe55d4571dbb294563/codex-rs/core/src/compact.rs#L662-L739)

## Responses compact 返回的不一定是可读摘要

OpenAI Responses API 的独立 `/responses/compact` 接收当前窗口，返回一个新的压缩窗口，其中包含不透明的加密 compaction item，也可能包含保留的其他条目。官方要求将该返回窗口作为后续输入使用，不要自行只挑一段看得懂的文字，或把独立端点返回结果再随意删改。它不是公开保证可解码的自然语言摘要，更不能当成可以读出模型内部推理的接口。[Responses Compaction](https://developers.openai.com/api/docs/guides/compaction)

另一种方式是在普通 Responses 请求的 `context_management` 中设置 `compact_threshold`。达到阈值后由服务端在同一响应流程中执行压缩，流中包含 compaction item，无需另发独立 compact 请求。客户端自行累计 input/output 与使用 `previous_response_id` 的链式方式，续接规则也不同；尤其不能把一种模式的裁剪建议套给另一种。

两种 API 模式和 CLI 命令解决相近的容量问题，但抽象层不同：API 返回可继续请求的条目，CLI harness 决定何时调用、如何管理会话和显示状态。因此前面的可读摘要仅是教学模型，不能替代不透明条目的真实格式。

## 与其他“压缩”和 memory 的区别

| 机制 | 主要改变什么 | 与 compaction 的边界 |
| --- | --- | --- |
| KV cache | 保存已经计算的注意力键值表示，减少重复计算 | 不是把历史语义总结成新消息 |
| 数值量化 | 用较低精度表示权重或缓存等数值 | 不是缩写任务目标和工具记录 |
| 直接截断 | 按长度或规则删除输入的一部分 | 不必生成能继续任务的摘要，可能直接丢信息 |
| 长期 memory | 选择需要跨轮或跨任务保存、检索的信息 | 生命周期和写入规则独立，不等于当前窗口摘要 |
| Context compaction | 重构后续请求使用的历史表示 | 可以结合保留、摘要与截断，但不自动持久记住一切 |

Claude Code 也把自己定义为管理工具、上下文与执行环境的 harness。它的命令文档支持 `/compact [instructions]`，可给摘要指定关注方向；这只证明其公开入口与功能，不说明它采用与 Codex 相同的内部保留规则、预算或加密表示。[Claude Code 架构](https://code.claude.com/docs/en/how-claude-code-works)、[Commands](https://code.claude.com/docs/en/commands)

持久规则文件与原材料的存在可以帮助恢复上下文，但文件存在不等于下一次请求已经读过。摘要若写“按之前约定处理”，却没保留约定或位置，后续模型仍可能猜错。需要精确内容时重新读取，确认版本没有变化；重新读入又会消耗 token，应只取任务所需范围。

## 什么时候压缩，怎样检查没有改变任务含义

适合压缩的时机是一个阶段已经形成稳定结论、旧探索占据大量输入，而后续仍需继续同一目标时。压缩要保留尚未完成的动作和最新验证，而不是只保留漂亮的结论。测试只在 demo-v3 上通过，就不能省略版本变成“测试全部通过”；状态 processing 也不能省成“导出完成”。

反复压缩可能让“摘要的摘要”进一步丢失限定，旧推断又可能逐渐被写成事实。可以用检查问题验证摘要：目标是否改变，禁止事项是否仍在，原文件定位是否可用，已做与待办是否分开，外部操作 ID 和未知状态是否保留。关键证据有歧义时回到原始文件、测试记录或业务系统；不能用压缩器的确定语气覆盖来源。

如果任务范围已经换了，另起会话并提供明确交接可能更合适；若必须继续当前任务，compaction 提供的是新的上下文预算，而不是免除复核的保证。其成本包括额外生成、等待、可能重读资料，以及有损表示的风险，不能只看 token 数下降。

**一分钟回答：/compact 究竟做了什么？**

它通常由模型外的 harness 或服务重构当前任务的后续上下文，把长历史变成较短摘要或压缩条目，并保留必要消息和有效规则。下一轮使用新表示，所以能释放窗口，但模型权重、原代码和外部业务状态不会因此重置。摘要应保存目标、约束、文件版本、验证、待办和操作 ID，缺失时重新查原证据。具体产品不同：Codex CLI 有手动、自动及多种实现路径，Responses compact 返回不透明加密条目，不能一律称作纯文字总结。

**追问一：压缩后为什么还可能重复做事？**

因为摘要可能漏掉已执行动作或操作 ID。外部副作用仍存在，所以必须保留“做过什么、最后确认到什么状态”，恢复时核对原任务而非重新提交。compaction 是上下文管理，不能替代业务幂等和状态存储。

**追问二：为什么不等窗口满了再压缩？**

压缩请求自己也需要输入和生成空间。独立 compact 的输入仍须符合窗口；某些实现超窗时先删除旧项再重试，可能进一步丢信息。应该在大结果进入前预留预算，而不是假定满窗口能无限无损压缩。

**追问三：能否把 encrypted compaction item 解成隐藏思维？**

官方把它定义为不透明、非供人阅读的续接条目，没有承诺可解码的文本结构。应用应按接口契约传递，不能把它当作获取内部推理或代替业务记录的接口。

## 练习：预算够了，摘要就合格了吗

沿用 32000 窗口的例子，压缩后上下文是 10000 tokens。下一步预计读取 16000 tokens，输出仍预留 4000。新摘要只写“脚本基本修好，导出已提交”。请判断预算是否容纳得下，以及摘要至少缺哪些恢复信息。

<details>
<summary>参考思路</summary>

预算为 $10000+16000+4000=30000$，在此假设下剩 2000 tokens，但尚须考虑是否有未计入的请求开销。容量够不说明语义足够。摘要遗漏字段顺序和生产禁改约束、demo-v3 文件定位、18/19 测试及失败用例、J7 与 op-84、processing 观察和不得重复提交要求。

应恢复这些信息，必要时重读原测试与业务状态。若新读入 16000 tokens 又大多是重复日志，应先缩小读取范围，而不是不断压缩同一批无关内容。答案只说明教学预算，没有对当前会话执行任何压缩。
