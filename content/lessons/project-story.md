# 项目面试：怎样说清自己做了什么

“我主导了一个企业 Agent 项目，结合 RAG 和工具调用，大幅提升了效率。”这句话包含技术名词、责任和结果，却没有提供可追问的事实：谁遇到了什么问题，候选人具体改了什么，为什么采用这个架构，所谓提升在哪个范围成立。面试官继续问两句，讲述者就可能从“我主导”退回到“团队做了很多”。

项目面试需要把真实工作组织成别人能够理解和核验的说明。Microsoft Careers 的官方建议强调，用与岗位有关的具体经历说明能力，也允许讨论自己会怎样处理某项任务；招聘行为准则要求如实表达技能与经验。因此，真实经历和假设方案都可以有价值，但必须明确区分。[Microsoft：Interview tips](https://careers.microsoft.com/v2/global/en/hiring-tips/interview-tips.html)、[How we hire](https://careers.microsoft.com/v2/global/en/hiring-tips.html)

本篇给出一个完全虚构的政策咨询项目，用它展示如何把笼统表述改成具体叙述。所有角色、问题、行动和数字都是教学假设，不代表 Nathan 或任何真实人员做过这些工作。阅读时关注组织方法，准备自己的回答时只填写能够确认的事实。

## STAR 是信息顺序，不是四段固定台词

STAR 分别是 Situation（背景）、Task（任务或职责）、Action（行动）和 Result（结果）。它帮助听者先理解问题，再判断行动是否合理。背景交代为什么需要做，职责说明你被要求完成哪部分，行动解释你怎样推进，结果说明最终发生了什么。四项不需要各占相同时间，也不必机械地说“现在进入 Action”。

最容易混淆的是 Task。项目整体目标可能是减少员工咨询与资料退回，你本人的职责却只是建立评估集、实现版本过滤，或协调制度确认。把整体目标直接写成“我负责端到端落地”，会掩盖真实贡献。相反，明确说“我负责检索链路与评估，不负责审批接口”，反而让听者知道接下来应该在哪些技术细节上追问。

Action 也不能只是技术清单。“用了向量库、重排序和多 Agent”没有说明它们为什么必要。更有效的表述是某个问题触发了一项选择，你比较过什么方案，实际决定是什么，付出什么代价。架构图只应服务这条因果关系；如果一个组件没有参与你要说明的决策，可以暂时不讲。

Result 则需要和前面的任务对应。完成了评估集，不等于提高了系统准确率；离线问答更好，不等于员工办理更快；成功创建申请，也不等于申请已经获批。先区分结果类型，才能决定哪些证据足以支持它。[Agent 评估](#/lesson/agent-metrics) 中的样本、分母和范围，在项目叙述里同样适用。

## 把一个虚构项目讲到能够追问

假设一个团队正在开发员工政策咨询助手。试用时发现，它经常引用过期制度，也会把表格里的员工类别和额度接错。项目暂时只提供政策解释和申请材料清单，不负责提交申请。虚构候选人负责检索链路与离线评估，另一位工程师维护文档解析，业务同事确认政策适用范围。团队采用现有身份和文档服务，没有重新建设这些基础系统。

把这个背景讲出来以后，原来那句“大幅提升效率”就可以改写为一段有边界的开场。下面的第一人称只属于虚构候选人，不能直接冒用为自己的经历：

> 在一个员工政策咨询原型中，我负责检索链路和离线评估。试用暴露了旧制度被引用、表格条件对应错误两类问题。我把它们拆成不同故障，先补齐版本筛选，再与负责解析的同事修复表格关联。项目范围是给出带依据的政策解释与材料清单，当时还没有接入申请提交。

这段开场没有把所有背景一次说完，却明确了问题、职责和阶段。面试官问“你具体怎么发现原因”，候选人可以继续说明一次诊断：固定同一批问题，查看进入模型的检索片段，而不是只看最终回答。某个错误答案确实引用了第 2 版制度，索引中也有第 3 版；但查询没有按生效状态过滤。另一个问题检索到的版本正确，文本却已经把两行表格拼错。两种错误发生在不同位置，不能统一归因于模型推理不足。

个人行动随之变得具体。候选人亲自修改检索条件，保留文档版本与生效状态，并在自动检查中加入“旧版不能进入当前答案候选”的用例；表格结构问题则由解析工程师实现修复，候选人提供最小失败样本和回归问题。说“我定位并推动修复”与说“我编写解析器”不同，前者如果符合事实就是完整贡献，不需要把协作方的实现占为己有。

接着解释架构取舍。团队比较了“让一个 Agent 自由检索、多轮判断政策”与“固定检索当前制度、检查必要字段、生成带引用回答”的流程。由于第一阶段问题类型集中、主要数据源明确，候选人建议先保留固定流程，减少无法解释的重复查询；只有证据缺失时补问或转交。这个选择牺牲了一部分开放探索能力，换来更容易复现和验收的路径。这里需要说清当时约束，而不是事后声称某一种架构永远正确。

如果面试官问“为什么不先换更强的模型”，回答可以落到证据：“我们观察到错误片段在进入模型前就已经过期或错位。换模型可能改善部分输出，但不能可靠恢复被丢失的表头关系，所以先修复上游，再判断是否仍需要升级模型。”这表达了可检验的判断，不依赖术语数量。需求边界如何决定架构，可接续 [业务抽象](#/lesson/business-scope)。

## 失败复盘要解释发生了什么变化

继续这个虚构项目。第一轮修复只按“上传时间最新”筛选政策，结果一份后来补传的旧文件覆盖了真正生效的新版本。候选人最初把文件时间误当成政策时间，因此自己的修复仍有漏洞。一个可信的失败复盘应承认这个判断，而不是把故事改写成“外部数据不规范，我完美处理了”。

后续行动是把上传时间、文档版本和生效日期拆开。候选人与业务负责人明确哪个字段表示当前适用，工程侧增加显式状态与冲突出口，再把“新上传的旧版文件”纳入回归集。这个变化可被代码、问题记录和测试样本支持。复盘的学习点是“发现并修正了一个错误的数据契约”，而不是泛泛地说以后加强沟通。

还要说明失败是否已经解决到位。假设修复后该用例通过，但其他政策的历史数据仍在整理，就应说“已修复并覆盖这一类已知案例，历史库清理尚未完成”。不能把局部回归通过扩成“彻底解决所有时效问题”。如果后来证明思路不适用，讲清停止或回退的依据也属于结果，不要求每个项目都以全面成功收尾。

面试里的追问通常在寻找你的判断依据和可迁移经验。可迁移的不是“以后永远加一个字段”，而是先核对业务含义与系统字段是否对应，再设计过滤和异常行为。换到另一类文档，仍可以使用这种判断方法，而不会机械照搬政策版本规则。

## 数字要说明口径，没数字也能讲清事实

假设团队在一个冻结的 80 题测试集上比较修复前后的系统，输入文档快照和评分标准一致。旧流程有 56 题合格，新流程有 64 题合格。手算可得 $56 / 80 = 70\%$、$64 / 80 = 80\%$，提高的是 10 个百分点。若说相对提升，则是新增的 8 题除以原先 56 题，约为 14.3%。不能把这两种口径混成“提升了 10%”而不解释。

这些数字仍然只是教学假设。就算真实项目有同样结果，也要继续说明测试集如何构成、哪些题用于开发、哪些保留作评估，以及新流程是否修好旧题却弄错其他题。如果反复根据同一组题调参，它就越来越像开发集，不能继续宣传成完全独立的泛化证明。

本例的提升发生在版本过滤和表格修复一起完成之后。因此候选人可以说团队新流程在相同评估集上提高了 10 个百分点，不能说全部提升都由自己那一项过滤修改造成。要拆出各项效果，需要保持其他条件不变的对照。也没有线上员工耗时数据，所以不能顺势声称节省了某个百分比的人力。对因果关系留出这条边界，往往比一个更大的数字更有说服力。

准备材料时，可以用一张小表帮助自己检查证据，而不是把它全文背给面试官：

| 要说的主张 | 能支持它的材料 | 不能顺带推断的结果 |
| --- | --- | --- |
| 我实现了版本过滤 | 设计记录、本人修改与评审、回归用例 | 全部问答提升都由我造成 |
| 团队离线合格率提高 | 同口径输入、评分表、前后结果 | 线上办理速度或收入已改善 |
| 修复了旧版补传问题 | 原失败样本与修复后检查 | 所有文档时效错误已消失 |
| 已进入试用阶段 | 可核实的发布范围与验收记录 | 已全面上线或被所有用户采用 |

没有量化数据时，应把能够确认的结果说具体。“当时没有完整埋点，因此我不能给出整体效率提升。能够确认的是，交付了可重复运行的评估脚本和一组已复现的失败案例，团队据此接受了版本字段与过滤规则的修改；线上收益尚未验证。”这段话只有在这些交付和接受确实发生时才能使用，但它展示了不依赖编造比例的表达方式。

定性证据也要有来源。“用户觉得不错”比较模糊，“评审指出引用缺少版本，修订后该项验收通过”更容易核对。实在没有正式验收，就说交付到哪一步、观察到了什么，不把自己的满意写成用户接受。结果未达预期时，说明原因判断、残留风险和下一步验证，比省略 Result 更完整。

涉及内部项目时，可以脱敏描述机制、职责和量级，保留不能公开的细节。保密并不要求发明替代数字；无法披露精确值时说明采用范围或定性结果，并确保这种表达仍符合实际材料。若使用 AI 辅助整理，应核对每个动词、数字和完成状态。Microsoft 的候选人准则鼓励负责任地用于准备，同时要求表达真实能力；不能把整理出的流畅故事自动当成已经发生的经历。[Microsoft：Candidate Code of Conduct](https://careers.microsoft.com/v2/global/en/hiring-tips.html)

一份可用的项目回答通常准备两个层次：短版本交代问题、本人责任、关键选择和证据边界；追问时再展开失败样本、数据流和取舍。准备不是把每个问题的台词背完，而是确保这些细节彼此一致。若你只能讲结果，却解释不了输入、修改和限制，应先回到真实材料补齐理解。

<summary>面试怎么回答</summary>

**一分钟回答：** 我会用 STAR 组织真实项目，先说明业务问题和项目范围，再划清本人职责与协作方职责，重点讲一次有依据的技术选择和一次失败修正。结果给出可核实的交付或指标，并说明样本、基线和未验证部分。比如离线问答改善不能直接说成线上效率提升，团队整体结果也不能全部归因于个人。没有完整量化数据时，就讲确实交付了什么、谁验收、哪些失败得到复现和修复，明确收益还没有测量。

**追问一：面试官问“你到底亲手做了什么”，怎样回答？** 用具体动作和交付对象回答，例如定位某个失败样本、修改某个过滤规则、设计评估集或协调制度确认。区分“我提出并验证”“我实现”“他人实现、我提供问题与验收”。可参考设计和评审记录，但不要用拥有提交权限代替对全部实现的理解。

**追问二：为什么不用一个漂亮的估算填补缺失指标？** 估算可以在假设明确、用途合适时讨论，但不能冒充测量结果。若没有线上基线，就说没有，再提供真实可核实的交付与观察，并说明怎样补做评估。为了让故事完整而补一个百分比，会让后续样本量、口径和归因的追问全部失去依据。

练习：选择自己实际参与的一项工作，写一个不超过两分钟的项目回答。只填写能够确认的信息：一个具体问题；本人负责与未负责的部分；一项实际选择及备选方案；一个失败或限制；一个结果及证据。没有指标的地方直接标记“未测量”，不要套用本篇的项目、动作或数字。

<summary>参考思路</summary>

先列事实再成文。为每个“我完成了”找到交付物或记录，为每个“提高了”找到可比基线，为每个“上线了”确认范围与状态。把无法确认的断言删掉或改成计划、推测、待验证。若只有协作贡献，说明你提供了什么输入、改变了哪项决定，不必把自己改写成全栈负责人。最后请一个不了解项目的人追问两次，检查是否能解释关键动作与结果边界；不知道的部分如实回答，不靠继续扩写故事补洞。

</details>
