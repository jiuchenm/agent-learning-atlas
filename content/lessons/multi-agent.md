# 多 Agent：什么时候分工真的划算

**多 Agent 系统**是应用把一个任务交给多个能各自决定下一步、调用工具并保留局部状态的 Agent，再安排它们交换结果和结束工作的方式。它适合有几条相对独立的调查线、单个 Agent 难以同时覆盖的任务；每增加一位参与者，应用也多一份委派、通信、权限和核对工作。

假设应用通过导出 API v2 查询订单，已知有 1500 条符合条件，界面却只显示 100 条。如果读取一段已知调用代码就能发现“只请求第一页”，**一个 Agent 足够**。如果处理步骤已经确定，程序按“读配置→查日志→对照分页规则”依次执行，**固定 Workflow 也足够**。只有在服务端契约、SDK 行为和运行日志都可能藏着不同线索，而且能独立核查时，才值得考虑多个 Agent 并行调查。本文沿这个完全虚构的案例走完分工、消息、共享状态、停止和合并；接口、日志、数字和耗时都是教学设定，没有查询真实客户系统。

这里的 Agent 是应用中的工作单元：收到任务后，它能依据结果选择接下来查什么，基础循环见 [Agent 基础](#/lesson/agent-basics)。固定 Workflow 的下一步由程序预先规定；单 Agent 也能连续调用多个工具。多 Agent 新增的问题是：**谁决定让谁工作，工作结果怎样成为下一步的依据？**如果三个单元都收到同一句“查为什么只有 100 条”，它们可能都读旧版 SDK 的同一示例，交来三份一致而错误的报告。三份答案不会自动弥补同一次遗漏。具体计划与复核方法可接着读 [Planning](#/lesson/planning) 和 [Reflection](#/lesson/reflection)。

## 先判断哪些工作可以独立进行

一个部分能并行，不只是因为它有不同的标题。需要看它的输入是否已经确定、输出是否有清楚边界，以及是否会依赖其他工作单元正在修改的状态。

在导出排查中，读取指定版本的 API 文档、检查固定版本 SDK 的默认参数、分析同一份脱敏请求记录可以同时进行。三者共享接口版本和问题定义，但不必等待彼此才能开始。反过来，“根据新发现设计修复”“修改实现”“验证修复”存在强依赖。若三个 Agent 各自猜一个修复并同时修改相同文件，最终要付出冲突处理和重新验证的成本。

给三个相同上下文分别冠以“专家”“审查者”“反方”名称，可能仍得到高度相关的判断。**真正的独立性来自不同证据路径、明确检查条件或分开的执行范围。**独立探索有助于发现遗漏，但最终仍需要证据来判断，不能按支持某结论的 Agent 数量投票代替核验。

## 主管怎样分工并收回证据

用户的假设输入是：“应用通过导出 API v2 获取订单，已知有 1500 条符合筛选条件，但界面只显示 100 条。请给出原因和可审查的修复建议，先不要改配置。”主管先固定调查范围：使用 SDK 3.2，查询日期范围与请求记录已经提供，只读现有文档、代码和脱敏日志，不产生新的订单或导出任务。

主管把任务消息分别发给三个工作单元：A 查 v2 服务端分页契约，B 查 SDK 3.2 和当前调用代码，C 核对请求响应与界面聚合记录。三人各自调查，再把结论、来源、范围和未确认项作为消息交回主管；只有主管负责合成最终答复。给 B 的分工合同可以写成下面的**教学用 JSON 示例**，它并非某个框架的通用 API：

```json
{
  "task_id": "export-sdk-check",
  "objective": "确认 SDK 3.2 默认分页值及调用方是否遍历后续页",
  "inputs": ["固定版本SDK源码", "当前调用片段"],
  "allowed_actions": ["读取", "本地静态分析"],
  "excluded_actions": ["修改代码", "更改配置", "发送真实导出请求"],
  "output_fields": ["claim", "source", "scope", "unknowns"],
  "stop_condition": "给出相关参数与分页代码证据，或说明未找到",
  "budget": "最多8分钟；超时返回已确认事实与缺口"
}
```

合同让执行者知道要交付什么、哪里不能越界、如何判断完成。A 不必重复检查 SDK，C 也不能把日志里的数值直接推广成协议限制。Anthropic 在其多 Agent 研究系统的工程说明中强调委派时明确目标、输出格式、工具与来源边界，以减少重复调查或遗漏；上述字段是本文为讲解而设计的。[Anthropic：How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)

假设三个工作单元返回以下消息。来源代号只表示本课给定材料，不是虚构的真实链接。

| 单元 | 返回结论 | 证据与范围 | 未确认项 |
| --- | --- | --- | --- |
| A | 单次请求最多可取 1000 条 | DOC-v2 第 4 节；请求字段为 page_size | 不知道调用方实际传了多少 |
| B | SDK 默认每页 100 条，当前代码只调用一次 | SDK-3.2 默认值与 APP-12 调用片段 | 不知道运行日志是否与代码一致 |
| C | 记录中请求 page_size=100，响应100条，并有 next_cursor；UI只接收这一批 | LOG-7 与 UI-9，属于指定排查时间窗 | 没有验证修改后的行为 |

主管起初可能把 A 与 B 当成冲突：“一个说 1000，一个说 100，谁错了？”比较**对象与范围**后可以发现，1000 是服务端允许的上限，100 是 SDK 默认值，二者可以同时成立。C 再补上运行证据，确认本次请求确实采用 100，并且还有下一页游标 `next_cursor`。

因此，人工推导的合成结果是：“本次只显示 100 条，与调用方只获取第一页一致；服务端 1000 条上限不能解释为何完全没有后续页。建议按 next_cursor 遍历并聚合所有页面，保持原筛选条件。提高 page_size 可减少请求次数，但不能代替分页循环。修复尚未执行。”1500 条即使每页取 1000 条，也仍至少需要两页，单纯调大上限不会完整解决问题。

主管不能只拼接三份报告，还要核对对象、版本、时间与概念范围，再将有限的事实合成可检验结论。如果 A 引用的是 v1、B 检查的是另一版 SDK，应退回对应部分补证据。**三位 Agent 意见一致也不等于独立核验**：它们可能都读了同一份过期示例。

## 谁维护共享状态，谁决定停止

各工作单元需要同一份任务范围，但不必接收完整历史和所有凭据。上述例子可以共享一个**固定调查快照**：接口 v2、SDK 3.2、查询条件、脱敏记录 ID。每个单元只写自己的结果文件，主管读取并更新总报告。这样既减少互相覆盖，也让失败后可以单独重做某个部分。

若所有单元共同修改“当前结论”字段，后写入者可能覆盖更早的限定，主管也很难判断哪条证据支持哪次修改。应明确字段或文件的所有者，对变更保留版本，合并时检查冲突。任务状态还要区分执行中、已完成、失败和取消；**没有返回结果表示未知**，不能被当成“没有发现问题”。B 的合同写明最多 8 分钟；到期仍没找到调用代码，就返回已查范围和缺口，主管不能把它记为“确认没有分页代码”。

本例的调度顺序是：主管派发 A、B、C，等待各自结果或预算到期，再核对证据，最后交付带限定的诊断。如果新证据引出一个独立问题，可以再派一条有边界的调查；重复问同一来源则不补足证据。**停止条件需要覆盖成功、超时、证据不足和取消**，避免工作单元反复互相委派。这里描述的是应用应设计的行为，不是多 Agent 框架自动保证的行为。

权限不会因为主管能够委派就自动扩大。子 Agent 应使用任务所需的最小工具范围，工具服务仍需验证实际身份和授权。只读日志单元不需要生产写入凭据；拥有敏感日志访问权的单元，也不能把未经处理的原文发送到权限更宽的共享区。共享记忆的长期保留规则同样需要明确，不能把一次排查的猜测写成所有任务都默认接受的知识，相关区别见 [Agent Memory](#/lesson/agent-memory)。

交接时还应带上当前状态和未决事项。例如把排查交给修复单元时，需要传递已确认原因、来源、待执行建议、用户授权边界和尚未验证的假设。接收者不能只拿到“问题已解决”这类摘要，因为本例实际上只完成了诊断。

## 四种协作形式，控制权怎样移动

本例同时使用了“主管与工作单元”和“并行分工”：主管决定查什么，A、B、C 在同一份固定输入上同时取证。相邻的两种形式是路由与交接：

| 方式 | 核心安排 | 放到导出案例会怎样用 |
| --- | --- | --- |
| 路由（routing） | 判断输入类别，交给一位合适的执行者 | 已知故障只在 SDK 调用，直接交给 B |
| 并行分工（parallelization） | 多个独立部分同时执行，再汇总 | A、B、C 同时核查三类证据 |
| 主管与工作单元（supervisor / workers） | 主管根据进展委派、收回结果并决定下一步 | 发现 v1/v2 混用后，追加版本核验 |
| 交接（handoff） | 当前阶段把控制权移交给下一位 | 诊断完成并取得授权后，转给修复单元 |

路由可以只运行一个 Agent；交接是阶段顺序，未必并行。实际应用可以组合方式，但必须说明**谁持有最终决定权**。Anthropic 的架构文章讨论了路由、并行和 orchestrator-workers，其中主管可动态分解并汇总子任务；它也建议从能满足目标的简单方案开始，根据实际收益增加复杂性。[Anthropic：Building effective agents](https://www.anthropic.com/research/building-effective-agents) 本文的交接合同与共享状态约束是工程解释，不能当作该文规定的统一接口。

多 Agent 与混合专家模型（Mixture of Experts，MoE）处在不同层次。前者是应用层的任务、工具和状态协作；MoE 是模型内部选择部分专家网络参与计算的结构。运行三个使用同一模型的 Agent 不会把模型变成 MoE，模型内部有多个专家也不意味着它已经安排好了研究分工。

## 并行缩短等待，却可能增加总成本

假设 A、B、C 分别需要 4、6、5 分钟，任务分发用 1 分钟，汇总用 2 分钟，且三者能够真正同时运行、没有共享限流。**顺序执行**耗时为 `1 + 4 + 6 + 5 + 2 = 18` 分钟；**并行执行**为 `1 + max(4, 6, 5) + 2 = 9` 分钟。这是手算的理想例子，不是实测加速。

如果三者竞争同一个限流接口，或主管需要反复澄清同一问题，实际时间会增加。并行也没有把三人的总工作量变成六分钟：每个 Agent 仍要读取上下文、调用模型、运行工具，主管还要阅读报告。把完整对话广播给每个单元，会重复支付输入 token；摘要过短又可能丢掉关键限定。通信内容应包含足够证据与稳定引用，同时避免无意义的进度往返。

错误还可能逐层累积。B 把默认值误称为上限，主管省略“只查了代码”的限定，最终报告再写成“服务不能导出更多记录”，一次局部误读便变成强结论。多个模型都重复它不构成独立证实。验收时应查看最终断言是否能回到来源，而不仅检查子任务是否全部显示完成。

Anthropic 在自己的内部研究评估中报告了多 Agent 的收益，也同时报告了更高 token 消耗，以及强依赖、需要大量共享上下文的任务不一定适合。这些是其特定系统与评估条件下的结果，不是任意任务增加 Agent 后都会变快、变准的保证。比较方案时应把模型、工具、总预算和任务集合记录清楚，不能把更多计算带来的收益全部归因于协作结构。[Anthropic：How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)

## 什么时候一个 Agent 更合适

如果只需要读取一段已知代码、解释一个明确错误，或者每一步都依赖上一轮刚产生的状态，单 Agent 往往能保留更连贯的上下文，省去任务分发和结果合并。步骤已经确定时，用程序写成固定 Workflow 更直接；有限的并行工具调用也可能已经足够，无须再创建多个独立执行循环。

如果任务确实需要多个独立来源、每条调查线较长、结果又能用小而明确的合同汇总，多 Agent 才有更清楚的价值。可以在同一批任务上比较单 Agent 与多 Agent 的最终正确性、覆盖范围、无依据断言、耗时、总 token 和人工返工。既看是否更快，也看为了核对冲突多花了多少工作。已确定的证据缺口应触发有针对性的追加调查，而非无止境地增加角色。

<summary>面试怎么回答</summary>

**一分钟回答：什么时候应该用多 Agent？**

多 Agent 是应用组织多个能各自调用工具、保留局部状态的 Agent 协作。任务有几条输入确定、可独立取证且足够复杂的调查线时，可以并行分工，再由主管按证据合成。委派消息要明确目标、来源、权限、输出与停止条件，共享状态要有写入所有者。简单任务、强依赖步骤或频繁改写同一状态时，单 Agent 或固定 Workflow 通常更省协调成本。选择方案应在相同任务和清楚预算下比较质量、延迟、token 与返工，而不是按角色数量判断。

**追问一：三个 Agent 都同意，为什么仍不能直接接受？**

它们可能共享同一来源或同一个错误前提。独立性需要来自不同证据和检查路径。应核对结论范围、原文和运行证据；投票数量不能替代事实支持。

**追问二：主管与交接有什么区别？**

主管通常保留最终控制权，把部分工作委派出去再收回汇总。交接把下一阶段控制权交给另一个执行单元，需要传递状态、已完成内容、授权和未决事项。它不一定有并行，也不意味着前一个阶段已经解决全部任务。

**追问三：共享一个文件最方便，为什么还要限制写入？**

并发写入可能互相覆盖或混合不同版本的结论。更稳妥的安排是单元各自提交结果，由一个明确的所有者合并，并保存冲突和证据。确实需要共同写入时，要有并发控制和版本检查，不能仅靠提示“请小心”。

## 练习：把一个错误拆分改好

主管把任务拆成：“A 改分页函数，B 改同一个函数提高 `page_size`，C 同时验证修复。”三者使用同一工作目录，尚未确认故障原因，也没有写入授权。请判断哪些工作存在依赖，怎样改成一个能审查的分工，并说明 C 何时可以准备验收、何时能实际验证修复。

<details>
<summary>参考思路</summary>

A 与 B 修改同一逻辑，存在写冲突，C 的输入还在变化。先让独立部分只读收集 API 契约、调用代码和日志，由主管确认原因并形成修复方案。获得修改授权后，指定一个写入所有者实现修复；若其他文件能独立修改，也要划定边界。

C 可以提前准备固定的验收条件，例如多页、空页、游标终止和聚合数量，但实际验证应针对明确的候选版本执行。所有者交付后，C 记录验证版本与结果，主管再决定是否完成。不要把“验证通过”套到之后被别人覆盖的代码上。

</details>
