# 多 Agent：什么时候分工真的划算

假设要排查一项数据导出为什么每次只返回 100 条。三个 Agent 同时查文档，看起来应该更快，最后却各自交来一份“接口最大支持 100 条”的报告。汇总后才发现，它们都看了旧版 SDK 的同一个示例，没有人检查服务端限制或实际请求。三份一致答案放大了同一次遗漏。

多 Agent 系统让多个能够使用工具、保留局部状态的执行单元协作。它可以扩大调查覆盖面、并行处理独立问题，也会增加委派、通信、权限和合并结果的工作。这节课以一个完整的假设排查为主线，判断这些新增工作是否值得；具体计划和反思机制分别见 [Planning](#/lesson/planning) 与 [Reflection](#/lesson/reflection)。文中的接口、限制、日志和耗时均为教学设定，没有查询真实客户系统。

## 多个执行单元如何协作

常见协作方式首先区别在控制权怎样流动。

| 方式 | 核心安排 | 适用条件 |
| --- | --- | --- |
| 路由（routing） | 判断输入类别，交给一个合适的执行单元 | 类别可以区分，后续工具或指令明显不同 |
| 并行分工（parallelization） | 多个相互独立的部分同时执行，再汇总 | 各部分可以在同一份固定输入上独立取得结果 |
| 主管与工作单元（supervisor / workers） | 主管根据进展委派、收回结果并决定下一步 | 子问题会随任务发现而变化 |
| 交接（handoff） | 当前执行单元把下一段工作的控制权移交给另一个 | 任务进入需要不同职责或工具的阶段 |

路由不要求所有 Agent 一起运行；交接也不等于并行。主管委派后通常还要负责合成最终结果，而交接强调当前阶段结束后由接收方继续推进。实际系统可以组合这些方式，但必须说明谁持有最终决定权，不能让每个 Agent 都认为自己应该无限派出更多工作。

Anthropic 的架构文章分别讨论路由、并行和 orchestrator-workers，其中后者由主管动态分解并汇总子任务。它还强调应从能满足目标的简单方案开始，根据实际收益增加复杂性。[Anthropic：Building effective agents](https://www.anthropic.com/research/building-effective-agents)

多 Agent 与混合专家模型（Mixture of Experts，MoE）处在不同层次。前者是应用层的任务、工具和状态协作；MoE 是模型内部选择部分专家网络参与计算的结构。运行三个使用同一模型的 Agent 不会把该模型变成 MoE，模型内部有多个专家也不意味着它已经安排好了研究分工。

## 先判断哪些工作可以独立进行

一个部分能并行，不只是因为它有不同的标题。需要看它的输入是否已经确定、输出是否有清楚边界，以及是否会依赖其他工作单元正在修改的状态。

在导出排查中，读取指定版本的 API 文档、检查固定版本 SDK 的默认参数、分析同一份脱敏请求记录可以同时进行。三者共享接口版本和问题定义，但不必等待彼此才能开始。反过来，“根据新发现设计修复”“修改实现”“验证修复”存在强依赖。若三个 Agent 各自猜一个修复并同时修改相同文件，最终要付出冲突处理和重新验证的成本。

多 Agent 也不等于多角色写作。给三个相同上下文分别冠以“专家”“审查者”“反方”名称，可能仍得到高度相关的判断。真正的独立性来自不同证据路径、明确检查条件或分开的执行范围，而不是名字数量。独立探索有助于发现遗漏，但最终仍需要证据来判断，不能按支持某结论的 Agent 数量投票代替核验。

## 一次排查怎样写出分工合同

用户的假设输入是：“应用通过导出 API v2 获取订单，已知有 1500 条符合筛选条件，但界面只显示 100 条。请给出原因和可审查的修复建议，先不要改配置。”主管先固定调查范围：使用 SDK 3.2，查询日期范围与请求记录已经提供，只读现有文档、代码和脱敏日志，不产生新的订单或导出任务。

接着委派三个互补部分：A 查 v2 服务端分页契约，B 查 SDK 3.2 和当前调用代码，C 核对请求响应与界面聚合记录。给 B 的分工合同可以写成：

```json
{
  "task_id": "export-sdk-check",
  "objective": "确认 SDK 3.2 默认分页值及调用方是否遍历后续页",
  "inputs": ["固定版本SDK源码", "当前调用片段"],
  "allowed_actions": ["读取", "本地静态分析"],
  "excluded_actions": ["修改代码", "更改配置", "发送真实导出请求"],
  "output_fields": ["claim", "source", "scope", "unknowns"],
  "stop_condition": "给出相关参数与分页代码证据，或说明未找到",
  "budget": "最多8分钟；超时返回已确认事实与缺口"
}
```

合同不需要写成冗长剧本，但应让执行者知道要交付什么、哪里不能越界、如何判断完成。A 不再重复检查 SDK，C 不把日志里的数值直接推广成协议限制。Anthropic 的研究系统文章明确指出，子任务需要目标、输出格式、工具与来源指引以及边界；否则容易重复调查或留下空白。[Anthropic：How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)

假设三个工作单元得到以下结果。来源代号只表示本课给定材料，不是虚构的真实链接。

| 单元 | 返回结论 | 证据与范围 | 未确认项 |
| --- | --- | --- | --- |
| A | 单次请求最多可取 1000 条 | DOC-v2 第 4 节；请求字段为 page_size | 不知道调用方实际传了多少 |
| B | SDK 默认每页 100 条，当前代码只调用一次 | SDK-3.2 默认值与 APP-12 调用片段 | 不知道运行日志是否与代码一致 |
| C | 记录中请求 page_size=100，响应100条，并有 next_cursor；UI只接收这一批 | LOG-7 与 UI-9，属于指定排查时间窗 | 没有验证修改后的行为 |

主管起初可能把 A 与 B 当成冲突：“一个说 1000，一个说 100，谁错了？”比较范围后可以发现，1000 是服务端允许的上限，100 是 SDK 默认值，二者可以同时成立。C 再补上运行证据，确认本次请求确实采用 100，并且还有下一页。

因此，人工推导的合成结果是：“本次只显示 100 条，与调用方只获取第一页一致；服务端 1000 条上限不能解释为何完全没有后续页。建议按 next_cursor 遍历并聚合所有页面，保持原筛选条件。提高 page_size 可减少请求次数，但不能代替分页循环。修复尚未执行。”1500 条即使每页取 1000 条，也仍至少需要两页，单纯调大上限不会完整解决问题。

这个过程说明主管的主要工作不是把三份报告拼接成一篇文章，而是核对对象、版本、时间与概念范围，将各自有限的事实合成可检验结论。如果 A 引用的是 v1、B 检查的是另一版 SDK，应退回对应部分补证据，不能用更流畅的措辞掩盖真实冲突。

## 共享状态要分清谁能写、谁能看

各工作单元需要同一份任务范围，但不必接收完整历史和所有凭据。上述例子可以共享一个固定调查快照：接口 v2、SDK 3.2、查询条件、脱敏记录 ID。每个单元只写自己的结果文件，主管读取并更新总报告。这样既减少互相覆盖，也让失败后可以单独恢复某个部分。

若所有单元共同修改“当前结论”字段，后写入者可能覆盖更早的限定，主管也很难判断哪条证据支持哪次修改。应明确字段或文件的所有者，对变更保留版本，合并时检查冲突。任务状态还要区分执行中、已完成、失败和取消；没有返回结果不能被当成“没有发现问题”。

权限不会因为主管能够委派就自动扩大。子 Agent 应使用任务所需的最小工具范围，工具服务仍需验证实际身份和授权。只读日志单元不需要生产写入凭据；拥有敏感日志访问权的单元，也不能把未经处理的原文发送到权限更宽的共享区。共享记忆的长期保留规则同样需要明确，不能把一次排查的猜测写成所有任务都默认接受的知识，相关区别见 [Agent Memory](#/lesson/agent-memory)。

交接时还应带上当前状态和未决事项。例如把排查交给修复单元时，需要传递已确认原因、来源、待执行建议、用户授权边界和尚未验证的假设。接收者不能只拿到“问题已解决”这类摘要，因为本例实际上只完成了诊断。

## 并行缩短等待，却可能增加总成本

假设 A、B、C 分别需要 4、6、5 分钟，任务分发用 1 分钟，汇总用 2 分钟，且三者能够真正同时运行、没有共享限流。顺序执行耗时为 1 加 4 加 6 加 5 加 2，共 18 分钟；并行耗时为 1 加最长的 6 加 2，共 9 分钟。这是手算的理想例子，不是实测加速。

如果三者竞争同一个限流接口，或主管需要反复澄清同一问题，实际时间会增加。并行也没有把三人的总工作量变成六分钟：每个 Agent 仍要读取上下文、调用模型、运行工具，主管还要阅读压缩报告。把完整对话广播给每个单元，会重复支付输入成本；摘要过短又可能丢掉关键限定。通信内容应包含足够证据与稳定引用，同时避免无意义的进度往返。

错误还可能逐层累积。B 把默认值误称为上限，主管省略“只查了代码”的限定，最终报告再写成“服务不能导出更多记录”，一次局部误读便变成强结论。多个模型都重复它不构成独立证实。验收时应查看最终断言是否能回到来源，而不仅检查子任务是否全部显示完成。

Anthropic 在自己的内部研究评估中报告了多 Agent 的收益，也同时报告了更高 token 消耗，以及强依赖、需要大量共享上下文的任务不一定适合。这些是其特定系统与评估条件下的结果，不是任意任务增加 Agent 后都会变快、变准的保证。比较方案时应把模型、工具、总预算和任务集合记录清楚，不能把更多计算带来的收益全部归因于协作结构。

## 什么时候一个 Agent 更合适

如果只需要读取一段已知代码、解释一个明确错误，或者每一步都依赖上一轮刚产生的状态，单 Agent 往往能保留更连贯的上下文，省去任务分发和结果合并。有限的并行工具调用也可能已经足够，无须再创建多个独立执行循环。

如果任务确实需要多个独立来源、每条调查线较长、结果又能用小而明确的合同汇总，多 Agent 才有更清楚的价值。可以在同一批任务上比较单 Agent 与多 Agent 的最终正确性、覆盖范围、无依据断言、耗时、总 token 和人工返工。既看是否更快，也看为了核对冲突多花了多少工作。已确定的证据缺口应触发有针对性的追加调查，而非无止境地增加角色。

<summary>面试怎么回答</summary>

**一分钟回答：什么时候应该用多 Agent？**

当任务可以拆成输入明确、相互独立的调查部分，而且各部分足够复杂，多 Agent 可以并行扩大覆盖面。主管需要明确目标、来源、权限、输出和停止条件，再按证据合并结果。强依赖任务、共享状态频繁变化或简单问题，单 Agent 通常更省协调成本。多 Agent 会增加上下文复制、工具调用和错误传播风险，不能按角色数量判断质量。应与单 Agent 在相同任务和记录清楚的预算下比较结果、延迟与成本。

**追问一：三个 Agent 都同意，为什么仍不能直接接受？**

它们可能共享同一来源或同一个错误前提。独立性需要来自不同证据和检查路径。应核对结论范围、原文和运行证据；投票数量不能替代事实支持。

**追问二：主管与交接有什么区别？**

主管通常保留最终控制权，把部分工作委派出去再收回汇总。交接把下一阶段控制权交给另一个执行单元，需要传递状态、已完成内容、授权和未决事项。它不一定有并行，也不意味着前一个阶段已经解决全部任务。

**追问三：共享一个文件最方便，为什么还要限制写入？**

并发写入可能互相覆盖或混合不同版本的结论。更稳妥的安排是单元各自提交结果，由一个明确的所有者合并，并保存冲突和证据。确实需要共同写入时，要有并发控制和版本检查，不能仅靠提示“请小心”。

## 练习：把一个错误拆分改好

主管把任务拆成：“A 改分页函数，B 改同一个函数提高 page_size，C 同时验证修复。”三者使用同一工作目录，尚未确认故障原因，也没有写入授权。请判断哪些工作存在依赖，怎样改成一个能审查的分工，并说明何时允许 C 开始验证。

<details>
<summary>参考思路</summary>

A 与 B 修改同一逻辑，存在写冲突，C 的输入还在变化。先让独立部分只读收集 API 契约、调用代码和日志，由主管确认原因并形成修复方案。获得修改授权后，指定一个写入所有者实现修复；若其他文件能独立修改，也要划定边界。

C 可以提前准备固定的验收条件，例如多页、空页、游标终止和聚合数量，但实际验证应针对明确的候选版本执行。所有者交付后，C 记录验证版本与结果，主管再决定是否完成。不要把“验证通过”套到之后被别人覆盖的代码上。
