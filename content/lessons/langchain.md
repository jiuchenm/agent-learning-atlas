# LangChain：框架替应用包住了哪些工作

假设已经做出一个订单助手：用户输入订单号，模型请求查询订单，程序访问业务接口，再把结果交给模型组织回答。第一版只接一家模型服务，代码不多。后来要支持另一家服务、记录每次工具调用、遇到超时返回统一错误，并限制一次任务的查询次数。业务本身没有大改，消息转换和运行控制却开始散落在各处。LangChain 主要试图整理的，就是模型周围这些反复出现的连接工作。

LangChain 是开发 LLM 应用的开源框架，不是一家新的模型服务。程序员用它提供的模型、消息、工具和 Agent 接口，把原本散在应用里的连接代码组织起来；真正查订单的函数和访问权限仍由自己的应用提供。[LangChain 官方概览](https://docs.langchain.com/oss/python/langchain/overview) 本篇看一次订单查询具体穿过哪些边界，再判断什么时候框架带来的统一接口值得额外依赖。

它不会替应用自动理解订单状态，也不会因为工具包了一层框架就获得访问订单的权限。读过 [Function Calling](#/lesson/function-calling) 和 [RAG](#/lesson/rag-basics) 后，更适合把 LangChain 看成一组可组合的接口与运行机制，再逐项判断是否值得引入。本文的订单、工具和返回结果均为教学假设，没有连接真实订单服务或运行模型 SDK。

## 统一接口究竟统一到哪里

在核验于 2026-09-28 的 Python 官方文档中，LangChain 以 create_agent 作为可配置的 Agent 入口，将模型、工具、提示与中间件组合起来。文档把围绕模型循环的运行机制称为 harness，包括提供上下文、安排工具和控制行为的部分。这里把它理解为“模型周围的运行代码”就够了，没必要因为一个新名称再发明一套业务层。[LangChain overview](https://docs.langchain.com/oss/python/langchain/overview)

以订单 O42 为例，模型收到用户问题后可能提出查询工具请求；运行代码把请求交给应用实现的函数，把结果写回消息，再决定是否继续问模型。LangChain 可以组织这条往返路径，harness 指的就是支撑这些往返的代码。只知道它是框架还不够，接下来要看模型请求、工具执行和最终答案在哪一步分别负责什么。

模型接口（model interface）把不同服务的调用适配到较一致的输入输出形式。应用可以围绕通用调用组织代码，由提供方适配包处理相应请求格式。这样更换提供方时，有机会少改一部分连接代码。但接口相似不代表能力相同：工具调用、结构化输出、流式事件、图片输入和特有参数仍可能不同。切换模型之后还需要验证真实任务，不能把“初始化成功”当成行为兼容。

消息（message）是传递上下文的基本单位。用户消息提供本次请求，模型消息可能包含普通文字或工具请求，工具消息携带某次调用的结果；消息还可以包含标识、用量等元数据。应用不必把所有响应都当成一段字符串再手工猜它的类型。LangChain 的消息文档提供统一表示，但也说明一些字段的实际行为随提供方变化。[LangChain：Messages](https://docs.langchain.com/oss/python/langchain/messages)

工具接口（tool interface）则描述一项可调用能力：名称、用途、输入结构和执行函数。框架可以从函数类型与说明组织工具定义，并把模型产生的请求分派给相应函数。应用仍要实现函数本身，决定查询哪个系统、怎样验证参数，以及返回哪些字段。把函数称为 tool，没有让数据库连接、身份授权或业务错误处理凭空出现。[LangChain：Tools](https://docs.langchain.com/oss/python/langchain/tools)

## 一次最小订单查询穿过哪些边界

假设用户已经登录应用，身份为 U7，询问：“订单 O42 到哪里了，预计何时送达？”应用授权本次只读查询，提供两个工具：读取当前用户可见的订单，读取该订单关联包裹的物流。身份 U7 来自应用的已验证会话，不让模型通过工具参数填写“我想查哪个用户的订单”。订单号可由模型从问题中提取，查询权限必须由业务代码检查。

这段 Python 风格伪代码表示责任划分，不是可以直接运行的 LangChain 示例；register_tool 和 build_agent 等名称也是本例自定义抽象。这样可以先看清框架包住了什么，再按实际锁定版本改写成 SDK 代码。


```python
# 教学伪代码：省略网络连接和具体框架类型，不可直接运行。
def read_order(order_id, trusted_context):
    order = order_service.read_visible_order(
        user_id=trusted_context.user_id,
        order_id=order_id,
    )
    return select_order_fields(order)

def read_shipment(order_id, trusted_context):
    order = order_service.read_visible_order(
        user_id=trusted_context.user_id,
        order_id=order_id,
    )
    if order.shipment_id is None:
        return {"status": "no_shipment", "order_status": order.status}
    return shipping_service.read(order.shipment_id)

agent = build_agent(
    model=provider_adapter,
    tools=[register_tool(read_order), register_tool(read_shipment)],
    instructions="只依据查询结果回答；缺少预计送达时间就明确说未知。",
    middleware=[trace_calls, enforce_tool_budget],
)
result = agent.run(user_message, context=verified_session)

```

两个工具都重新通过订单服务校验访问范围。第二个工具接收订单号，而不是接受一个任意包裹号再直接查询物流，这使业务代码可以把物流访问绑定到可见订单。trusted_context 是应用提供的运行信息，不属于让模型自由生成的参数。官方 Tools 文档同样区分当前任务可变状态与调用时传入的 context；具体注入写法应查所用版本，而不是照抄上述伪代码。[LangChain：Tools 的 Access context](https://docs.langchain.com/oss/python/langchain/tools)

一次假设执行中，模型先请求 read_order，参数为 O42。框架把请求交给已注册的函数，函数验证 U7 可读这张订单，再返回：状态已发货，包裹 S9，仓库发出时间为 9 月 27 日 18:00。框架将这个结果关联到对应工具调用，再提供给下一次模型调用。此时“已发货”还不能回答包裹在哪里，模型继续选择 read_shipment。

物流工具返回：包裹 S9 在 9 月 28 日 09:20 到达分拨中心，预计送达时间为空。模型现在有依据回答位置，但没有依据承诺何时送达。最后输出：“订单 O42 已发货；截至 9 月 28 日 09:20，包裹到达分拨中心。物流系统尚未提供预计送达时间。”这份结果标明事实时间，保留空缺，也没有把“查询完成”说成“订单已经送达”。

| 环节 | 框架可以提供的工作 | 应用仍需决定或实现 |
| --- | --- | --- |
| 模型调用 | 提供方适配、通用消息表示 | 选择模型、验证能力与费用约束 |
| 工具请求 | 解析与分派、结果关联 | 参数含义、访问权限、业务查询 |
| 后续循环 | 将结果交给模型继续决定 | 哪些能力开放、何时停止或交接 |
| 最终输出 | 返回消息或结构化结果 | 空值含义、证据要求、面向用户的契约 |

这个例子中，工具结果是外部事实依据，框架只负责让它到达正确的下一轮。若订单服务返回了错误的包裹关联，消息格式再标准也不会自动修好数据。若模型把空的预计送达时间补成“明天”，问题发生在答案生成或校验，而不是物流工具没有被调用。

## 固定链、中间件和任务状态

同一业务也可以写成固定链：程序总是先查订单，再在已发货且有包裹时查物流，最后调用模型生成回答。这里的“链”（chain）指预先安排的步骤组合，不特指历史教程中的某个类。这个流程仍然可以使用 LangChain 的模型与消息抽象，但下一步由程序分支决定，不必让模型自行挑工具。

使用 Agent 时，框架组织“调用模型—执行所选工具—把结果交回模型”的循环。它更适合后续操作依赖自然语言问题与中途发现的场景。例如用户可能只问订单是否取消，也可能问配送状态；两者需要的信息不同。模型自由选择有助于少写复杂路由，也带来选错工具、重复查询或提前回答的风险。官方 Agents 与 Middleware 文档描述了这种循环；框架能管理循环，不代表每次“模型不再调用工具”就已满足业务交付要求。[LangChain：Agents](https://docs.langchain.com/oss/python/langchain/agents)

中间件（middleware）把横跨多步的控制放到明确的调用边界。例如模型调用前选择要提供的上下文，工具执行前检查调用预算，执行后记录耗时，遇到明确错误时转换为模型可理解的返回。官方文档提供模型和工具步骤前后的扩展点，并把日志、重试、格式处理和提前终止列为用途。[LangChain：Middleware overview](https://docs.langchain.com/oss/python/langchain/middleware/overview)

对 O42 来说，“最多查两次”和“每次查完记下耗时”都不属于模型要回答的业务内容，却要在每次调用前后重复执行。中间件就是让这些检查有固定插入位置的机制；订单是否属于 U7 仍由订单服务验证，不能把中间件的一次计数检查当作权限校验。

本例可以设置一次任务最多允许 2 次工具执行，工具开始前检查剩余次数，执行后记录结果。预算属于本次任务状态，不能用全局变量把所有用户混在一起；已验证用户身份则来自调用上下文，不允许模型在对话里自我修改。若任务中途退出，是否保存并恢复这份状态，要另外配置持久化机制。中间件读得到状态，不等于状态已经写入了跨进程存储。

中间件也可能互相影响。先对结果做摘要再记录日志，留下的是摘要后的内容；先记录再摘要，能保留原始结构，但要考虑敏感字段和存储范围。重试中间件尤其需要区分只读查询与会修改业务的操作，不能让所有错误都走“自动再执行一次”。采用框架以后，这些决定集中到了可配置位置，但仍是应用的责任。

复杂状态图、明确的分支与恢复机制可以继续学习 [LangGraph](#/lesson/langgraph)。当前官方文档把它定位为更低层的编排框架，LangChain Agent 的中间件运行在其编译后的图中。这个关系解释了两者可以组合，不意味着简单订单查询必须先手工设计一张大图。[LangChain：Middleware inside a LangGraph workflow](https://docs.langchain.com/oss/python/langchain/middleware/overview)

## 可观测性和直接 SDK 的选择

框架最容易掩盖的问题，是只看最后一段回答，不知道中途发生了什么。可观测性（observability）在本例至少应回答：模型请求过什么工具、使用什么参数、哪个调用标识对应哪个结果、工具耗时多久、结果为何为空、是否重复调用，以及哪一步触发了停止。记录这些信息，可以区分权限拒绝、业务接口错误、模型误读和预算耗尽。

LangChain 文档提供 LangSmith 作为跟踪、调试和评估的一种集成选择，但引入框架不会自动证明一次任务成功，也不要求所有日志都送到同一个服务。应用应根据环境选择记录方式，并控制订单和用户数据的保存范围。用一条完整调用记录定位失败，比根据最终文字猜测“模型今天状态不好”更有依据。[LangChain overview：Tracing](https://docs.langchain.com/oss/python/langchain/overview)

如果应用只接一家服务、只有一次生成，或固定执行一个很短的只读查询流程，直接使用原生 SDK 往往已经足够。直接调用让请求字段、错误和流式事件更接近提供方原貌，也少一层版本依赖。代价是需要自己维护消息循环、工具关联与记录。反过来，团队有多种模型集成、共享工具接口和通用运行控制时，框架可能减少重复代码，但需要接受抽象边界和升级维护。

选型可以从本例做一个小对照：两种实现都处理正常订单、没有包裹的订单、权限拒绝、物流超时和预计时间缺失，比较业务代码是否更清楚、失败是否更容易定位，以及是否引入不需要的复杂度。不要用示例代码行数代替可维护性判断。真实落地还要锁定核心包与提供方适配包的版本，按同一代官方文档编写；不能把旧 chain 类、旧 Agent 初始化方式和当前 create_agent 中间件随意混用。

<summary>面试怎么回答</summary>

**一分钟回答：** LangChain 主要组织模型、消息、工具和 Agent 运行机制。统一接口减少提供方格式适配，Agent 循环负责把工具结果带回模型，中间件提供调用边界上的日志、预算和其他控制。应用仍要实现业务工具、身份授权、错误语义和交付验收。固定查询链由程序决定顺序，Agent 让模型根据上下文选下一步。只有一家模型和简单固定流程时，可以直接 SDK；当共享接口和运行控制的重复维护明显时，再评估框架收益。

**追问一：用统一模型接口，换提供方是不是就不用改代码？** 可能少改连接代码，但不能保证行为兼容。工具调用、内容格式、流式事件和特有参数都有能力差异，模型对同一任务的表现也不同。至少要复测工具选择、参数、空值处理和失败路径。

**追问二：加了中间件，权限和工具可靠性是不是交给框架了？** 中间件提供执行检查的位置，不替应用决定权限政策，也不创造安全重试契约。身份来自已验证上下文，业务服务仍要校验订单访问，超时要保留真实错误。框架负责运行这些规则，规则的正确性仍须应用验证。
