# Embedding：相似句子怎样变成相近的向量

假设知识库有一篇《未发货订单取消流程》，用户却问“还没出库的订单怎么撤回”。如果检索只要求词语重合，“撤回”找不到“取消”，“没出库”也不一定匹配“未发货”；真正有用的流程可能排不上来。分词、同义词表或人工改写查询可以补救一部分，但要维护这些规则。检索用的**嵌入（embedding）**提供另一条路：把问题和资料编码成可比较的数字向量，找含义相关的候选。

这一步出现在 [RAG](#/lesson/rag-basics) 的“查资料”环节。入库时，应用把文档切成可检索片段；查询时，它要从片段中取回可能支持答案的原文。分块怎样做可另读 [Chunking](#/lesson/chunking)，不必先掌握分块算法才能理解本篇。Azure 的嵌入指南描述了问题与资料编码、比较并取回内容的流程。[Azure：Generate Embeddings Phase](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/rag/rag-generate-embeddings)

关键词与向量检索在这个假设中的职责可以这样对照；表中没有实际运行或排名数据。

| 检索路线 | 用什么找候选 | 在订单问题中的作用 | 仍需检查什么 |
| --- | --- | --- | --- |
| 关键词 | 查询词与文档词的匹配 | 命中相同的订单号、政策编号或词语；词面不同可能漏掉流程 | 同义表达能否召回，以及命中条款是否适用 |
| 向量 | 问题与片段的表示有多接近 | 可能找回“撤回”与“取消”这类表达不同但相关的片段 | 旧政策、否定条款、权限和版本是否被混入 |

二者可以结合，具体融合方式留给 [混合检索](#/lesson/hybrid-search)。本篇只问：文字怎样变成能比较的向量，比较后的分数究竟说明什么？假设另有一份旧政策写着“未发货订单也不允许取消”，它也与问题高度相关。**相近只帮助找候选，不证明候选说得对或仍然有效。**

## 从一段文字到一个向量，中间发生了什么

把编码器看作函数 $E$：输入一段文本 $x$，输出 $d$ 个数，即 $E(x)\in\mathbb{R}^{d}$。$d$ 是**向量维度**，$\mathbb{R}^{d}$ 是由 $d$ 个实数组成的空间。对本例，应用离线编码“尚未发货的订单可以在订单页取消”及其他片段，保存向量、原文 ID 与版本；在线编码“还没出库的订单怎么撤回”，用问题向量比较资料向量，取回候选 ID 和原文。不同长度的文本可以输出相同维度，方便比较，但一条定长向量并没有把文本里的每个事实逐字保存，也不能把某一维直接解释为“可取消程度”。

以一种常见实现为例，文本先经过分词器变成 token，模型对这些 token 计算带上下文的表示，然后用池化（pooling）把多个位置的表示汇总成一个向量，再根据模型约定做归一化。池化可以有不同形式，不能随便用第一项或平均值替代模型规定的方法。Hugging Face 上由模型作者维护的 multilingual-e5-base 示例，采用带 attention mask 的平均池化，排除补齐位置，再做向量归一化。[E5 模型卡：Usage](https://huggingface.co/intfloat/multilingual-e5-base)

池化解决的是“一个片段有多个 token，索引却要存一条定长记录”的问题。订单流程无论被切成几个 token，最终都要汇总为一条向量；汇总规则由所选模型决定。归一化则按模型要求调整向量长度，不会自动纠正旧政策或业务条件。

这与 Transformer 内部的 **token embedding** 要分开。token embedding 通常是单个 token 进入模型时的输入表示，随后还要经过上下文计算；本篇的**检索 embedding** 是供问题与整段资料比较的表示，常经过上下文编码、汇总和面向检索的训练。两者共用 embedding 一词，却处于不同粒度和用途。直接平均任意生成模型的 token 输入向量，没有理由就能得到可靠的检索编码器。相关性怎样体现在距离中，取决于选定模型的训练与使用约定。

训练时，检索模型可以利用相关问题与段落这样的正配对，以及不相关或容易混淆的负配对，让适合当前任务的文本在表示空间中更容易区分。这里先理解目标，不展开损失函数。向量的作用是支持比较；它不是一段自然语言答案，也不带“该政策当前有效”的自动证明。

## 余弦相似度怎样计算

余弦相似度（cosine similarity）比较两个非零向量的方向：

$$
\operatorname{cos}(q,v)=\frac{q\cdot v}{\lVert q\rVert_2\lVert v\rVert_2}
=\frac{\sum_{i=1}^{d}q_i v_i}{\sqrt{\sum_{i=1}^{d}q_i^2}\sqrt{\sum_{i=1}^{d}v_i^2}}
$$

$q$ 是问题向量，$v$ 是候选片段向量；$q_i$、$v_i$ 是第 $i$ 个分量；点积 $q\cdot v$ 是对应分量乘积之和；$\lVert q\rVert_2$ 是向量长度。分母去除了长度的影响，因此同方向但长度不同的向量可以得到相同分数。数学范围是 $[-1,1]$，但实际模型的分数可能集中在其中一小段。零向量不能直接使用这个式子，应用应把它视为需要处理的异常。

用二维向量手算一次。以下数字由本课人为指定，**不是实际 embedding 模型输出**，仅展示计算与证据边界。

| 对象 | 假设文本 | 向量 | 与问题的余弦相似度 |
| --- | --- | --- | --- |
| 问题 Q | 未发货订单能自行取消吗？ | $(1,0)$ | 不适用 |
| 片段 A | v2：尚未发货的订单可以在订单页取消 | $(4,3)$ | $0.8$ |
| 片段 B | v1：未发货订单也不允许自行取消 | $(8,6)$ | $0.8$ |
| 片段 C | 如何下载银行账单 | $(0,5)$ | $0$ |

对 A，点积为 $1\times4+0\times3=4$，问题长度为 1，片段长度为 $\sqrt{4^2+3^2}=5$，所以分数是 $4/5=0.8$。B 的点积为 8、长度为 10，因此同样得到 0.8。C 与问题的点积为零，分数为零。

这组手算只说明：按给定向量，A 与 B 都比 C 更接近问题。它不能从相似度判断 A 和 B 谁正确。两个片段谈论同一业务，却给出相反规定；后续必须核对版本、生效时间与适用范围。真实模型是否给否定句较高分，需要实际测量，不能从这个人为例子推断某个模型一定犯错。

分数也不是正确概率。0.8 不代表有 80% 的机会支持答案，不同模型下也没有统一的“超过 0.8 就可信”规则。E5 模型卡特别指出，其分数分布有自身训练原因，检索时应关注候选的相对顺序；应用仍需在自己的任务上确定排序与阈值如何使用。

## 问题和文档必须进入配套的表示空间

很多知识检索属于非对称检索：短问题希望匹配包含答案的长段落，而不是寻找一句改写得很像的问题。Sentence Transformers 文档区分了这种情况与“找相似问题”的对称检索，并提供 query 与 document 编码入口；是否使用不同提示或内部路径，取决于所选模型。[Sentence Transformers：Semantic Search](https://www.sbert.net/examples/applications/semantic-search/README.html)

所谓配套，并不要求问题和文档必须加同一前缀。例如 multilingual-e5-base 的作者要求检索问题加 `query: `，资料加 `passage: `，非英文文本也采用这两个前缀。这是该模型的契约，不能推广成所有 embedding 模型的规则。漏加前缀、前后使用不同池化方法或一侧忘记归一化，都可能让实际比较偏离模型预期。

把开头的订单问题走成一个完整流程，可以按以下概念伪代码组织。函数名用于展示职责，不是某个 SDK 的可直接执行调用：

```text
离线输入：
A = {id: "cancel-v2-3", version: "v2", text: "尚未发货的订单可以在订单页取消"}
B = {id: "cancel-v1-3", version: "v1", text: "未发货订单也不允许自行取消"}

使用固定模型与固定配置：
向量A = encode_document("passage: " + A.text)
向量B = encode_document("passage: " + B.text)
保存：片段ID、原文、版本、模型版本、预处理配置、向量

在线输入：
问题 = "还没出库的订单怎么撤回？"
问题向量 = encode_query("query: " + 问题)
计算问题与允许访问、适用版本候选的相似度
返回：候选片段ID、分数、原文及来源元数据
```

这段示例采用 E5 前缀约定，但没有下载或运行模型，因此不提供伪造的真实排名。假设应用已确认 v2 当前有效且用户有权查看，版本过滤后可以返回 A 的原文。答案生成阶段再据此解释取消流程；embedding 阶段的输出仍然是候选及分数，而非“取消已执行”。权限和版本是来源元数据的责任，不能靠向量距离代替。

## 长度、语言和领域会改变结果

编码器有输入长度限制。超过限制时，具体接口可能拒绝输入，也可能截断；必须查看模型和调用配置。E5 的作者示例将最大长度设为 512 tokens，并启用截断。512 tokens 不等于 512 个汉字，前缀和其他输入内容也会占用位置。若关键例外条款在被截掉的末尾，向量无法代表那段从未被模型读到的内容。增加一个更长的片段，不一定增加有效证据。

“支持中文”也不意味着所有中文领域表现相同。普通订单词语、公司内部缩写、产品型号、中英混写都应放进代表性测试。E5 模型卡说明它覆盖多种语言，同时承认低资源语言可能退化；这类作者说明是候选选择的依据，不能替代实际业务验证。还要区分中文问中文资料，与中文问英文资料这样的跨语言检索。

分词器把生词拆成子词并不自动意味着语义失效，模型仍可能通过训练学会这些组合。真正要观察的是含专业术语的问题能否找回正确片段，以及容易混淆的缩写是否挤掉答案。Azure 指南强调领域、词汇、语言和许可适配；具体选型应回到数据，避免仅根据榜单总分决定。

## 维度成本与模型升级

维度越高，每条向量存储的数越多，但维度并不是质量分数。假设有一百万个片段，每个向量 768 维，每个分量用 4 字节的 float32 存储，则仅向量原始数据需要：

$$
10^6\times768\times4=3{,}072{,}000{,}000\text{ bytes}
$$

按十进制 GB 计，这是 3.072 GB；换成 1536 维则是 6.144 GB。这里没有计算文本、元数据、搜索数据结构、副本和服务运行开销。向量传输量和逐分量计算工作也会随维度增加；质量是否改善要测，不能把维度翻倍理解成语义准确率翻倍。未经模型支持或评估，任意截掉后半向量也不能假设保留效果。

升级 embedding 模型时，原索引中的向量通常需要重新生成，并建立对应的新向量索引。原因是不同模型学出的空间没有默认的坐标兼容性。即使新旧模型都输出 768 维，把新问题向量直接与旧资料向量比较也可能得到无意义的排名。模型版本、query/document 配置、池化、归一化或输出维度变化，都应纳入兼容性检查。

一种可审查的迁移方法是保留旧版本，给全部片段用新配置生成向量，建立独立索引；使用同一组真实问题对比必要证据是否被找回，验证后一起切换问题编码器与文档索引。只有生成答案的 LLM 升级、embedding 路径没有变化时，不必因此机械重建向量。本课到此只讨论表示与兼容性，如何加速大规模搜索留给 [向量索引](#/lesson/vector-index)。

<summary>面试怎么回答</summary>

**一分钟回答：Embedding 在检索里做什么？**

它把问题和资料编码成可比较的向量，用余弦等度量找出语义相关的候选。问题与文档要使用配套模型和预处理约定，必要时采用各自的前缀或编码入口。相似度只代表这个表示空间中的接近程度，不是答案正确概率，也不能替代权限、版本和证据支持检查。选模型要评估实际语言、领域、输入长度与成本；更换 embedding 模型通常要重算资料向量，并和问题编码器一起迁移。

**追问一：两个模型输出维度一样，可以混用吗？**

不能据此判断兼容。维度只是数组长度，不保证同一坐标表达同样特征。除非模型明确提供兼容契约且经过验证，否则使用新问题向量比较旧资料向量会破坏检索假设。

**追问二：相似度 0.9，为什么回答还可能错？**

它可能找到了同一主题下的否定规定、旧政策或不适用对象。相似度不是事实支持判定。要取回原文并核对条件，还要确保正确证据没有在编码时截断、在检索时遗漏。

**追问三：token embedding 和检索 embedding 有何区别？**

前者常指单个 token 的模型输入表示；后者代表完整片段，通常经过上下文编码、汇总与适合检索的训练。二者的粒度和使用目标不同，不能直接把任意 token 表示当作成熟检索向量。

## 练习：高分候选与索引迁移

给定问题向量 $q=(0,1)$，两个候选向量 $a=(3,4)$、$b=(-3,4)$。A 是旧版政策，B 是当前政策，用户有权读取两者。计算两个余弦分数，并说明能否仅按分数决定答案。随后计划把 768 维模型更换为另一个 768 维模型，怎样准备迁移？

<details>
<summary>参考思路</summary>

问题长度为 1，两个候选长度均为 5，点积均为 4，因此两个分数都是 $4/5=0.8$。相同分数不能消除版本差异；当前制度问题应使用适用的现行条款，并保留原文与来源。若问题问历史日期，旧版可能反而适用。

迁移时保留原文、ID 与元数据，用新模型及其规定的 document 编码生成新向量，建立独立索引；问题端也使用配套编码。比较包含否定、版本、跨语言和长片段边界的测试，再切换并保留回退路径。维度没有变化只能说明存储形状相同，不能证明语义空间相同。

</details>
