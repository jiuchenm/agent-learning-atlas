# 业务抽象：怎样判断一个需求需要 Agent

假设业务方提出：“做一个培训助手，员工问什么都能答，还能帮他们把申请办完。”这句话听起来包含一个产品，实际混着几种不同工作：解释政策、判断某次申请缺什么、填写表单、提交审批，甚至代替负责人作决定。如果直接选择模型和框架，很容易把“能回答问题”演示成“能办完申请”，上线后才发现权限、系统接口和验收标准都没有说清。

业务抽象的作用，是把模糊愿望转为能设计、实现和验收的一项任务。这里说的 Agent，是由程序让模型根据任务进展选择后续动作、调用允许的工具，并利用返回结果继续处理的系统；它只是几种实现方式之一。最先要确定谁在什么情况下需要什么结果，再谈模型是否需要承担这段动态决策。下面用一个假设的企业课程申请案例完成这个过程。公司、制度、人员、数值和结果均为教学构造，不是实际客户案例或用户业绩；所讨论的是软件任务边界，不是现实企业费用政策。

## 从“智能办理”改写成可观察的交付

先拆开两个目标。政策咨询帮助员工理解当前适用的规则；申请准备帮助员工提交完整、与事实一致的材料。前者成功时交付有依据的解释，后者成功时交付可以审核或提交的申请。它们可以共享资料与界面，但不能用“回答率”同时衡量，也不能把咨询时的一句“你可以申请”当作审批已经通过。

假设先选择一个有明确责任方的范围：为中国区在职员工准备外部职业课程申请，使用当前生效的培训制度和本人可见的申请记录，支持咨询、补齐缺项和生成草稿；只有员工确认具体草稿后，才通过既有接口创建申请。预算批准和特殊例外仍由既有审批角色决定。这里的每个限定都影响可执行设计：用户范围决定身份查询，课程类型决定采用哪份政策，交付终点决定有哪些工具可以开放。

一份任务定义至少需要把输入、输出和限制写到同一张表里。它不是为了填文档，而是让研发、业务负责人和测试人员讨论同一个对象。

| 项目 | 本例的明确约定 |
| --- | --- |
| 用户与目标 | 已登录员工了解资格并准备一份可审核的课程申请 |
| 用户输入 | 课程名称、日期、供应方和报价附件，允许先不齐全 |
| 系统输入 | 本人身份、当前政策、当年已批准记录及其时间范围 |
| 输出 | 带政策依据的解释、缺项列表、申请草稿，或已核实的申请编号 |
| 约束 | 不补造报价，不查询他人记录，提交只使用已确认版本 |
| 成功条件 | 所需字段真实齐全，规则适用明确，输出状态与实际执行一致 |
| 异常出口 | 规则冲突、权限缺失、来源不可用或超出范围时交给指定负责人 |

输入并不一定一次性齐全，这也是自然语言交互可能有用的地方。但每个字段都要有来源。员工说“课程大约两千块”可以触发补问，不能直接变成正式申请金额；系统查到旧年度额度，也不能静默当成本年度可用数据。定义缺信息时的行为，比把“准确、智能、无缝”写进需求更容易测试。

## 一次申请如何沿着范围走完

假设用户输入：“我想报名 10 月的沟通课程，报价 2400 元，帮我看看能不能申请。”应用验证身份为 U7，读取本年度记录，得到已经批准的培训金额为 900 元。当前制度第 4 版规定：在适用范围内，年度累计申请额度上限为 3000 元；若新申请使累计金额超出该上限，需要额外审批。这里所有金额均按本例制度使用同一币种与同一计入规则，不涉及退款、预占用或跨年度折算。

系统可以用确定性计算得到：$900 + 2400 = 3300$ 元，比上限多 $3300 - 3000 = 300$ 元。这个结果支持“会触发额外审批”，不支持“不能申请”，更不支持“已获批准”。模型的职责是把适用条款、计算及后续要求解释清楚；程序负责金额运算和字段校验，业务负责人决定制度是否确实这样适用。

此时用户只问能否申请，系统先交付解释：“按当前记录，本次申请使年度累计金额达到 3300 元，超过 3000 元上限，需要额外审批。仍可准备申请，但批准结果由审批流程决定。”同时说明还缺具体课程日期和报价附件。没有这些信息，不能生成一份貌似齐全的提交记录。问题从资格咨询进入材料准备，需要用户继续提供事实，而不是由模型替他想一个日期。

假设用户随后提供课程日期与正式报价，要求准备草稿。应用保存这些输入及来源，生成 draft-1，包含课程信息、2400 元金额、本年度已批准 900 元、触发额外审批的标记，以及所采用政策的版本。界面展示的是“申请草稿”，不是“办理成功”。用户发现日期写错，改成 10 月 18 日，应用生成 draft-2；先前对 draft-1 的认可不能自动作为提交 draft-2 的确认。

用户明确确认 draft-2 并要求提交后，程序校验版本、必填字段与授权，再调用申请系统。假设接口返回申请编号 R88，状态为待审批，应用核实记录内容一致，最终交付“已创建 R88，当前待审批”。这一次的办理成功可以定义为“正确创建已确认申请”，并不意味着课程一定获批。若提交响应超时，当前状态应为“提交结果待核实”，不能重新填一张表就算恢复，也不能把未知当失败告诉用户重来。

完整例子揭示了几个容易混淆的层次：政策允许发起申请、材料完整、系统创建成功、审批通过是四个不同状态。任务范围应选定自己负责到哪一个状态，输出和指标也随之变化。否则即使工程运行完全正常，业务双方仍可能对“做完了”产生相反理解。

## 哪一段用程序，哪一段需要 Workflow 或 Agent

普通程序适合已知输入结构和明确规则。例如验证课程日期、把两项金额相加、检查必填项，以及按确定条件路由额外审批，都可以直接编码。若所有员工总是填写相同字段，政策已经结构化且稳定，一个带校验的表单可能就是成本更低、行为更清楚的方案。存在聊天入口，并不构成必须加入动态 Agent 的理由。

工作流（Workflow）预先安排步骤，模型可以参与其中。对于本例，先识别咨询意图，再读取政策与本人记录、计算、澄清缺项、生成草稿、等待确认、提交并核实，顺序和主要分支都可以明确表达。LLM 处理自然语言提问、非结构化报价和解释文字；应用控制身份、数据源与写入边界。它已经可能满足需求，不需要把每一步都交给模型临场规划。

Agent 更适合下一次调查行动要根据中途发现决定的环节。假设不同课程涉及不同例外，而用户描述与项目材料分散在几个允许访问的系统里，无法合理枚举所有查询路径，就可以让 Agent 在只读调查范围内选择要补查什么，再把结果交回固定的草稿与提交流程。需要动态性的是调查路径，审批权限和提交条件不会因此变得可自由决定。

Anthropic 的工程文章也按预定义代码路径与模型动态选择过程区分 Workflow 和 Agent，并建议从能满足任务的简单方案开始。文章指出多步 Agent 会以延迟、成本及错误累积风险换取灵活性。本篇采用这组架构区分，而不把它当作所有产品的统一命名标准。[Anthropic：Building effective agents](https://www.anthropic.com/research/building-effective-agents)

| 子任务 | 本例的起始选择 | 选择依据 |
| --- | --- | --- |
| 金额计算、字段校验 | 普通程序 | 规则与输入明确，结果可直接复核 |
| 政策咨询到草稿提交 | 固定 Workflow，局部使用 LLM | 主要阶段和边界可预先描述 |
| 跨多来源查清例外 | 有需要时增加只读 Agent 环节 | 下一步取决于调查结果 |
| 特殊批准与责任承担 | 既有审批人和业务流程 | 属于业务授权，不是生成能力 |

这个划分也留下了渐进扩展空间。先做咨询和草稿，确认效果与接口契约，再开放经确认的提交能力，比一开始承诺“所有问题全自动办完”更容易识别真实限制。但阶段性范围必须公开写在产品行为里，不能把尚未支持的提交伪装成后台正在处理。

## 异常、责任和成功都要能追到具体对象

异常不只是接口抛错。若新旧政策都标成有效，问题是规则来源冲突；若缺报价，问题是输入不足；若本人记录读不到，问题可能是权限或系统不可用；若业务要批准超过额度的特殊课程，问题是决策权限。这些情况需要不同出口。模型可以整理已知事实和待决定项，却不能用更肯定的文字消除来源冲突或取得新的权限。

责任也需要拆开。制度负责人确认适用条款、例外与生效时间；数据和接口负责人维护身份、权限及记录一致性；产品或流程负责人定义完成、拒绝与转交状态；研发落实校验、执行记录与恢复；用户确认申请事实，审批人决定批准。模型可以承担解释和建议，但上线后出现错误时仍要找到负责修正规则、数据或代码的人，不能把“Agent 决定的”当成责任终点。

如何证明这个需求值得做，需要先观察现有办理流程，而不是先假设人人都需要聊天。可以在授权范围内抽样记录咨询类型、资料退回原因、员工花在哪里，以及现有搜索或表单能覆盖多少。若反复咨询主要来自政策入口难找，改善导航可能比新增 Agent 更有效；若退回来自固定三项必填内容，表单校验可能已经解决主要问题；若用户需要在多份规则之间解释适用条件，模型才有更清楚的价值空间。

为让比较可执行，假设评估集含 100 个脱敏任务，其中 60 个咨询、40 个申请准备。这是示意分组，不是本项目实测。若 60 个咨询里 54 个解释有正确依据，咨询成功率是 $54 / 60 = 90\%$；40 个准备任务中 30 个一次形成合格草稿，准备成功率是 $30 / 40 = 75\%$。两者混成一个总分，会掩盖申请准备仍有明显缺口。提交成功、审批通过还需要各自分母，不能重复计作同一指标。

还要记录错误性质和人的补救工作。一个答案措辞不好，与一次未经确认的提交，不能在平均分里当成同等小错。试验前应约定哪些行为绝不允许、遇到什么问题必须转交，以及相较现有流程要减少多少真实负担；具体阈值由业务风险和基线决定，不从通用教程抄一个数字。验收方法可接续 [Agent 评估](#/lesson/agent-metrics)。

业务抽象最后留下的应是一份可被反驳的任务契约：这个用户提交这些信息，系统依据这些来源，在这些限制内交付这些状态，异常交给这些负责人。架构选择能由证据调整；若固定流程已满足需求，就保持固定流程，若调查路径确实限制了完成率，再考虑让模型承担更多过程决策。

<summary>面试怎么回答</summary>

**一分钟回答：** 我会先把需求写成用户、目标、输入输出、约束、成功条件、异常出口和责任人，再选架构。以课程申请为例，解释政策、准备草稿、创建记录、审批通过是不同结果，必须明确负责到哪一步。金额和必填校验用普通程序，主要阶段明确时用 Workflow，只有下一步调查需要根据中途发现动态决定时才引入 Agent。然后与现有搜索、表单或人工流程对照，分别评估咨询与申请质量、耗时和补救成本，而不是把使用了模型当作业务成果。

**追问一：如何证明痛点真实，而不是团队想做 Agent？** 看真实任务和现有基线。抽样统计咨询内容、退回原因、处理时间与人工补救，再检查改导航或表单能否解决主要问题。用户说喜欢聊天不是充分证据，系统是否减少完成任务的负担才是要检验的假设。

**追问二：规则有例外，是不是就应该交给 Agent？** 不一定。可枚举的例外仍可以写成分支或交给既有审批。Agent 适合调查下一步难以预先穷尽的部分，但查明例外与有权批准例外不同。政策冲突时要保留缺口并交给负责人，不能把模型选出的解释当作新的制度。
