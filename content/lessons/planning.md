# Planning：Agent 怎样制定并修订任务计划

**规划（Planning）是 Agent 应用围绕一个目标，确定下一步做什么、先要满足什么条件、取得什么结果才算完成，并在执行中根据新信息修改安排。**它处理的是应用的任务推进：模型可以提出步骤，程序可以保存、检查和执行步骤。计划不等于模型的内部思维链（Chain-of-Thought），也不是把推理过程展示给用户；应用只需要能检查的动作、依据和完成状态。计划写得合理，也不证明任务已经完成。

假设用户向一个报修助手提出：“301 会议室今天无法无线投屏，帮我整理一份可提交的报修草稿，先别提交。”最初看起来可以按固定流程查设备、查操作手册、写草稿。然而查询服务状态后，助手可能发现楼内正在发生无线投屏故障。若它仍机械地查本机设置，最后可能把公共服务事件写成投影仪故障。**固定流程的问题是它在运行前就决定了后续动作，而此处的调查方向取决于尚未取得的结果。**当然，若只有少数已知分支，程序里的条件判断就可能足够；Planning 值得考虑的是分支和依赖随观察而变化的任务。

本篇沿这份报修草稿走完输入、计划、执行、重规划和停止。地点、设备、服务、事件编号及返回结果都是**教学假设**，没有运行真实工具。[任务状态](#/lesson/agent-state) 已说明事实和进度怎样保存；这里关心应用怎样利用状态选择下一步。Anthropic 的 [《Building effective agents》](https://www.anthropic.com/research/building-effective-agents) 区分预定代码路径的 Workflow 和依据环境反馈动态选择动作的 Agent，也建议从能完成任务的简单实现开始。这是理解取舍的参考，不表示本文的报修流程是 Anthropic 的实现。

## 第一步：先确定交付物，再写步骤

“处理投屏问题”太宽。它可能指诊断根因、修好设备、创建工单，也可能只是整理报修材料。用户这次要求的是草稿，因此完成条件应当是：有一份可供用户查看的报修内容，写明地点、设备、现象、已核实信息和未知项；判断是否存在相关服务事件；没有向工单系统提交。设备恢复正常并不是本次完成条件。

完成条件（completion criteria）约束最终产物，步骤的验收条件则判断中间工作是否达到要求。例如，“查设备”不能因为工具返回了一段文字就算完成，而要确认返回的设备确实对应 301 会议室，并取出后续查询需要的服务标识。缺少服务标识时，下一步不能自行编造一个。这也是计划能供执行器检查的原因：每步都有可见的输入与产物，而非只有“认真调查”这类意图。

计划还需要前置条件（precondition）：执行这一步之前必须已经成立的事实。查服务状态需要服务标识；判断事件是否相关，需要服务、地点、时间和症状等线索；写最终草稿需要经过核实的内容和明确保留的未知项。把这些关系写出来，依赖（dependency）才有意义。箭头表达的是“下游消费上游的结果”，不能仅仅因为清单排了先后，就认定两步存在依赖。

针对本例，初始计划可以是下面这样。这里的表格是一种教学表示，不要求使用某个框架。

| 步骤 | 输入与依赖 | 预期产物及检查条件 |
| --- | --- | --- |
| P1 查设备登记 | 用户给出的 301 会议室 | 匹配的设备记录、关联投屏服务标识 |
| P2 查服务状态 | P1 的服务标识 | 当前状态、更新时间、可能相关的事件编号 |
| P3 补充故障材料 | P2 未发现可能相关的公共故障时，查匹配设备的指导说明 | 可放入草稿的排查线索，未经执行的建议不能记成已尝试 |
| P4 生成并检查草稿 | P1、P2，以及实际需要的补充材料 | 事实可追溯、未知项保留、未提交 |

P3 具有条件，因为它依赖尚未取得的观察。初始计划不必预先列出所有可能的故障，更不能假设所有分支都会执行。计划先写到**下一步能执行、关键分叉能识别**即可；更远的分支等结果到来再展开。表格中的 P1 至 P4 是应用层的任务计划，可以记录版本与状态；它没有声称记录模型怎样在内部得出这些步骤。

## 第二步：执行、接收新事实、局部重规划

假设 P1 返回：301 位于 B 楼，显示设备为 PJ-301，无线投屏由服务 WCAST-B 提供。这条结果把“投影仪”和“无线投屏服务”区分开了。助手将设备与服务标识写入状态，P1 标为完成；P2 的前置条件也随之满足。此时只需要继续执行已有计划，没有理由重新生成整份清单。

P2 随后返回：WCAST-B 存在活动事件 INC-77，摘要为“部分楼层无线投屏失败”，但摘要未列出具体房间范围。这个结果改变了计划。如果继续按旧清单查设备操作手册，就可能偏离当前最需要核实的问题：公共事件是否覆盖 301。同时，摘要里的“部分楼层”还不能直接证明 301 在影响范围内。

重规划（replanning）因此只修改受影响的部分：P1 与 P2 的结果保留；原 P3 因条件不满足而跳过；增加 P3b，读取 INC-77 的完整范围、时间与症状。P4 仍是生成草稿，但输入改成事件核对结果。任务目标没有变，助手没有擅自把“写草稿”升级为“修复公共服务”或“创建事件”。

假设 P3b 返回如下事实：事件影响 B 楼二至四层，包含 301；上午 9:10 开始；症状为无线连接失败；登记的临时建议是使用有线连接；恢复时间未知。工具读取发生在上午 10:00。已知影响范围与用户现象相符，可以在草稿中记录关联线索，但仍不足以排除房间设备同时存在其他问题。

这一次变化在状态里应当看得见，而不只是助手在对话中说“调整一下计划”。例如保留以下内容：计划版本从 1 改为 2，触发依据是 P2 返回的 INC-77，旧 P3 被跳过而非完成，新增 P3b 已完成，已核实事实仍指向各自的工具结果。这样才能区分“做过排查”和“因为新证据没有继续排查”。下表把**观察**和**计划变化**分开：

| 时点 | 新观察 | 对计划的影响 |
| --- | --- | --- |
| P1 后 | 设备对应 WCAST-B | 满足 P2 输入，计划不变 |
| P2 后 | 有活动事件，具体范围待核实 | 跳过手册查询，改为核对 INC-77 |
| P3b 后 | 事件覆盖 301，症状相符，恢复时间未知 | 材料已足够生成草稿，不继续追查恢复时间 |

最终的假设草稿可以写为：“B 楼 301 会议室今天无法无线投屏。设备登记为 PJ-301，关联服务 WCAST-B。10:00 查询到活动事件 INC-77，自 9:10 起影响二至四层，范围包含 301，症状与本次反馈相符。事件列出的临时建议为有线连接，是否已在本房间尝试尚未确认；预计恢复时间未知。建议关联现有事件核查本房间情况。”随后明确标注“草稿，尚未提交”。

助手应检查每句话的身份：“用户反馈”来自用户，“事件覆盖范围”来自查询，“建议关联核查”是处理建议。这样，输入的“只要草稿”经过设备查询、事件核对和局部改计划，最后仍落在未提交的草稿上。没有执行有线连接测试，就不能写成“有线连接正常”；没有维修结果，就不能写成“故障已经解决”。计划的完成状态只能证明约定产物已经交付，不能代替业务世界的结果。

## 第三步：检查计划能否执行、何时停下

模型很容易写出“深入分析原因”“全面核实情况”这样的步骤。读起来像计划，执行者却不知道调用什么工具、消费什么输入、何时停止。一个实用的步骤粒度是：能够映射到一个有明确结果的动作，或一组边界清楚、可以独立验收的动作。“查 INC-77 的影响范围”够具体；“找到真正根因”仍需要拆解。

反过来，拆得过细也有成本。把读取返回值、取出房间号、复制事件编号分别列成三个模型决策，只会增加调用和状态维护。如果这些步骤可以由程序确定完成，就不必反复交给模型选择。规划应集中在方向会变化、输入存在歧义、或者决策有明显代价的位置。

计划生成后还需要校验。应用可以检查工具是否存在、依赖引用是否有效、是否存在循环，以及每个写操作是否符合当前授权。若 P2 依赖 P4 的草稿，而 P4 又依赖 P2 的查询，两个步骤就互相等待；若计划中出现工具列表没有提供的“重启投屏服务”，执行器不能因为模型写出来就把能力补出来。模型提出候选方案，程序和业务规则决定哪些动作可执行。

语义上的检查同样重要：步骤是否真能推动完成条件？查到事件覆盖范围后，继续搜索整栋楼所有历史维修记录是否还必要？这些问题未必都能写成静态规则，但应当让判断有依据，例如指出草稿还缺哪个字段、哪条事实存在冲突。没有新的缺口，仅把计划措辞改得更长，不算推进任务。

每次重规划也不应丢弃已完成且仍有效的工作。需要重新检查的是被新事实影响的部分。若用户后来把房间从 301 改成 501，P1 的设备匹配就不再满足目标，依赖它的服务查询和范围判断也可能失效；若用户只是要求草稿更简短，事实仍可复用，只需改写产物。这是依赖记录的实际用途：帮助识别变化究竟传播到哪里。

## 第四步：给探索和检查留出预算

不断调整计划可能让调查走得很远。查询摘要后能查事件详情，查详情后又能查历史事件、值班记录和设备日志。如果没有停止标准，每条新信息都可以成为继续调查的理由。Anthropic 的原文要求 Agent 利用工具或执行结果这样的环境反馈判断进度，并指出可以用最大迭代次数等停止条件保持控制；作者也提醒自主执行可能增加成本并累积错误。[环境反馈与停止条件](https://www.anthropic.com/research/building-effective-agents#agents)

本例可以预先设定四次外部读取、最多两次重规划，并为最终草稿核对保留一次检查。这里的数字是教学预算，不是通用推荐值。初始规划不计入两次重规划；一次重规划可以比较至多两个候选方向，避免不断生成新方案却不执行。搜索有界的意思是候选数量、展开深度或资源消耗受到约束，不表示找到了所有可能路径中的最优计划。

本例实际使用三次读取：设备登记、服务状态、事件详情。完成一次重规划后，草稿所需材料已经齐备，还剩一次读取额度；剩余额度不需要用完。最终检查核对事实来源、未知项和“未提交”边界，不额外访问系统。若检查发现缺失关键字段，才能考虑使用剩余读取；若发现的只是句子不清楚，就直接修改文字。

如果第四次读取用完仍不能判断事件是否覆盖房间，预算用尽只意味着本轮停止，并不代表成功。助手应交付带有明确缺口的草稿，说明已查询的范围和待确认问题；根据产品设计等待用户补充或转交人工。它不能为了显示完成，把“范围未知”改成“已确认相关”。检查也不能在所有预算用完以后才临时安排，否则容易出现调查做了很多，最后没有资源验证产物的情况。

工具失败也要改变状态。若 P2 查询超时，助手没有得到服务状态，便不能把 P2 标成“无相关事件”，更不能据此执行 P3 的条件分支。它可以在允许的预算和重试规则内再查一次；仍无结果时，应把服务状态记为未知，在草稿中说明这个缺口，并按产品要求停在待核实或交给人工。这里的失败与“已经查到没有事件”是两种不同状态。

是否值得引入规划，可以用固定流程作为对照：同样一组任务，比较材料完整性、错误动作、工具次数和总耗时。若输入与路径始终稳定，固定流程中的一个条件分支可能已经足够。只有新证据经常改变动作顺序或调查方向时，让模型持续调整计划的额外成本才可能换来实际收益；这需要测量，不能从计划长度推断。

**一分钟回答：** Planning 是应用把目标转成带依赖、前置条件和完成证据的步骤，再在执行中根据反馈调整；它不是模型内部思维链。先定义最终产物，例如报修草稿而不是修好设备。执行器只选择依赖已满足、工具可用且权限允许的步骤，结果写入状态。新事实推翻假设时，只重规划受影响部分，保留有效结果。还要限定工具次数、重规划次数和检查预算。固定路径用 Workflow 往往更省成本，只有后续方向依赖未知观察时，按反馈修订计划才更有价值。

**追问一：计划与普通待办清单有什么区别？** 待办清单可以只列动作，可执行计划还需要说明每步为什么能执行、用什么输入、产出什么证据、失败或条件不成立时怎样处理。模型把某项打勾不能证明完成；例如没有核实事件范围，就不能把“关联事件已确认”标成完成。

**追问二：什么时候重规划，为什么不每轮都重做？** 新事实使前置条件失效、关键假设不成立，或目标及约束变化时需要重规划。普通成功结果只需更新进度。每轮整份重做会增加延迟，并可能丢掉已核实事实、反复执行工作；依赖关系可以帮助缩小修改范围。

**追问三：计划越详细，成功率越高吗？** 不一定。远期步骤依赖未知信息，提前细化容易产生无依据假设；过细拆分还会增加模型调用。步骤应细到能执行和验收，程序能确定的细节交给代码，未知分支等反馈到来再展开。

<summary>练习参考思路</summary>

INC-77 的原始查询结果可以保留为有时间戳的历史证据，但“它覆盖目标房间”的结论不再成立。目标改为 501 后，P1 的设备匹配需要重新检查，依赖旧设备和服务的后续步骤也不能直接沿用。现有查询只核实了 301，不能仅凭“501”这个房号断定实际楼层或事件是否覆盖它，更不能把“原事件覆盖 301”复制成“覆盖 501”。

剩余一次读取可用于确认 501 的设备和关联服务，之后保留事件关联尚未核实的缺口。交付应是“501 报修草稿，关联问题待确认，尚未提交”，并说明哪些信息来自用户、哪些来自登记查询、下一步需要核实什么。若产品要求必须确认事件关系才算完成，就标为材料不足或等待补充，不能宣称完整任务已完成。继续调查需要新的预算或人工接手。
