# Agent Runtime 与沙箱：企业开发面试五篇系列大纲

一段 Python 已经在沙箱里生成了报表，但用户要等主管明天批准上传。今天销毁环境，明天怎样继续？今天保留环境，租户数据、凭据和资源账单又由谁负责？如果上传已成功，Agent 在记录结果之前崩溃，恢复一次会不会上传两份？这些问题连着任务状态、操作系统隔离、业务授权和平台调度，适合拆成五篇依次学习。

本页是五篇文章的规划与阅读路线，核验日期为 2026-10-01。五篇完整正文尚未编写。目标是准备腾讯企业 Agent 高级开发岗位的架构与工程追问；招聘记录用来选题，不能据此推断腾讯内部实现。先读 [Agent Runtime 与沙箱](#/lesson/agent-runtime-sandbox)、[任务状态](#/lesson/agent-state)、[工具失败](#/lesson/tool-reliability) 和 [Agent 安全](#/lesson/agent-security)。已有单篇给出整体入口，系列逐层补足机制和取舍。

## 贯穿任务：A17 企业销售报表

下面是教学假设。甲公司的用户 u7 上传 `sales.csv`，要求汇总每月销售额、画图，并准备上传企业报表库。输入只有三行：`Jan,60`、`Jan,40`、`Feb,30`。手算应得 Jan=100、Feb=30，总额 130。分析授权包括读这份 CSV 和在临时目录生成结果；上传企业报表库需要另一次审批。乙公司也在同一平台运行自己的报表任务。

五篇保持同一任务、同一授权边界。第一篇跟踪 A17 如何执行；第二篇考虑模型生成的代码会不会损伤宿主或邻居；第三篇处理数据、网络与身份；第四篇处理隔夜审批和崩溃恢复；第五篇把任务扩展到月末高峰。示例中的公司、数据、故障、资源与时间均是假设，没有部署或性能实测。

## 第一篇：从一次代码执行看 Agent Runtime 与沙箱分工

前置知识：Function Calling 的请求—执行—结果过程、任务状态与进程基础。中心问题是“模型说运行 Python 之后，谁确认它能运行、到哪里运行、什么时候结束”。

现实问题：`run_code` 返回成功，只说明一次执行得到了结果，未交代租户归属、文件授权、运行预算和后续回收。任务 A17 与环境 S17 也不能永远当成同一个对象：重试可能换环境，暂停可能保留环境，一个环境是否允许多次执行则是平台契约。

详细节纲：

1. 从模型提出 `run_code` 开始，画出模型、Agent 编排、Runtime 服务、执行环境和结果存储的调用路径。先定义任务、会话、工具调用、进程、沙箱 ID，避免把 conversation ID 当成环境授权凭据。
2. 给出本系列的职责划分。Runtime 控制面处理任务归属、准入、策略、环境分配、租约、状态、取消和回收；沙箱数据面执行进程、提供受限文件与网络视图、输出 stdout/stderr/退出码。控制面和数据面是教学架构分法，各产品的组件名称可能不同。
3. 分开编排状态与环境状态：任务可能“等待批准”，环境可能“已暂停”；任务成功也可能尚未完成环境回收。设计两组状态和明确转换，不把终端断线当成任务终止。
4. 解释申请环境、输入落盘、执行、结果校验、产物保存、撤销权限、销毁环境的完整路径。哪些记录必须保存在沙箱外，哪些只是可丢弃的中间文件？
5. 加入创建返回超时、客户端断开、取消与完成竞态三个故障。讨论租约、幂等创建标识和定期核对孤儿环境，它们属于平台设计建议，不能冒充 SDK 自动承诺。

一个样例：Runtime 核实 u7 属于甲公司、只接收三行 CSV，为 A17 建立 S17，运行求和脚本。执行结果为 Jan=100、Feb=30，Runtime 保存文件引用和摘要；上传步骤进入等待审批。S17 是否暂停、销毁或继续保留由后续策略决定。返回给模型的结果包含执行状态和产物引用，不要求模型从日志猜成功。

面试核心：“我会先把任务管理和代码隔离分开，再把任务 ID、租户 ID、执行尝试与环境 ID 关联起来；运行成功、业务完成和环境回收分别记录。”追问一：Runtime 服务重启后怎样找到已创建却未登记的环境？讨论稳定关联标识、租约和清理核对。追问二：为何不能直接将 Sandbox SDK 包成工具？解释 SDK 提供环境操作，应用仍需承担授权、任务状态、取消和业务结果验证。

证据来源与未知：[腾讯云 Agent 沙箱概述](https://cloud.tencent.com/document/product/1814/123811) 公开了多种环境、生命周期、文件和权限能力；[快速入门](https://cloud.tencent.com/document/product/1814/123816) 区分创建环境的超时和执行代码的超时；[E2B lifecycle](https://docs.e2b.dev/sandbox.md) 提供创建、查询、延长存活和销毁接口。本篇据这些接口设计职责图，尚未核验任一产品内部控制面、调度器或孤儿环境实现。

## 第二篇：容器、gVisor 与 microVM 怎样隔离不可信代码

前置知识：第一篇，Linux 进程、系统调用、内核与用户态的基本含义。中心问题是“恶意 Python 程序怎样抵达宿主，不同隔离机制切断哪条路径”。

现实问题：独立目录不能防止进程读取其他可见路径；限制内存不能阻止越权读取；运行在容器里仍可能共享宿主内核。选择技术前，要写清攻击者能提供什么代码、碰到什么数据，以及需要保护的宿主、邻居和服务。

详细节纲：

1. 用进程调用 `open`、`socket`、`fork` 的路径解释系统调用。列出 namespaces 对 mount、PID、network、user 等资源视图的隔离；说明 cgroup namespace 隔离视图，与 cgroup controller 分配资源是两件事。
2. 解释 cgroups v2 对 CPU、内存、进程数量的约束。CPU 带宽、内存上限、进程数限制分别处理资源争用；磁盘容量、网络授权和业务权限仍需另外设计。指出内存到达限制后可能出现 OOM，而非所有任务都“平滑变慢”。
3. 解释 seccomp 对系统调用及参数的过滤、`no_new_privs` 的作用与限制。内核文档明确说系统调用过滤本身不是完整沙箱；仅能检查参数值也不能自动理解某个路径属于哪个业务租户。
4. 比较三条执行路径：普通容器直接使用共享宿主内核；gVisor 用 Sentry 在用户态实现应用的系统接口，再通过受限宿主接口工作；microVM 让应用首先进入 guest kernel，宿主一侧保留 KVM/VMM 和虚拟设备边界。gVisor 的 KVM platform 不等于运行一个普通完整 guest Linux VM。
5. 解释 Firecracker 的精简设备模型、jailer、宿主侧 seccomp/cgroup/namespaces；Kata 将 OCI/CRI 容器工作流接到 VM，常见 Kubernetes Pod 内的多个容器可以共用一个 VM。指出 Firecracker 是 VMM，Kata 是容器运行时集成，不能把名称列为同级互斥产品。
6. 把选择落到目标负载：Python 数据库依赖、文件 I/O、网络、浏览器、GPU或特殊系统调用逐项核查兼容性、资源开销和运维要求。加固宿主与 VMM、镜像供应链、侧信道和控制面也是威胁模型的一部分。

一个样例：A17 的脚本故意无限创建子进程并尝试读取宿主密钥。分别判断 namespace、进程数 cgroup、文件挂载策略和 gVisor/VM 边界在哪一步介入；输出是一张攻击路径表。样例只推演机制，不能凭纸面配置声称抵御了真实内核漏洞。

面试核心：“普通容器共享内核；gVisor 增加用户态应用内核；microVM 引入 guest kernel 与虚拟化边界。我按恶意代码能力、允许的宿主接口、负载兼容性和运维成本选型，不按产品名称保证安全。”追问一：VM 是否一定比 gVisor 更安全？比较具体暴露接口、VMM 配置、漏洞与共享硬件，不能给无条件排序。追问二：用了 gVisor 是否还需要 cgroups？需要，资源耗尽与网络策略并未由 Sentry 自动替应用解决。

证据来源与未知：[Linux namespaces 手册](https://man7.org/linux/man-pages/man7/namespaces.7.html)、[cgroups v2](https://docs.kernel.org/admin-guide/cgroup-v2.html)、[seccomp](https://docs.kernel.org/userspace-api/seccomp_filter.html)、[gVisor 架构](https://gvisor.dev/docs/architecture_guide/intro/)、[安全模型](https://gvisor.dev/docs/architecture_guide/security/)、[Firecracker 设计](https://github.com/firecracker-microvm/firecracker/blob/main/docs/design.md)、[Kata 架构](https://github.com/kata-containers/kata-containers/blob/main/docs/design/architecture/README.md)。没有运行逃逸测试，也未测各方案在本任务上的兼容性或速度。

## 第三篇：给沙箱企业身份，同时管住文件、网络和凭据

前置知识：第二篇、Agent 安全、鉴权与授权的区别。可先读 [企业租户](#/lesson/enterprise-agent-tenancy)。中心问题是“允许一段代码访问企业服务时，谁以什么身份授予哪项权限”。

现实问题：S17 成功隔离宿主之后，若仍持有甲公司的管理员 token，代码可以通过合法 API 泄露数据。把长期密钥写进环境变量，也可能让子进程、日志或快照持有它。外部数据中的恶意指令则可能诱导 Agent 申请原本没有的权限。

详细节纲：

1. 画清用户身份、租户身份、Runtime 服务身份、沙箱实例身份、企业工具服务身份。区分调用沙箱管理 API 的控制凭据和沙箱访问业务数据的凭据，不把一把 API Key 解释为全部授权。
2. 定义 A17 的授权集合：只读输入对象、临时目录可写、指定报表库的批准上传动作。路径、对象存储前缀、下载链接、输出检索和日志都要带租户边界；控制面不能接受模型自行声明的 tenant ID 作为事实。
3. 讨论出网默认拒绝、受控代理、域名或服务允许列表、DNS与重定向处理；防范访问云 metadata、内网服务和横向探测。既要限制出口，也要验证请求身份、目标与数据内容，允许访问某个域名不代表可以任意上传敏感文件。
4. 比较按任务发放短期凭据与代理代签/代理调用：凭据作用域、有效期、撤销、审计与代理的失陷风险。把“零凭证”解释为需核验的产品契约，不能从宣传词推出代码从未接触任何认证材料。
5. 用 Kubernetes 的 RBAC、Namespace、NetworkPolicy、存储隔离和 RuntimeClass 分别对应控制面授权、工作负载隔离、网络和运行时选择；Namespace 本身不能构成恶意租户的完整安全边界。私有化/VPC部署还要考虑升级、日志、供应链和运维权限。
6. 对照公开本地 Agent 沙箱实现。Anthropic 与 OpenAI 文档都把文件/网络限制与批准流程拆开；它们为具体本地命令设置边界，不能直接推成企业 SaaS 的跨租户架构。

一个样例：A17 需要安装绘图库并上传结果。选择固定依赖模板，避免临时开放整片公网；确需安装时只通过受控包源。审批通过后，Runtime 为确定的报告摘要和目标位置取得最小上传权限，工具网关记录 tenant=甲、task=A17 和操作标识。脚本要求读取乙公司的 CSV 或访问 metadata 时，按策略拒绝并记录原因。

面试核心：“沙箱降低代码跨越系统边界的风险，企业授权决定边界内的代码还能做什么。我将用户、租户、环境和工具身份串起来，限制文件、出口、凭据作用域并留下审计链。”追问一：VPC 内是否能关闭出网策略？不能，内部服务、metadata和邻居仍有不同权限。追问二：密钥不放进沙箱就安全了吗？代理仍要鉴权、限制目标和操作、保护日志与返回值，且必须考虑自身失陷。

证据来源与未知：[Kubernetes 多租户](https://kubernetes.io/docs/concepts/security/multi-tenancy/)、[RuntimeClass](https://kubernetes.io/docs/concepts/containers/runtime-class/)、[Anthropic sandboxing](https://www.anthropic.com/engineering/claude-code-sandboxing)、[公开 sandbox-runtime](https://github.com/anthropic-experimental/sandbox-runtime)、[OpenAI sandboxing](https://developers.openai.com/codex/sandboxing/)、[公开 Linux sandbox README](https://github.com/openai/codex/blob/main/codex-rs/linux-sandbox/README.md)。腾讯云概述公开了角色访问控制，但未在本轮核验身份交换协议或端到端访问行为；本地产品公开机制也不证明其云端采用相同实现。

## 第四篇：从隔夜审批到崩溃恢复，分清 checkpoint、暂停与快照

前置知识：前三篇、工具重试和幂等性。中心问题是“恢复之后，怎样知道哪些工作完成了，哪些副作用可能已经发生”。

现实问题：保存聊天或图状态无法保住 Python 进程；保存 VM 内存也无法撤销企业报表库里的上传。网络连接、凭据有效期、墙上时间与唯一标识在恢复后可能变化，不能假设“同一状态”意味着外部世界也没有变化。

详细节纲：

1. 将状态分成任务 checkpoint、进程/内存、文件系统、产物对象和外部副作用五层，说明每层的所有者和恢复方法。定义任务停机恢复目标，不能只用一个“支持持久化”覆盖全部需求。
2. 比较保持运行、pause/resume、只保存文件系统、完整快照、从干净模板重建。E2B 当前默认 pause 保留内存和文件，也支持文件系统专用方式；后一方式恢复需冷启动。暂停的同一实例与从快照创建新实例具有不同身份语义。
3. 解释 Firecracker 快照的内存文件、VM 状态文件和用户管理的磁盘文件；磁盘、TAP、vsock 等宿主资源也需协调。快照文件信任、加密鉴权、完整性、容量和保留策略属于集成者责任，CRC不能替代安全验证。
4. 解释 LangGraph 的 thread/checkpoint、super-step 和重放。Functional API 从 entrypoint 边界重放，已完成 task 结果可以复用；未完成 task 可能再执行。对时间、随机值与副作用封装 task，外部写操作还需要幂等契约或结果核对。讨论 `sync`、`async`、`exit` 对持久性和开销的取舍。
5. 推演上传已接受、结果尚未持久化时崩溃的窗口：先保存意图与操作标识，调用远端，记录确认；恢复遇到 unknown 先查询或按幂等契约重试。没有远端幂等/查询能力时，保留未知并交给核对流程，不能承诺 exactly-once。
6. 补上快照克隆的唯一标识/随机状态、临时凭据刷新、断开的长连接、重新授权、旧 worker fencing 和回收。checkpoint 版本迁移、审批过期与环境模板升级也是恢复条件。

一个样例：A17 得到审批并上传报告，报表库已接受 `operation=A17-upload-v1`，随后 Runtime 在写成功状态前崩溃。恢复后的记录是“上传结果未知”。按报表库是否支持按 operation 查询或幂等写入分别推演；文件与内存仍在不改变外部上传事实。给出重试导致重复文件的反例，再说明可验证恢复的条件。

面试核心：“任务 checkpoint、沙箱快照和外部事务有三个不同的恢复边界。我要定义重放起点与副作用标识，恢复时重新核验授权和外部结果，并处理旧执行者和凭据失效。”追问一：为什么 LangGraph task 仍需要幂等？结果落盘之前崩溃时，已开始但未完成的 task 可能再跑。追问二：从同一快照启动一百个实例有什么问题？检查 token、随机种子、唯一身份、共享文件和网络状态，不能将含租户数据的快照变成通用池。

证据来源与未知：[LangGraph Functional API](https://docs.langchain.com/oss/python/langgraph/functional-api)、[Checkpointers](https://docs.langchain.com/oss/python/langgraph/checkpointers)、[E2B persistence](https://docs.e2b.dev/sandbox/persistence.md)、[E2B snapshots](https://docs.e2b.dev/sandbox/snapshots.md)、[Firecracker snapshots](https://github.com/firecracker-microvm/firecracker/blob/main/docs/snapshotting/snapshot-support.md)。E2B 文档包含按区域上线的 pause 拒绝行为，本轮未核验 SDK/地域实际版本；腾讯暂停/恢复接口公开存在，状态保留的精确实现与迁移契约未核验。

## 第五篇：月末高峰下的调度、预热、观测与成本

前置知识：前四篇、基础队列与 [Agent 可观测性](#/lesson/agent-observability)。中心问题是“环境能启动之后，怎样让平台长期以可接受的价格和等待时间运行”。

现实问题：每个报表都从空白环境安装依赖会慢；一直保留所有环境会贵；共享热环境又可能串租户数据。月末突发还可能受控制 API QPS、CPU/内存配额、镜像拉取、IP与存储吞吐共同限制。

详细节纲：

1. 拆解用户等待时间：准入与排队、调度、镜像/磁盘准备、环境启动、任务执行、结果保存。分别观察首次命令可执行时间和任务完成时间，避免用 VMM 启动时间代表端到端延迟。
2. 讨论租户配额、加权公平队列、背压、超时、取消、优先级与重试抖动；容量同时看 CPU、内存、实例数、暂停实例、API QPS 和下游服务限制。区分调度控制面的拥塞与工作负载自身耗时。
3. 比较镜像预热、干净模板、活跃热池与快照恢复。镜像已缓存不保证实例已就绪；快照恢复也可能按需缺页。热池只保存审查过的公共依赖，在绑定租户后建立任务身份和数据，避免复用污染。
4. 用 RuntimeClass 的节点选择、容忍和 Pod overhead 说明异构执行池如何匹配运行时及计入开销。Kata/Firecracker/gVisor 接入、GPU和区域能力需逐方案核验，不能由 RuntimeClass 名称推断已安装可用。
5. 建立运行、空闲、暂停、快照、产物的保留和回收策略。发布模板、内核或 VMM 新版本时灰度并保留兼容恢复路径；杀环境前先核对任务和产物状态。
6. 指标分四层：业务成功与产物正确率；队列/启动/执行/恢复延迟；OOM、拒绝、重试、清理失败和安全策略命中；CPU时间、内存驻留、热池空闲、存储与网络费用。租户/task/attempt/environment 关联可用于日志和 trace，高基数 ID不直接作为所有指标标签，输出内容也须脱敏。
7. 明确成本口径与负载假设，设计一个只测代表性报表的比较：冷启动、预热、恢复分别采集分位数、成功率、单位已验证任务成本。失败/重试和长期快照存储也要计入，不能只比每秒单价。

一个样例：假设突发 40 个 A17 型任务；每个执行 30 秒、需 1 个资源槽，平台有 10 个槽，不含启动和传输时按四批理想执行，最后一批在 120 秒完成。前四批开始等待分别为 0、30、60、90 秒。预热只能影响环境准备时间，不能消除执行容量造成的等待。若额外保持 10 个热槽一小时，空闲储备就是 10 槽小时；它只是资源口径，不是某云产品账单或实测。

面试核心：“我先拆延迟和瓶颈，再做租户公平、配额和背压；预热与快照用来缩减环境准备，池子保持无租户状态。我以成功交付的任务为分母比较成本，并通过运行、恢复和回收指标解释风险。”追问一：为什么预热后 p95 仍差？检查队列、配额、存储、下游工具和恢复缺页，不先归因模型。追问二：暂停是否等于零成本？计算资源停止不代表快照、磁盘、对象、代理与控制面都免费，需查实际计费契约。

证据来源与未知：[腾讯云配额与使用限制](https://cloud.tencent.com/document/product/1814/123815) 公开镜像预热、不同资源配额和接口限流；[RuntimeClass](https://kubernetes.io/docs/concepts/containers/runtime-class/) 公开 scheduling 与 overhead；[gVisor Performance Guide](https://gvisor.dev/docs/architecture_guide/performance/) 区分结构开销与实现开销；E2B snapshots 区分 template 与运行态 snapshot。本文没有采用厂商宣传的启动/并发数字作为比较结果，也未查询当前价格或运行容量测试。

## 面试怎么回答

<details>
<summary>约一分钟的总回答与两个系统追问</summary>

我会把企业 Agent Runtime 设计成受控任务执行系统。控制面记录用户和租户权限、任务步骤、执行尝试、环境租约与结果；数据面用隔离环境运行不可信代码，并限制文件、网络和资源。底层按威胁模型、兼容性和运维条件选择容器加固、gVisor或microVM，业务工具再用最小权限身份访问。长任务要分清图状态 checkpoint、沙箱内存/文件和远端副作用，采用幂等标识、结果核对、凭据刷新与旧执行者约束。平台层再处理公平排队、干净模板和热池、恢复与回收，用任务正确率、分段延迟和成功任务成本评估方案。

追问一：如果所有代码都在 VM 内执行，还会在哪些地方越权？检查控制 API、挂载文件、可访问网络、工具代理、过大凭据、产物下载与日志。VM边界不能判断 u7 是否获准上传某个报告。

追问二：已有 checkpoint 和 VM snapshot，可否承诺恰好一次上传？不能。远端接受写入与本地记录成功之间可能崩溃；需要远端的幂等/查询契约和本地操作账本才能收敛结果。缺少契约时应保留结果未知，不能盲目重放。

</details>

练习：A17 生成了总额为 130 的报表，主管隔夜审批；次日大量租户同时恢复，旧上传 token 已过期，部分实例又在上传成功后丢失确认。画出你的任务记录、沙箱保留策略、恢复顺序和观测方案，指出五篇中每篇负责解决哪部分问题。

<details>
<summary>练习参考思路</summary>

记录租户、用户、task/attempt/environment、输入与产物引用、审批内容摘要、状态版本和上传操作标识。审批等待时，根据是否需要活进程选择暂停或保存产物后销毁；恢复先核对审批有效性、最新权限、输入/产物摘要与外部操作结果，刷新有作用域的短期身份，再排队执行。旧 worker 使用租约/版本约束，沙箱不能自行认领新权限。未知上传先查询或遵循远端幂等契约，无此契约则等待核对。高峰采集队列、环境准备、恢复、上传、结果持久化和清理耗时，同时计算保留与重试成本。第一篇定义职责，第二篇选系统边界，第三篇管身份访问，第四篇确定恢复语义，第五篇管理规模与成本。

</details>
