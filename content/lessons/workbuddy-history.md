# WorkBuddy：长对话怎样整理历史、压缩并继续执行

WorkBuddy 是桌面 Agent 应用。在一项持续多轮的任务里，**历史整理**决定哪些消息和工具结果仍属于这次执行，**上下文压缩（compaction，常简称 compact）**则把这些内容换成更短的表示，为下一轮模型请求腾出空间。前者要选对记录、修好关联，后者要控制体积和信息损失；它们共同影响模型接下来依据什么行动。

假设 WorkBuddy 正在修复订单导出脚本。历史里已有几轮读取、一段很长的日志、一个取消的要求，还有只记下调用却没有结果的测试。用户说“继续检查分页”，应用既要保住“CSV 字段顺序不能变”，也要说明测试是否真的通过。如果只按长度删掉旧消息，约束和测试证据可能一起丢掉；如果原样发送，又可能带入旧任务或超过窗口。本篇沿这一个假设任务解释整理、压缩、失败恢复与续跑。先修是 [WorkBuddy 会话入口](#/lesson/workbuddy-session)和 [上下文压缩](#/lesson/compact)。

本篇范围固定为 WorkBuddy **5.6.2** 安装包的 `cli/dist/codebuddy-lite-wb.mjs`，2026-10-01 只读复核 SHA-256 为 `921e0bb17274e77c2a0f3bb3e8c3f067d4012da8ef2c6542752044fe8b32be93`，与原快照一致。它说明随包交付的可见实现，未确认当前桌面会话实际使用这个 bundle。下文例子和输出均为教学假设；本次未运行供应商代码、模型或压缩命令，未读取用户聊天与配置。[公开证据目录](https://jiuchenm.github.io/workbuddy-study/#S28)提供条目定位，不提供完整源码；压缩后的代码常把多个函数放在一行，所以引用保留行号与必要列号。

## 先整理历史：选活动分支，再配对调用与结果

假设下表条目的 `id` 与 `parentId` 连成当前活动分支，没有更早的压缩边界或会话分隔符。`user-context` 指消息中附带的用户背景或约束，本例让它包含字段顺序要求。表格只呈现教学所需状态，省略产品完整格式。

| 条目 | 内容及已知状态 |
| --- | --- |
| U0 | 修复 `C:/demo/orders/export.py` 的分页；附带保留 CSV 字段顺序的 user-context |
| C1 / R1 | Read 调用及结果；R1 是很长的旧文件内容 |
| A1 | 已完成的助手消息：没有跟随 `next_cursor`，尚未修改文件 |
| U2 | 临时要求先统计测试样例，随后取消 |
| C2 / R2 | 取消前已经完成的 Read 调用及结果；尚无完成的助手回答 |
| I2 | 中断标记，`skipRun=true`，父链能追到 U2 |
| U3 | 继续检查分页，先运行本地测试 |
| C3 | 已记录测试调用，结果缺失，成功与失败均未知 |

**历史拦截器（HistoryAgentRunInterceptor）**是在 Agent 运行入口整理输入的程序。输入是数组且未设置 `skipAddHistory` 时，它先按条件加入新记录，再取得活动分支、去掉自定义条目并处理会话分隔符，之后筛选取消消息、压缩边界、任务范围、截断条目和特定 API 错误消息，最后修复工具配对。这里的活动分支由 `lastMessageId` 与父链确定，特定条件下还使用 `logicalParentId`；已存在于存储中的记录，不一定进入本轮请求。会话分隔符和压缩边界也可能排除更早的条目，所以选取规则无法概括成“最近若干条”。（L113 C2440–4684；L2572 C25303、C26249；[S28](https://jiuchenm.github.io/workbuddy-study/#S28)、[S57](https://jiuchenm.github.io/workbuddy-study/#S57)。）

本例取消过滤生效需要三个条件：I2 是相应中断标记并带 `skipRun=true`，父链可找到真实用户消息 U2，而且 U2 到 I2 之间没有已完成的助手消息。满足后，`filterCancelledPromptHistory` 可以过滤 U2、I2 等有关消息，却显式保留内部类型为 `function_call`、`function_call_result` 的 C2/R2。如果中间已有完成回答，就不能套用这次过滤结论。（L2576 C1132–2428；[S57](https://jiuchenm.github.io/workbuddy-study/#S57)。）

这个选择有实际意义：取消改变接下来要做的事，已经发生的读取、写入或外部提交仍可能有效。本例 C2 只读了样例；若换成已经写文件的调用，过滤 U2 不会还原文件。该函数管理历史视图，没有实现业务回滚，也不能把对这两种内部类型的处理扩展到所有 provider 格式。

接着，`fillFunctionCallResultHistory` 按 **callId（调用关联标识）**连接调用与结果，去掉重复调用、重复结果和没有对应调用的结果，把结果放到对应调用批次后。C1/R1、C2/R2 能配上；C3 没有结果，程序补出空输出、`status=incomplete`、`skipRun=true` 的结果项。补项让输入中的关系完整，但空输出没有证明“零个测试失败”。（L2576 C3429–4247；[S57](https://jiuchenm.github.io/workbuddy-study/#S57)。）

整理后的普通请求可以概括为 U0、C1/R1、A1、C2/R2、U3、C3/未完成补项。模型应从中得到：分页还待修复，统计样例已取消，已发生的读取保留，测试结果未知。至此解决的是记录归属与关联问题，长源码仍可能占据大量空间。

## 缩小输入：工程压缩先省内容，模型摘要再做语义取舍

**工程压缩（engineering compaction）**由程序按规则改写内容。`HistoryEngineeringCompactor` 先取压缩边界后的历史，保留选中范围内的用户和助手文本，将工具调用改写为工具名与部分参数；它跳过 `function_call_result` 等类型，用 `<omitted />` 标注省略的结果，并隐藏参数中的 `content`、`widget_code`、`new_string`。因此 Write 可以留下文件路径，但当时写入的完整正文不再保留。（L335 C33112–L353 C903；[S58](https://jiuchenm.github.io/workbuddy-study/#S58)。）

放回订单例子，A1 中“未跟随 next_cursor、尚未修改”若处于选中范围，可以留下；R1 的长源码被省略。C3 的名称和参数可以留下，缺失或未完成的结果状态却不能从 `<omitted />` 反推出。以后需要精确源码就重新读取，需要测试结论就核对原测试记录。规则可预测，并不使省略后的内容无损。

这里必须分清两个入口：普通请求经过前述 interceptor；**PreMessage 策略**负责发送消息前的压缩，直接将 `session.history` 交给工程压缩器，而工程函数自身未调用取消过滤器。因此，普通请求能过滤 U2，不能证明 PreMessage 的工程文本也已去掉 U2。读取源码时要跟踪实际调用链，不能把一个入口的保障移到另一个入口。（L356 C6087–10385；[S59](https://jiuchenm.github.io/workbuddy-study/#S59)。）

以下是原创的简化语义对照，既非真实运行输出，也不承诺实际摘要逐字如此：

```text
普通请求输入：U2 可被过滤；C2/R2 保留；C3 补 incomplete 结果。
工程压缩文本：选中范围内的用户/助手文字、工具名与部分参数；结果省略。
续跑需要的信息：分页未修复；字段顺序不变；测试结果未知；统计要求已取消。
```

PreMessage 先比较工程文本的**估算 token 量**与目标预算。token 是模型计量输入的单位，这里的估算用字符长度粗略换算，未调用模型 tokenizer 精确分词。此工程压缩器的规则是 `ceil(文本长度 / 4)`，其中 `ceil` 表示向上取整，4 是该实现的换算系数；实际长度取 JavaScript 字符串的 `length`，按 UTF-16 单元计。举个手算假设：包装后的文本长度为 20,000，估算就是 5,000 token；若这次目标为 4,000，就进入模型摘要分支。这个算式解释分支选择，不代表中文文本实际恰好占 5,000 token。（L335 C33103；L353 C764–826；[S58](https://jiuchenm.github.io/workbuddy-study/#S58)。）

**模型摘要**由 `CONTEXT_SUMMARY` 接收工程文本与摘要要求，再用更短文字表达任务状态。足够小的工程结果直接采用，省去这次模型调用；仍过大才请求摘要。摘要失败或为空，就先取最近五个真实用户轮次做工程回退；该回退也没内容时，最后采用原工程结果。目标预算结合模型上下文限制与配置比例，代码在缺少限制时用 128,000 作为回退值；这既非所有模型统一窗口，也不证明最后一种回退一定达到目标。（L356 C6430–10385；[S59](https://jiuchenm.github.io/workbuddy-study/#S59)。）

本例期望摘要明确分页目标、字段约束、已取消的统计要求与未知测试状态，但源码分支只能证明会请求和保存摘要，不能保证这些细节都被保留。体积校验与任务语义校验需要分别做：短摘要仍可能把“尚未测试”误写成“测试通过”。

另一条 COMPACT agent 入口使用 **microcompact（局部结果裁剪）**：对指定工具类型保留最近五个结果，清除更旧结果正文，并对保留项作长度截断；默认截断阈值是 1,500 字符。随后处理图片和隐藏 reminder。它削减送去压缩的材料，仍会损失内容。这里数的是指定工具的结果，前述回退数的是真实用户轮次；一次用户要求可引出多个工具，不能把两种“五个”混为一条通用规则。（L113 C3500 附近；L2712 C12120–L2714；[S65](https://jiuchenm.github.io/workbuddy-study/#S65)。）

## 超长或取消：恢复历史到哪一层

**MaxToken**是紧急超长处理策略。它保存历史数组成员的浅副本和 `lastMessageId`，停止当前流，按边界裁剪后请求摘要。首次失败或摘要为空，且会话仍在压缩、未取消时，会把最后一批工具结果换成截断占位，再重试摘要。调用仍存在，只减少结果体积。实现还有连续 MaxToken 压缩次数的上限检查，达到配置上限会停止压缩循环；不能把它描述成无限重试。（L356 C10574–L358 C4400；[S29](https://jiuchenm.github.io/workbuddy-study/#S29)。）

这条路径在订单任务中的分支顺序如下：

1. 摘要有效时，准备写入摘要；摘要仍失败时，可用最近五个用户轮次做工程回退。
2. 两种方式都拿不到内容，恢复原历史成员和 `lastMessageId`，返回失败，跳过 `sendContinueMessage`。
3. 已拿到内容，但替换前发现用户取消，也恢复原历史并返回失败。
4. 可以继续时，先恢复原历史，再通过 `addHistory` 增加带 `isCompacted`、`isCompactInternal`、`isSummary` 等元数据的条目，标记压缩完成，再按相应条件续跑。

其中 `restoreOriginalHistory` 以展开数组保存原成员，再通过 `splice` 放回；**浅恢复**意味着原对象引用和游标得到恢复，无法据此承诺对象内部所有字段都回到旧值。它更不会撤销文件写入、结束的测试进程或已经提交的外部操作。比如 C3 的测试其实已经运行完，只是结果未写入历史，恢复后依然需要核对进程或输出文件，不能把历史里的空结果当作“从未执行”。（L356 C11597 附近、L358 C1–4400；[S29](https://jiuchenm.github.io/workbuddy-study/#S29)。）

成功后，`markCompactionComplete` 更新压缩时间与 `hasCompactedHistory`，发出历史重载通知。旧记录可以仍在存储中，下一轮按新边界取上下文；增加短表示与销毁旧历史是不同操作。`sendContinueMessage` 如果返回 false，主任务仍可能没有恢复，必须区分**压缩完成**与**续跑完成**。（L356 C11；L353 C3324 附近；[S29](https://jiuchenm.github.io/workbuddy-study/#S29)。）

另一个 Blocking 策略会分别判断等待不到结果、结果不是流、无法提取摘要以及取消等情况。它的 `restoreSessionStateAfterFailedCompact` 主要恢复 `resultSubject` 和 `lastMessageId`，不同于 MaxToken 的数组恢复；部分超长错误还会进入后续截断处理。不同策略的恢复范围需要逐条看，不能统称“失败便完整回滚”。（L358 C5639–14000；[S29](https://jiuchenm.github.io/workbuddy-study/#S29)。）

## 续跑与记忆：约束、任务状态和文件分别核对

普通 Agent 再进入历史拦截器时，会把 COMPACT agent 的工作条目换成提取出的摘要。若输入含内部压缩用户消息，它还尝试从 `session.history` 提取 user-context；当前输入没有同样文本时，在首条消息位置补一个 system reminder，即附加的系统提示。本例把字段顺序写进可识别的 user-context，因此约束有这条补回路径，不必完全依赖摘要器。（L113 C4142–4684；L2576 C404–1066；[S28](https://jiuchenm.github.io/workbuddy-study/#S28)、[S57](https://jiuchenm.github.io/workbuddy-study/#S57)。）

补回仍有条件：原历史里必须有能匹配的上下文，程序还要按提取文本判断当前输入是否已包含它。如果“字段顺序不变”只在一条被排除的普通对话里，既未进入摘要，也不属于可恢复的 user-context，这条机制无法保证找回。接回本例，恢复后应核对目标还是分页修复、字段约束仍在、统计请求没有复活，且测试保持未知直到读到证据。

**长期 Memory（记忆）**另有职责：跨轮次或跨会话提供可再次使用的信息。安装包 memory Prompt 区分云端资料、用户级本地记忆与项目记忆，并写明各自读写范围；这些是给模型的约定，模板存在不证明当前会话已加载、规则已强制执行或写入已成功。本次只读取随包模板，没有读取用户实际记忆。（`workbuddy-memory-system.md` L1–58；[S30](https://jiuchenm.github.io/workbuddy-study/#S30)。）

因此本例要分开看：活动历史决定下一轮模型看到的消息，长期记忆提供补充信息，`export.py` 和测试输出保存任务的实际状态。上下文变短不会清空文件；文件确已修改也不保证摘要正确记住。要继续执行，应将摘要中的状态与实际证据对齐，尤其对结果未知的写入先查再决定是否重做。进程恢复和请求重放的边界见 [WorkBuddy 会话恢复](#/lesson/workbuddy-recovery)。

<details>
<summary>面试怎么回答</summary>

**约一分钟回答：** WorkBuddy 这份实现先整理历史，再按路径压缩。整理时按活动分支和边界选记录，过滤符合条件的取消消息，用 callId 配对工具调用与结果；结果缺失只能补 incomplete。工程压缩按规则省略结果和部分参数，仍过大时才请求模型摘要，两种方式都会损失信息。PreMessage 直接读取历史，不能默认已做普通入口的取消过滤。MaxToken 超长路径包含一次摘要重试、工程回退和取消检查；恢复只覆盖相应历史成员与游标，没有撤销外部操作。成功后建立压缩边界再请求续跑，两个完成状态分别判断。user-context 有补回条件，长期 Memory 和文件状态则独立核对。

**追问一：取消了请求，为什么还保留工具调用？** 取消不能证明先前的操作没有发生。这个过滤器也显式保留两种内部工具类型。保留关联有助于解释已发生的动作，但未收到结果仍只能认为结果未知；副作用是否需要补偿，要由业务层查证和处理。

**追问二：工程压缩是否比模型摘要可靠？** 工程规则可预测，但它明确省略结果和部分参数，可能删掉成功状态的唯一证据。模型摘要能做语义取舍，也可能遗漏或误述。选择要同时看输入预算和必须保住的信息，本次没有测量速度或任务质量。

**追问三：五轮回退能否保证不再超长？** 不能。一轮用户消息可产生很多很长的工具内容，计数并不限制总字数；字符估算也不是精确 tokenizer。PreMessage 的最后回退还能采用原工程结果，不能推导出必然满足目标预算。

<details>
<summary>练习参考思路</summary>

不能补测试通过，缺失结果只支持未知。按已读 MaxToken 分支，替换前发现取消应恢复原历史成员与 `lastMessageId`，返回失败，跳过正常续跑；不能声称本轮压缩成功。浅恢复不会改变外部测试已经结束的事实。下次先查原进程或输出文件、退出状态、测试对应的脚本版本，再核对分页目标、字段约束与已取消要求。如果原结果不足以判断，才决定补读或重跑；不能仅凭历史缺项自动推断需要重做。进程查询、重复执行控制和外部补偿不由这段压缩代码保证。

</details>
