# Context Window：模型这一轮能看到什么

假设一个差旅问答应用已经聊了二十轮。最早的一轮明确说过“只讨论国内差旅，金额都按人民币计算”，最近几轮又贴入酒店说明和报销政策。用户接着问“那这次住宿能报多少”，模型却引用了国际差旅标准。聊天界面里原话还在，为什么回答没有遵守？排查时先看本轮实际送给模型的内容：那条约束可能已经被应用删去，也可能仍在输入里，只是模型没有正确使用。两种情况的修法不同。

读过 [一次 LLM 请求到底发生了什么](#/lesson/llm-basics)，已经知道模型接收消息，再逐个生成 token。上下文窗口（context window）就是这一次生成可使用的 token 容量；它不是聊天页面或数据库能保存的历史长度。本篇继续追问：一次请求能容纳多少消息；消息多起来以后，谁决定留下哪些；输入没有超限，为什么仍可能答错。这里讨论普通文本请求，不要求先学 Transformer 的矩阵计算。

## 窗口限制的是这一轮，不是聊天界面的长度

在常见的自回归文本接口中，已有输入和本轮生成的输出共同占用这个窗口。输入不仅是用户刚打的一句话，还可能包括应用指令、前面的用户消息、模型回答、附带文档，以及消息格式产生的开销。Anthropic 的官方说明也明确把请求中的系统提示、消息、文档和本轮输出纳入上下文计算。[Context windows](https://docs.anthropic.com/en/docs/build-with-claude/context-windows)

“上下文”与“模型训练时学过的知识”需要分开。模型可能凭参数中学到的规律解释什么是差旅，但某份政策本月刚改过、这次订单住了几晚，都应通过当前输入提供。把一段文字发送给模型，也不等于立即把它训练进参数。它首先是本轮可用的材料。

聊天应用可以保存一整年的记录，模型这一轮却只收到其中一部分。界面上能向上滚动到旧消息，只证明应用保存过它；数据库里有文件，也不证明这次请求带上了全文。即使某个接口支持会话 ID，由服务端替应用续接历史，最终仍要组织出有边界的本轮上下文。排查“忘了”时，应该检查实际请求及服务端的上下文管理行为，不能只截一张聊天记录。

窗口通常用 token 标注，而非汉字、字节或页数。不同分词器对相同文本的切分可能不同，英文、中文、代码和表格也没有通用换算比例。工程上应对准备发送的完整请求计数，换模型后重新计数。官方计数端点可能返回估计值，因此还要结合真实响应中的用量核对，不能把“约四千字”直接当成“四千 token”。[Token counting](https://platform.claude.com/docs/en/build-with-claude/token-counting)

## 先留回答的空间，再装入材料

假设接口的总窗口是 8,192 token，单次输出上限是 2,048 token。两个数字表达不同限制：总窗口决定输入与输出合起来能放多少，输出上限限制这一轮最多生成多少。即使几乎没有输入，也不能凭总窗口要求它输出八千 token。反过来，输入已经放了八千 token，也不能再假定还留着两千 token 的回答空间。实际限制和超限处理应查所用模型与接口，下面的数字只用于手算，不对应任何当前产品规格。

给这轮回答预留 1,200 token，再留 300 token 余量，应满足：

$$
I + O + M \leq C.
$$

$I$ 是完整输入的 token 数，$O$ 是计划允许的输出预算，$M$ 是计数误差等因素的余量，$C$ 是总窗口容量。余量是应用自己的预算安排，不是模型必然消耗的一段文本；输出预算是上限，模型可以提前结束。这里还需保证 $O$ 不超过假设接口的 2,048 token 输出限制。

沿用差旅问答。当前问题是：“按已确认的国内差旅范围，酒店每晚 360 元、住两晚，这次住宿能报多少？给出依据，不提交申请。”应用已准备了政策材料，其中相关段落规定：在本例的假设条件下，住宿标准为每晚不超过 400 元，有合规票据；本次票据条件已确认。其他附件用于解释例外情况。假设完整请求各部分的计数如下，所有数字均为教学设定：

| 输入组成 | token 数 |
| --- | ---: |
| 应用的回答规则 | 600 |
| 旧对话，包含此前的模型回答 | 3,300 |
| 本轮问题与订单信息 | 200 |
| 政策正文及附件 | 2,900 |
| 消息格式等开销 | 100 |
| 合计 | 7,100 |

如果只比较 7,100 与 8,192，会以为材料已经放得下。但加上回答与余量，得到 $7,100+1,200+300=8,600$，比预算多出 408 token。根据接口行为，请求可能报错，或者可生成长度受到限制；某些应用还会先裁剪历史。开发者应明确处理超限，不能依赖一个未经核验的自动行为。

这次由应用选择压缩旧对话，而不是让模型自己扩大窗口。旧对话里有 2,500 token 是早期讨论，将其换成一份 600 token 的摘要，保留近期的 800 token 原文。摘要必须写明国内范围、人民币、每晚金额与晚数已经确认、票据条件已满足、只回答不提交。于是历史从 3,300 变为 $800+600=1,400$，输入从 7,100 变为 $7,100-2,500+600=5,200$。现在 $5,200+1,200+300=6,700$，预算还剩 1,492 token。若下一轮还是引用国际差旅标准，至少已经不能只归因为“窗口装不下”；还需检查实际发送的摘要和模型对政策的使用。

在这些假设成立时，期望答案应说明每晚 360 元低于 400 元标准，两晚合计 $360\times2=720$ 元，并指向对应政策段落。这里的 720 元是手算的期望结果；没有实际调用模型，也不表示真实报销资格已经确认。若摘要漏掉票据条件，正确回答就应补问，不能自行补成“已满足”。

假设本轮实际回答用了 850 token，则本轮输入加实际输出为 $5,200+850=6,050$。下一轮如果继续带上全部保留内容，又新增了共 150 token 的问题与格式开销，输入就变成 6,200 token。再留 1,200 输出和 300 余量，合计 7,700。上一轮的输出，会成为下一轮的输入；多轮聊天因此不断增长。预留而没有用掉的 350 token 则不会变成历史。

上述账本限定为普通文本生成。某些接口还会为内部推理等内容计入额外的输出用量，不能只数界面里看得见的答案；具体口径需要按模型文档核对。基础阶段先把输入、输出、余量分清，再处理接口的特殊规则。

## 裁剪历史时，删掉的到底是什么

最容易实现的办法是只保留最近若干轮，但消息长度并不固定，按轮数截取不能保证 token 预算。它还可能删掉最早说过、至今仍有效的限制。因此更合理的做法是先确定当前任务必须保留什么，再按实际长度安排近期对话和补充材料。这里的“必须保留”来自任务要求，不能由“消息比较旧”来否定。

对于还在继续的任务，可以把旧对话压成摘要，再与近期原文一起发送。这类压缩通常称为 compaction。摘要应保留目标、限制、已确认事实、关键依据和未解决问题。原始记录可以继续保存在应用中，需要核对时再取回。Anthropic 的工程文章介绍了这种做法，也指出压缩过度会丢掉后来才显出重要性的细节。[Effective context engineering：Compaction](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

摘要本身也是新文本，会占 token，也可能出错。例如原话是“如果发票合规，就可以按实际金额申请”，摘要若变成“可以报销”，就丢失了条件。压缩后的字数减少了，任务含义却变了。对金额、日期、否定、适用范围等字段，应核对摘要是否保留原意；需要精确引用的条款可以保留原文，不必强行全部转述。

裁剪与摘要是应用管理输入的选择，不代表模型容量自动扩大。应用可以处理很长的任务，是因为它逐轮选择并保存必要信息。当前窗口外的记录若没有重新提供，不能指望模型可靠还原其中的细节。

## 放得下，仍需要验证是否用得好

标称窗口描述允许处理的容量，有效利用上下文描述模型在具体任务上能否找到并正确使用材料。后者不是一个固定的“实际窗口数”：同样长度，找一个订单号与比较多条相互约束的政策，难度就不同。无关材料、重复版本、证据位置和任务复杂度，也会改变回答表现。

《Lost in the Middle》用多文档问答和键值查找任务移动相关信息的位置，发现其受测模型往往更容易使用开头或末尾的信息，而在中间位置表现下降。这是论文对当时模型和任务的实验结论，不能直接推出今天每个模型都会在相同长度下降，也不能承诺把答案放在末尾就一定正确。它说明需要分别检验“接受了输入”和“使用了证据”。[论文摘要与引言](https://arxiv.org/html/2307.03172v3)

在差旅应用里，可以固定问题与政策内容，分别把关键条款放在材料开头、中间和末尾，比较是否都得到 720 元、是否仍保留票据条件、是否引用了正确版本。再加入无关附件，检查结论是否改变。这样的测试能区分输入被裁掉、摘要漏条件和模型误用证据；只有成功接收请求的日志，无法完成这项判断。这里给出的是测试设计，没有声称任何模型已经通过。

更长输入通常也会增加处理工作，具体延迟与费用还受缓存、服务实现和计费规则影响。理解这一点只需认识 KV cache（键值缓存）：它保存已处理 token 的部分中间计算，供后续生成复用，减少重复计算。缓存不把被删掉的对话变成永久记忆，也不会自动增大接口的窗口。其矩阵和显存计算留到后续模型课程。[Hugging Face：Caching](https://huggingface.co/docs/transformers/main/en/cache_explanation)

**约一分钟的口头回答：** 上下文窗口是模型一次生成可处理的 token 容量，常见文本接口里输入和本轮输出共享它。输入包括规则、当前问题、保留的历史和材料，所以聊天界面里的全部记录不一定都进入了模型。我会先为输出留预算，再对完整请求计数，超限时按任务保留关键约束、近期消息和证据，用摘要压缩旧讨论。同时区分标称窗口与实际利用能力：请求放得下，模型仍可能漏掉中间证据，因此要用任务样例检查答案、条件和引用，而不只检查是否报错。

**追问：把输出上限调大，回答一定更完整吗？** 不一定。上限只允许生成更长，不保证利用这些 token；共享窗口下，它还挤占可用于输入的预算。如果完整解释需要的证据因此被删掉，答案可能变长却更不可靠。应先确定任务需要保留的证据，再选择足够的输出预算。

**追问：摘要和只保留最近十轮，应该选哪个？** 最近十轮实现简单，但长度不固定，也容易遗漏早期约束。摘要能跨越较长历史保留任务状态，却有丢失条件或写错事实的风险。连续任务通常可保留经过核对的摘要与最近原文，精确条款另外保留；短任务也可能只需最近消息，选择取决于信息依赖。

**追问：窗口很大，是否就不用筛选材料？** 仍需筛选。重复或冲突的材料会增加模型选错依据的机会，也增加输入处理量。可以先保留相关且版本清楚的证据，再验证长材料下的表现；更大的窗口只是给了更多可用空间。

## 练习：这轮请求该怎样缩减

假设总窗口为 10,000 token，输出上限为 2,000。应用计划留 1,500 token 给回答、500 token 作余量。规则与本轮问题共 900，历史 3,600，政策材料 4,000，格式开销 100，单位均为 token。历史中有 2,800 token 可替换成 500 token 摘要，其余原文需要保留。

请算出原请求是否满足预算、摘要后还能放多少材料。随后解释：如果必须精确引用的旧条款在那 2,800 token 中，能否只保留摘要？

<details>
<summary>参考思路</summary>

原输入是 $900+3,600+4,000+100=8,600$，加回答与余量后为 10,600，超过预算 600 token。允许的输入最多为 $10,000-1,500-500=8,000$。

摘要后历史为 $3,600-2,800+500=1,300$，输入为 $900+1,300+4,000+100=6,300$，剩余输入预算为 1,700 token，因此在其他条件不变时还能加入至多 1,700 token 的材料。

精确引用所需的旧条款应从原始记录取回并保留原文，然后重新计数。摘要可以记录它的适用范围和出处，但不能保证逐字复原。如果保留条款后又超限，可优先移除无关附件；不能只为凑够数字删掉回答所必需的依据。

</details>
