# 工具失败：超时以后能直接重试吗

假设用户确认创建一笔 680 元的差旅费用申请。Agent 调用费用服务的创建工具，等了一秒，只收到“请求超时”。如果此时把超时当作创建失败，再提交一遍，审批列表里可能出现两笔申请：第一次已经写入数据库，只是成功响应在返回途中丢失了。创建申请尚不等于审批通过或支付；这里的费用系统、金额、接口与时间线都是教学假设。

**超时（timeout）只说明调用方在期限内没有收到可信结果。** 它不能证明服务端没有执行，也不能证明已经执行。工具可靠性要解决的正是这个分叉：Agent 如何记录“结果未知”，如何找回同一次操作的结果，以及何时才允许重试。这里的“工具”指 Agent 应用调用的外部能力；本例的工具背后是一项会写入业务状态的服务。前一篇 [Agent 状态](#/lesson/agent-state) 解释了为什么任务信息要保存在对话之外，本篇沿同一笔费用申请使用那份持久化状态。

## 一秒后，调用方究竟知道什么

假设请求在 0.02 秒发出，服务端在 0.40 秒创建了申请 EXP-204，0.41 秒发出的响应丢失。调用方在 1.02 秒触发超时。此时它只知道“没有及时收到响应”；服务端的真实状态需要另查。另一种可能是请求还没到服务端，也会表现为超时。AWS 的幂等 API 文章以创建响应丢失后无法确定资源是否存在为例，解释直接重复创建的风险。[AWS：Making retries safe with idempotent APIs](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

因此，应用至少要区分三个本地结果：`succeeded` 表示取得可信的成功终态；`rejected` 表示取得明确的拒绝结论；`unknown` 表示尚无可信终态。**`unknown` 是一个需要继续确认的状态，不是“确定未创建”。** 如果总预算用完，也只是停止自动尝试，不能把它改写成失败。对用户应说“提交结果尚未确认”，避免引导用户再按一次创建。

读取工具通常可以重复查询，只是会增加延迟和负载；创建、发送、扣减等写入工具可能产生第二个业务对象。应用决定下一步时还要看接口返回的错误语义，不能把所有异常折成一个 `failed`：

| 调用方观察到的结果 | 可以据此确认什么 | 下一步 |
| --- | --- | --- |
| 金额格式错误，且接口保证未提交 | 输入不合法，本次没有创建 | 修正输入；原样重发没有用 |
| 当前用户无创建权限，且服务明确拒绝 | 本次未获授权 | 处理授权，不能用重试绕过 |
| 限流或暂时不可用 | 服务暂时无法正常处理；提交状态仍依契约判断 | 查看该接口是否允许重试与如何确认 |
| 超时、连接中断、响应无法解析 | 没有可信终态 | 保存 `unknown`，查询或安全重放 |
| 返回编号和已提交状态 | 服务报告创建成功 | 保存编号，停止创建 |

HTTP 500 也不足以单独证明“没有写入”：它可能发生在副作用之后。故障是否暂时、操作是否可安全重复，是两个不同的问题；两者都要满足，重试才有意义。

## 先固定“同一次申请”，再发网络请求

调用方需要一个**幂等键（idempotency key）**来标识这次业务意图。用户确认创建这一笔申请时，应用生成操作键，并把键与已确认输入一起持久化；首次网络请求、超时后的重放、进程重启后的恢复，都使用原键和原参数。用户另行确认创建第二笔申请，即使金额、日期与用途完全相同，也应是新的业务意图，用新键。仅凭参数相同无法区分这两种情况，AWS 文章因此强调由调用方提供请求标识来表达意图。[AWS：请求标识与语义](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

本例在首次发送前保存的记录如下。金额用分表示，`68000` 分等于 680 元；短键仅为方便阅读，真实系统需要足够唯一的标识。

```json
{
  "operation_key": "op-8f4c2a",
  "state": "prepared",
  "payload": {
    "amount_minor": 68000,
    "currency": "CNY",
    "category": "travel",
    "description": "差旅住宿"
  },
  "create_attempts": 0,
  "expense_id": null
}
```

恢复时从这条记录取回输入和键，不让模型从新对话里猜金额、用途或操作标识。每次发送只更新尝试记录；重试时随机生成新键，会让服务端把它当作另一笔创建。

有键还需要服务端兑现契约。假设本例的 `create_expense` 在“当前租户、当前用户、幂等键”范围内去重：同键同参返回原申请，同键异参返回冲突。服务端用事务和唯一约束处理并发，并把申请创建与键、参数摘要、申请编号的记录原子地提交。否则可能出现“申请创建了、去重记录没保存”，重放仍会重复创建。AWS 文章明确讨论了去重标识和副作用原子性的要求。[AWS：原子性边界](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

**键本身不保证任意系统上的 exactly-once。** 去重记录有保存期限；过期后旧键可能重新代表一次新请求。跨其他系统的副作用也未必被同一个数据库事务覆盖。具体服务对并发和失败响应的约定各异：Stripe 文档说明它会比较同键请求的参数，保存已开始执行请求的结果（包括某些失败响应），并说明键清理后的行为。这是 Stripe 的接口契约，不能推成所有工具的行为。[Stripe：Idempotent requests](https://docs.stripe.com/api/idempotent_requests)

## 沿原键找回 EXP-204

再给本例后端一项假设能力：`get_expense_operation` 可按操作键查询权威操作记录，返回 `succeeded`、`processing` 或 `not_found`。下面的时间线从已确认输入走到最终用户输出；时间和结果均为人工构造：

```text
0.00 s  调用方持久化 op-8f4c2a 与已确认输入，记录第一次尝试。
0.02 s  调用 create_expense，携带该键和原 payload。
0.40 s  服务端事务提交：创建 EXP-204，保存 op-8f4c2a → EXP-204。
0.41 s  服务端发出成功响应，但响应在网络中丢失。
1.02 s  一秒超时触发；调用方将本地状态记为 unknown。
1.14 s  调用方查询 get_expense_operation(op-8f4c2a)。
1.34 s  查询返回 succeeded 与 EXP-204。
1.35 s  调用方保存 expense_id，状态改为 succeeded，停止创建。
```

假设查询给出这份结果：

```json
{
  "operation_key": "op-8f4c2a",
  "status": "succeeded",
  "expense_id": "EXP-204",
  "amount_minor": 68000,
  "currency": "CNY"
}
```

调用方此时可以告诉用户：“费用申请 EXP-204 已创建，金额 680 元。首次响应超时后，已通过操作记录确认成功。”**确认依据是后端按操作键返回的状态，不是模型觉得两次描述相似。** 这一条路径只有一次创建调用和一次状态查询，业务对象只有 EXP-204。

查询没有直接给出成功时，恢复仍围绕原键进行：

1. 返回 `processing`：保留尚未确认的状态，在总期限内等待并再次确认，不开启第二笔创建。
2. 返回 `not_found`：原请求可能仍在途中，查询也可能有可见性延迟。不能立刻换键。本例在去重有效期内允许以原键、原参数重放；由服务端唯一键和原子写入防止并发产生两笔。
3. 查询不可用、又没有可靠的幂等契约：停止自动重复写入，保留 `unknown`，让后续核对后台记录。此时即使用户需要及时反馈，也不能把未知改称“创建失败”。

这套恢复决策依赖本例假设的查询与幂等契约。接入真实工具时，要先核对它们是否存在、查询结果是否权威、键有效期多长；不能只因请求里有一个 `operation_key` 字段就沿用上述分支。

## 可以重放，也要设停止线

服务暂时过载时，立即连续重放会增加负载。退避（backoff）让每次重试前的等待上限逐步增长；抖动（jitter）在上限内随机等待，使多个客户端不必同时再发。AWS 的退避文章用竞争写入模拟比较这些策略；模拟效果不能当作本例费用服务的实测收益。[AWS：Exponential Backoff And Jitter](https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/)

一种 Full Jitter 表达式是：

$$
d_k \sim U\left(0,\min(d_{\max},b\,2^{k-1})\right)
$$

`k` 从 1 开始，表示第几次重试；`b` 是基础等待上限；$d_{\max}$ 是封顶等待上限；`U(0,x)` 表示在 0 到 `x` 之间均匀抽样；`d_k` 是实际等待时间。假设 `b=0.2` 秒、`d_{\max}=2` 秒，前两次重试的抽样区间分别为 0—0.2 秒和 0—0.4 秒。0.12 秒、0.31 秒都只是可能抽到的值。

**重试预算（retry budget）同时限制次数和总耗时。** 假设最多三次创建尝试（含首次），每次请求最多一秒，总恢复窗口六秒。两次最大等待合计 0.6 秒，三次请求等待上限合计三秒，所以创建路径最多 3.6 秒；状态查询和等待也必须算进六秒，不能在外面无限轮询。这些是可手算的教学数字，实际阈值要依据下游延迟、故障类型和用户等待要求制定。超时还要确认覆盖了 DNS、连接建立等哪些阶段。[AWS：Timeouts, retries, and backoff with jitter](https://d1.awsstatic.com/builderslibrary/pdfs/timeouts-retries-and-backoff-with-jitter.pdf)

应用还应统一计数层级。如果 SDK 对一个逻辑调用最多发送三次，Agent 外层又调用 SDK 三次，底层最多可能收到九次请求。需要查清 SDK 当前策略，由一层控制尝试并记录真实底层次数。Agent 可以解释结果、决定是否请人处理，却不该在看见超时后绕过持久化记录自行再次创建。

要验证这套设计，应故意在“服务端提交之后、响应抵达客户端之前”丢弃响应，再重启调用方并恢复原键。检查是否只存在一个申请，是否最终关联 EXP-204，以及查不到终态时是否仍报告 `unknown`。正常网络下返回成功，无法覆盖最关键的失败位置。

<details>
<summary>面试怎么回答</summary>

**一分钟回答：工具超时后能不能直接重试？**

先看操作有没有副作用及接口契约。超时只说明调用方没收到结果，写入可能已经成功，先保存为结果未知。创建类操作在首次调用前持久化幂等键和输入；之后同一次意图始终复用原键。超时后按操作键查终态，或在服务端确有幂等保证时重放原请求。明确的校验拒绝应修正输入，权限拒绝应处理授权。允许重试时设退避、抖动、次数与总时间预算，避免 SDK 和 Agent 多层放大；预算耗尽仍无终态就报告未知并留下恢复记录。

**追问一：参数相同，为什么还需要幂等键？**

两笔真实申请可能都是 680 元、同一用途。参数相同只说明内容相似，不能说明是同一次业务意图。调用方在用户确认操作时生成键，服务端在约定的身份范围内识别重放，并检查同键参数是否一致。

**追问二：有键就能保证 exactly-once 吗？**

不能。要核对服务端是否持久去重、并发是否受控、键与业务写入是否原子提交、记录何时过期，以及其他副作用是否纳入契约。即使服务端没有重复创建，响应仍可能丢失；可承诺的只是明确范围和期限内的效果。

**追问三：把超时设得很大，能避开问题吗？**

过长等待占用资源，也拖慢反馈；过短会制造多余重试。应按真实延迟分布设定单次期限，并确认它覆盖的网络阶段。总任务期限仍要单独设定，因为等待更久也不能消除响应丢失后的不确定性。

</details>

## 练习：恢复时金额变了怎么办

假设操作键 K 原本对应 680 元，服务端已创建 EXP-204，但调用方只看到超时。Agent 重启后收到“改成 860 元”，准备拿 K 提交 860 元。这属于原请求的重试吗？原结果还未知时，应怎样处理？另假设外层规定最多三次创建尝试，而 SDK 也最多尝试三次，怎样避免九次底层发送？

<details>
<summary>参考思路</summary>

同键改金额已经改变业务意图，不能当作原请求重试。先用持久化的 K 确认原操作。若已创建 EXP-204，应走用户授权的修改流程；若业务规则要求重新申请，也要先处理原申请并确认新的创建意图。不能换键重发，使旧的 680 元申请悬而未决；服务端应拒绝同键异参，暴露恢复错误。

三次上限应由一层负责。SDK 策略符合要求时，外层发起一个逻辑调用并记录 SDK 的实际尝试；若外层负责状态确认和重放，则配置 SDK 避免额外自动重试。查询和等待也要算入总时间预算。具体配置取决于所用 SDK，不能假设所有客户端有同一个开关。

</details>
