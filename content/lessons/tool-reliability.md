# 工具失败：超时以后能直接重试吗

假设用户已经确认创建一笔 680 元的差旅费用申请。Agent 调用工具后等待一秒，得到“请求超时”。它告诉用户“创建失败”，接着又调用一次创建工具。这次返回了申请编号，但审批列表里出现两笔相同申请：第一次其实已经写入数据库，只是响应在返回途中丢失了。

问题出在对“超时”的解释。超时（timeout）表示调用方没有在期限内收到结果，不表示被调用方撤销了操作。对于读取，重复一次通常只是多花资源；对于创建、发送、扣减等会改变外部状态的操作，重复执行可能产生第二个业务对象。本课承接 [Agent 状态](#/lesson/agent-state)，讨论怎样保存未知结果、确认执行情况，以及在有边界的条件下重试。费用系统、金额和时间均为教学假设，创建申请也不代表批准或支付。

## 失败需要分型，未知需要留下来

调用方看到的信息不足以直接还原服务端发生了什么。请求可能根本没发出去，也可能到达后尚未执行，还可能已经提交成功而响应丢失。AWS 的幂等 API 文章正是从“没有收到创建响应，无法确定资源是否存在”的困境出发，说明为什么直接重复创建会产生额外副作用。[AWS：Making retries safe with idempotent APIs](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

处理时应先区分错误的含义，再选择动作：

| 观察到的结果 | 能确认的事实 | 合适的下一步 |
| --- | --- | --- |
| 明确返回金额格式错误，接口保证未提交 | 本次输入不合法且没有创建 | 修正输入，不重复相同请求 |
| 明确返回当前用户无创建权限 | 这次操作未获得授权 | 处理权限问题，不靠重试绕过 |
| 限流或暂时不可用 | 服务当前不能正常接受或完成请求 | 按接口语义判断是否可重试 |
| 请求超时、连接中断、响应无法解析 | 调用方未获得可信终态 | 保存为结果未知，查询或安全重放 |
| 返回申请编号及已提交状态 | 服务报告创建成功 | 保存编号，停止创建重试 |

业务失败意味着服务给出了可解释的业务结论，例如校验拒绝。传输失败意味着通信未可靠完成；两者不能只用一个 `failed` 字段表示。即使是 HTTP 500，也不能脱离接口契约推断“没有任何写入”。临时故障是否值得重试，和操作能否安全重复，是两个需要同时满足的条件。

因此，本地状态至少应区分 `succeeded`、`rejected` 与 `unknown`。重试预算用完，只意味着暂时停止尝试，不能把 `unknown` 改成“确定未创建”。向用户报告时也要保持这层区别：“提交结果尚未确认”比“创建失败，可以重新提交”更符合现有证据。

## 幂等键标识的是同一次业务意图

幂等（idempotency）要求重复同一个操作不会产生额外的目标副作用。创建接口通常需要调用方提供幂等键（idempotency key），让服务端识别“这是上一次请求的重放”。对于同一笔费用申请，首次发送、超时后的重试、进程重启后的恢复，都应使用同一个键；用户明确要创建另一笔申请，才使用新键。

键不能每次请求都随机生成，否则服务端看到的始终是新操作。仅用金额、日期等参数计算哈希也不够：用户可能确实有两笔参数相同的申请。应在创建这次逻辑操作时生成标识，连同经过确认的输入一起持久化，之后每次尝试只增加尝试记录，不更换操作标识。AWS 的文章选择调用方提供的请求标识来表达这类意图，并要求幂等记录与相关写入具有原子性，避免“对象已创建，去重记录却没保存”的空档。[AWS：请求标识与原子性](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

在本例的假设后端中，去重范围是“当前租户、当前用户、幂等键”。第一次请求校验通过后，服务端在一次数据库事务里创建申请，并记录键、参数摘要、最终申请编号。相同范围内的同键同参请求返回原申请；同键异参返回冲突；并发请求由唯一约束和事务控制，不能各自创建一笔。若还涉及其他系统的副作用，单个数据库事务未必能覆盖，需要另外设计恢复流程，不能仅因接口收到了一个键就宣称端到端只执行一次。

幂等保证也有保存期限。服务端删除去重记录后，再用旧键可能被当作新请求。不同产品对失败结果是否缓存、并发请求如何处理的约定也不同。例如 Stripe 会保存已开始执行请求的结果，包括某些失败响应，并比较重放参数；其文档还明确说明键被清理后的行为。这是具体接口契约，不能推广成所有工具的统一规则。[Stripe：Idempotent requests](https://docs.stripe.com/api/idempotent_requests)

## 一次响应丢失后，怎样确认已经创建

假设费用服务提供两项能力：`create_expense` 支持上述幂等契约；`get_expense_operation` 能按操作键查询权威记录，返回 `succeeded`、`processing` 或 `not_found`。这些名称是本课设计的接口。用户确认输入后，调用方在首次网络请求前保存：

```json
{
  "operation_key": "op-8f4c2a",
  "state": "prepared",
  "payload": {
    "amount_minor": 68000,
    "currency": "CNY",
    "category": "travel",
    "description": "差旅住宿"
  },
  "create_attempts": 0,
  "expense_id": null
}
```

`amount_minor` 使用分作为单位，68000 分等于 680 元，避免示例中把元与分混用。金额、用途和键从保存的记录读取，恢复时不让模型重新猜一遍参数。实际系统应使用足够唯一的标识；这里的短键仅便于阅读。

以下是人工构造的时间线，展示每一步知道什么：

```text
0.00 s  调用方持久化 op-8f4c2a 与已确认输入，记录第一次尝试。
0.02 s  调用 create_expense，携带相同操作键和 payload。
0.40 s  服务端事务提交：创建 EXP-204，保存 op-8f4c2a → EXP-204。
0.41 s  服务端发出成功响应，但响应在网络中丢失。
1.02 s  调用方的一秒超时触发，将本地状态记为 unknown。
1.14 s  调用方开始查询 get_expense_operation(op-8f4c2a)。
1.34 s  查询返回 succeeded 与 EXP-204。
1.35 s  调用方保存 expense_id，状态改为 succeeded，不再创建。
```

查询的假设输出如下：

```json
{
  "operation_key": "op-8f4c2a",
  "status": "succeeded",
  "expense_id": "EXP-204",
  "amount_minor": 68000,
  "currency": "CNY"
}
```

最终对用户的回答可以是：“费用申请 EXP-204 已创建，金额 680 元。首次响应超时后，已通过操作记录确认成功。”确认依据是后端按操作键返回的记录，而不是模型认为“两次描述看起来一样”。这里只发生一次创建调用和一次状态查询，服务端业务对象始终只有一个。

如果查询返回 `processing`，保留未知状态并在预算内继续确认。如果返回 `not_found`，也要注意原请求可能仍在途中，或查询存在可见性延迟；不能立刻换新键创建。本例契约允许在去重有效期内用原键、原参数重放 `create_expense`。若原请求已完成，返回 EXP-204；若尚未执行，则由唯一键和原子写入保证不会分别创建两笔。若查询不可用而工具又不支持幂等，安全的恢复路径就是保留未知状态并核对后台记录，停止自动重复写入。

## 什么时候再试，以及试到哪里停

即使可以安全重放，也不应该立即无限重试。服务过载时，更多请求可能让恢复更慢。退避（backoff）逐步拉长重试间隔；抖动（jitter）再加入随机等待，避免大量客户端同时醒来。AWS 的退避文章用竞争写入的模拟比较这些策略；其中效果数字属于该模拟，不能直接当成费用工具的性能收益。[AWS：Exponential Backoff And Jitter](https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/)

一种常见的 Full Jitter 写法是：

$$
d_k \sim U\left(0,\min(d_{\max},b\,2^{k-1})\right)
$$

这里 $k$ 从 1 开始，表示第几次重试；$b$ 是基础等待上限；$d_{\max}$ 是等待上限的封顶值；$U(0,x)$ 表示在 0 到 $x$ 之间均匀抽样；$d_k$ 是本次实际等待时间。假设 $b=0.2$ 秒、$d_{\max}=2$ 秒，两次重试的抽样区间分别为 0—0.2 秒、0—0.4 秒。0.12 秒和 0.31 秒只是可能的抽样值，并非必须等待的常数。

重试预算（retry budget）还应限制总调用次数和总耗时。例如教学策略规定：最多三次创建尝试，包含首次调用；每次请求最多一秒；总恢复窗口六秒。两次最大等待合计为 0.6 秒，三次请求等待上限合计三秒，仅创建路径上限为 3.6 秒，状态查询也必须计入六秒总期限，不能在外面再无限轮询。实际参数应依据下游延迟、故障类型和用户等待要求设定，这些数字不构成通用推荐。

重试由一层代码统一管理，模型负责理解结果和说明状态。若 SDK 每次最多发送三次，Agent 外层又调用它三次，底层最多可能收到九次请求。需要核对 SDK 已有策略，避免层层放大。AWS 的超时文章也指出超时覆盖范围可能遗漏 DNS 或连接建立，并讨论了单点重试、次数上限和下游负载。[AWS：Timeouts, retries, and backoff with jitter](https://d1.awsstatic.com/builderslibrary/pdfs/timeouts-retries-and-backoff-with-jitter.pdf)

实现验证应故意在“服务端提交后、客户端收到前”丢弃响应，再恢复进程并读取原键重放。验收的是只存在一个申请、最终能关联同一编号，以及无法确认时仍报告未知；仅测试正常网络下返回成功，覆盖不到这次事故的原因。

<summary>面试怎么回答</summary>

**一分钟回答：工具超时后能不能直接重试？**

先看操作副作用和接口契约。超时只说明没收到结果，写入可能已经成功，所以要保存为结果未知。创建类操作应在首次调用前持久化幂等键和输入，后续同一次意图始终复用原键。超时后可按操作键查结果，或在服务端幂等保证下重放。明确校验失败就修正输入，权限失败就处理授权。允许重试时使用退避、抖动和总预算，避免 SDK 与 Agent 多层放大。预算耗尽仍不能确认，就报告未知并留下可恢复记录。

**追问一：为什么相同参数还需要幂等键？**

相同参数可能表达两次真实业务意图，例如两笔同额住宿。参数只能说明内容相似，不能说明是不是同一次操作。键在调用方确定业务意图时生成，服务端结合身份范围识别重放，并检查同键参数是否一致。

**追问二：有幂等键就能保证 exactly-once 吗？**

不能仅凭字段存在作保证。还要看去重持久化、并发控制、原子写入、键的保存期，以及其他副作用是否覆盖在契约内。网络响应也仍可能丢失。可以在明确范围内保证重放不额外创建，但不等于任意系统、任意时间都恰好执行一次。

**追问三：为什么不把超时设得很大？**

过长等待会占用资源，也让用户迟迟得不到反馈；过短又可能制造多余重试。应结合真实延迟分布确定期限，并确认它覆盖哪些阶段。总任务期限与单次请求超时也要分别设置。

## 练习：恢复时金额变了怎么办

假设原操作键 K 对应 680 元，服务端已经创建 EXP-204，但调用方超时。Agent 重启后从新消息里读到“改成 860 元”，准备拿 K 提交 860 元。请判断这次调用是否属于重试，并说明在原结果还未知时怎样处理。另假设总预算为三次创建尝试，SDK 内置也最多尝试三次，应怎样避免九次发送？

<details>
<summary>参考思路</summary>

同键却改了金额，已经改变业务意图，不能当作原请求重试。先用持久化的 K 确认原操作。如果已创建 EXP-204，应走用户授权的修改流程；如果业务规则要求重新申请，也必须先处理原申请并确认新的创建意图。不能简单换键重发，让旧的 680 元申请悬而未决。服务端应拒绝同键异参，以便暴露这个恢复错误。

三次上限应由一层负责。如果 SDK 的策略满足要求，就让外层只发起一个逻辑调用，并把 SDK 尝试计入记录；若外层必须控制状态确认和重放，就配置 SDK 避免额外自动重试。还应把查询与等待纳入总时间预算。具体配置依据使用的 SDK，不假设所有客户端都能用同一个开关。

</details>
