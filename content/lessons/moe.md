# MoE：参数很多，为什么每次只用一部分

MoE 是模型内部的一种网络结构，讨论的是一次计算要经过哪些参数，不是让几个聊天 Agent 分工。看到一个模型写着“总参数 236B，每个 token 激活 21B”，很容易产生两个判断：它应该只需要保存 21B 参数，而且速度应当接近一个同规模的小模型。两者都不能直接成立。B 表示十亿；总参数描述模型拥有多少权重，每个 token 激活参数描述一次计算经过哪些权重；存储、计算与跨设备通信是相关但不同的成本。

混合专家（Mixture of Experts，MoE）让模型在一部分网络里拥有多个可选的计算分支，每个 token 只经过其中少数分支。这样可以增加总参数容量，同时避免每个 token 都计算所有分支。DeepSeek-V2 报告的 236B 总参数与 21B 激活参数就是一种具体配置，不是所有 MoE 的固定比例，也不等于其运行显存只有 21B 权重那么多。[DeepSeek-V2 技术报告 v5](https://arxiv.org/html/2405.04434v5)

先修 [Transformer](#/lesson/transformer-basics) 已介绍 attention（让一个位置读取其他位置的信息）与前馈网络 FFN（处理该位置已有的表示）。本篇先把一个普通前馈层替换成四个可选专家，跟踪一次 token 计算，再讨论多 token 与多设备带来的代价。向量、权重和参数规模的手算均为教学假设，没有运行真实模型，也不把例子当作 DeepSeek 的具体实现。

## Dense FFN 怎样变成路由与专家

在普通的稠密前馈网络（dense FFN）中，同一层的所有 token 都使用同一套 FFN 权重。注意力已经让每个位置吸收上下文信息，FFN 再对该位置的隐藏向量做变换。这里说“逐 token”，并不代表 token 没有上下文；它进入 FFN 的表示已经经过前面的网络。

一种常见 MoE 做法，是把这个 FFN 换成路由器（router）和多个专家（expert）。每个专家仍是一套 FFN 参数，输入与输出维度应与所在层兼容。路由器读取 token 的隐藏向量，为各专家计算选择分数，选出得分最高的 $k$ 个，再对这些专家的输出加权求和。

“专家”是网络子模块的名称，不是独立的聊天机器人，也不是人为事先指定的数学老师、代码老师。训练可能形成某些分工，但没有检查证据就不能给每个专家贴上稳定语义标签。同一句话中的不同 token 可以选择不同专家，同一个 token 到另一层也可能走另一组专家。

DeepSeekMoE 论文从这种替换 FFN 的基本结构出发，提出细粒度专家划分与共享专家，目标是减少不同路由专家反复学习共同内容的冗余。这里的“目标”和论文消融结果属于作者的架构主张，不应扩展成所有 MoE 都已达到完美分工。[DeepSeekMoE v1，第 2、3 节](https://arxiv.org/html/2401.06066v1)

## 四个专家、top-2 的完整手算

设一个 token 进入本层时的隐藏向量为 $h$。路由器为四个专家产生分数 $s=(0.1,0.4,0.3,0.2)$，选择最大的两个，即专家 E2 与 E3。这里的分数是选择信号，不是“专家回答正确的概率”。本例采用选中后重新归一化的加权约定：

$$
w_2=\frac{0.4}{0.4+0.3}=\frac47,\qquad
w_3=\frac{0.3}{0.4+0.3}=\frac37
$$

$w_2$ 与 $w_3$ 是两个专家输出的权重，总和为 1。真实模型的门控分数是否重新归一化、是否另有缩放，需要看具体架构；这里明确选择一种便于手算的规则，不把它冒充 DeepSeek 论文中的完整门控公式。

假设只为显示计算，将专家输出简化成二维向量：$E_2(h)=(2,0)$，$E_3(h)=(0,3)$。两个未选中的专家无需计算此 token 的 FFN 输出。路由部分的合成结果为：

$$
y_{\text{routed}}=\frac47(2,0)+\frac37(0,3)
=\left(\frac87,\frac97\right)
$$

$y_{\text{routed}}$ 仍是隐藏表示，而不是输出文字。它会经过后续残差连接与其他层，最后才产生词表上的预测。不能把两个专家的二维向量理解成两个完整答案再让另一个模型投票。

再加入一个共享专家（shared expert）S。它对每个 token 都运行，不参与这四个路由专家的 top-2 竞争。假设其输出为 $S(h)=(1,1)$，本例将它直接与路由部分相加：

$$
y=S(h)+y_{\text{routed}}
=\left(\frac{15}{7},\frac{16}{7}\right)
\approx(2.1429,2.2857)
$$

这里的 $y$ 只是 MoE 分支的输出，尚未加上残差输入，也省略了具体模型的归一化与缩放。共享专家不是把四个专家的结果平均一下，而是另一套始终参与的可训练 FFN。DeepSeekMoE 的共享专家隔离设计希望它承载跨 token 常用的信息，使路由专家不必各自重复承担全部共同内容；但共享专家到底学到了什么，需要分析与实验，不能仅由名字推出。

共享专家也不是免费增加的。上面的演示在原 top-2 外又加一个共享专家，所以计算量增加了。DeepSeekMoE 论文为了在比较中保持计算预算，会相应调整其他被激活的专家数。读架构时要分清是在相同预算下重新分配，还是实际上多运行了一个分支。

## 专家变细，组合更多，也更难调度

如果四个专家太宽，可以把每个 FFN 的中间维度减小，得到更多小专家。在一种理想化比较中，把每个专家分成两个半宽专家，并把每 token 选择数从 2 增至 4，专家参数与主要矩阵计算量可大致保持，而可选择的组合更丰富。这就是细粒度划分的动机之一，实际还有路由、核函数和通信成本，不能只用专家数量证明效率。

DeepSeek-V2 的报告给出了具体例子：除第一层外，FFN 被替换为 MoE；每个 MoE 层有 2 个共享专家与 160 个路由专家，每 token 激活 6 个路由专家。这里是“2 个始终运行，加 160 个中选 6 个”，不能读成所有 162 个只运行 6 个。论文还采用另一种 attention 设计，因此报告中的整体效率不能全部归因于 MoE，也不能把 KV cache 的改善算到专家选择头上。[DeepSeek-V2，第 3.1.2 节](https://arxiv.org/html/2405.04434v5)

对于教学例子，一个 token 只选 E2、E3，不代表这一批 token 只使用两套专家。下一个 token 可能选 E1、E4；一批输入合起来可以覆盖全部专家。所谓稀疏激活是对单个 token 的选择而言，不能据此假设其他专家在整个请求期间始终不用。

## 负载均衡要同时考虑学习与硬件

假设一批有 8 个 token，每个选择 2 个路由专家，总共形成 16 次 token 到专家的分配。理想均匀分配是每个专家 4 次，但若实际计数为 E1 收到 7 次、E2 收到 6 次、E3 收到 2 次、E4 收到 1 次，前两个专家会繁忙得多。

这会带来两类问题。训练上，少数专家长期接收大部分 token，其余专家得到的使用与学习机会不足，可能出现路由塌缩（routing collapse）。系统上，即使专家参数平均分到设备，每轮完成时间仍可能被最忙的设备拖慢。硬件等待不会因为理论上每 token 只用了 top-2 就消失。

负载均衡（load balancing）因此要让学习到的路由兼顾任务与资源。DeepSeekMoE 和 DeepSeek-V2 报告中使用额外的均衡损失，对专家或设备上的分配施加约束；V2 还区分通信负载。它们不是硬性要求每个小批次都完全均匀，约束太强也可能妨碍有用的专家分工。需要同时观察任务损失、专家分配和设备利用率。[DeepSeekMoE，第 3.3 节](https://arxiv.org/html/2401.06066v1)、[DeepSeek-V2，第 2.2.3 节](https://arxiv.org/html/2405.04434v5)

容量处理也会影响实际结果。当某个专家接收过多 token，系统可能需要更大的缓存、额外调度，或采用架构定义的溢出策略。是否丢弃某些路由、怎样限制容量，不是 MoE 这个名称就能确定的属性，必须读具体模型与运行时的契约。

## 专家分布在不同设备时，向量需要移动

当所有专家放不进一台设备，可以使用专家并行（expert parallelism）：把不同专家部署到不同设备。token 的隐藏向量要被发送到选中专家所在设备，计算完成后，再把输出送回并按权重组合。传递的是模型内部张量，不是 Agent 之间发送自然语言消息。

若一个 token 的目标专家散落在多台设备，通信会更复杂。即便两种路由选择的专家数量相同，它们涉及的设备数也可能不同。DeepSeek-V2 因此采用设备受限路由：先选择允许的设备集合，再在这些设备上的专家中选 top-k，限制一个 token 涉及的设备数量。论文报告的实际训练配置将路由专家分布在 8 台设备上，每 token 最多送至 3 台；这些是该版本的系统配置，不是所有 MoE 的要求。[DeepSeek-V2，第 2.2.2、3.1.2 节](https://arxiv.org/html/2405.04434v5)

这是一项取舍：减少跨设备通信可能限制自由选择专家的空间，设备内部也可能出现不均衡。速度还取决于批大小、网络带宽、专家矩阵计算是否足够大，以及通信与计算能否重叠。只报告激活参数比例，无法预测实际吞吐或单用户延迟。

## 总参数、激活参数与显存分别怎么算

回到四个路由专家加一个共享专家。假设每个专家有 100 万参数，这一层的 attention、router 与其他始终参与部分合计 200 万参数。总参数为 5 乘以 100 万，再加 200 万，共 700 万；一个 token 使用两个路由专家、一个共享专家和其余部分，共 500 万激活参数。

路由专家部分选了二分之一，并不意味着整层只有二分之一的计算。共享专家、attention、路由、归一化与残差相关操作仍存在；attention 的工作量还随上下文和执行阶段变化。500 万除以 700 万也只是本例的参数计数比例，不能直接当作 FLOPs、显存或运行时间比例。

假设所有权重以每参数 2 字节保存，700 万参数的原始权重存储为 1400 万字节，即十进制约 14 MB。不能因为每 token 激活 500 万，就只准备 10 MB 然后丢掉其余权重：其他 token 可能马上选中它们。权重可以分片到多台设备或换入换出，但分片改变位置，卸载增加数据搬运，模型拥有的参数不会因此消失。

实际显存还包含 KV cache、临时激活、通信缓冲和运行时开销；训练则另外需要梯度、优化器状态及可能的高精度权重副本。量化、并行方式与卸载都可能改变设备占用，所以“每 token 激活多少 B”不能单独回答“几张卡能运行”。同样，总参数很多也不保证质量更高，还需要足够训练数据、有效路由与可用的系统吞吐。

MoE 与多 Agent 的差别到这里就清楚了：MoE 是模型层内对 token 张量选择计算分支，专家共享整个模型的训练与表示接口；多 Agent 则是应用层让多个执行角色交换任务与结果。它们可以同时存在，但不是同一种扩展方式，不能用“有很多专家”推出系统会规划、调用工具或自动协作。

**一分钟回答：** MoE 常把 Transformer 的 dense FFN 换成 router 和多个专家 FFN。每个 token 根据隐藏表示选 top-k 专家，再加权合成输出；共享专家则对所有 token 都运行。这样可以增加总参数而只计算其中一部分，但整层仍有 attention 和其他公共计算。总参数决定权重容量，激活参数描述单 token 路径，设备显存还要计入实际驻留权重、KV cache 与缓冲。路由还要处理负载不均和跨设备通信，实际速度不能由参数比例推出。专家是模型内部子网络，不是多个独立 Agent。

**追问一：为什么总参数很大，显存不能只按激活参数算？** 因为不同 token 会选择不同专家，未被当前 token 使用的权重仍需可访问。分片或卸载能改变单设备驻留量，却会引入系统约束；还要加上缓存、临时激活和通信空间。

**追问二：共享专家是不是让 top-k 失去稀疏性？** 它增加了一条始终计算的路径，但路由专家仍只选少数。是否增加总计算取决于预算安排，不能只看名称。本篇示例额外加了共享专家，计算增加；论文可通过减少其他激活专家保持预算。

**追问三：为什么不能让 router 总选最喜欢的两个？** 单个 token 的选择还要放到整体训练与硬件负载中看。长期只用少数专家可能使其他专家缺少训练，并让部分设备成为瓶颈；均衡约束能缓解，但也要防止过强约束损害任务效果。
