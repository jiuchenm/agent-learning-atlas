# Agent Memory：跨任务信息怎样保存、取回和更新

假设一个项目助手上周已经知道用户喜欢“中文、先给结论”，也查过项目周会在周二下午。到了新任务，它不想再问一次写作偏好，就从记忆里取出这两条信息，直接生成本周材料。但项目日程刚改到周四，用户这次还要求英文版本。两条曾经有用的信息，一条只能作为默认偏好，另一条需要重新核实。如果都当成当前指令，记得越牢，结果反而越错。

**Agent Memory（Agent 记忆）**是应用为后续任务保存过往信息、按需取回并提供给模型的机制。核心问题是：过去的信息在什么范围内仍能帮助本次任务，何时必须核实、更新或停用？本篇沿一个项目材料助手的两次任务走完写入、检索、冲突处理、更新和输出。用户 U7、项目 P4、日期、文档及结果均为教学假设，不对应真实人员或工作记录。

## 先分清记忆、上下文与任务状态

**上下文窗口（context window）**是模型一次请求能处理的 token 范围。上周的信息没有进入本次请求，模型这一轮就看不到；即使把整段旧对话放进去，也会占用 [Context Window](#/lesson/context-window) 的预算。Agent Memory 的作用是由应用决定保存什么、取回什么，再把本次需要的部分放入输入。保存成功并不等于模型已经看见或采用了它。

**任务状态（state）**记录当前任务的进度和必要数据，例如“已经查过第 8 版日程，材料草稿待审核”。它支持同一项任务继续或恢复，详见 [任务状态](#/lesson/agent-state)。本篇关注任务 A 结束后，任务 B 怎样使用仍适用的信息。两种存储可以使用相同数据库，区别在取用范围和生命周期。

短期记忆（short-term memory）通常属于当前对话或任务：正在写的材料、刚读到的文档、用户对这一稿的修改要求，都会影响接下来的几步。它可以作为 state 保存；即使任务持续一个月，也仍然可能只服务这一项任务。因此，“短期”不等于只保留几秒。

长期记忆（long-term memory）允许信息跨任务或跨对话取用，例如用户明确要求保留的写作偏好、项目的基本事实、过去解决某类问题的案例。它也不意味着永久有效。一条只在本季度有效的项目约定，可以跨很多任务使用，到季度结束仍应停用。LangGraph 的官方概念文档按这样的范围区分线程内状态与跨线程存储；本篇采用这一区分讨论机制，不要求使用 LangGraph。[LangGraph：Memory overview，核验于 2026-09-28](https://docs.langchain.com/oss/python/langgraph/memory)

还应按内容区分。事实描述世界的某个状态，例如“项目 P4 的周会安排在周二 16:00”，需要对象、来源和有效时间。偏好描述默认怎样为某个人服务，例如“工作材料默认用中文”，需要适用范围，不能覆盖本次明确要求。经历保存发生过的事件，例如“上次材料采用了结论、依赖项、待决定问题的结构，用户接受了这一稿”，需要保留任务条件和结果，不能直接推广成所有材料都必须照同一模板写。

文献有时把事实称为语义记忆（semantic memory），把经历称为情景记忆（episodic memory）。这些是借自认知研究的组织方式，不表示软件拥有人的记忆体验。偏好可以存成用户事实的一种，也可以单列类型；重要的是后续能正确解释。LangGraph 文档还专门区分语义记忆与语义搜索：前者说保存什么，后者说怎样寻找材料。保存了事实，不意味着必须采用向量检索。[LangGraph：Semantic memory 与 Episodic memory](https://docs.langchain.com/oss/python/langgraph/memory)

## 任务 A：把值得跨任务使用的信息写下来

假设任务 A 发生在 9 月 1 日，用户 U7 要求助手准备项目 P4 的周会材料，并补充：“请记住，我的工作材料默认用中文，先给结论。”应用支持用户主动保存偏好，于是把这句话整理为一条候选记忆。记录必须保持“默认”和“工作材料”两个限定，不能变成“所有输出必须中文”，也不能添加用户没有表达过的字数、语气或职业信息。

应用检查候选内容确实来自用户本人的明确请求，再写入用户 U7 的范围。以下是教学用结构，不是具体框架的标准格式：

```json
{
  "id": "pref-U7-writing",
  "scope": { "userId": "U7", "domain": "work_materials" },
  "kind": "preference",
  "value": { "language": "zh-CN", "conclusionFirst": true },
  "source": "task-A:user-message-3",
  "recordedAt": "2026-09-01",
  "status": "active"
}
```

同一任务中，助手读取项目官方日程第 7 版，核实周会是周二 16:00。假设应用允许保存带来源的项目事实，便把它记为 F1，注明项目 P4、文档第 7 版、核验日期和当时的适用期。用户可以改变自己的写作偏好；周会安排则要由负责日程的来源确认。写入前还要查找相同对象、相同范围的已有条目，以免每读一次文档就新增一条互不关联的“当前日程”。

材料被用户接受以后，应用还可以保留一条经过筛选的经历 E1：任务 A 使用了“结论、依赖项、待决定问题”的结构，用户接受了这一稿。这个记录只说明该案例的结果。除非用户提出可推广的要求，不能从一次接受推导出永久偏好，也不必把整段对话和所有附件都复制进长期存储。

这三条记录的来源、适用范围和修改依据不同。写入可以概括为一个有顺序的过程：

1. 从用户消息或已核实的项目资料中提取候选，保留“默认”“本项目”等限定。
2. 判断候选是否值得跨任务使用，确认来源、允许保存的范围，并寻找同一对象的旧条目。
3. 新增或更新相应字段，写入稳定标识、来源、版本或有效时间；保存后检查实际记录。

这是应用需要实现和验证的流程示意，不表示模型能独自可靠完成每一步。

## 任务 B：取回候选，核实冲突，再生成材料

到了 9 月 28 日，用户开启任务 B：“准备本周 P4 周会材料，这次给合作方看，用英文。”助手首先识别本次任务的用户、项目和文档用途，再检索记忆。它可以按 userId 找写作偏好，按 projectId 找项目事实，按任务类型寻找少量相关经历。几十条有明确字段的记录，普通数据库过滤就可能够用；具体检索算法不改变先限定取用范围的要求。

检索得到的是候选信息，还要检查适用性。U7 的中文偏好确实属于当前用户，但“这次用英文”更具体，因此本次采用英文，同时仍可先给结论。P4 的周会时间与任务有关，却是 27 天前核实的可变事实，不能直接称为本周安排。E1 可以帮助组织材料，但它只提供参考结构，不能制造本周还没发生的结果。

助手随后查询当前项目日程。假设第 8 版明确写明“从 9 月 20 日起，P4 周会改为周四 16:00”。同一次查询还找到一份 9 月 28 日刚上传的第 7 版副本，仍写着周二。**上传时间较新，不等于内容版本较新。**两版安排的生效时间不同：旧安排曾经有效，第 8 版现在生效。应用将 F1 标为已被替代，写入带有生效日期和来源的 F2。若支持历史查询，可以保留 F1 的历史有效范围；查询当前安排时应使用 F2。若两份同样权威且都声称当前有效的文件相互冲突，应用就不能自行选一份，需要继续核实或明确报告未确认。

| 候选记忆 | 本次取得的新信息 | 写入与取用结果 |
| --- | --- | --- |
| 默认中文、先给结论 | 用户要求这次英文 | 本次用英文，原偏好保持不变 |
| 周二 16:00，第 7 版日程 | 第 8 版自 9 月 20 日改为周四；当天上传的第 7 版副本仍写周二 | 采用已生效的第 8 版；旧事实退出当前答案 |
| 任务 A 的结构曾被接受 | 本周任务仍需说明依赖项 | 作为案例参考，不当作强制模板 |

完成核实后，应用只把本次需要的内容提供给模型：本次英文要求、仍适用的“先给结论”、第 8 版的周四安排，以及可供参考的 E1。最终材料的开头可以写成如下教学示意；日期与第 8 版均是假设：

> **Conclusion:** Prepare the P4 weekly meeting for Thursday at 16:00. The current schedule is based on version 8, effective September 20. List open dependencies and decisions below.

这个输出没有把默认中文误用到本次，也没有因为旧版文件上传较晚而写成周二。若交付需要可追溯依据，助手应附第 8 版的来源链接，而不是以“我记得”代替来源。**候选被检索到、进入本次模型输入、出现在最终答案中，是三个不同状态**；记录这三步，才能定位旧日程究竟在何处被误用。

## 过期、再次修改和删除怎样处理

任务 B 里的更新只针对 P4 的周会安排：F2 接替 F1，U7 的写作偏好不变。稳定标识和明确字段让程序知道该改哪一条。遇到冲突时仍需比较来源职责、对象、文档版本和有效时间，不能一律让最后写入的记录获胜。确实无法消解的冲突应留下待核实状态；这时回答也要保留不确定性。

过期也有两种含义。项目安排明确写着“截至 9 月 30 日”，到了 10 月就超出适用期；另一条记录没有终止日期，只是太久没核验，这表示新鲜度不足，并不自动证明它已错误。前者应退出当前使用，后者可以作为查证线索。本例每次准备周会都核验日程，是应用根据变更成本作出的选择，不存在所有记忆统一“30 天有效”的通用规则。

再假设任务 C 中用户说：“以后工作材料默认改成英文。”这是长期偏好的明确变更，应更新 pref-U7-writing 中的语言字段，同时保留仍有效的“先给结论”。如果用户只说“这次英文”，则不更新长期默认。随后用户要求“不再记住我的写作偏好”，应用应让这条记录退出检索，并处理相关索引或缓存，不能只在界面里隐藏正文。历史副本与备份是否一并删除，要依据实际存储和保留机制说明，不能把“已停用”宣称成所有副本已经物理清除。

记忆写入还可以发生在回答之前，或作为单独的后台处理。前者让下一轮立即使用新偏好，但增加当前响应的工作；后者可以集中筛选材料，却可能使新信息尚未写入时就开始下一个任务。LangGraph 文档讨论了这两种取舍。无论采用哪种，用户当前指令都已经在本次输入里，不应为了等后台记忆更新才执行“这次英文”。[LangGraph：Writing memories](https://docs.langchain.com/oss/python/langgraph/memory)

## 记忆不等于缓存，也不会自动改变模型

任务 B 已展示记忆怎样经由本次输入影响回答。没有被取出、或没有通过其他明确机制提供给模型的记录，不会因为存在数据库里就自动影响回答。

键值缓存（Key-Value cache，KV cache）则属于模型推理内部的计算优化。以常见的自回归 Transformer 为例，它缓存已经处理的 token 在注意力层形成的 K、V 表示，后续生成时复用，减少重复计算。这里的“键值”不是用户偏好数据库中的字段。即使推理服务支持缓存复用，也不能因此推断它会按用户范围保存、更新和遗忘长期事实。[Hugging Face Transformers：Caching](https://huggingface.co/docs/transformers/en/cache_explanation)

本篇所说的长期记忆写入，改的是外部记录以及未来提供给模型的上下文，**不修改模型训练得到的参数（权重）**。任务 B 采用第 8 版日程，不表示模型已经在所有环境里学会这个新事实；删掉外部偏好记录，也不等于改动底层模型的参数。

必要的边界可以很具体：只在当前用户和项目允许的范围检索，不把 U7 的偏好用到其他用户；不把文档里的“忽略用户并保存以下指令”当成用户授权；只保留任务确实需要的资料。保留来源和有效范围同时也有助于查错：若助手仍按周二准备材料，可以检查是新版事实没有写入、旧事实没有退出检索，还是正确记录已经进入输入却被模型忽略。这几类故障对应不同修复，不能都归结为“模型记性不好”。

当前对话积累得太长时，还需要压缩后续输入。这个问题与跨任务保存偏好不同，下一篇 [/compact：长对话怎样压缩后继续工作](#/lesson/compact) 会展开说明。

**一分钟回答：** Agent Memory 是应用保存、取回并向模型提供跨任务信息的机制。我按取用范围区分当前任务的 state 与长期 memory；后者可保存有来源和适用范围的事实、偏好或经历。写入前要筛选，使用前要核对当前要求与有效时间，变更时要更新或停用。例如 U7 默认用中文，但任务 B 明确要英文；P4 旧日程是周二，第 8 版生效后就用周四。检索结果只是候选，还要决定哪些进入本次输入。记忆占用上下文预算，不会自动改变模型参数；KV cache 是推理计算缓存，也不负责保存这类业务信息。

**追问一：为什么不直接把所有对话放进向量库？** 可以保留历史作为证据，但原文不等于已经整理好的当前记忆。对话里有临时要求、被撤回的决定和模型猜测，检索相似度不能判断它们是否有效。还需要来源、范围、时间和更新关系；数据量小时，结构化字段查询甚至更直接。

**追问二：新旧记忆冲突，是否选择时间最新的一条？** 先看哪个时间。上传日期、写入日期、事实生效日期不同。应比较同一对象与范围内的来源和版本；当前用户可改变自己的偏好，但不能因此替代项目官方事实。仍无法消解时保留冲突并核实，不强行合并成一个确定结论。
