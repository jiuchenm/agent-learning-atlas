# 一次 LLM 请求到底发生了什么

假设你在写一个订单问答页面。用户输入“订单 A17 明天能到吗？”，程序把这句话发给大语言模型（Large Language Model，LLM），几秒后收到“可以，明天送达”。页面能跑了，问题却刚开始：模型在哪里查了订单？为什么再问一次变成“预计明天送达”？既然只是一次函数调用，为什么回答会变？

先固定这个教学场景：应用已经通过普通数据库查询拿到订单 A17 的记录，其中只有“预计周三送达”，没有履约保证。今天是周二。订单、日期和后面的概率都是假设数据，不代表实际商家或模型测试。我们要让应用依据这条记录回答问题，同时弄清输入与输出之间发生了什么。本文只讨论常见的自回归文本生成；多模态输入和更复杂的推理服务留到后续。

## 从页面上的一句话，到模型的输入

用户看见一个输入框，后端通常组织的是一组消息（message）。一条消息至少说明谁在说话，以及说了什么。下面是描述数据结构的 JSON 示例，不是任何服务可直接执行的完整请求：

```json
{
  "messages": [
    {
      "role": "system",
      "content": "根据提供的订单记录回答。保留预计、不确定等限定，不承诺确定到货。"
    },
    {
      "role": "user",
      "content": "今天是周二。订单记录：A17，预计周三送达。问题：订单 A17 明天能到吗？"
    }
  ]
}
```

`system` 在这里承载应用设置的行为要求，`user` 承载本轮资料与问题，生成的回复通常记为 `assistant`。消息是应用组织对话的结构。进入模型前，聊天模板（chat template）会把角色、消息边界和正文格式化成模型约定的序列。不同模型的控制标记可能不同，不能因为两个接口都接受 `messages`，就假设底层格式完全相同。[Hugging Face 的 Chat templates 文档](https://huggingface.co/docs/transformers/main/chat_templating)实际展示了同一消息列表怎样转成不同模型的格式。

接着是分词器（tokenizer）。这里的“分词”容易让人误以为它只按中文词语或英文空格切分；更准确地说，它把文本编码成一串 token ID。Token 是词表中的一个单位，可能对应一个词、词的一部分、标点，或者更细的字节片段。它不是“一个字”的固定别名，也不是一个知识点。切分规则和词表属于具体 tokenizer；同一段中文换一个 tokenizer，数量可能变化。[Hugging Face 的 Tokenizers 课程](https://huggingface.co/learn/llm-course/chapter2/4)解释了词、字符、子词三种切分粒度以及从 token 到数字 ID 的转换。

为了把流程看清，暂时假设一个教学 tokenizer 会把答案“预计周三送达。”切成 `预计 | 周三 | 送达 | 。`，对应 ID 为 `41, 52, 63, 7`。这些 ID 是人为编的，不能拿去调用真实模型。数字本身没有“周三比预计大 11”的含义，它们只是词表索引。实际工作应使用目标模型配套的 tokenizer 计数，不能按字数直接得出精确 token 数；消息边界等控制标记也可能占用输入。

这时已经能定位第一个常见错误。如果后端只发送“订单 A17 明天能到吗”，没有发送日期、记录，也没有安排任何查询，模型并未因此获得这笔订单的当前状态。它能生成很像客服回答的句子，但这个能力不能补上缺失的记录。我们把记录放进输入，是应用提供了证据。模型收到的是这段证据的文本表示。

## 一段回答怎样逐步长出来

常见的自回归语言模型会根据当前输入及已经生成的内容，计算下一 token 的候选分数。生成程序把分数转换为概率，再按照选取规则决定接哪个 token。选出的 token 加到序列后面，成为下一步的条件。“自回归”（autoregressive）在这里指输出会继续参与后续预测。它并不是先写好一整篇答案，再由页面逐字放映。[Hugging Face 的生成说明](https://huggingface.co/blog/how-to-generate)用条件概率解释了这种逐步生成方式。

继续使用教学 tokenizer。为了省去庞大的真实词表，假设第一步只有下表三个候选，概率相加为 1；真实模型的候选集合通常大得多。

| 当前已生成内容 | 下一 token | 假设概率 |
| --- | --- | ---: |
| 空 | 预计 | 0.60 |
| 空 | 可以 | 0.30 |
| 空 | 无法 | 0.10 |

如果这一轮选中 `预计`，下一步会在“输入消息＋预计”这个条件下重新计算。为完整走完例子，假设之后选中的 token 依次是 `周三`、`送达`、`。`，最后是结束标记 EOS（End of Sequence）。输出 ID 为 `41, 52, 63, 7, EOS`，解码并去掉结束标记后，应用得到“预计周三送达。”，再把它展示给用户。这是一个手工设定的生成轨迹，不是实测日志。

每一步的概率会变化。选择“可以”以后，模型面对的前缀已经不同，不能继续沿用“预计”分支的候选表。因此，第一步的一个差异可能改写后面整句话。也不能把“预计”的 0.60 解释为“订单明天到货的概率是 60%”：前者是特定条件下生成某个 token 的概率，后者需要物流履约数据，两者的对象不同。

生成还需要停止条件。正常遇到结束标记可以停；达到输出上限也会停，但这时句子可能没写完。上限为 100 个新 token 的意思是最多允许生成这么多，不是要求恰好写满。输出上限和输入可容纳的内容有关，下一篇 [Context Window：模型这一轮能看到什么](#/lesson/context-window)再计算这笔预算。

下面的 Python 伪代码只表示责任与顺序，不是可运行 SDK，也省略了底层并行计算、缓存和服务调度：

```python
# 教学伪代码：函数名和对象均为示意。
sequence = tokenizer.encode(chat_template(messages))
answer_ids = []
for _ in range(max_new_tokens):
    scores = model.next_token_scores(sequence)
    next_id = choose_token(scores, decoding_config)
    if next_id == EOS:
        break
    sequence.append(next_id)
    answer_ids.append(next_id)
answer = tokenizer.decode(answer_ids)
```

## 为什么相同的问题会得到不同回答

`choose_token` 有不同实现。贪心解码（greedy decoding）每步取概率最大的候选；在上表中它取“预计”。采样（sampling）则按概率抽取，0.30 的“可以”仍然可能被选中。抽样具有随机性，不表示模型每次都换了参数，也不表示它临时学到了新知识。[Generation strategies 官方文档](https://huggingface.co/docs/transformers/main/generation_strategies)分别说明了这两种选择方式。

温度（temperature）调整抽样前的概率分布。温度降低，较大的概率通常更集中；温度升高，分布趋于平缓，较低概率候选有更多机会。它改变“从这些候选中怎样选”，不会把订单记录里的“预计”升级为“保证”。Hugging Face 的说明也指出，温度趋近于零时，采样趋近于贪心选择；具体接口是否接受 `temperature=0`、怎样解释它，需要查该接口，不能把数学极限直接当作通用 API 参数。[temperature 说明](https://huggingface.co/blog/how-to-generate#sampling)

可以只用刚才三个概率手算。设原始概率为 $p_i$，温度为 $T>0$，只考虑温度变换、不叠加其他候选筛选时，新概率为：

$$
q_i=\frac{p_i^{1/T}}{\sum_j p_j^{1/T}}
$$

$i$ 表示当前候选，$j$ 遍历所有候选；分母把变换后的权重重新归一化，使概率总和为 1。这个写法等价于常见的“分数除以温度后再做 softmax”。当 $T=1$，三个概率仍是 0.60、0.30、0.10。当 $T=0.5$，先平方得到 0.36、0.09、0.01，总和为 0.46，所以新概率约为 0.783、0.196、0.022；表面加和略有偏差来自四舍五入。温度降低后，“预计”更容易被选中，“可以”却没有消失。

如果原始分布把错误候选排在第一，降低温度只会更稳定地选它。由此得到一个工程判断：遇到事实错误，先检查输入是否包含正确资料、模型有没有遵守限制，以及应用是否验证关键字段；调温度主要处理生成差异，不能代替事实校验。也不要把“使用贪心规则”扩展成“跨模型版本、硬件和服务实现必定逐字一致”的承诺。

## 模型调用结束了，应用的工作还没结束

在这个例子里，模型承担的是根据输入生成候选回答；应用负责查哪条订单、把什么信息送进去、选哪个模型与生成配置，以及怎样展示和保存结果。模型参数是在训练中得到的；一次普通推理请求通常不更新这些参数。应用保存聊天记录，也不等于把记录训练进模型。后续一轮能参考哪些旧消息，取决于应用或服务实际提供了什么上下文。

如果用户接着问“那周四还没到怎么办”，页面上虽然保留着上一轮气泡，程序仍须保证新请求能获得必要的订单与对话信息。某些服务替应用保存和关联历史，但保存是服务能力；不能仅凭界面有历史，就推断底层模型看到了全部历史。聊天模板文档中输入本身就是显式的消息列表，这提供了理解责任边界的一个具体例子。

这也解释了为什么更换模型并不等于更换整个产品。同一个模型可以被接到订单问答、代码补全或摘要工具中，实际行为还受输入、数据和应用逻辑影响。订单系统要承诺到货，必须有支持承诺的业务规则与数据；让文本听起来更肯定，并没有改变订单状态。之后学习 [Prompt](#/lesson/prompt) 和 [Agent 与 Workflow](#/lesson/agent-basics) 时，可以一直追问：这一环是在改变给模型的信息、改变生成方式，还是让应用执行了一个真实动作？

<details>
<summary>面试怎么回答</summary>

**约一分钟口头回答：一次 LLM 请求发生了什么？**

应用先把任务要求、用户问题和必要资料组织成消息，按模型的聊天模板编码，再由 tokenizer 转成 token ID。常见自回归模型根据这些输入计算下一 token 的分数，生成程序用贪心或采样规则选一个，把它加入已有内容，重复到结束标记或输出上限，最后解码成文本。Temperature 改变采样分布的集中程度，不能保证事实正确。模型负责生成；查询订单、保存历史、校验结果和执行业务操作属于应用或服务。比如模型说“明天送达”，只有输入里有可靠的订单证据，才能讨论这个回答是否成立。

**追问一：temperature 设得很低，为什么还可能回答错？**

因为概率最大的下一 token 也可能导向错误回答。缺少订单记录、资料过期或模型误读时，降低温度没有增加证据，只让选择更集中。需要分别验证输入事实和输出是否符合事实；稳定性与正确性要分开评估。

**追问二：messages 里的一个对象就是一个 token 吗？**

不是。Message 是应用层的对话单元，一条可以含很长正文；token 是模型处理序列的单位。消息列表经模板加入角色和边界标记，再转成许多 token。不能通过消息条数或中文字数精确判断 token 数量，应使用配套 tokenizer 或服务返回的实际用量。

<summary>练习参考思路</summary>

必须把本轮实际输入中的订单记录更新为“预计周四送达”，保留今天周二的日期关系，以及不要承诺确定到货的要求。可接受的示例回答是“记录显示预计周四送达，无法据此确认明天到货”。这是期望行为，需要通过实际请求验证。

如果输入仍写“预计周三”，模型收到的事实没有随数据库变化，降温不能修复这个数据传递错误。对给定的教学分布，“可以”的新概率是 $0.3^2/(0.6^2+0.3^2+0.1^2)=0.09/0.46\approx19.6\%$。它描述某个 token 的抽样机会，无法估计物流概率。输入变成周四后，模型真实算出的候选分布也可能改变，不能把旧分布当作新请求的测量结果。
