# 企业 Agent 的多租户隔离：甲公司的助手为什么看不到乙公司的资料

假设一家厂商提供“费用报销 Agent”，甲公司和乙公司都买了。甲公司的员工打开同一个网页，问：“出差住宿费上限是多少？顺便查一下我上个月的报销单。”助手需要查公司政策、检索历史单据，还可能调用报销系统。如果它把乙公司的差旅政策拿来回答，问题已经发生；如果它拿着乙公司的工具凭证去查询，哪怕最终没有显示结果，边界也已经被越过。

腾讯招聘的三个岗位提到企业版、多租户隔离、SaaS/PaaS、VPC、专有云或私有化交付。这些词说明岗位需要处理企业场景，**不能据此推断腾讯某个产品的现网架构**。[岗位一](https://careers.tencent.com/jobdesc.html?postId=2077641608832135168)、[岗位二](https://careers.tencent.com/jobdesc.html?postId=2077641607687090176)、[岗位三](https://careers.tencent.com/jobdesc.html?postId=2074756587444158464)。下面只讨论一个假设产品如何设计，以及面试时如何判断方案是否靠谱。

先修 [Agent 权限](#/lesson/agent-security) 里的“谁有权读、谁有权执行”、[MCP](#/lesson/mcp) 里的工具连接，以及 [任务状态](#/lesson/agent-state) 里的持久化。这里把视角抬高一层：同一套产品服务许多客户时，授权、数据、工具和运行资源怎样沿着一次请求保持一致？

## 先说清“租户”指谁

租户（tenant）是产品拿来划分客户边界的单位，不等于单个登录用户。本文约定甲公司是租户 A，乙公司是租户 B；甲公司有许多员工，每个人又有不同职位和单据权限。Microsoft 的多租户架构指南也特别提醒，产品自己的 tenant 与 Microsoft Entra tenant 是相关但不同的概念：一家客户可能有多个目录，一个产品租户也可能需要对接不同身份系统。[Azure：Architect multitenant solutions](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/overview)、[Azure：Tenancy models](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/considerations/tenancy-models)

甲公司员工通过登录，只能证明“这个人是谁”。系统还要确定：他当前代表租户 A 吗？在 A 里能读哪些政策、哪些单据？用户可能同时为两家客户工作，所以“登录成功”不能自动确定当前租户。请求里出现 `tenantId: "A"` 也不能作为证明，因为浏览器参数、模型生成的工具参数都可能被改。后端应依据已验证身份和租户成员关系确定有效租户，再在每次资源读取、工具调用时强制检查。Azure 的身份设计指南把 authentication（验证身份）与 tenant 范围内的 authorization（授权）分开；AWS 的租户隔离说明进一步指出，用户已认证、甚至拥有某种角色，也不自动保证不会读到其他租户的资源。[Azure：Identity in a multitenant solution](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/considerations/identity)、[AWS：Tenant isolation](https://docs.aws.amazon.com/whitepapers/latest/saas-architecture-fundamentals/tenant-isolation.html)

于是，一次请求的可信上下文至少要同时包含用户、有效租户、该用户在该租户下的权限、当前任务标识。它应由服务端建立并随调用传递。模型可以帮忙理解“住宿费上限”是什么意思，但不能自行决定“这次切到乙公司”。

## 沿着一条请求，隔离到底落在哪里

假设甲公司员工小林问上面那句话。应用首先验证小林的登录状态，查出他是 A 的成员，有读取 A 的差旅政策和本人报销单的权限。然后启动任务 `T-41`，记录有效租户为 A。以下是教学伪代码，展示检查所在的位置，不是可直接运行的 SDK：

```text
principal = verify_login(request.credentials)
tenant = authorize_membership(principal, requested_tenant="A")
task = create_task(principal.id, tenant.id, goal=request.message)

policy = policy_store.search(tenant.id, "住宿费上限")
claims = expense_tool.for_tenant(tenant.id)
  .list_claims(user=principal.id, month="上个月")

answer = model.respond(policy, claims)
audit.write(tenant.id, task.id, sources=[policy.id, claims.ids])
```

这个例子中，假设 A 的政策写着“普通城市每晚 500 元”，小林上个月有一张 480 元的报销单；B 的政策是 650 元。输出应使用 A 的 500 元规则与小林有权看的 480 元单据。数字只是为了跟踪请求，不是任何公司的真实政策。只在最终答案前检查“有没有提到 B”太晚了：如果检索已把 B 的政策送进模型，数据边界已经失效。检索、数据库查询、向量索引、缓存以及模型输入都得带着服务端确定的租户范围。

可以把这次运行拆成几道门：

| 边界 | 需要隔开什么 | 常见漏点 |
| --- | --- | --- |
| 身份和权限 | A 的用户与 B 的用户；A 内普通员工与管理员 | 仅验登录，不验有效租户、资源归属 |
| 资料和状态 | 政策、单据、向量片段、会话、checkpoint、缓存、日志 | SQL 带租户过滤，向量检索或缓存键却没带 |
| 工具和凭证 | 各客户报销系统连接、OAuth 授权、API key、工具允许范围 | 共用高权限服务账号，让模型传 `tenantId` |
| 配置和运营 | 各客户启用的工具、模型、知识源、保留期限、管理员权限 | 运营后台“一键查看所有对话”缺少严格控制 |
| 计算和网络 | CPU/GPU 配额、执行沙箱、网络出口、故障影响面 | 数据分库了，共享任务队列仍能串单或互相拖慢 |

表中“资料和状态”很容易被低估。Agent 不只读业务数据库：它会把检索片段交给模型，把中间结果写进任务 state，失败时保存 checkpoint，缓存重复查询，日志记录调用。只隔离主数据库，而共享向量索引的检索过滤、缓存键或日志查询权限没有跟上，仍可能把乙公司的内容带到甲公司任务里。Azure 的存储指南给出共享数据库、独立数据库、独立账号等不同层级，强调依据数据驻留、加密密钥、备份恢复和性能要求选择，没有一种结构适合所有租户。[Azure：Storage and data in multitenant solutions](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/approaches/storage-data)

工具连接还要看“以谁的身份去做”。甲、乙分别授权了各自的报销系统，连接配置和令牌必须关联租户；某些操作还要关联具体用户。模型提出 `list_claims(user="小林")` 只是一个候选调用，执行器根据 T-41 的 A 租户上下文取 A 的连接、核对小林的资源权限。若模型误给了乙公司的单据 ID，执行器应拒绝。MCP Server 或普通 HTTP API 都不会神奇地解决这层业务授权；它们提供调用通道，服务端仍要验证身份与资源范围。

还有一层是运维人员。厂商工程师要排查失败任务，不代表他可以随手读取所有客户的原文、密钥和对话。配置发布、日志查询、紧急访问、密钥轮换与审计，都应有各自的授权和记录。否则面向终端用户的隔离做得再细，后台通道仍可能跨租户。这里的具体权限模型要依据合同和系统设计确定，不能凭“SaaS”三个字推出来。

## 共享服务、独立 VPC、私有化，是三个不同的承诺

“SaaS”说的是厂商交付并运营软件服务；“PaaS”通常说客户在平台能力上开发或部署应用。它们是产品责任和服务抽象层级，**不是隔离等级刻度**。一个 SaaS 可以为大多数客户共享服务，同时给某些客户提供独立部署；一个 PaaS 也可能有许多租户共用底层资源。面试里如果把 SaaS、VPC、私有化排成单轴优劣，往往会漏掉真正的问题：客户究竟要求哪些资源独立，谁负责升级和排障，数据与密钥放在哪里？

对假设产品，可以从三种常见形态理解取舍。它们是示意方案，不代表某家公司的产品菜单。

| 形态 | 请求运行在哪里 | 主要收益与代价 |
| --- | --- | --- |
| 共用服务 | A、B 使用共享应用集群，可按逻辑分区、独立数据库或混合配置 | 单位成本和统一升级较好；授权、配额与数据过滤必须细致，性能可能互相影响 |
| 客户专属部署 | 给 A 独立应用实例及部分或全部数据/网络资源，例如独立 VPC 或云账号；B 仍在共享池 | 更容易满足特定网络、容量、数据位置要求；实例增多，发布与运营成本上升 |
| 私有化交付 | 应用部署到客户控制的环境，具体是客户云、专有云还是自有机房由合同定义 | 客户可掌握更多环境和数据控制权；厂商需要处理版本碎片、升级窗口、观测和故障支持边界 |

独立 VPC 主要是网络层的一道边界。它可以限制东西向连接、设置独立网络出口，但**不会自动证明**应用代码、模型服务、控制台、日志、备份、运营人员都隔离。反过来，共享应用也不意味着资料一定混在一起：它可以使用严格的租户授权、独立数据库、独立密钥和配额。真正的架构往往混合：共享控制面，给某些客户独立数据面或部署单元。Azure 将一个客户或一组客户放进独立 deployment stamp 作为模式之一，并明确列出隔离、成本、管理和 noisy neighbor 的取舍。[Azure：Architectural approaches](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/approaches/overview)

这里出现“控制面”（control plane）和“数据面”（data plane）。在本例中，控制面负责租户开通、分配部署位置、下发配置与版本、管理配额；数据面接收小林的请求，检索 A 的资料，运行模型和工具，返回答案。这是便于分析的职责划分，不是所有产品都必须部署成两组独立服务。若 A 使用独立 VPC，但厂商的中央控制面还能把 B 的连接配置发给 A，独立网络并没有保护这条管理路径。应检查控制面下发对象、目标租户、权限和审计，也检查数据面实际执行的边界。

为甲公司选方案时，先写需求再谈名词：数据需要留在哪个区域？是否必须由甲持有密钥？能否通过私网访问报销系统？峰值请求是否会影响其他客户？甲能否接受厂商统一升级，还是需要自定维护窗口？合同约定谁看日志、谁做备份和恢复？这些问题决定共用、专属或私有化的边界。Azure 的 tenancy models 指南也把合规、规模、自动化和商业成本并列为决策因素。[Azure：Tenancy models](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/considerations/tenancy-models)

## 怎么证明隔离真的生效

只展示架构图不够。给 A、B 建两组测试账号和同名政策，故意让政策值不同；分别发起请求，核对检索命中的文档、工具使用的连接、任务状态和最终答案。再让 A 用户请求 B 的文档 ID、工具资源 ID、历史任务 ID，期望在**读取前**被拒绝。测试后台管理员、定时任务、缓存命中和故障重试；这些路径不一定经过网页入口。还要做容量测试：B 的请求暴涨时，A 的延迟、错误率和配额是否在承诺范围内。隔离既包含保密性，也包含客户间的性能和故障影响边界。

假设 T-41 的答案正确显示 500 元和 480 元单据，但调用日志显示检索曾返回 B 的 650 元片段，只是模型没采用。这次测试仍然失败。若把检索改成独立索引，也要验证索引写入、删除、重建和恢复过程带着正确租户标识。某一次样本通过，只说明被测路径和当时配置通过；要把跨租户访问与泄露的回归测试放进发布流程。

<summary>面试怎么回答</summary>

**一分钟回答：** 企业 Agent 的多租户隔离要沿一次请求逐层检查。登录后由服务端确定用户与有效租户，资源授权不能相信模型传的 tenant ID。检索、业务库、向量索引、缓存、任务状态、工具凭证和日志都要按租户限制，执行器在调用工具前再验具体资源权限。共享服务、独立 VPC 和私有化是部署与运营方案，不能只按名字判断安全；先确认数据位置、密钥、网络、容量、升级和运维责任，再选择共享或专属资源。控制面下发配置，数据面执行请求，两边都要防止跨租户。最后用 A、B 两套资料做越权和性能测试，检查真实读取过程，而非只看最终答案。

**追问一：数据库已经按租户分表，还会串数据吗？** 会。检索索引、缓存、checkpoint、工具连接、日志和后台管理权限仍可能共用。分表也要确保每次查询带服务端校验过的租户条件，并检查异步任务和恢复流程。

**追问二：客户要求独立 VPC，是否就能承诺完全隔离？** 不能直接承诺。VPC 主要约束网络；模型服务、控制面、密钥、日志、备份、运维通道可能仍共享。应把“哪些资源独立、谁有访问权、哪些路径跨边界”写成可检查的部署和责任清单。

**追问三：都私有化了，还有多租户问题吗？** 可能有。客户内部可能有部门或环境边界，厂商也可能共用升级控制台、镜像仓库或远程支持通道。要按实际部署和合同定义租户，不能认为软件一进客户环境，所有权限问题就消失。

练习：甲公司要求数据留在自己的云账号，报销工具只能走私网，系统每月按甲指定日期升级。团队提出“把数据库搬进甲的 VPC，Web 服务、模型调用、任务队列和运维后台仍共用”。这个方案满足了哪些要求？哪些问题还需问清或验证？

<details>
<summary>练习参考思路</summary>

数据库位置可能满足部分数据驻留要求，但先要确认检索索引、checkpoint、缓存、日志、备份和模型输入是否也属于要求覆盖的数据。私网要求要沿工具调用的真实网络路径验证，不能只看数据库所在 VPC。甲指定升级日期意味着共享 Web 服务如果统一发布，可能与要求冲突；要讨论独立部署、兼容版本或合同调整。共用队列需验证租户路由、配额和故障影响，运维后台需核对访问权限、审计与紧急支持流程。最后将每项要求对应到可检查的资源和测试，而不是给方案贴一个“专属”标签。
