# 企业 Agent 多租户：甲公司的助手为什么看不到乙公司的资料

企业 Agent 的多租户（multitenancy），是一套产品同时服务多个客户，并按客户划分数据、权限和运行资源的工程设计。租户（tenant）就是产品定义的客户边界：本文假设甲公司是租户 A，乙公司是租户 B。两家公司可以打开同一个网页，但甲的员工不应读到乙的政策，也不应借用乙的工具凭证。

先分清三个动作。身份认证（authentication）确认“登录者是谁”；授权（authorization）判断“这个人在当前租户能做什么”；隔离（isolation）让这些限制在检索、工具、任务状态和运行资源中持续生效。同属于甲公司的员工也有不同权限：小林能读自己的报销单，并不意味着能读同事的单据。

假设厂商提供一个费用报销 Agent，能查政策、调用报销系统并整理回答。小林问：“普通城市出差住宿费上限是多少？顺便查一下我上个月的报销单。”我们要沿这次请求解释：系统怎样从输入到答案保持同一套权限？腾讯三个岗位中的企业版、多租户、SaaS/PaaS、VPC 和私有化要求是选题背景，不能证明腾讯产品的内部架构或现网交付方式。[岗位一](https://careers.tencent.com/jobdesc.html?postId=2077641608832135168)、[岗位二](https://careers.tencent.com/jobdesc.html?postId=2077641607687090176)、[岗位三](https://careers.tencent.com/jobdesc.html?postId=2074756587444158464)。下文只讨论假设产品。

先修 [Agent 权限](#/lesson/agent-security) 里的“谁有权读、谁有权执行”、[MCP](#/lesson/mcp) 里的工具连接，以及 [任务状态](#/lesson/agent-state) 里的持久化（任务跨多次调用时怎样保留进度）。这里把视角抬高一层：同一套产品服务许多客户时，授权、数据、工具和运行资源怎样沿着一次请求保持一致？

## 先说清“租户”指谁

产品租户也不等于身份目录。Microsoft Entra tenant 表示一个身份目录，费用 Agent 的租户表示产品定义的客户单位。一家客户可能接多个目录，或一个目录里的用户进入不同产品租户，因此要明确客户、用户和目录的映射。[Azure 多租户指南](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/overview)、[租户模型](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/considerations/tenancy-models)

小林登录后，浏览器可以请求进入 A，后端仍须核对成员关系。用户可能同时服务两家公司，浏览器参数也可能被改；模型生成 `tenantId: "B"` 更不能成为切换身份的依据。后端应依据已验证身份建立有效租户，在每次资源读取和工具调用时强制检查。Azure 身份指南分别定义认证与租户范围内的授权；AWS 隔离说明也提醒，只验证登录或角色无法自动阻止跨租户访问。[Azure 身份设计](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/considerations/identity)、[AWS 租户隔离](https://docs.aws.amazon.com/whitepapers/latest/saas-architecture-fundamentals/tenant-isolation.html)。AWS 这页已标为历史参考，本文的部署取舍同时依据 Azure 指南。

于是，一次请求的可信上下文至少要同时包含用户、有效租户、该用户在该租户下的权限、当前任务标识。它应由服务端建立并随调用传递。模型可以帮忙理解“住宿费上限”是什么意思，但不能自行决定“这次切到乙公司”。

## 沿着一条请求，隔离到底落在哪里

假设甲公司员工小林问上面那句话。应用首先验证小林的登录状态，查出他是 A 的成员，有读取 A 的差旅政策和本人报销单的权限。然后启动任务 `T-41`，记录有效租户为 A。以下是教学伪代码，展示检查所在的位置，不是可直接运行的 SDK：

```text
principal = verify_login(request.credentials)
tenant = authorize_membership(principal, requested_tenant="A")
task = create_task(principal.id, tenant.id, goal=request.message)

policy = policy_store.search_authorized(tenant.id, principal, "住宿费上限")
claims = expense_tool.for_tenant(tenant.id)
  .list_authorized_claims(principal, month="上个月")

save_state(task, principal, tenant, sources=[policy.id, claims.ids])
answer = model.respond(policy, claims)
store_answer_with_access_rules(task, principal, tenant, answer)
audit.write(tenant.id, task.id, sources=[policy.id, claims.ids])
```

这个例子中，假设 A 的政策写着“普通城市每晚 500 元”，小林上个月有一张 480 元的报销单；B 的政策是 650 元。输出应使用 A 的 500 元规则与小林有权看的 480 元单据。数字只是为了跟踪请求，不是任何公司的真实政策。只在最终答案前检查“有没有提到 B”太晚了：如果检索已把 B 的政策送进模型，数据边界已经失效。检索、数据库查询、向量索引、缓存以及模型输入都得带着服务端确定的租户范围。

先看检索的 `search_authorized`。文档的访问控制列表（Access Control List，ACL）说明哪些用户或组能读它。租户范围过滤掉 B 的政策，文档权限再过滤掉 A 内小林无权看的资料；两道限制缺一不可。检索增强生成（Retrieval-Augmented Generation，RAG）把外部资料作为模型回答依据，因此结果进入模型前必须已经满足这些权限。Azure AI Search 给出了按用户或组过滤结果的方式，也介绍了基于权限元数据的访问控制；其中若干原生权限功能仍标为 preview，不能笼统称为全部可用于生产。[文档级访问控制](https://learn.microsoft.com/en-us/azure/search/search-document-level-access-overview)，核验日期：2026-10-01。

若政策被拆成片段，放进向量存储（vector store，用于按内容相似程度检索片段），片段也要保留租户与文档权限的关联。甲乙的政策措辞可能几乎一样，内容相似不表示有权读取。共享索引可由服务端施加权限条件；独立索引还要保证请求路由到正确位置。两种方案都要检查写入、权限更新、删除和恢复，不能只验证一次查询。

再看工具的 `list_authorized_claims`。甲乙分别授权了自己的报销系统，连接配置和令牌必须关联正确租户。执行器根据 T-41 的上下文选择 A 的连接，再判断以谁的身份查询：若支持用户委托身份，就核对小林的权限；若使用服务身份或 API key，凭证可能能读取更多资料，业务服务仍须限制这次请求的范围。教学伪代码中的函数表示这些强制检查，不能理解为传一个用户名字就取得了授权。

若模型误给 B 的单据 ID，执行器应在读取前拒绝；即使单据属于 A，还要核对小林是否有权看它。MCP Server 或 HTTP API 提供调用通道，实际权限由执行器和工具服务校验。本例只查询政策和单据；提交或修改报销单需要另行检查写入权限和确认条件。

接着看任务怎样继续。任务状态（state）保存进度，检查点（checkpoint）保存用于失败恢复的进度。T-41 重试时，应从 A 的范围加载任务，并重新核对当前用户仍有访问权。任务 ID 只用于定位，知道 ID 并不表示获得权限；撤权后也不能靠旧检查点继续读取受限资料。

缓存（cache）复用已有结果，也可能绕过检索。只拿“上个月报销单”当缓存键，会让 B 或 A 的其他员工拿到小林的结果。个人查询至少要绑定租户和用户，权限变化时还要失效或重新授权；公共政策则可以在获授权的范围内共享。只加租户 ID 并不能保护个人数据。Azure 存储指南讨论共享与独立存储在隔离、密钥、备份和性能上的取舍；具体缓存键与恢复检查是由本例权限要求推导出的设计。[Azure 存储与数据](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/approaches/storage-data)

最后看留下的产物和日志。回答、导出的表格、下载文件都应继承 T-41 的访问范围；数据库受保护，下载链接却开放给所有登录用户，仍会泄露小林的单据。审计要能追踪租户、执行身份、任务、资源和结果；完整提示词与工具响应可能含客户资料，是否保存原文、保存多久、谁能查询需另行确定。厂商工程师需要排障，不等于可以任意浏览全部客户的对话、密钥和单据。配置发布、紧急访问和密钥轮换也需要各自的权限与记录。

## 共享服务、独立 VPC、私有化，是三个不同的承诺

到这里还没有要求甲乙必须用不同服务器。逻辑隔离靠授权、资源范围和路由阻止越权；部署隔离进一步用独立资源限制网络访问、容量竞争和故障影响。两者可以组合，分到哪一层取决于客户需求。

SaaS（Software as a Service，软件即服务）强调客户使用厂商运营的软件；PaaS（Platform as a Service，平台即服务）强调客户在平台能力上开发或部署应用。它们描述服务职责，不能直接表示隔离强度。VPC（Virtual Private Cloud，虚拟私有云）提供云内网络边界；私有化交付要约定应用进入哪个客户控制的环境、谁运维、怎样升级。这些名称讨论的是不同问题。

对假设产品，可以从三种常见形态理解取舍。它们是示意方案，不代表某家公司的产品菜单。

| 形态 | 请求运行在哪里 | 主要收益与代价 |
| --- | --- | --- |
| 共用服务 | A、B 使用共享应用集群，可按逻辑分区、独立数据库或混合配置 | 单位成本和统一升级较好；授权、配额与数据过滤必须细致，性能可能互相影响 |
| 客户专属部署 | 给 A 独立应用实例及部分或全部数据/网络资源，例如独立 VPC 或云账号；B 仍在共享池 | 更容易满足特定网络、容量、数据位置要求；实例增多，发布与运营成本上升 |
| 私有化交付 | 应用部署到客户控制的环境，具体是客户云、专有云还是自有机房由合同定义 | 客户可掌握更多环境和数据控制权；厂商需要处理版本碎片、升级窗口、观测和故障支持边界 |

独立 VPC 主要是网络层的一道边界，不会自动证明模型服务、控制台、日志、备份和运维身份都隔离。共享应用也可配合授权、数据分区、独立存储、配额与密钥建立隔离。Azure 的部署单元（Deployment Stamps）模式把一组资源重复部署，每组可以服务一个或多个租户。独立单元能减少客户间的影响，但增加成本和管理负担；共享单元仍要实施内部隔离。[Azure 多租户架构方式](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/approaches/overview)

云原生（cloud native）在这里解决的是怎样可重复地部署、运行和管理系统。CNCF 的定义涵盖公有云、私有云和混合云，列举了容器、声明式 API 等常见技术。因此私有化也可采用云原生方式；把费用 Agent 放进容器，不会自动解决小林的单据权限。自动部署能帮团队为甲乙创建环境，仍须验证网络、存储和权限配置。[CNCF Cloud Native Definition v1.1](https://github.com/cncf/toc/blob/main/DEFINITION.md)

这里出现“控制面”（control plane）和“数据面”（data plane）。在本例中，控制面负责租户开通、分配部署位置、下发配置与版本、管理配额；数据面接收小林的请求，检索 A 的资料，运行模型和工具，返回答案。这是便于分析的职责划分，不是所有产品都必须部署成两组独立服务。若 A 使用独立 VPC，但厂商的中央控制面还能把 B 的连接配置发给 A，独立网络并没有保护这条管理路径。应检查控制面下发对象、目标租户、权限和审计，也检查数据面实际执行的边界。

为甲公司选方案时，先写需求再谈名词：数据需要留在哪个区域？是否必须由甲持有密钥？能否通过私网访问报销系统？峰值请求是否会影响其他客户？甲能否接受厂商统一升级，还是需要自定维护窗口？合同约定谁看日志、谁做备份和恢复？这些问题决定共用、专属或私有化的边界。Azure 的 tenancy models 指南也把合规、规模、自动化和商业成本并列为决策因素。[Azure：Tenancy models](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/considerations/tenancy-models)

## 怎么证明隔离真的生效

给 A、B 建两组测试账号和同名政策，故意让政策值不同，并在 A 内增加一位同事。先核对正常请求的检索文档、工具连接、状态和产物，再让小林请求 B 的文档、工具资源、历史任务，以及 A 同事的个人单据，预期在读取前被拒绝。覆盖后台管理员、定时任务、缓存命中、下载链接、撤权和故障恢复，因为这些路径可能绕过网页入口。这是测试设计，本文没有运行真实客户系统。

还要验证客户间的性能影响。乙的请求量暴涨时，共享队列或模型资源可能拖慢甲，这叫 noisy neighbor（邻居负载造成资源干扰）。配额和限流能控制部分影响，独立资源也有容量上限；应按承诺检查甲的延迟、错误率和配额。

假设 T-41 的答案正确显示 500 元和 480 元单据，但调用日志显示检索曾返回 B 的 650 元片段，只是模型没采用。这次测试仍然失败。若把检索改成独立索引，也要验证索引写入、删除、重建和恢复过程带着正确租户标识。某一次样本通过，只说明被测路径和当时配置通过；要把跨租户访问与泄露的回归测试放进发布流程。

<details>
<summary>面试怎么回答</summary>

一分钟回答：企业 Agent 的多租户，是同一产品服务多个客户并保持客户边界。认证确定用户，授权确定当前租户下能读和能做什么，隔离让约束贯穿执行。以报销查询为例，服务端建立可信上下文，检索按租户和文档 ACL 筛选，工具用对应连接并检查具体单据权限；恢复、缓存、产物和日志也要保持范围。共享服务、独立 VPC 和私有化各有责任与资源取舍，云原生帮助部署管理，无法代替业务授权。最后用跨租户、同租户越权、撤权和容量测试检查真实过程。

追问一：向量索引已经按租户独立，还需要 ACL 吗？需要。独立索引把甲乙分开，甲内部仍有个人、部门和财务权限；路由正确后，还要检查小林能否读取命中文档，维护片段与源文档权限的关联。

追问二：缓存键加上 tenant ID 就够了吗？对个人报销查询不够，同租户还有其他员工。缓存键和命中后的检查都要考虑用户与权限变化；公共政策可在获授权的范围内共享。

追问三：独立 VPC 或私有化能否保证隔离？先界定承诺覆盖的资源。VPC 主要提供网络边界，控制面、模型服务、日志、备份和支持通道可能仍共享；客户环境内也仍有员工权限。要把实际路径写清并验证。

数据库位置可能满足部分数据驻留要求，但先要确认检索索引、checkpoint、缓存、日志、备份和模型输入是否也属于要求覆盖的数据。私网要求要沿工具调用的真实网络路径验证，不能只看数据库所在 VPC。甲指定升级日期意味着共享 Web 服务如果统一发布，可能与要求冲突；要讨论独立部署、兼容版本或合同调整。共用队列需验证租户路由、配额和故障影响，运维后台需核对访问权限、审计与紧急支持流程。最后将每项要求对应到可检查的资源和测试，而不是给方案贴一个“专属”标签。
