# Agent PRD：为 Agent 写清任务、权限与验收

**Agent PRD 是面向 Agent 应用的产品需求文档**（Product Requirements Document）。它把“希望助手做什么”写成各方能共同评审的约定：服务谁、依据哪些资料、允许做哪些动作、正常或失败时怎样结束，以及用什么证据验收。Agent 的回答和动作选择可能随输入变化，因此 PRD 还要明确缺参、证据冲突和工具故障时的行为。它不能只写“准确、安全、响应快”。

假设产品负责人提出：“做一个懂设备借用政策的 Agent，最好还能帮员工申请。”有人理解成政策问答，有人做自动填单，还有人认为可以直接提交。演示时，助手回答“相机可以借 7 天”，看似完成；用户若没给开始日期，或问到旧政策，或要求立即提交，团队就没有共同的判断依据。这里的 Agent 可以按问题选择查询资料、补问或准备草稿；文字由模型生成，查询和提交由程序执行。**PRD 要约束的是用户可见的结果和程序实际执行的动作。**

本篇沿“政策问答 v0.1 → 申请草稿 v0.2”写一份可审查的假设 PRD。设备、政策、用户、案例数与阈值均为教学设计，没有实测成绩。[业务抽象](#/lesson/business-scope) 已讨论怎样确定用户问题；现在要把这个问题落实为范围、权限、输入输出、失败路径与发布决定。

## 第一步：从愿望划出本期任务和动作边界

最初的 v0.1 只回答设备借用规则：用户说出设备类别与借用日期，助手检索当前有效政策，说明期限、资格和例外，并给出来源。后续访谈提出“每次还要重新填表，希望把已说过的信息放进草稿”，因此 v0.2 增加草稿能力。这个变化有依据：减少同一用户任务中的重复录入，但并未得到自动提交的授权。

下面是 v0.2 的范围约定。每一行都对应本次评审可以接受或修改的要求，而不是留给开发者自由解释的标题。

| PRD 字段 | v0.2 的具体约定 |
| --- | --- |
| 目标用户 | 具有设备借用门户访问权限的本组织员工 |
| 用户任务 | 理解本人适用规则，形成可检查、可复制的申请草稿 |
| 数据依据 | 设备政策库已发布版本、当前用户可见的设备登记；政策负责人确认有效期 |
| 本期输出 | 带来源的政策回答，或包含明确缺失项的版本化草稿 |
| 本期边界 | 不创建正式申请，不修改审批结果，不承诺设备已预留 |
| 任务结束 | 草稿已展示并可复制；或者缺失信息、证据冲突或服务不可用已明确说明 |
| 责任分工 | 产品负责人确认范围；设备政策负责人标注规则；工程负责人落实权限和运行；发布负责人依据验收决定扩大使用范围 |

**“不创建正式申请”是动作权限，不只是界面提示。** 本期不向模型提供提交工具，服务器也要拒绝对应写入口。没有预留能力，草稿中的“设备可用”只能说明某次查询结果，不能显示成“已为你锁定”。这样，用户任务、数据能力与系统权限才指向同一个范围。

RAG（检索增强生成）是先从资料里找相关内容，再让模型据此回答；本例的政策问答就可能采用这条路径。Azure 的 RAG 设计指南要求先定义业务领域与需求，准备代表性资料和测试问题，并分别评估各阶段与最终体验。这些是形成验收依据的步骤，而不是模型选择完成后才补写的文档。[Azure Architecture Center：RAG design and evaluation，2026-09-28 查阅](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/rag/rag-solution-design-and-evaluation-guide)

## 第二步：把一条请求写成可检查的输入输出

假设用户输入：“想借 CAM-18 七天，给我填一下。”登录身份由应用提供，模型不填写申请人账号。政策查询确认该员工类别允许申请，但用户没有开始日期。系统此时可回答适用期限，草稿则保留 `start_date` 与 `end_date` 为空，并把开始日期列入 `missing_fields`。它不应该擅自用今天作为起点。**本轮正确结果是等待用户补充日期，不是生成一张看似完整的表单。**

用户补充日期后，生成下一版草稿。每个字段保留来源类别：来自用户、设备登记、政策推导，或仍然缺失。状态只允许“等待补充”“草稿可检查”“需要人工确认政策”“暂时无法完成”等含义清晰的值。草稿可检查表示材料足以让用户查看，不表示正式申请已存在，也不表示后续审批一定通过。

PRD 对成功输出约定四部分：简短结论、支持结论的政策条款、草稿内容及版本、尚未解决的问题。对于刚才的输入，可接受的输出是“政策允许申请七天，草稿缺少开始日期，请补充”；一份字段齐全却日期错误的表单反而失败。字段越齐并不一定越好；在输入不足时，准确暴露空缺才符合要求。

此外，用户修改设备或日期应产生新草稿版本，旧版本仍可识别。只修改语言风格则不应让业务字段悄悄变化。这个约定使后续加入审批时有可延续的内容身份，也让测试能检查用户到底看到了哪份材料。

## 第三步：让正常与失败路径进入同一份验收

前面的 CAM-18 请求至少要测两次：缺日期时能否保留空字段并补问，补全日期后能否生成正确版本的草稿。但只测这条顺利路径还不够。本例准备 100 个独立验收案例：35 个正常政策问答、25 个草稿任务、20 个缺参或不支持的问题、10 个版本冲突及服务失败、10 个权限和禁止写入场景。各组互斥，避免统计时把同一案例算两遍。每个案例固定输入与数据快照，并运行 3 次，共 300 次观察，用来暴露部分生成波动；它仍不是对所有真实任务的证明。

下表阈值是假设的产品验收草案，需要根据基线、用户成本和风险评审后才能采用。读者不应把这些数字复制成通用质量标准。

| 验收项 | 具体通过条件 | 谁来判断 |
| --- | --- | --- |
| 权限及禁止写入 | 10 个边界案例的 30 次运行均无越权正文输出，所有 300 次运行均无正式申请创建 | 程序检查服务审计与工具调用，安全审核抽查入口是否覆盖 |
| 政策回答 | 35 个案例共 105 次，至少 100 次结论、适用条件与来源均正确；另不得把测试中的过期规则当成当前规则 | 业务人员按答案依据评分，程序核对引用 ID 与版本存在 |
| 草稿字段 | 25 个案例共 75 次，用户明确给出的设备和日期在所有输出中保持正确，未确认的字段不得编造 | 程序与固定输入逐字段比对，人工评审自然语言用途是否忠实 |
| 缺失及不支持 | 20 个案例共 60 次，至少 57 次准确指出缺失或范围限制，不把可回答问题误判为不支持 | 人工标注后程序汇总，单独统计正确澄清与误拒绝 |
| 冲突与失败 | 10 个案例共 30 次，均不宣称政策已确认或草稿已提交；展示可继续处理的状态 | 程序验证状态与动作，人工检查解释是否清楚 |
| 延迟 | 固定模型与配置，5 个并发请求持续补位，输出上限 800 token；正常问答与草稿的 180 次运行端到端 p95 不超过 8 秒，失败组另报 | 自动记录请求接收到结果显示的时间，不计等待用户输入；缓存开关与预热状态随结果记录 |

100 除以 105 约为 95.2%，57 除以 60 为 95%。这些是两个不同分母，不能合并成一个好看的“总准确率”。权限和禁止写入也不参与平均分抵消：其他题答得再好，出现一次越权仍不满足这份验收约定。反过来，边界测试零失败也不能宣称系统今后永远不会失败，只能说明本轮已覆盖样本通过。

程序适合检查字段、格式、允许的工具集合、是否存在写调用、来源版本和时间计数。它不一定能判断一段解释是否遗漏了规则例外，所以需要业务人员按证据核验。模型评分可以帮助初筛，但人工要检查争议项和关键错误，并记录一致的裁决依据。否则“人工看起来不错”与“自动评分很高”都难以复查。

## 第四步：用坏例修正行为约定

假设第一轮演示发现旧版政策排在新版前面。修正要求应当是：依据目标日期与政策有效期选择版本；如果同一范围存在无法解释的冲突，输出“需要确认政策”，保留两个来源供政策负责人核实。仅在提示词里补一句“优先新版”仍有问题，因为用户可能询问历史日期。

第二个失败是用户没给日期，模型自动填写今天。这对应的 PRD 修改是：日期没有可靠来源时为空，进入等待补充，禁止生成“草稿可检查”的完成状态。第三个失败是读取服务超时，界面却显示“没有找到政策”。这里要区分“查询成功但无结果”与“没有获得查询结果”，后者应保留暂不可用状态，不把网络故障解释成政策不存在。

这三个例子说明，坏例（bad case）要能追到**输入条件、错误输出、期望行为和对应验收项**。团队修复后，把它加入固定回归集；新增样本需要记录测试集版本，不能悄悄更换分母再与上一轮百分比比较。

人工接手（human fallback）也要有具体交接内容。本例遇到政策冲突时，用户可以查看设备、日期、当前草稿、冲突条款与来源版本，以及系统无法确定的那一个问题。v0.2 不集成外部转交接口，只提供可复制的交接摘要与设备政策咨询入口，由用户自行提交。页面明确显示“尚未发送给负责人”，不能把生成摘要当成已经联系。用户离开咨询页面后回来，原草稿仍可查看。

人工兜底不能用来掩盖普通任务的大量失败。需要单独记录触发原因、用户是否接受交接，以及最终是否得到解决。若所有问题都转人工，禁止写入指标可能很好看，产品却没有完成减轻重复查资料与填表的任务。

## 第五步：写清观察、停止扩展与回滚

为了复查一次错误，日志需要串起请求 ID、用户的受控身份标识、模型与提示词版本、政策和索引版本、被选入的证据、草稿版本、工具动作、失败类型与各阶段耗时。原始私人内容不必全部进入通用日志，可以保存权限受控的引用或经过处理的必要字段。本例拟定任务诊断记录保留 30 天，仅指定运维角色可访问，期满自动删除；政策审核只取得完成核验需要的脱敏案例。草稿保留规则另行告知用户，不随着日志清理被误删。这些是待评审的产品约定，“为了调试全量保存”不是默认答案。

这些记录决定灰度发布能否判断风险。假设 v0.1 问答能力已有可回退版本，v0.2 先对 10 名自愿试用员工开放草稿；不少于 3 个工作日且累计至少 50 个任务后，才由发布负责人检查指标。达到时间但没有实际使用，不算通过观察期。这些数字同样是假设的发布计划，不是已经发生的运行结果。

试用期间若出现未经允许的正式写入或越权内容，立即关闭新功能并调查；若任意连续 50 个任务中有至少 3 个已核实的关键日期错误，也暂停扩展。这里的关键日期错误定义为用户明确输入与输出日期不一致，不能把用户后来改主意混入统计。扩展到下一组之前，还需要检查政策问题覆盖、误拒绝和端到端耗时，而不是只看服务没有崩溃。

Azure Well-Architected 的安全发布指南建议小步变更、逐步扩大使用范围、每阶段检查健康信号，并在发现问题时停止扩展、恢复到已知可用配置；它也提醒回滚数据和其他有状态组件比回滚代码更复杂。[Azure：Safe deployment practices](https://learn.microsoft.com/en-us/azure/well-architected/operational-excellence/safe-deployments)

因此，本例回滚定义为关闭 v0.2 草稿入口，恢复 v0.1 问答配置，保留用户已有草稿供查看与复制，不继续自动处理。旧版本必须能识别新草稿或提供独立的只读展示，不能回滚后让用户内容丢失。如果问答本身也受影响，就切换到政策搜索与人工入口。恢复的是受控服务路径，不是把已经展示给用户的错误答案从现实中撤销；必要时还需根据日志识别受影响任务并更正。

回到 CAM-18 的请求：用户缺少日期时要看到待补充草稿；日期补齐后，要看到带来源和版本的可检查草稿；政策冲突或服务超时，要看到尚未完成的原因；无论哪条路径，v0.2 都不能创建正式申请。工程据此设计状态和接口，测试据此观察动作，业务据此核对条款，发布负责人据此决定何时停止扩展。模型、框架与检索方案可以在实现中比较，但不能借更换模型悄悄改变这些用户可见约定。

**一分钟回答：** Agent PRD 是 Agent 应用的产品需求文档，要定义用户任务、数据依据和动作权限，再写正常与失败时的输入输出。例如设备借用 v0.2 只回答政策并生成草稿，不创建申请。验收要固定案例、分组、重复次数和分母；字段及工具动作可以程序检查，规则解释与例外完整性需要业务核验。坏例要变成回归项，人工接手要携带当前状态和证据。最后规定日志、灰度观察条件、停止阈值和回滚后草稿如何保留。不能用总体准确率掩盖越权或错误动作，也不能把假设目标写成已有成绩。

**追问一：用户满意是不是最好的验收指标？** 它有价值，但不能替代事实与动作检查。回答流畅、字段齐全时，用户可能没有发现日期被猜测或条款过期。应同时看任务是否正确完成、用户是否需要返工，以及权限等不可被平均分抵消的边界。

**追问二：既然生成不确定，怎么写硬验收？** 对应用能控制的动作与数据边界写硬条件，例如没有提交工具、参数字段不被改写；对语言解释使用固定测试集、重复运行和可复核评分。样本通过代表当前证据，不代表未来零风险，因此仍需灰度监测和恢复路径。

**追问三：转人工算成功还是失败？** 取决于任务与约定。政策冲突下准确交接可以是正确处理；普通政策能回答却转人工是误拒绝或能力不足。应分开统计交接正确性与业务最终解决率，不能把所有转交一律算成功。

<summary>练习参考思路</summary>

首先改变动作边界与授权：正式申请会产生外部记录，需要显示最终参数、确认具体草稿版本并校验用户权限。其次改变状态与失败处理：必须区分未提交、提交中、结果未知和已创建，考虑重复点击、响应丢失与结果核实，不能只保存一段草稿文字。

还要增加验收与发布保护：确认内容被修改后不得沿用旧批准，重复操作不能产生意外申请，失败时不能谎称已完成，并能审计实际写入。原来“300 次均无正式申请创建”的通过条件也必须重写为授权写入行为的精确定义。最后明确回滚只能关闭入口，不能撤销已经存在的申请；已有业务记录需要单独处置。新范围应重新评审，而不是复用问答与草稿的通过成绩。

</details>
